# The import linters and CML

sakai does not read the imports of code.
Each language already has a linter that teams run in CI; `sakai build` writes that linter's settings from the map, and the linter holds the code to the map.
For Rust, `sakai check` reads the crates' dependencies from Cargo itself.
`sakai export cml` writes the map as Context Mapper's CML.

## What may import what

The code a context owns falls into four kinds of group:

- the **inside**: the context's directories that are none of the three below;
- the **code generated** from a published language: the `generated dir` of a `published language` block;
- a **shared kernel**: the directories listed under `shared kernel with`;
- an **anticorruption layer**: the directories listed as `layer` under `upstream … anticorruption layer`, inside the downstream.

A file belongs to the deepest group that holds it; at the same depth, generated code, a layer and a shared kernel come before the inside.
These imports are allowed, and no other:

| From | To |
|---|---|
| anywhere in a context X | anywhere in X: its inside, its generated code, its layers |
| X | a shared kernel X has (from either side); inside a shared kernel, only the shared kernel |
| X (only its layer toward Y, when the layer is written) | the code generated from the packages of an upstream Y listed in `through` |
| X | the code generated by a partner Y |
| the code generated by X | the code generated by Y, when X's `.proto` imports Y's and the map allows it |

What the settings cannot say (an `owns` entry naming one file of code, a directory that is not a module name; in Go and Java a package is a directory) is E501, and nothing is written.
The example's map makes 11 groups in each language:

```console
$ sakai build examples/shop/shop.ctx --target import-linter --check
examples/shop/py/.importlinter: Up to date (11 contracts)
$ sakai build examples/shop/shop.ctx --target dependency-cruiser --check
examples/shop/ts/.dependency-cruiser.cjs: Up to date (11 rules)
$ sakai build examples/shop/shop.ctx --target archunit --check
examples/shop/java/src/test/java/SakaiContextsTest.java: Up to date (11 rules)
$ sakai build examples/shop/shop.ctx --target go-arch-lint --check
examples/shop/go/.go-arch-lint.yml: Up to date (11 components)
```

`--check` writes nothing: it says whether the settings there are what the map writes now, and E502 when they are not.
The settings explain each rule in the language of `--lang`, so run `--check` with the `--lang` they were written with.
Each file starts with the map it was written from.

## Python: import-linter

One `protected` contract for each group: `protected_modules` is the group, `allowed_importers` the groups that may import it, and the group itself.
The settings are `.importlinter` (INI), written where `code python` says.

```ini
[importlinter:contract:sakai-inventory-pl-warehouse.v1]
name = The code made from Inventory's published language warehouse.v1 is imported only by Ordering, Inventory and Delivery's anticorruption layer toward Inventory
type = protected
protected_modules =
    warehouse.v1
allowed_importers =
    delivery.acl.inventory
    inventory
    ordering
    shop.ordering.v1
    warehouse.v1
```

`root_packages` names the packages under the code's directory, and also each directory without `__init__.py` down to where modules are (`warehouse.v1`, `shop.ordering.v1`): the namespace packages protoc writes.
import-linter (grimp) does not go into a directory without `__init__.py` under a package, so such directories are named as roots of their own.
A contract whose group holds another group, under a package with its own `__init__.py`, lists its modules one by one (`as_packages = False`).
The version the tests run is import-linter 2.15 (`tools/requirements.txt`).

## TypeScript and JavaScript: dependency-cruiser

One `forbidden` rule for each group: `to.path` matches the group's files, `from.pathNot` the files of the groups that may import it.
A group that holds another leaves it out with a negative lookahead, on either side.
The settings are `.dependency-cruiser.cjs`, written where `code typescript` says, with `tsPreCompilationDeps` on so that imports of types count too.

```js
    {
      name: "sakai-delivery",
      comment: "The inside of Delivery (delivery) is imported only by Delivery",
      severity: "error",
      from: { pathNot: "^(?:delivery/|shop/delivery/v1/|delivery/acl/inventory/)" },
      to: { path: "^(?:delivery/(?!(?:acl/inventory)/))" },
    },
```

Run it in CI with `--output-type err`: it prints each violation and exits with their number.
`--output-type json` exits 0 even with violations, which sit in `summary.violations`.
The tests run dependency-cruiser 16.10.4 with TypeScript 5.9.3 (`tools/package.json`).
Mind the version of TypeScript: dependency-cruiser 16 reads TypeScript below 6, and with TypeScript 6 or later it reads no `.ts` file at all and passes without a word, so a check that says nothing is not a check that found nothing.
The tests make sure the files were read (`summary.totalCruised`).

## Java: ArchUnit

A JUnit 5 test class, `SakaiContextsTest.java`, written where `code java` puts its `test` (E501 without one), with a predicate for each group and a rule for each: the classes outside the groups that may use it do not depend on its classes.

```java
  private static final DescribedPredicate<JavaClass> SAKAI_DELIVERY = resideInAnyPackage("delivery..").and(resideOutsideOfPackages("delivery.acl.inventory.."));
…
  static final ArchRule sakai_delivery =
      noClasses().that(DescribedPredicate.not(SAKAI_DELIVERY.or(SAKAI_DELIVERY_PL_SHOP_DELIVERY_V1).or(SAKAI_DELIVERY_LAYER_INVENTORY)))
          .should().dependOnClassesThat(SAKAI_DELIVERY)
          .as("The inside of Delivery (delivery) is used only by Delivery");
```

ArchUnit reads the dependencies of compiled classes, not import statements: it catches a class used by its full name with no import, and it does not see an import that nothing uses.
A class in the default package cannot be named by a package, so the map that has one is E501.
The tests run ArchUnit 1.5.1 with JUnit 5 (`tools/java/fetch.sh`).

## Go: go-arch-lint

A component for each group (`in:` its directories with `**`), and `mayDependOn` listing the components it may import, itself among them: go-arch-lint stops an import between two packages of one component unless the component lists itself.
The settings are `.go-arch-lint.yml` (version 3), written where `code go` says (where `go.mod` is; E501 without it).
Files left out by `except` go in `excludeFiles`.

```yaml
  sakai-delivery-layer-inventory:
    mayDependOn:
      - sakai-ordering-pl-shop.ordering.v1
      - sakai-inventory-pl-warehouse.v1
      - sakai-delivery
      - sakai-delivery-pl-shop.delivery.v1
      - sakai-delivery-layer-inventory
      - sakai-billing-kernel-delivery
```

The tests run go-arch-lint v1.19.0 (`tools/go/install.sh`).
A file that no component holds fails the whole run, so the tests also see that no file is left out.

## What each catches

The tests copy the example, write each tool's settings, and run the real tool.
The example as it is passes all four.
Each of four imports added to a copy is caught by every tool, at the file it was added to: the inside of Ordering importing the inside of Inventory, code outside Billing's layer importing what is generated from Ordering's published language, Ordering importing the shared kernel of Billing and Delivery, and Reviews importing Billing (they are separate ways).
The first one, as each tool says it:

```text
Illegal imports of protected package inventory:
- ordering.bad_internals -> inventory.ledger (l.2)
```

```text
error sakai-inventory: ordering/bad_internals.ts → inventory/ledger.ts
```

```text
Rule 'The inside of Inventory (inventory) is used only by Inventory' was violated (1 times):
Method <ordering.BadInternals.take(java.lang.String, java.lang.String)> calls method <inventory.Ledger.hold(java.lang.String, java.lang.String, int)> in (BadInternals.java:6)
```

```text
Component sakai-ordering shouldn't depend on example.com/shop/inventory/ledger in ordering/bad_internals.go:4
```

The tools catch slightly different things.
import-linter, dependency-cruiser and go-arch-lint read import statements; ArchUnit reads what compiled classes use.
None of them sees a call made at run time by a name in a string.

## Rust: what Cargo says

For `code rust "<workspace>"`, `sakai check` asks Cargo once for the workspace's crates (`cargo metadata`, which reads the manifests and builds nothing) and holds each crate's dependencies on other crates of the workspace to the relationships, as it holds any other reference (E107 when Cargo cannot answer).
A crate a context publishes is written `crate "…"` in a `published language` block.
`[dev-dependencies]`, and dependencies on crates from a registry or git, are not checked.

## CML

`sakai export cml` writes the map for Context Mapper:

| sakai | CML |
|---|---|
| the map | `ContextMap <alias>`, `type = SYSTEM_LANDSCAPE`, `state = AS_IS`, every context in `contains` |
| a context | `BoundedContext <alias>`, its description as `domainVisionStatement`, its terms as `responsibilities`; its name and owner in a comment |
| conformist | `<downstream> [D,CF]<-[U,<roles>] <upstream>` |
| anticorruption layer | `<downstream> [D,ACL]<-[U,<roles>] <upstream>` |
| customer and supplier | `<downstream> [D,C]<-[U,S,PL] <upstream>` (`[D,C,ACL]` with a layer) |
| shared kernel | `<one> [SK]<->[SK] <other>` |
| partnership | `<one> [P]<->[P] <other>` |
| separate ways | a comment: CML has no form for it |
| the upstream's roles | `OHS,PL` when a package in `through` has an open host service, else `PL` |
| the packages and services | the relationship's `implementationTechnology`: `Connect: <package>.<service>` for a `.proto`, `OpenAPI: <name> (<operations>)` and `AsyncAPI: <name> (<channels>)` for OpenAPI and AsyncAPI documents, with their open host services |

Names are the aliases, since CML takes ASCII identifiers only.
The examples' CML is `tests/golden/cml/shop.cml` and `tests/golden/cml/webshop.cml`; the tests have Context Mapper 6.12.0's validator, with every check, find nothing in them.
The relationship of the web shop's Shipping and Payments, which talk by OpenAPI and AsyncAPI documents, is written:

```cml
  shipping [D,ACL]<-[U,OHS,PL] payments {
    implementationTechnology = "OpenAPI: payments.v1 (createCharge, getCharge); AsyncAPI: payments.v1 (paymentSucceeded, paymentFailed)"
  }
```
