# 何を検査するか

`dandori check` は `.flow` と、それが使う規則を読みます。そして、すべての分岐、呼び出しが返しうるすべてのエラー、外部のサービスの側で起きうるすべてのイベントを考えに入れて、処理の流れを追います。診断には、そこへ至る短い実行の例が付きます。

## 終わっていない案件を残す

カードに与信を取ってチェックアウトの日に確定するホテルの予約
（[tests/fixtures/hotel_naive.flow](https://github.com/i2y/ritsu/blob/main/crates/dandori/tests/fixtures/hotel_naive.flow)、例の最初の下書き）を `--lang ja` で検査すると、次の診断が出ます。

<div class="dd-term" markdown>

```text
エラー[E020]: tests/fixtures/hotel_naive.flow:95:1: 案件 `pi` が requires_payment_method・processing のまま、ここでワークフローが終わることがあります（終わりの状態は succeeded・canceled）
    95 |   succeed outcome = stayed
  そうなる例:
      81  quote = hold(…)
      84  match quote.handling: auto
      84  create_intent: pi が requires_confirmation で始まる
      85  confirm_intent: pi が requires_confirmation → requires_capture
      90  match pi.status: requires_capture
      90  booking.check_out まで待つ
      93  capture_intent: pi が requires_capture → processing
          外部のサービスで `settle` が起きる: pi processing → requires_payment_method
      95  succeed
```

</div>

案件 `pi` は、ワークフローが状態を追いかける Stripe の PaymentIntent です。その遷移は `payment_intent.rule` に書いてあります。Stripe の文書から、PaymentIntent の状態の変わり方を rulec のステートマシンに転記したものです。ワークフローには、Stripe の側でひとりでに起きるイベントを `external authenticate, settle, expire` と宣言してあり、検査はそれが起きる場合もたどります。チェックアウトの日まで待つあいだに与信の有効期限が切れれば、確定の呼び出しは拒否されます。確定したあとでも、銀行の処理で支払いが通らないことがあります。

## 検査の項目

**型と名前。** 名前はどれも一度だけ宣言し、その型で使います。オプショナルな値は `match` で確かめてから使い、引数と出力はそろっていなければなりません（E001〜E006）。列挙の型は、宣言した場所で決まります。同じ `enums` ファイルの同じ列挙は、フローとフローが呼ぶ規則がどの名前で読んでも一つの型で、別の場所で宣言した列挙は、値が同じでも別の型です（E003）。型の書かれていない所に名前で書いた列挙の値は、その名前を持つただ一つの列挙の値で、二つの列挙が持つなら型を書きます（E002）。

**分岐と文の置き場所。** `match` は、そこに届く実行がとりうるどの値にも分岐がなければならず（E010）、通ることのない分岐があってもいけません。届く実行のどれも持たない値の分岐はエラーです（E011）。変数を読めるのは、そこへ至るどの経路でも値が入っている場所だけです（E012）。`yield`、`break`、`succeed`、案件への呼び出しは、意味のある場所にしか書けません（E009）。

**案件。** 案件にタスクを呼べるのは案件を始めたあとだけで、始められるのは一度だけです（E013）。どの状態でも拒否されるイベントを送るのはエラーです（E021）。拒否されることがあるイベントを送るなら、拒否されたときの処理を書かなければなりません（E022）。ワークフローが終わるとき、始めた案件はどれも終わりの状態になっていなければなりません。例外は、`fail … leaving` で引き渡すときだけです（E020）。どこでも処理しないエラーで失敗して、案件が終わらないまま残ることもあります（W101）。これは `on failure` で片付けます。`retry` を付けた呼び出しも数えます。リトライを使い切ると、その呼び出しは失敗するからです。`on failure` や `on cancel` が案件を片付けている最中に呼び出しが失敗すると、案件はそこではもう片付けられません。その呼び出しで失敗を受け、`fail … leaving` で案件を人に渡してください。案件の状態での `match` が読むのは案件のレコードで、レコードはワークフローが最後に聞いた状態を言います。呼び出しが失敗しても、外部のサービスではイベントが起きていることがあり、そのとき案件はレコードより先へ進んでいます。検査はその両方を持っているので、`match` が絞るのはレコードだけで、案件がいるかもしれない状態は絞りません。そこでレコードが言うはずのない状態の分岐は、通ることのない分岐です（E011）。

**日付と帳簿。** 日付には、入力が受け取るものを渡します。日付か、カレンダーが UTC オフセットを言うなら時刻です（E003）。帳簿の操作をするタスクは、操作が受け取る引数を取り、仮押さえを返し、帳簿が拒否しうる理由だけをエラーに宣言します（E016、E007）。案件として追う仮押さえは、確定する前に期限が切れることがあり、そこで帳簿が拒否しうる理由は、どれも処理しなければなりません（E022）。[日付と帳簿](dates-and-books.md)

**リトライ。** 外部のデータを変える呼び出しを冪等キー（`key`）なしでリトライすると、同じ変更を二度加えてしまうかもしれません（E030。変えるかもしれない、というだけなら W030）。案件を始めるタスクに `key` が無いのは警告です（W103）。

**タイムアウト。** `timeout until` は、答えを待つタスク（`event` か `callback`）に書き、タスクの `timestamp` の引数を一つ挙げます（E007、E002、E003）。そのタスクの `retry` では、タイムアウトをリトライできません。期限を過ぎてからリトライしても、すぐまたタイムアウトするからです。`aws` のコールバックには書けません。引数が API の引数だからです（E007）。[呼び出しにかけてよい時間](tasks.md#呼び出しにかけてよい時間)

**範囲。** 規則、タスク、レコード、出力に渡す値は、そこの範囲に収まっていなければなりません（E014）。範囲の分からない値を渡すと警告になります（W104）。順序のある列挙の値も同じで、規則の入力やフローの場所に値で書いた範囲（`range >=basic <=gold`）に入る値でなければなりません。範囲に収めた値の `match` は、範囲に入る値だけで分けます。日付と時刻も同じで、日で書いた範囲（`range >=2026-01-01 <=2027-12-31`。時刻はオフセットで読むなら `offset +09:00`）に入る値でなければなりません。動く期間を書いたワークフロー（`now range …`）の `now` は、その期間の中の時刻として数えます。[範囲](tour.md#範囲)

**規則の前提。** 規則には、入力の型だけでは書けない前提があります。ある入力が別の入力を超えないこと（`constraint asked <= paid`）、ある組み合わせが起こらないこと（`never has_tool = true, all_parts = true`）、日付が koyomi の日付のとる日のどれかであること（`range from koyomi`）です。`ritsu check` は、呼び出しが渡しうる値でその前提が保たれるかを確かめ、破る値があれば例を添えて E201 に、決められなければ W201 にします。`never` の行では、呼び出しが渡す真偽と列挙の値を、そこでとりうる値として読みます。書いた値はその値、`match` で分けた値は、そこへ来るまでの分岐が残す値です。決められない前提は、`ritsu dandori gen` が書くコードが、ワークフローを走らせたときに、値ができたところですぐに確かめます。ふつうはその値を返したタスクの直後で、呼び出しまでにほかへ進むことがあれば、もうほかへ進まないところまで下げます。前提を破る実行は、どのプラットフォームでも、そこで `Dandori.BrokenPrecondition` で失敗します。`ritsu dandori run` と `ritsu run` で流しても同じです。規則が計算した値に書いた受け付ける範囲（`define 手数料 : money[円] = … range <=2万円`）も前提で、`ritsu check` は同じように確かめます。決められないものは、規則の計算を繰り返すことになるのでワークフローでは確かめず、規則から生成したコードが、その値を計算したところで受け付けません。

**ワークフローが動く期間。** 期間は、前提と同じく、`gen` が書くコードがワークフローを走らせたときに確かめます。期間の外で走り始めた実行は、何も呼ばずに `Dandori.OutOfPeriod` で失敗します。`now` を読む文は、その前で時計を確かめ、外なら、処理されなかったタスクのエラーと同じく `on failure` に入ります。検査は、この確かめを、失敗しうる呼び出しと同じく、実行が失敗しうるところとして数えます。`on failure` の無いワークフローが、案件を開いたままそこで失敗しうるなら W101 です。`ritsu check` は、`now` がなりうる日を日付のファイルのカレンダーで読み、日付が受け付ける日に収まるかを確かめます（外れうるなら E205、期間を書いていなければ W205）。[ワークフローが動く期間](dates-and-books.md#ワークフローが動く期間)

**タスクが呼ぶもの。** ほかの `.flow` を走らせるタスクは子と（E015）、記述のある API を呼ぶタスクはその記述と（E016）照らし合わせます。[タスクが呼ぶもの](tasks.md)

判断のタスク（`jev`）は、結果の型が判断のモデルに答えられるものか（E007）、確信度を使うなら、ひとりでに別のモデルに移らない名前でモデルを書いているか（W032）を確かめます。拒否（`refusal`）を宣言できるのは、Decisions API のタスクだけです（E007）。[判断のモデル](jev.md)

**実装するサービス。** 入口を proto のサービスとして書いたワークフローは、そのサービスと照らし合わせます。入力と出力が実行を始めるメソッドのリクエストとレスポンスに合うか、失敗の名前がすべて並んでいるか、サービスに書いたイベントとコールバックをフローが待っていて、送られてくる値を読めるかを確かめます（E017）。[サービスを実装する](services.md)

**秘密の値と鍵。** 契約が秘密と印を付けた値（`.proto` の `debug_redact`、OpenAPI の `x-data-classification`・`x-sensitive-data`・`format: password`、`.flow` の `secret`）が、入力・出力・結果・引数・`fail` の理由として実行の履歴に残ること（W904）と、タスクが `discloses` と書いていないのにプロジェクトの外へ送ること（E906）を言います。`.flow` に書いた鍵（W901）と、ほかのマシンへの暗号化しない HTTP（W902）は、行や URL に理由が書いてなければ警告になります。[秘密の値](secrets.md)

**プラットフォーム。** プラットフォームごとに違うことは、`dandori gen` が確かめます。一回の実行がプラットフォームの上限を超えうるか（E040）と、プラットフォームに要るものが欠けていないか、プラットフォームにできないことをしていないか（E050）です。

## 値の出どころ

手書きのコードは、ほかの場所から取った値で実行を始めます。API が受けた申請から金額を、帳簿から残りを取る、といった具合です。入力の行とレコードのフィールドの行の最後の `fed by` は、処理系全体の参照の書き方でその出どころを書く形です（[examples/refund_request](https://github.com/i2y/ritsu/tree/main/crates/dandori/examples/refund_request)）。

```flow
record 残高
  残り : money[USDc]  range >=0USDc <=10000000USDc  fed by chobo "books/refunds.ja.book" account 返金できる残り

inputs
  申請額 : money[USDc]  range >=1USDc <=1000000USDc  fed by openapi "specs/refunds.ja.json" schema 返金の申請 property 金額
```

パスは `.flow` のあるディレクトリから書きます。指せるものは、ほかの言語と同じです。

| 値の出どころ | 書き方 |
|---|---|
| 規則の出力 | `rulec "<ファイル>" output <名前>` |
| 帳簿の勘定 | `chobo "<ファイル>" account <名前>` |
| 日付のファイルの日付 | `koyomi "<ファイル>" date <名前>` |
| `.proto` のメッセージのフィールド | `proto "<ファイル>" message <名前> field <名前>` |
| OpenAPI のスキーマのプロパティ | `openapi "<ファイル>" schema <名前> property <名前>` |
| OpenAPI の操作がその場に書いたもの（リクエストの本文、パラメータ） | `openapi "<ファイル>" pointer "<ポインタ>"` |
| JSON Schema のプロパティ | `jsonschema "<ファイル>" def <名前> property <名前>`、または `jsonschema "<ファイル>" pointer <ポインタ>` |
| ワークフローの出力、そのレコードのフィールド | `dandori "<ファイル>" output <名前>`、`dandori "<ファイル>" record <名前> field <名前>` |
| kaname のレコードのフィールド | `kaname "<ファイル>" record <名前> field <名前>` |
| 先に値を受け取った場所 | `rulec "<ファイル>" input <名前>`、`koyomi "<ファイル>" input <名前>`、`dandori "<ファイル>" input <名前>`、`sekisho "<ファイル>" resource <名前> attribute <名前>`（`principal` も）、`sekisho "<ファイル>" action <名前> input <名前>` |

契約が上限を書かず、コードが手で確かめてからゲートとワークフローに同じ値を渡すことがあります。このとき後の場所は先の場所を指せます。場所から来るのは、その行に書いた範囲です。二つの場所が互いを指すと、同じ値を受け取るという意味になり、どちらを動かしても片方が止まります。

`ritsu check` が両側の言語に尋ね、答えは三つのどれかになります。

- **成り立つ。** 出どころがとりうる値を、受け取る側が全部受け取ります。受け取る側が広いのは問題ありません。
- **E207。** 受け取る側が受け取らない値に、出どころがなることがあります。文に、その値と、出どころが言えるならそれを出す入力が出ます。
- **W207。** 決められません。文に理由が出ます。たとえば、rulec が数えた規則の出力の端にどのベクタも届かないとき、契約が日付を文字列か `.proto` の `google.type.Date` で運び、日を並べていないとき。

E208 は、出どころがそこに無いことを言います（ファイル、またはその中の名前）。

数は単位と刻みを揃えて比べ、単位が違えば成り立ちません。列挙の値は、ファイルに書いた名前か公開名のどちらかが同じなら同じ値です（綴りの違いを読み替えるのは値を運ぶコードの役目です）。日付は日で、真偽と文字列は型だけで比べます。OpenAPI の文書や JSON Schema が `format: date-time` と書いた文字列は時刻（時刻の付いた日時）で、日付の場所は受け取らず、ワークフローの `timestamp` が受け取ります。ほかのワークフローの `timestamp` と、`.proto` の `google.protobuf.Timestamp` も同じです。`.proto` の `google.type.Date` は、dandori と同じく名前で分かる日付です。`.proto` のフィールドのうち、設定しないことがあるもの（`optional`、`oneof` の中、メッセージ型。規則か proto2 の `required` が付いたものを除く）は値が無いことがあり、`T?` でない場所は受け取りません。受け取る側が書いていない端は比べません。契約に上限か下限が無いと、受け取る側を超える値を通すので、規則の `from` と同じく（E122）成り立ちません。帳簿の勘定に `at most` が無いときも、chobo の上限（2⁶³ − 1）まで届くので成り立ちません。

次は、帳簿から `at most` を消した場合です。これが無ければ、実行が `Dandori.BadResponse` で終わって初めて分かります。

```console
$ ritsu check refund_request.ja.flow books/refunds.ja.book --lang ja
books/refunds.ja.book: ok
  売上.do  拒否されうる理由: key_conflict
  返金.do  拒否されうる理由: 残りなし（返金できる残り(注文) at least 0.00）、key_conflict、already_refused
  キー: 売上 は、注文 ごとに一度だけ動きます。キーが同じで 金額 が違う二度目の呼び出しは、key_conflict で拒否されます。
  キー: 返金 は、申請 ごとに一度だけ動きます。キーが同じで 注文、金額 のどれかが違う二度目の呼び出しは、key_conflict で拒否されます。

エラー[ritsu E207]: refund_request.ja.flow:8:1: `record 残高 field 残り` は money[USDc] >=0USDc <=10_000_000USDc を受け取りますが、出どころ chobo "books/refunds.ja.book" account 返金できる残り は 10_000_001USDc になることがあります
     8 |   残り : money[USDc]  range >=0USDc <=10000000USDc  fed by chobo "books/refunds.ja.book" account 返金できる残り
  = 帳簿が受け付ける値です。`at least`・`at most` を書いていない端は、chobo の限度（2⁶³ − 1）まで受け付けます。
  = 受け取る側を広げるか、出どころを狭めてください。どちらにするかは人が決めることです。
ritsu check: ファイル 2 個（chobo 1、dandori 1）。検査を通らないもの 1 個（エラー 1 件）。言語の境目: 確かめた 3 か所、決められない 0 か所
```

`dandori check` は単独では、形を読めるかと書ける場所かだけを言います（E023）。相手のファイルはほかの言語が読むものだからです。**手書きのコードが本当にその値を運ぶかは、何も確かめません。** `dandori doc` のページもそう書きます。dandori が生成するものは、どの出力先でも変わりません。

## 一回の実行の大きさ

一回の実行の大きさには、プラットフォームごとに上限があります。実行履歴は、Step Functions で 25,000 件、Temporal で 51,200 件、Lambda durable functions で 3,000 操作までです。Argo Workflows では Workflow のオブジェクトがすべてのノードを抱えるので、dandori は 10,000 ノードを目安にしています。ループには回数の上限を書き（`repeat at most 12 times`、`for x in xs at most 50`）、再帰も無いので、ビルドは一回の実行履歴が最も長くなる場合を数えられます。数え方は多めなので、上限に近いワークフローは、実際には収まる場合でもエラーになることがあります。

Temporal では、フローの一番外のループは、履歴が長くなったところで新しい実行に引き継ぎます（Continue-As-New）。そのため、そのループは引き継ぐまでの分だけを数えます。それでも上限を超えるのは、ループの外の部分か、ループの一回分が大きすぎるときです。診断は、そのどちらなのかを示します。

## 生成するコードの名前

dandori が生成するコードは、呼ぶ側が読む `.flow` と `.proto` の名前をそのまま持ちます。型、自分で実装するメソッド、フィールド、入力と出力、サービスのメソッドとメッセージです。あるプラットフォームのコードがそれをそのまま持てないとき、つまりそういう二つの名前が一つの識別子になるとき（Go の `send_mail` と `sendMail`、TypeScript と Python と Go での `.proto` のメッセージ `shop.Line` とレコード `shop_Line`）、コードが呼ぶ側のためにその名前を宣言するとき（Go のパッケージの `Transport`、TypeScript と Python の `WorkflowInput`）、その言語が自分のために取っておく語のとき（Python の `class`、`def`、TypeScript の `interface`、`any`）は、`dandori check` がプラットフォームを挙げて警告します（W105）。`dandori gen` は、そのプラットフォームを書くときは何も書かずに止まります（E051）。名前を変えるか、そのプラットフォームを `--target` から外してください。

コードが自分のためだけに持つ名前は、何も止めません。フローの名前がそれを取れば、コードが自分の方を別の名前にします。そういう名前を取らないフローのコードは、前と同じです。

| プラットフォーム | コードが自分のために持つ名前 | フローがその名前を取ったとき |
|---|---|---|
| Go | パッケージが自分のために宣言する名前（`WorkflowType`、`DefaultTransport`、`DATE`） | 後ろに `_` を付けた名前になる（`WorkflowType_`）。どれがそうなったかは `doc.go` に書く |
| TypeScript | `types.ts` が読むグローバルな型（`Array`、`Record`） | `types.ts` がグローバルの方を `globalThis.Array` と読む |
| TypeScript | クライアントが読むグローバルな型（`Promise`、`Omit`） | クライアントがグローバルの方を `globalThis.Promise` と読む |
| TypeScript | クライアントが読み込むか自分で宣言する名前（`Connection`、`encrypted`） | クライアントが `_Connection`、`_encrypted` として読み込むか宣言する |
| TypeScript | クライアントのモジュールが持つ名前（`require`、`exports`、`globalThis`） | メソッドの関数を `_require` で宣言し、`require` として export する |
| Python | コードが読む組み込み（`str`、`list`）、`types.py` が使う名前（`Any`、`re`） | 組み込みを `_builtins.str` と読み、自分の名前は `_Any` になる |
| Python | `make_activities` が読む名前（`transport`、`beating`） | タスクのアクティビティが関数 `_transport` になる。Temporal の上では `transport` のまま |
| Argo | 呼ぶ側の誰も読まない、caller の型 | 一つの名前になる二つの型のうち、フローの方が後ろに `_` を付けた名前になる |
| TypeScript、Python、Go、Step Functions | コードの変数（`dd_error`） | フローの変数が後ろに `_` を付けた名前になる |

あるプラットフォームで一つの名前になるフローの二つの変数（Python の `class` と `class_`、`_x` と `v_x`）も、同じように分けます。そのプラットフォームがそのまま取れる方はその名前のままで、もう一方が後ろに `_` を付けた名前になります。

Go では、パッケージが自分の方に付けた名前を、`doc.go` が `WorkflowType_ for WorkflowType` の形で挙げます。パッケージの部品からワーカーを組むコードはそこを読みます。そうしたコードを dandori をライブラリにして書くプログラムは、同じ表を `dandori::temporal_go::renamed` から受け取ります。dandori の Go のランナーもそうしています。呼ぶ側が読む名前（`Workflow`、`NewWorker`、`Start`）は変わらないので、`NewWorker` でワーカーを組むコードはどちらも要りません。
