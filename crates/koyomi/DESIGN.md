# koyomi 設計文書

締めと支払、営業日、月の足し算を書く小さな言語。ファイルは `.cal`、コマンドは `koyomi`。書いた条件を範囲のすべての日について総当たりで確かめ、条件を満たさない日付をそのまま出す。検査を通ったものだけを、TypeScript・Python・Go・Rust・SQL（PostgreSQL）のコードにする。

名前は暦（こよみ）から取った。

この文書は設計の段階（A）で書き、言語の芯を作った段階（B）、出力先を作った段階（C）、人が読むページと文書を作った段階（D）で直した。B で作ったのは、字句と構文、名前と型、カレンダー、参照インタプリタ、検査、診断、`check`・`eval`・`explain`・`api` のコマンドである。C で作ったのは、五つの出力先の生成（`gen`）、`vectors`、生成したコードと参照インタプリタの突き合わせ、`source fetch`・`pin`・`outdated` である。D で作ったのは、`doc`（7 章）、例の仕上げと英語の版（10 章）、`docs/`、README.md と README.ja.md、エージェント向けのスキル（`skills/koyomi`）、THIRD_PARTY_NOTICES.md である。3〜10 章に載せた出力とコードは、その段階の koyomi が実際に出したものに差し替えた。そのあと ritsu に移ってから、例とテストの材料を英語を先にした（England and Wales の例、日本の暦の例の英語の版、英語の名前のテストの材料と変異を足し、日本語のものは日本語の版として残した。10.1）。

文書に出てくる日付と日数は、A の段階で、使い捨ての試作（Python）が内閣府と GOV.UK の祝日の表から計算したものである。B の参照インタプリタが同じ数を出すことを、`tests/check.rs` が確かめている（一つも食い違わなかった）。

## 0. 全体像

```
.cal ── 字句・構文 ── 名前と型 ── カレンダー（出典のコピーを読む。通信しない）
                                      │
                                      ├── 参照インタプリタ（意味を決める。計算の段を残す）
                                      │     ├── check：範囲のすべての入力で、条件・無い日・データの範囲・例を確かめる
                                      │     ├── eval：一つの入力の計算を一段ずつ見せる
                                      │     ├── vectors：範囲のすべての入力の結果
                                      │     └── doc：人が読むページ（月の表、言い直し、エッジケース）
                                      ├── api：関数・引数・カレンダー・データの範囲・出典のハッシュ（JSON）
                                      └── gen：TypeScript・Python・Go・Rust・SQL（祝日の表を埋め込む）
```

### 0.1 芯にする主張

期日の決まりは、書いたあとで全部の日を試せる。100 年分でも 36,525 日で、3 万 7 千日に満たない。だから koyomi は、条件を式の上で解くことも、一部の日を選んで試すこともせず、宣言した範囲の日を一日ずつ全部計算する。条件を満たさない日があれば、その日付を全部挙げ、最初の日がどう計算されたかを一段ずつ見せる。

看板の言い方は、次を候補にする。rulec の看板（Write rules. Prove them. Compile them.）と同じ三つの句にした。真ん中を prove にしない理由は 3.4 にある。

- **Write due dates. Check every day. Compile them.**
- **期日を書く。全部の日で確かめる。コードにする。**

### 0.2 なぜ別の言語にするか

「20 日締め翌月 10 日払い、休みなら前の営業日」のような計算は、いまの rulec でも dandori でも書けない。

- rulec は日付を順序だけの型にしていて、足し算と引き算を E048 でエラーにする（rulec の DESIGN §2.1・§2.3・§15.84）。rulec の §0.1 は、時刻も在庫も引数で渡すと決めている。
- dandori は `wait until <timestamp>` で時刻を受け取るだけで、営業日も締めも計算しない（dandori の DESIGN §1.5）。

そのため、こうした計算はいま利用者が書くコードの中にある。そこには食い違いの元が三つある。月の足し算はライブラリごとに結果が違う（1.7 の表。2023-01-31 の 1 か月後は、2023-02-28 になるものと 2023-03-03 になるものがある）。祝日の表は法改正で変わり、毎年 2 月に翌年分が出る。フロントエンドとバックエンドで別々に書けば、支払期日がずれる。

期日の決まりは、rulec が対象に選んだ五つの性質（rulec の §0.1）を全部持っている。お金が動く（支払期日）。元の文書が外にある（契約書、約款、法令、祝日の表）。条件が絡み合う（締め、月の足し算、休みの扱い）。期日で改定される（祝日の表が毎年延び、法令が変わる）。書く人と決める人が違う（書くのは開発者、決めるのは経理や法務）。だから rulec の作り方がほぼそのまま使える。出典を固定して改正を知る、人が読むページ、ベクタ、多くの言語へのコード生成、参照インタプリタとの突き合わせ、である。

**決定**：rulec に足さず、別の言語にする。

理由は、確かめ方が違うことにある。rulec のセルは自分の列への単項テストなので、表の一行が区画になり、抜けと重なりを区画の代数で決められる（rulec の §6.2）。期日のほうは、有限の範囲の日を全部計算して確かめる。二つを一つの言語に入れれば、rulec の小ささ（だから証明できる）が崩れる。dandori を rulec の外に作ったのと同じ理由である（dandori の §0.2）。

**費用**：構文、検査、生成、確かめ方を、もう一揃い作ることになる。書き方は rulec と dandori にそろえ（0.4）、覚えることを減らす。

### 0.3 前提

- **P1**：意味を決めるのは参照インタプリタ一つ。check・eval・vectors・doc はどれもそれを通す。生成したコードは、範囲のすべての入力でそれと突き合わせる（6.4）。
- **P2**：検査は総当たりで、サンプリングはしない。範囲のすべての日（整数の入力があれば、その範囲のすべての値との組）を一つずつ計算する。予算を超えたら、確かめていないと言って止まる（3.2）。
- **P3**：無い日の扱い（1 月 31 日の 1 か月後をどうするか）は、書く人が書く。ツールは既定を持たない（1.7）。
- **P4**：祝日は表で持ち、計算しない。表は出典のファイルを sha256 で固定し、表が分かっている範囲（データの範囲）を宣言する。データの範囲の外の日が営業日かを問う計算は、検査でも生成したコードでも通さない（2.4）。
- **P5**：ループと一般の条件分岐を持たない。日付の関数は、操作を上から順に並べたものである。条件分岐は「休みなら〜する」の一つだけ（1.8）。
- **P6**：時刻は固定の UTC オフセットだけを扱う。夏時間のあるタイムゾーンは受け付けない（1.9）。
- **P7**：rulec と dandori は変えない。koyomi はどちらも読まず、どちらからも読まれない。将来 dandori が読めるよう、`koyomi api` で JSON を出しておく（8 章）。

### 0.4 rulec と dandori にそろえるもの

| | そろえるもの |
|---|---|
| 書き方 | キーワードは英語の一種類だけ。名前は日本語で書ける。公開する名前には ASCII の別名（rulec の §1.3）。範囲は `range >=… <=…`。例は `examples` のパイプの表で、出力の列は `->` |
| 出典 | `source <名前> = file "…" url "…" sha256:<16 桁>`、`koyomi source fetch \| pin \| outdated`。`check` は通信しない（rulec の §15.68・§15.76） |
| 診断 | dandori の形（`error[E301]: <ファイル>:<行>:<列>: …`、原文の行、そうなる例）。英語が既定で、`--lang ja` で日本語。台帳は一か所にあり、`koyomi explain` が引く |
| CLI | コマンドとフラグを一枚の表に置き、知らないフラグは exit 2（rulec の §12.1）。exit code は 0・1・2 |
| 生成物 | 依存の無い読めるコード。どの言語にも同じ手順の小さな関数を生成物の中に置き、言語の標準の日付の計算は使わない（1.7、6.1）。頭に元の `.cal` と出典のハッシュを書く |
| 確かめ方 | 参照インタプリタとの突き合わせ。ツールが無ければ `SKIP:` の行を出して通す |
| 語 | 「証明」は否定形でだけ使う（rulec の §15.47。3.4） |

そろえないもの：決定表、ヒットポリシー、単位と丸めの型。koyomi が扱う値は日付と整数だけである。

## 1. 言語

### 1.1 二種類のファイル

**決定**：`.cal` のファイルは二種類ある。一行目の語で分かれる。

- `calendar`：カレンダーを書く。どの日が休みか（休みの曜日、毎年の休み、祝日の表、特定の日）、例外の営業日、UTC オフセット。
- `dates`：日付の関数を書く。一つの日付（と整数）を受け取り、そこから決まる日付を返す。条件と例もここに書く。カレンダーは `use calendar "<ファイル>"` で読む。

例は英語の版を先に置き、日本語の版を並べる（10.1）。英語の版：

```
calendar tokyo_business_days v1
description "Saturdays, Sundays, Japan's national holidays and other days off, and 29 December to 3 January are closed. The English version of 東京の営業日.cal"
offset +09:00

source national_holidays = file "data/syukujitsu.csv" url "https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv" sha256:cec37a743c96995c
  format csv shift_jis
  covers 1955-01-01..2027-12-31

closed weekly sat, sun
closed national_holidays
closed every 12-29..01-03 "New Year holidays"
```

```
dates payment_20th_close_next_10th v1
description "Closes on the 20th; pays on the 10th of the next month, or on the business day before when that day is closed. The English version of payment_20th_close_next_10th.ja.cal. The claim within_60_days_of_receipt is this example's own, written as it reads; it does not say how any law is read"
use calendar "calendars/tokyo_business_days.cal"

inputs
  received : date  range >=2026-01-01 <=2027-11-20

date closing = received
  close day 20          # "closes on the 20th"

date payment = closing
  day 10 of month +1    # "pays on the 10th of the next month"
  roll preceding        # "on the business day before when that day is closed"
  at 09:00

claims
  paid_on_a_business_day      : payment is open
  within_60_days_of_receipt   : payment <= received + 60 days
  later_receipt_later_payment : payment is monotonic

examples
| received   | -> closing | -> payment |
| 2026-04-01 | 2026-04-20 | 2026-05-08 |
| 2026-12-21 | 2027-01-20 | 2027-02-10 |
```

日本語の版（名前を日本語で書き、ASCII の別名を付けたもの。計算と結果は英語の版と同じ）：

```
calendar 東京の営業日(tokyo) v1
description "土日、国民の祝日と休日、12 月 29 日から 1 月 3 日までを休む"
offset +09:00

source 祝日 = file "data/syukujitsu.csv" url "https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv" sha256:cec37a743c96995c
  format csv shift_jis
  covers 1955-01-01..2027-12-31

closed weekly sat, sun
closed 祝日
closed every 12-29..01-03 "年末年始"
```

```
dates 支払条件(payment_terms) v1
description "20 日締め翌月 10 日払い。支払日が休みなら前の営業日。条件「受領から60日以内」は、この例の条件として文字どおりに書いたもので、法令の読み方を示すものではない"
use calendar "calendars/東京の営業日.cal"

inputs
  受領日(received) : date  range >=2026-01-01 <=2027-11-20

date 締め日(closing) = 受領日
  close day 20          # 「20 日締め」

date 支払日(payment) = 締め日
  day 10 of month +1    # 「翌月 10 日払い」
  roll preceding        # 「支払日が休みなら前の営業日」
  at 09:00

claims
  営業日に払う       : 支払日 is open
  受領から60日以内   : 支払日 <= 受領日 + 60 days
  遅い受領は遅い支払 : 支払日 is monotonic

examples
| 受領日     | -> 締め日  | -> 支払日  |
| 2026-04-01 | 2026-04-20 | 2026-05-08 |
| 2026-12-21 | 2027-01-20 | 2027-02-10 |
```

「受領から60日以内」は、この例の条件として文字どおりに書いたもので、何かの法令の読み方を示すものではない。

節の順序は決まっている。calendar のファイルは、見出し、`description`、`offset`、`use calendar`、`source`（表と法令）、`closed` と `open` の順。dates のファイルは、見出し、`description`、`use calendar`、`source`（法令だけ。表はカレンダーに書く）、`inputs`、`date`（いくつでも）、`claims`、`examples` の順（違えば E004）。`closed` と `open` は混ぜて書いてよい（どちらが先かに意味は無い。1.4）。`description`、`offset`、`use calendar`、`inputs`、`claims`、`examples` は一つのファイルに一度までで、二度あれば E004。表の出典に `format` か `covers` の行が無いときも E004 にした（どちらも省けないので）。字下げは、節の中身と、日付の操作と、出典の下の行を表す（スペースで書き、揃っていなければ E005。タブは使えない）。見出しの `v1` は人のための目印で、koyomi はそれを生成物の頭と `api` に書き出すだけである（rulec と同じ）。

受領日の範囲の終わり 2027-11-20 は、祝日の表（2027 年まで）から決まる。2027-11-21 に受領すると、締め日は 2027-12-20、支払日は 2028-01-10 になり、その日が休みかを表は知らない（4.3 の E203）。三つの条件は、受領日 2026-01-01〜2027-11-20 の 689 日のすべてで成り立つ。受領から支払までがいちばん長いのは 51 日（受領日 2026-07-21、2026-12-21、2027-07-21）、いちばん短いのは 18 日である。例の一行目は、翌月 10 日の 2026-05-10 が日曜で、土曜も休みなので、2026-05-08（金）に動く。

**理由**：カレンダーは会社に一つで、期日の決まりは取引先や契約ごとにある。同じカレンダーを多くの dates のファイルが読む。カレンダーだけのファイルは、それだけを総務や経理が読んで確かめられる（`koyomi doc` で月の表になる。7 章）。

**捨てたもの**：

- dates のファイルの中にカレンダーを書くこと。書ける場所が二つになり、同じカレンダーが何か所にもコピーされて食い違う。
- 一つの見出し（`calendar`）で両方を書くこと。「calendar 支払条件」は支払条件をカレンダーと呼ぶことになり、人が読むページで読み違える。

calendar のファイルも `use calendar` で別のカレンダーを読める。読んだカレンダーの休みに、自分の休みを足す（国の祝日のカレンダーに、会社の休業日を足す形）。決まりは 1.4 にある。

### 1.2 キーワードと名前

**決定**：キーワードは英語の一種類だけで、日本語の綴りや略語は置かない。名前（ファイル、入力、日付、条件、出典）は日本語で書ける。公開する名前（ファイルの見出しの名前、入力、日付）には、ASCII の別名を丸括弧で付ける。別名は `[a-z][a-z0-9_]*` で、生成したコードの識別子になる。条件と出典の名前は生成したコードに出ないので、別名は要らない。名前がもとから `[a-z][a-z0-9_]*` の形なら、別名は要らない（`dates net30 v1`、`invoice_date : date …`）。別名を求めるのは、漢字とかなに大文字が無く Go の公開する識別子になれないからで、`invoice_date` にはその問題が無い（rulec と同じ決まり）。

名前の頭が数字でも、日本語が続けば名前として読む（`40営業日以内`、`142条の満了日も単調`）。`30days` のように ASCII だけで数字から始まるものは、数と語のあいだの空白の書き忘れとして E001 にする。

語彙は次で全部である（B の段階で `src/kw.rs` の一枚の表にし、`explain` と予約語の検査はそこから引く）。

| 位置 | 語 |
|---|---|
| 行頭 | `calendar` `dates` `description` `offset` `source` `closed` `open` `use` `inputs` `date` `claims` `examples` |
| 出典 | `file` `url` `law` `asof` `sha256:` |
| 出典の下 | `format` `covers`、形式 `csv` `govuk`、文字コード `utf8` `shift_jis`、`listed years` |
| カレンダー | `weekly` `every`、曜日 `mon` `tue` `wed` `thu` `fri` `sat` `sun` |
| 型と範囲 | `date` `int` `range` |
| 操作 | `+` `-` `day` `days` `business` `month` `months` `year` `years` `of` `start` `end` `close` `roll` `following` `preceding` `modified` `if` `closed` `else` `at` |
| 無い日の扱い | `end_of_month` `start_of_next_month` `reject` |
| 条件 | `is` `open` `monotonic` `=` `<` `<=` `>` `>=` |
| 記号 | `->`（例の出力の列）、`..`（日の区間。両端を含む）、`@`（法令の引用）、`#`（行末までコメント） |

`day` と `days`、`month` と `months` は、英語の文法のための同じ語の形で、意味の違う二つの綴りではない（dandori の時間の書き方と同じ）。

**理由**：rulec の §1.1 と同じである。同じ意味の綴りが二つあると、grep と diff の両方で困る。ツールの語（ASCII）と業務の語（日本語）が見た目で分かれる。

同じ意味の書き方が二つ残る場所が三つある。`day 31 of month +k else end_of_month` は `end of month +k` と同じ、`day 1 of month +k` は `start of month +k` と同じ、`close day 31 else end_of_month` は `close end of month` と同じである。rulec には書き方をそろえる `fmt` があるが koyomi にはまだ無いので、短いほうを勧める警告（W202）で一つにそろえる（`day 1 of month` は B の段階で足した。言い直しの文が `start of month` と同じ「翌月 1 日」になり、二つを書き分ける理由が無いため）。

日の区間を `..` で書くのは、日付には「以下」と「未満」の取り違えが起きないからである。`2026-08-13..2026-08-15` は 13 日と 15 日を含む三日で、ほかの読み方が無い。rulec が裸の `..` を E010 でエラーにするのは、重さや金額の境目で「以下」と「未満」が分かれるからである。入力の範囲だけは、rulec と dandori にそろえて `range >=… <=…` と書く。

### 1.3 入力と型

**決定**：型は `date` と `int` の二つ。dates のファイルの入力は、`date` がちょうど一つと、`int` がいくつか。どの入力にも `range` の両端を書く。

```
inputs
  受領日(received)    : date  range >=2026-01-01 <=2027-11-20
  締め日(closing_day) : int   range >=1 <=31
```

日付の宣言（`date`）は、どれも日付を返し、どれも公開する。生成した関数が受け取るのは、その日付がたどって使う入力だけである（締め日が受領日しか使わなければ、引数は受領日だけ）。

`range` は rulec と同じく三つの役を持つ。総当たりで計算する範囲、生成したコードの入口のガード（範囲の外の入力は例外）、そしてデータの範囲の外に出ないことを確かめる範囲（2.4）である。生成したコードが結果を返すのは、検査がすべての条件を確かめた入力だけ、ということになる。

**理由**：日付の入力を一つにしたのは、総当たりの大きさを抑えるためである。日付が一つなら 100 年でも 36,525 通りで、整数の入力を足しても百万通りほどに収まる（10 章の整数を三つ受け取る例で 871,596 通り）。日付が二つあると、100 年どうしで 13 億通りを超える。二つめの日付が要る計算（「検収は受領の N 日後」）は、日数を整数の入力として受け取れば書ける。

**捨てたもの**：

- 日付の入力を二つ以上にすること。上の理由。
- `range` を省けること。範囲が無ければ、総当たりの範囲も入口のガードも決まらない。
- 整数を返す関数（「二つの日付のあいだの営業日数」）。「何営業日以内」は条件の形で書ける（1.10）。返す型が二つになると、生成物、vectors、doc の形が全部二通りになる。要る例が出てから考える。

### 1.4 カレンダー

| 行 | 意味 |
|---|---|
| `closed weekly sat, sun` | 毎週その曜日を休む |
| `closed every 12-29..01-03 "年末年始"` | 毎年その月日を休む。年をまたいでよい。`closed every 05-01 "創立記念日"` のように一日でもよい |
| `closed 2026-08-13..2026-08-15 "夏季休業"` | その日を休む |
| `closed 祝日` | 出典の表に載っている日を休む（1.5） |
| `open 2026-12-28 "臨時営業"` | 休みの決まりに当たっても営業する日 |
| `offset +09:00` | 時刻を出すときの UTC オフセット（1.9） |
| `use calendar "<ファイル>"` | 別のカレンダーを読み、その上に足す |

ある日が営業日なのは、`open` に書いてあるか、どの `closed` にも当たらないときである。`open` はいつも勝つ。`use calendar` で読んだカレンダーの行と自分の行は、区別せずに一つにする（休みの決まりも例外の営業日も、両方の分を合わせる）。オフセットは一つのカレンダーに一つで、読んだ先と食い違えば E015。

**データの範囲**：祝日の表には、分かっている範囲がある（内閣府の表は 2027 年まで）。カレンダーのデータの範囲は、そのカレンダーが使う表のデータの範囲の共通部分である。表を使わないカレンダー（休みの曜日と毎年の休みだけ）は、扱える日付の全部（0001-01-01〜9999-12-31）がデータの範囲になる。データの範囲の外の日が営業日かは分からない（P4、2.4）。

営業日が一日も無いカレンダー（休みの曜日が七つ、毎年の休みが一年全部）は E108 でエラーにする。翌営業日を探す計算が終わらなくなるからである。

**捨てたもの**：

- 振替休日や春分の日を規則で計算すること。祝日は法律で変わり、春分の日と秋分の日は前の年に決まる。内閣府の表には振替休日も「休日」の行として載っている（1.5）。表を正とし、計算しない（P4）。
- 「第 2 土曜日」のような、月の何番目の曜日を休む決まり。会社の休みにはあるが、その日は CSV の表に並べれば書ける。要る例が出てから考える。
- `open` と `closed` の順序に意味を持たせること（後に書いたほうが勝つ）。`use calendar` をまたぐと、どちらが後かを読む人が追えない。

### 1.5 出典と祝日の表

**決定**：祝日の表は `source` で宣言する。rulec の `source = file` と同じ形で、手元に保存したコピーを SHA-256 の先頭 16 桁で固定する。下の行に、ファイルの形式とデータの範囲を書く。

```
source 祝日 = file "data/syukujitsu.csv" url "https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv" sha256:cec37a743c96995c
  format csv shift_jis
  covers 1955-01-01..2027-12-31
```

- `file`：コピーのパス（その `.cal` からの相対）。`url`：`source fetch` と `source outdated` が取りに行く場所。`sha256:`：コピーのバイト列の SHA-256 の先頭 16 桁（rulec と同じ長さ）。
- `format csv [utf8 | shift_jis]`：一行が `<日付>,<名前>` の CSV。日付は `2026-01-01` と `2026/1/1` のどちらの形でもよい。一行目の最初の値が日付として読めなければ、見出しとして飛ばす。名前は無くてもよい。値に `,` を含めるなら `"…"` で囲む。文字コードの既定は UTF-8。
- `format govuk "england-and-wales"`：GOV.UK の `bank-holidays.json`。三つの地域（`england-and-wales`、`scotland`、`northern-ireland`）から一つを選ぶ。
- `covers <日付>..<日付>`：この表が休みを全部載せている範囲。`covers listed years` と書くと、表に行のある最初の年の 1 月 1 日から最後の年の 12 月 31 日まで（あいだに行の無い年があれば E106）。

検査は、コピーが無ければ E101（`koyomi source fetch` へ）、固定が無ければ E102（書き足す `sha256:…` を示す。`koyomi source pin` でもよい）、コピーが固定と違えば E103、読めなければ E104（どのバイトか、どの行か）、行が `covers` の外にあれば E105 を出す。通信はしない。

`covers` を日付でも書けるようにしたのは、会社の年間休日のカレンダーが年度（4 月〜翌年 3 月）で作られることが多いからである。行のある年から範囲を推すと、2026 年度の表から 2026-01-01〜2027-12-31 を推し、2026 年 1〜3 月と 2027 年 4〜12 月を知っていることにしてしまう。だから範囲は推さず、書かせる。

#### 内閣府の CSV

2026-10-02 に取った `syukujitsu.csv` について確かめたこと：

- 21,538 バイト。`Last-Modified: Mon, 02 Feb 2026 00:30:17 GMT`。SHA-256 は `cec37a743c96995cdb9cb52b685c9003634682a9b0e1a640a6b9b96881fe964a`。
- Shift_JIS で、改行は CR LF。一行目は見出し `国民の祝日・休日月日,国民の祝日・休日名称`。
- 1,067 行。1955 年から 2027 年までの 73 年で、どの年にも行がある。日付は `1955/1/1` の形（ゼロで埋めない）で、昇順で、同じ日付は無い。
- 振替休日と国民の休日は、どちらも名前が「休日」の行として載っている（116 行）。だから振替休日を計算しなくてよい。
- 内閣府の「国民の祝日について」のページは、2028 年の祝日を 2027 年の 2 月に載せると書いている。表は毎年 2 月に一年ずつ延びる。
- 内閣府のサイトのコンテンツには、公共データ利用規約（第1.0版）が適用される（内閣府ホームページ利用規約、令和 7 年 3 月 25 日現在）。例とテストにコピーを置き、出典の書き方と条件は THIRD_PARTY_NOTICES.md に書いた。

#### 文字コード

**決定**：コピーは配られているバイト列のまま置き、koyomi が自分で Shift_JIS を読む。変換表は、WHATWG の Encoding Standard の `index-jis0208.txt`（Identifier `cbaa91f3deb7d0841faf5c33041fc15a285da0e87e64ab802c4bf04b7c4da861`、Date 2024-09-18、7,724 個の符号）から作って koyomi に埋める。Encoding Standard は CC BY 4.0 で、ソースコードに取り込んだ部分は BSD 3-Clause License になる（その文面と著作権の表示は THIRD_PARTY_NOTICES.md）。

理由は、固定するハッシュを、誰がどの機械で取り直しても同じにするためである。`curl -s <url> | shasum -a 256` の先頭 16 桁が `.cal` の固定と同じなら、コピーが配られているファイルそのものだと誰でも確かめられる。取ってくるときに UTF-8 に変換し、そのコピーを固定する案では、固定するのは変換したもののハッシュになる。変換に使うツールの表（`〜` を U+301C にするか U+FF5E にするか、など）で値が変わりうるので、機械によって固定が合わなくなる。

WHATWG の表は、ブラウザが Shift_JIS のページを読むときに使う表で、版と識別子が付いて公開されている。表の 7,724 個の符号がどれも Python の `cp932` と同じ文字になることと、内閣府の CSV が `shift_jis` でも `cp932` でも同じ文字列になることを確かめた。読めないバイト列は置き換え文字にせず、E104 でそのバイトの位置を言う。埋める表は、符号の順に文字を並べた一つの文字列にする（11,104 字、空いている符号は U+FFFF。UTF-8 で 33,190 バイト）。

**捨てたもの**：

- 取ってくるときに `iconv` で UTF-8 に変換し、そのコピーを固定すること。上の理由。
- 名前を読まず、日付だけを読むこと。`,` と `/` と数字と CR LF は Shift_JIS の二バイトめに現れないので、日付は変換なしでも読める。しかし、月の表に祝日の名前を出せなくなる（7 章）。

#### GOV.UK の bank holidays

2026-10-02 に取った `https://www.gov.uk/bank-holidays.json` について確かめたこと：

- UTF-8 の JSON で、SHA-256 は `538b3482c28b85ecd2db606a0d5ae6ad17248900b6498700ce0a48d26a3ecde6`。三つの地域があり、`england-and-wales` は 2019 年から 2028 年までの 83 件。
- 土日に当たった祝日は、振り替えた平日の日付で載っている（`"notes": "Substitute day"`）。土日の日付は一つも無い。
- 古い年は落ちていく（取り直すと範囲の始まりが動く）。`covers listed years` と書けば、範囲は表に合わせて決まる。
- GOV.UK の内容は Open Government Licence v3.0 で使える（rulec のコーパスも同じ出典を使っている）。

JSON を読むので、依存に serde_json を使う（11 章）。

#### 法令の出典

**決定**：法令の出典も、rulec の `source = law`（rulec の §15.68）と同じ形で書ける。取れるのは e-Gov の法令だけである。

```
source 民法 = law "129AC0000000089" asof 2026-10-01
  第140条 sha256:e880059021fbb67d
  第141条 sha256:0575c131b9f08063
  第143条 sha256:6950bdfb988439b6

date 起算日(first_day) = 起点            @民法 第140条
  + 1 day
date 満了日(last_day) = 起算日           @民法 第141条, 第143条
  + 月数 months else start_of_next_month
  - 1 day
```

- コピーは `.cal` の隣の `sources/law/<法令ID>@<日付>/<要素>.xml`（条ごとに、e-Gov 法令 API v2 の `law_data` が返す XML をそのまま）と、版の ID を書いた `revision.txt`。rulec と同じ置き方である。固定はコピーのバイト列の SHA-256 の先頭 16 桁。
- 引けるのは本則の条・項・号（`第143条`、`第143条第2項`、`第143条第2項第1号`、`第20条の2`。漢数字でもよい）で、それぞれ e-Gov の要素（`MainProvision-Article_143-Paragraph_2`）に対応する。
- 引用は、`date` の宣言の行、操作の行、`at` の行、条件の行、カレンダーの `closed` と `open` の行の末尾に `@<出典> <条>` と書く（`#` のコメントより前）。条は `,` で区切っていくつでも書ける（`@民法 第141条, 第143条`。rulec と同じ）。`at` の行で引けるようにしたのは、141 条（その末日の終了をもって満了する）が `at end of day` に当たるからである。
- 検査は、引いた条が固定されていなければ E111（直し方は固定の行そのもの）、コピーが無ければ E101、固定と違えば E103、固定だけが残っていれば W102。通信しない。

koyomi は条文を読んで計算を決めるのではない。書いた人が条文に合わせて書いた計算の隣に、どの版の条文を見て書いたかを固定して並べる。人が読むページは、その日付の言い直しの隣に、コピーから引いた条文を載せる（7 章）。条文が改正されれば `koyomi source outdated` が施行日と一緒に言う（9 章）。

A の段階で、2026-10-01 時点の民法 140〜143 条を e-Gov 法令 API v2 から取り、`examples/sources/law/129AC0000000089@2026-10-01/` に置いた（版 `129AC0000000089_20260624_508AC0000000045`）。固定は 140 条 `e880059021fbb67d`、141 条 `0575c131b9f08063`、142 条 `fc8c35a0769d3b35`、143 条 `6950bdfb988439b6`。民法には 2026-10-01 より後に施行される版が五つ（2027-06-23、2027-12-05、2028-06-13、2028-12-23、2029-06-23）あり、どの版でも、この四つの条の XML は一バイトも変わらない（2026-10-02 に確かめた）。

**捨てたもの**：

- 法令の出典を入れず、コメントに条番号を書くだけにすること。それでは、ページに載せる条文がどの版のものかを言えず、改正を知る手段も無い。
- 附則と別表を引けるようにすること。期日の決まりで、そこを引く例を見ていない（rulec は附則と別表を引ける）。

### 1.6 日付の関数

**決定**：日付の宣言には、始まりの日付（入力か、ほかの日付）を書き、その下に操作を一行ずつ並べる。操作は上から順に一つずつ効く。

| 操作 | 意味 | カレンダー | 無い日の扱い |
|---|---|---|---|
| `+ 30 days`、`- 1 day` | 暦日で足す・引く | 要らない | 要らない |
| `+ 5 business days`、`- 2 business days` | 営業日で数える | 要る | 要らない |
| `+ 1 month else …`、`- 3 months else …` | 月を足す・引く | 要らない | 必ず書く |
| `+ 1 year else …` | 年を足す（12 か月と同じ） | 要らない | 必ず書く |
| `day 10 of month +1` | k か月後の N 日（`+0` は省ける。負の数で前の月） | 要らない | N が 29 以上になりうるときだけ書く |
| `start of month +1`、`end of month +2` | k か月後の月初・月末（`+0` は省ける） | 要らない | 要らない |
| `close day 20` | N 日締め：その日を含む期間の締め日 | 要らない | N が 29 以上になりうるときだけ書く |
| `close end of month` | 月末締め：その日を含む月の末日 | 要らない | 要らない |
| `roll following`、`roll preceding`、`roll modified following`、`roll modified preceding` | 休みなら営業日へ動かす（営業日の慣行） | 要る | 要らない |
| `if closed <操作>` | 休みのときだけ、その一つの操作をする | 要る | その操作による |

数（`30`、`5`、`1`、`10`、`20`）は整数の入力の名前でもよい（`close day 締め日 else end_of_month`、`day 支払の日 of month +支払の月 else end_of_month`）。そのときは、無い日の扱いが要るかを入力の範囲で決める。足す・引く数は 0 以上で、向きは `+` と `-` で書く。

日付の宣言の最後の行に `at 09:00` か `at end of day` を書くと、その日付を時刻でも出す（1.9）。

操作の定義は 2.2 にある。

**理由**：一行に一つの操作にすると、`eval` の一段、診断の「そうなる例」の一段、人が読むページの言い直しの一文が、どれも `.cal` の一行に対応する。読む人は、計算の段をそのまま原文の行と見比べられる。

**捨てたもの**：

- 式を入れ子にする書き方（`roll(day(10, month(+1, close(20, 受領日))), preceding)`）。読む順が計算の順と逆になり、読む人が追えない。
- 一行にパイプでつなぐ書き方（`受領日 |> close day 20 |> …`）。行が長くなり、変更の diff が一行に固まる。
- 「翌月 10 日」を `+ 1 month` と `day 10` の二つに分けること。1 月 31 日に `+ 1 month` をすると無い日に当たるが、そのあと 10 日にするので結果には効かない。それでも無い日の扱いを書かされる。だから「k か月後の N 日」を一つの操作にした。月初と月末も同じ。

### 1.7 無い日の扱い

月を足す、k か月後の N 日にする、N 日で締める。この三つは、その月に無い日（2 月 30 日、4 月 31 日）に当たることがある。

**決定**：無い日に当たりうる操作には、無い日の扱いを `else` で必ず書かせる。書かなければ E201。扱いは三つある。

| 書き方 | 意味 | 2026-01-31 の `+ 1 month` |
|---|---|---|
| `else end_of_month` | その月の末日に寄せる | 2026-02-28 |
| `else start_of_next_month` | 次の月の 1 日に送る | 2026-03-01 |
| `else reject` | エラーにする。範囲の中で一度でも当たれば、検査が E202 で止め、当たる入力を全部挙げる。生成したコードは例外を投げる | E202 |

当たりうるかは、書いたものから決める。月を足す操作は、いつも当たりうる。「k か月後の N 日」と「N 日締め」は、N が 29 以上になりうるとき（数が 29 以上か、整数の入力の範囲の上の端が 29 以上）だけ当たりうる。当たりえない操作に `else` を書くと W201。

範囲の中では一度も使われない `else` もある（20 日締めのあとの `+ 1 month`）。それは警告にしない。どの入力で使われたか、一度も使われなかったかは、人が読むページに出す（7 章）。

#### 民法の例

民法 143 条 2 項（e-Gov 法令 API v2 の版 `129AC0000000089_20260624_508AC0000000045` から取った）：

> 週、月又は年の初めから期間を起算しないときは、その期間は、最後の週、月又は年においてその起算日に応当する日の前日に満了する。ただし、月又は年によって期間を定めた場合において、最後の月に応当する日がないときは、その月の末日に満了する。

140 条は「日、週、月又は年によって期間を定めたときは、期間の初日は、算入しない。ただし、その期間が午前零時から始まるときは、この限りでない。」である。

この二つを文字どおりに書くと、次になる。応当する日が無いときは、次の月の 1 日に送ってから前日にすると、ちょうどその月の末日になる。

英語の版（`civil_code_period_end.cal`）では次のとおり。

```
date first_day = origin
  + 1 day                                        # the first day is not counted
date last_day = first_day
  + month_count months else start_of_next_month  # the corresponding day of the last month; with none, the 1st of the month after
  - 1 day                                        # the day before it: the last day of the last month when it had no corresponding day
date last_day_142 = last_day
```

日本語の版（`civil_code_period_end.ja.cal`）：

```
date 起算日(first_day) = 起点
  + 1 day                                 # 140 条：初日は算入しない
date 満了日(last_day) = 起算日
  + 月数 months else start_of_next_month  # 143 条 2 項：最後の月の応当する日。無ければ次の月の 1 日へ
  - 1 day                                 # その前日。応当する日が無かったときは、最後の月の末日になる
```

この書き方が条文どおりに計算することを、試作で確かめた。条文の場合分け（応当する日があればその前日、無ければその月の末日）をそのまま書いた関数と、起点 2000〜2027 年のすべての日と月数 1〜12 で一致した。

民法の期間は、無い日の扱いを法令の側が決めている例である。もし `else end_of_month` で書けば、条文と違う結果になる日がある。起点に月数を足して月末に寄せる書き方（`起点` から `+ 月数 months else end_of_month`）と比べると、起点 2026 年の 365 日と月数 1〜12 の 4,380 通りのうち 39 通りで結果が違う。最初の一つは起点 2026-02-28（土）、月数 1 で、条文どおりなら起算日は 2026-03-01、満了日は 2026-03-31。月数を足して寄せると 2026-03-28 になる。

| Rust の chrono 0.4.45（`checked_add_months`） | 2023-02-28 | 2024-02-29 | 2023-04-30 | 2023-05-30 | 2023-05-31 |
| macOS の `date -v+1m` | 2023-02-28 | 2024-02-29 | 2023-04-30 | 2023-05-30 | 2023-05-31 |
| Go 1.25.5（`time.AddDate`） | 2023-03-03 | 2024-03-02 | 2023-05-01 | 2023-06-01 | 2023-05-31 |
| JavaScript の `Date`（Node 23.11.0、`setUTCMonth`） | 2023-03-03 | 2024-03-02 | 2023-05-01 | 2023-06-01 | 2023-05-31 |

Temporal は `{ overflow: "reject" }` を渡すと、無い日で `RangeError` を投げる。Chrome 154 に組み込まれた Temporal も、試した五つの組で polyfill と同じ結果だった。Python の標準の `datetime` は月を足せない（`timedelta(months=1)` は `TypeError`）。

この表から分かることは三つある。

1. 多くは月末に寄せる（Catala の論文の切り捨て）。Go と JavaScript の `Date` は、余った日数を次の月へ繰り越す。そのため 2023-01-31 の 1 か月後（2023-03-03）が、2023-02-01 の 1 か月後（2023-03-01）より後になる。入力が遅いのに結果が早い（単調でない）。2023-05-31 の 1 か月前が 2023-05-01 になり、月が変わらないこともある。
2. どの実装でも、1 か月を二回足すのと 2 か月を一度に足すのとで結果が違う（2023-05-30 と 2023-05-31。Go と `Date` は 2023-06-01 と 2023-05-31）。月の足し算は結合しない。
3. 無い日をエラーにできるのは Temporal の `reject` だけで、それも既定ではない。

だから koyomi は、生成したコードの中で言語の日付のライブラリを使わず、通算日の整数で自分の手順を書く（6.1）。そうしないと、同じ `.cal` から生成した TypeScript と Go が違う日を返す。

#### Catala の論文から借りたもの

Monat、Fromherz、Merigoux の "Formalizing Date Arithmetic and Statically Detecting Ambiguities for the Law"（ESOP 2024、arXiv:2403.08935）は、月と年の足し算で無い日ができる計算を曖昧なものとし、丸め方を三つに分けた。切り捨て（その月の末日へ）、切り上げ（次の月の 1 日へ）、エラーである。koyomi の三つの扱いは、これと同じ意味にした。

- 年と月をまとめて足すときは、足し終えてから一度だけ丸める（論文の派生形 `rnd((e +y y) +m m) +d d`）。koyomi では一つの操作が一度だけ丸める。`+ 1 year else …` は `+ 12 months else …` と同じである（論文の Lemma 4）。一年と二か月を一度の丸めで足したいなら `+ 14 months else …` と書く。二行に分ければ、二回丸める。
- 切り捨てと切り上げは、どちらも単調で（論文の Theorem 3）、切り捨ての結果は切り上げの結果を超えない（Theorem 4）。試作で 1900〜2100 年のすべての日と月数 −24〜24 について確かめた。B の段階で、同じ総当たりを Rust のテストにする。
- Go と JavaScript の `Date` の繰り越しは、論文が coreutils について書いたのと同じもので、論文の意味では書けない。単調でないので、koyomi の扱いに入れない。
- 論文は、丸め方を替えると結果が変わるかどうか（rounding-insensitivity）を抽象解釈で判定した。koyomi は範囲を数え尽くせるので、同じ問いに総当たりで答える。扱いをほかの二つに替えると結果が変わる入力を全部数え、人が読むページに出す（7 章）。
- Catala は、丸めが要る計算で既定では実行時に例外を投げ、丸め方をスコープごとに書かせて、その根拠を法令か解釈で示すようにした。koyomi は、書かなければ検査で止める（P3）。

**捨てたもの**：

- 既定の扱いを置くこと（多くのライブラリのように月末に寄せる）。どの扱いが正しいかは契約や法令が決めることで、ツールが黙って決めれば、上の表のとおり誰かと食い違う。
- 余った日数を次の月へ繰り越す扱い（Go、JavaScript の `Date`）。単調でない。
- 年と月をまとめて書く操作（`+ 1 year 2 months`）。`+ 14 months` で足りる。二行で書けば二回丸めることを、別の書き方で隠すことにもなる。

### 1.8 営業日

**決定**：

- `+ n business days`：その日より**後**の営業日を数えて、n 番目の日。その日が休みでも、数え始めは次の日からである（土曜の 1 営業日後は月曜で、金曜の 1 営業日後と同じ）。`- n business days` は前へ同じように数える。
- `+ 0 business days` は、その日が営業日ならその日、休みなら翌営業日（`roll following` と同じ）。`- 0 business days` は、休みなら前営業日。どちらも、結果はいつも営業日になる。
- `roll following`：休みなら翌営業日。`roll preceding`：休みなら前営業日。`roll modified following`：翌営業日へ動かすが、月が変わるなら前営業日。`roll modified preceding`：前営業日へ動かすが、月が変わるなら翌営業日。営業日ならどれも動かさない。
- `if closed <操作>`：その日が休みのときだけ、一つの操作をする。`if closed + 1 day` は「休みなら翌日」で、翌日も休みでも、それ以上は動かさない。

休みの日から営業日を数えるときの結果は、ライブラリで分かれる。土曜（2026-10-03）の 1 営業日後を、手元で走らせて比べた。numpy 2.5.3 の `busday_offset` は、既定では休みの日を受け付けず（`ValueError`）、`roll='forward'` を渡すと先に月曜へ寄せてから数えて火曜（2026-10-06）を返す。QuantLib 1.43 の `Calendar.advance(土曜, 1, Days)` は次の日から数えて月曜（2026-10-05）を返し、`advance(土曜, 0, Days)` も月曜を返す（0 のときは翌営業日に寄せる）。

koyomi は QuantLib と同じ結果になるようにした。数え方が「その日より後の営業日を数える」の一通りで、受領日が休みでも営業日でも同じ言い方で済むからである。0 のときに寄せるのは、整数の入力で日数を受け取ると 0 が入りうるからで、そのときも「営業日で数えた日は営業日」が崩れないようにした。先に寄せてから数えたければ、`roll following` を一行足せば書ける。

**`if closed` を入れた理由**：P5 で一般の条件分岐は持たないとした。それでも「休みなら」だけは入れる。民法 142 条を文字どおりに書くには、これが要る。

> 期間の末日が日曜日、国民の祝日に関する法律（昭和二十三年法律第百七十八号）に規定する休日その他の休日に当たるときは、その日に取引をしない慣習がある場合に限り、期間は、その翌日に満了する。

条文の「その翌日」は、翌日も休みのときにさらに動くとは書いていない。これを `roll following`（休みが明けるまで動かす）で書けば、法令を一つの読み方で読んだことになる。koyomi は法令の読み方を決めない。文字どおりの「翌日」と「休みが明けた日」を二つの日付として書き、二つが等しいという条件を書けば、分かれる日を検査が全部挙げる。10 章の例では、起点 2026 年と月数 1〜12 の 4,380 通りのうち 121 通りで分かれる。最初の一つは起点 2026-01-22、月数 1 で、満了日 2026-02-22 が日曜、その翌日 2026-02-23 は天皇誕生日で、休みが明けるのは 2026-02-24 である。どちらを採るかは人が決める。

どちらの書き方にも、条文の「その日に取引をしない慣習がある場合に限り」は入らない。どの日を休みとするか（カレンダーを選ぶこと）が、その部分の読み方になる。それも人が決める。10 章の例のカレンダーは、条文が名指しする日（日曜日と、国民の祝日に関する法律に規定する休日）だけを休みにしたもので、「その他の休日」に何が入るかを決めていない。

`if closed` が見るのはカレンダーだけで、比較は書けない。続けられる操作は一つで、`if` を入れ子にはできない。だから、ループも任意の分岐も書けないままである。単調でなくなることはある（土日が休みなら、`if closed + 3 days` は日曜を水曜にし、翌日の月曜は月曜のままにする）が、それは条件の `is monotonic` が見つける。

**捨てたもの**：

- 比較で分ける一般の `if`（「受領が 25 日より後なら」）。締めの操作で書けない分岐が要る例を、まだ見ていない。
- `if open`。営業日なら何かをする決まりの例を見ていない。

### 1.9 時刻

**決定**：カレンダーに `offset +09:00` のような固定の UTC オフセットを書く。日付の宣言の最後に `at 09:00` と書くと、その日の 09:00（そのオフセットで）を時刻としても出す。`at end of day` は、その日が終わる時刻（次の日の 00:00）を出す。民法 141 条（前条の場合には、期間は、その末日の終了をもって満了する）の満了の時刻にあたる。

時刻は RFC 3339 の UTC で、`Z` で終わる形で出す（`2026-05-08T00:00:00Z`）。dandori の `timestamp` は `Z` で終わる形だけを受け付ける（dandori の `src/render.rs` の `TIMESTAMP_RE`）ので、そのまま `wait until` に渡せる。`eval` と人が読むページには、オフセット付きの形（`2026-05-08T09:00:00+09:00`）も並べる。

オフセットに `Asia/Tokyo` や `Europe/London` のようなタイムゾーンの名前を書くと、E107 でエラーにする。夏時間のあるタイムゾーンでは、同じ地域の同じ 09:00 でも季節でオフセットが変わり、固定のオフセットでは一年の半分で一時間ずれる。どのタイムゾーンに夏時間があるかを知るには tz データベースが要るので、どの名前も受け付けず、オフセットを数で書いてもらう。夏時間の無い地域なら、それで足りる。

`at` を書いたのに、カレンダーにオフセットが無ければ E110。

**捨てたもの**：tz データベースを埋め込むこと。夏時間の決まりは国が変え、データベースは年に何度も版が出る。祝日の表と同じ固定と更新の仕組みが要り、今回の範囲を超える。英語の例（England and Wales、夏時間がある）は日付だけを出し、時刻は出さない（10 章）。

### 1.10 条件

**決定**：`claims` の節に、名前と条件を一行ずつ書く。

```
claims
  paid_on_a_business_day      : payment is open
  within_60_days_of_receipt   : payment <= received + 60 days
  within_40_business_days     : payment <= received + 40 business days
  paid_after_closing          : payment > closing
  later_receipt_later_payment : payment is monotonic
  the_same_when_rewritten     : payment = payment_old
```

日本語の名前で書けば次のとおり。

```
claims
  営業日に払う       : 支払日 is open
  受領から60日以内   : 支払日 <= 受領日 + 60 days
  40営業日以内       : 支払日 <= 受領日 + 40 business days
  締めのあとに払う   : 支払日 > 締め日
  遅い受領は遅い支払 : 支払日 is monotonic
  書き直しても同じ   : 支払日 = 支払日_旧
```

- `X is open`：X が営業日である。
- `A <比較> B`：比較は `=`、`<`、`<=`、`>`、`>=`。A と B は日付の入力か日付の名前で、`+ n days`、`- n days`、`+ n business days`、`- n business days` を一つ付けてよい（n は操作と同じく、整数の入力の名前でもよい）。これで「ほかの日付との前後」「何日以内（暦日と営業日）」「二つの関数が一致する（書き直しの確かめ）」が書ける。
- `X is monotonic`：入力の日付が遅くなっても、X が早くならない。整数の入力があれば、その値ごとに日付について言う。

どの条件も、範囲のすべての入力について確かめる。単調性は、隣り合う二日（d と d+1）の組を全部比べれば、範囲全体について言える。≤ は推移するので、d < d' なら、あいだの隣り合う組をつないで X(d) ≤ X(d') が出る。

成り立たない入力が一つでもあれば、検査はエラーで止まる（E301。単調性は E302）。

**理由**：条件の形を比較と二つの述語に絞ったのは、どの条件も一つの入力ごとに真か偽が決まり、成り立たない入力を全部挙げられるようにするためである。

**捨てたもの**：

- `!=` と `is closed`。そう書きたい例を見ていない。
- 条件を一部の入力に限る書き方（`when 締め日 <= 28`）。条件の側に分岐が入る。限りたいなら、入力の範囲を狭めるか、ファイルを分ける。
- 成り立たなくてもエラーにしない「比べるだけ」の書き方。二つの読み方の違いを見たいときも、等しいという条件を書けば違う日が全部出る。それで足りるかは、例を書いて使ってみてから見直す（12 章）。

### 1.11 例

`examples` の表は、rulec と同じく、走らせて確かめる仕様である。入力の列と、`->` を付けた日付の列を書く。日付の列には、ファイルの日付を全部書く（足りなければ E304）。rulec の E111（例に出力の列が足りない）と同じ理由で、参照インタプリタと生成したコードが同じ誤りを持つと突き合わせは通ってしまい、それを破れるのは人が書いた値だけだからである。値が参照インタプリタと違えば E303。

## 2. 意味

### 2.1 日付の表し方

日付は先発グレゴリオ暦の暦日で、タイムゾーンを持たない。扱える範囲は 0001-01-01〜9999-12-31（Python の `datetime.date` と同じ）。内部では 1970-01-01 からの通算日の整数で持つ。rulec の `date` と同じ持ち方である。0001-01-01 は −719,162、9999-12-31 は 2,932,896 で、32 ビットの整数に収まる。年月日と通算日の変換には Howard Hinnant の `days_from_civil` と `civil_from_days` の手順を使う。範囲の 3,652,059 日のすべてで、変換して戻すと元に戻ることを試作で確かめた。

計算の途中で日付が範囲の外に出れば E204。

### 2.2 操作の定義

日付 z（通算日）の年月日を (y, m, d)、月 (y, m) の日数を len(y, m) と書く。(y, m) + k は k か月後の年月である。

- place(y, m, d, 扱い)：d ≤ len(y, m) なら (y, m, d)。そうでなければ扱いに従う。`end_of_month` は (y, m, len(y, m))、`start_of_next_month` は (y, m) + 1 の 1 日、`reject` はエラー。
- `+ n days`：z + n。`- n days`：z − n。
- `+ n months else P`：(y', m') = (y, m) + n として place(y', m', d, P)。`- n months` は −n で同じ。`± n years` は ± 12n months。
- `day N of month +k else P`：(y', m') = (y, m) + k として place(y', m', N, P)。
- `start of month +k`：(y, m) + k の 1 日。`end of month +k`：(y, m) + k の末日。
- `close day N else P`：月ごとの締め日 c(y', m') = place(y', m', N, P) のうち、z 以後で最も早いもの。候補は (y, m) − 1、(y, m)、(y, m) + 1 の三つの月で足りる。(y, m) + 1 の締め日はその月の中か次の月の 1 日なので、必ず z より後にある。(y, m) − 1 が要るのは `start_of_next_month` のときで、前の月の締め日がこの月の 1 日になることがある。
- `close end of month`：(y, m) の末日。
- `roll following`：z 以後で最初の営業日。`roll preceding`：z 以前で最後の営業日。`roll modified following`：following の結果の月が z の月と違えば、preceding の結果。`roll modified preceding`：preceding の結果の月が違えば、following の結果。
- `+ n business days`：n ≥ 1 なら、z より後の営業日の n 番目。n = 0 なら `roll following` と同じ。`- n business days`：n ≥ 1 なら、z より前の営業日の n 番目。n = 0 なら `roll preceding` と同じ。
- `if closed S`：z が休みなら S(z)、営業日なら z。

カレンダーに問い合わせる（ある日が営業日かを見る）のは、`business days`、`roll`、`if closed` と、条件の `is open` と `business days` だけである。

### 2.3 成り立つ性質と、成り立たない性質

`if closed` を除くすべての操作は、日付について単調（z ≤ z' なら f(z) ≤ f(z')）である。`end_of_month` と `start_of_next_month` の月の足し算（Catala の Theorem 3）、締め、月初と月末、営業日の数え方、四つの慣行のどれもそうである。単調なものをつないでも単調なので、`if closed` を使わない日付はいつも単調になる。それでも `is monotonic` を書けるようにしたのは、読む人に向けた主張として残すためと、`if closed` を使った日付を確かめるためである。

成り立たない性質もある（Catala の論文の Non-Property 1・2 と同じ種類のもの。試作で確かめた）。

- 月の足し算は結合しない。2023-03-31 に `+ 1 month else end_of_month` を二回すると 2023-05-30、`+ 2 months else end_of_month` を一回すると 2023-05-31。
- 日と月の足し算は、順序を入れ替えられない。2023-01-30 に 1 日足してから 1 か月足すと（月末に寄せて）2023-02-28、1 か月足してから 1 日足すと 2023-03-01。
- 月を足して同じだけ引いても、元に戻らない。2023-03-31 に `+ 1 month else end_of_month` で 2023-04-30、そこから `- 1 month else end_of_month` で 2023-03-30。
- `start_of_next_month` で月を引くと、引いたのに同じ月になることがある。2023-03-31 の `- 1 month else start_of_next_month` は 2023-03-01（2 月 31 日が無いので、次の月の 1 日へ送る）。

書き直したら同じ結果になるはずだ、という思い込みは、この性質のどれかで外れる。`=` の条件（書き直しの確かめ）が役に立つのはそこである。

### 2.4 カレンダーへの問い合わせとデータの範囲

ある日が営業日かを問うとき、その日がカレンダーのデータの範囲の外ならエラーにする。検査では E203 で、どの入力で、どの操作が、どの日を問うたかを言う。生成したコードは例外を投げる。

データの範囲の外に出ても、問い合わせなければエラーにしない。`+ 30 days` だけの日付は、結果が 2028 年でも祝日の表を見ないので、結果は表に依らない。エラーにするのは、結果が表に依るときだけである。

入力の範囲がデータの範囲に収まっていても、計算の先が外に出ることがある（1.1 の例の 2027-11-21）。検査は範囲のすべての入力を計算するので、それを全部見つける。E203 の直し方には、外に出る最初の入力の前日で終わる `range` を書き換え後の形として示す。その前の入力はどれも外に出ないことを、検査がもう確かめている。

## 3. 検査

### 3.1 何を確かめるか

`koyomi check` は次の順に確かめる。前の段でエラーがあれば、後の段へは進まない。

1. 字句と構文（E001〜E006）。
2. 名前と型（E007〜E015、E304）。`use calendar` の先も読み、読んだカレンダーの診断もここで出す。例の表に入力か日付の列が足りないこと（E304）も、書いたものだけから決まるのでここで見る。
3. カレンダーと出典（E101〜E111、W101、W102）。コピーを読み、固定と比べ、表を読む。通信はしない。
4. 書いたものから決まること（E201、W201、W202）。無い日の扱いが要るか。
5. 総当たり（E202〜E204、E301〜E303、E305）。入力の組み合わせの数が予算を超えれば、計算を始めずに E305 で止まる。超えなければ、範囲のすべての入力について、すべての日付と、条件が要る日を計算する。計算が止まる入力（E202〜E204）が一つでもあれば、それを言って終わり、条件と例は確かめない。範囲の一部の入力でしか計算できない決まりについて、条件が「すべての入力で」成り立つとは言えないからである。計算が止まらなければ、条件（E301、E302）と例（E303）を確かめる。

通れば、何を確かめたかを一行で言う（B の段階の実際の出力）。

```

### 3.2 総当たりと予算

入力の組み合わせの数は、日付の範囲の日数と、整数の入力それぞれの範囲の大きさの積である。1.1 の例は 689 通り、10 章の整数を三つ受け取る例は 639 日 × 31 × 2 × 22 で 871,596 通りで、koyomi の検査は 0.07 秒で終わる（A の段階の Python の試作では 6 秒ほどだった）。組み合わせごとに、すべての日付と条件を計算する。計算の段は、報告に使う入力（成り立たない最初の入力など）についてだけ、あとでもう一度計算して残す。

予算は入力の組み合わせの数で数える。既定は 10⁸（100,000,000）にした。B の段階で、手元のマシン（macOS、Apple シリコン。検査は一つのスレッドで走る）で次を測った。

| ファイル | 組み合わせ | 時間 |
|---|---|---|
| `closing_and_payment_days_as_inputs.ja.cal`（10 章） | 871,596 | 0.07 秒 |
| 100 年（1926〜2025 年）の日付 × 締め日 31 × 支払の月 12。締め、翌月の N 日、`roll preceding`、条件三つ | 13,587,300 | 0.92 秒 |
| 同じものに「支払日 <= 受領日 + 60 business days」の条件を足したもの | 13,587,300 | 3.5 秒 |

既定の予算いっぱいまで検査すると、表の二行目の重さの計算なら 7 秒ほど、三行目なら 26 秒ほどかかる。A の段階の目安（10⁷）は Python の試作の速さから見積もったもので、Rust の実装は試作より二けたほど速いので、一けた多い 10⁸ にした。超えたら E305 で止まり、確かめていないと言う。サンプリングして続けることはしない（P2。rulec の §6.3 と同じく、確かめていないのに緑を返すことは、このツールがある理由を否定する）。E305 は、どの入力の範囲が組み合わせの数を大きくしているかを添える。`--budget` で変えられる。

**捨てたもの**：

- 抽象解釈（Catala が使った Mopsa の方法）。範囲が有限で小さいので、総当たりのほうが厳密で、成り立たない日を全部挙げられる。抽象解釈で言えるのは「成り立たないかもしれない」までで、反例は手がかりにとどまる。
- SMT ソルバ。同じ理由に加え、依存を足さないため。
- サンプリング。上のとおり。

### 3.3 報告の形

成り立たない入力が多いとき（10 章の月末締め翌々月末払いは、669 日のうち 648 日）、全部を一行ずつ出すと読めない。そこで次の形にする。

- 続いている日はまとめる（`2026-01-01〜2026-01-29（29 日）`）。文面には最初の六か所までを書き、全部で何か所かを言う。`--format json` は全部を出す。ただし一つの診断につき 100 万か所までで、それより多いときは残りの数だけを言う。10⁸ 通りの入力で一日おきに成り立たない条件があると、続いている日のまとまりが 5,000 万か所になり、覚えておくだけでメモリが足りなくなるからである。
- 整数の入力があれば、その値の組み合わせごとにまとめ、組み合わせごとの数も注に並べる（`月数 1 で 11、月数 2 で 10、…`）。
- 最初の入力の計算を一段ずつ見せる。
- 比較の条件なら、いちばん外れる入力を一つ添える。

### 3.4 「証明」という語

koyomi の検査は、宣言した範囲のすべての入力を計算するので、サンプリングで試すテストとは違う。言えるのは、**書いた決まりが、宣言した範囲のすべての入力で条件を満たす**ことである。言えないことが三つある。範囲の外の入力。書いた決まりが元の文書（契約、約款、法令）と合っているか。祝日の表が現実と合っているか（コピーが配られたファイルと同じであることまでは、固定で言える）。

rulec の §15.47 にそろえ、ツールの出力では「証明」を肯定形で使わない。通ったことは「確かめた」と書く。生成したコードには「検査を通った決まりから生成した」と書き、コードそのものを「検証済み」とは書かない。生成したコードが参照インタプリタと同じ結果を返すことは、範囲のすべての入力で突き合わせたテストである（6.4）。看板の真ん中を prove にせず check にしたのも、同じ理由による。

## 4. 診断

### 4.1 形

dandori の形にそろえる。

```
error[E301]: <ファイル>:<行>:<列>: <一行の見出し>
    <行> | <原文の行>
  = <注>
  <そうなる例の見出し>:
      <計算の段>
```

一行目は業務の言葉で完結させる（rulec の §11 の原則 1）。どの診断にも、そこに至る具体的な入力か計算を添える（原則 2）。直し方は、書き換え後の形まで書く（原則 3）。書き換え後の行は `--format json` の `fix` に入れ、文面では、注がまだ言っていなければ `= 直した行: …` の一行で出す（E102、E103、E105、E111、E303）。

文面の作りで決めたことが二つある。英語の文は大文字で始める（文面の部品を組み合わせても、そうなるよう描くときにそろえる）。日本語の文では、ASCII の名前と日本語のあいだに空白を入れる（`invoice_date は`）。名前は書いた人のものなので、日本語の文に英字の名前が混ざることがあるからである。数字は対象にしない（`第140条` を崩さないため）。

文面は英語が既定で、`--lang ja` か環境変数 `KOYOMI_LANG=ja` で日本語にする。システムのロケールは見ない（rulec の §11 の原則 7）。日本語と英語は `tr!("…", "…")` で隣に書き、片方だけの文面を作れないようにする（rulec の `src/i18n.rs` と同じ考え）。ただし rulec の `tr!` がプロセス全体で一つの言語を読むのと違い、koyomi の `tr!` は二つの文を組にして返し、言語は描くときに渡す（dandori の `src/diag.rs` が文を二つ持つのと同じ）。テストが同じプロセスの中で、英語と日本語の golden を並行して描けるようにするためである。

`--format json` は、ファイルごとに一行で `{"file", "ok", "summary", "diagnostics": [{"code", "severity", "file", "line", "col", "message", "notes", "inputs", "steps", "fails", "fix"}]}` を出す。診断ごとの `file` は、`use calendar` で読んだカレンダーの診断のとき、そのカレンダーのパスになる。`inputs` は例の入力（そのまま `koyomi eval` に渡せる形）、`steps` は計算の段、`fails` は成り立たない入力の全部（続いている日をまとめた `{"from", "to", "params"}` の並び）、`fix` は `.cal` にそのまま貼れる書き換え後の形（無ければ null）。キーは `--lang` に依らず英語。

exit code は 0（エラーなし。警告はあってよい）、1（エラーあり）、2（引数の誤り、読めないファイル、koyomi 自身の不具合）。

### 4.2 台帳

番号と意味はこの表で決め、B の段階の `src/codes.rs` に移す。各コードは、いつ出るか、どう直すか、最小の再現（走る `.cal`）を持ち、`koyomi explain <コード>` が引く。テストが全コードの再現を走らせ、そのコードが出ることを確かめる（rulec の §11 と同じ）。

| コード | いつ出るか |
|---|---|
| E001 | 読めない字句（知らない文字、閉じていない文字列、形の崩れたリテラル） |
| E002 | この位置に書けない語 |
| E003 | ファイルが `calendar` か `dates` の行で始まらない |
| E004 | 節の順序や数が違う（同じ節が二度、calendar のファイルに `inputs` がある、表の出典に `format` か `covers` の行が無い、など） |
| E005 | 字下げが合わない（タブ、揃っていない） |
| E006 | 無い日付・月日・時刻のリテラル（`2026-02-30`、`13-01`、`25:00`） |
| E007 | 同じ名前を二度宣言している |
| E008 | 宣言されていない名前 |
| E009 | 名前や別名が予約語と同じ（koyomi のキーワード、出力先の言語の予約語、生成したコードが使う名前 `is_open`・`date`・`<別名>_at` など） |
| E010 | 公開する名前に ASCII の別名が無い |
| E011 | 型が合わない（日付のところに整数、など） |
| E012 | `date` の入力がちょうど一つではない |
| E013 | 範囲の誤り（両端が無い、空、`>` や `<` で書いた、足す数に負の数が入りうる、日が 1〜31 の外） |
| E014 | 日付どうしが循環している |
| E015 | `use calendar` の先が使えない（読めない、calendar のファイルでない、循環、オフセットが食い違う） |
| E101 | 出典のコピーが無い |
| E102 | 出典が固定されていない（`sha256:` が無い） |
| E103 | コピーが固定と違う |
| E104 | コピーが読めない（文字コード、形式、行の形、同じ日付が二度） |
| E105 | 表の行が `covers` の外にある |
| E106 | `covers listed years` で、あいだに行の無い年がある |
| E107 | オフセットが `±HH:MM` の形でない（タイムゾーンの名前は、夏時間を扱わないので理由を添えてエラーにする。`UTC` は `+00:00` と書くよう言う） |
| E108 | 営業日が一日も無いカレンダー |
| E109 | カレンダーが要る操作か条件なのに、`use calendar` が無い |
| E110 | `at` を書いたのに、カレンダーにオフセットが無い |
| E111 | 法令の引用が使えない（引いた条が固定されていない、条や引用の書き方が読めない、宣言の無い出典や法令でない出典を引いている） |
| W101 | `open` に書いた日が、もともと営業日 |
| W102 | 固定した法令の条が、どこからも引かれていない |
| E201 | 無い日に当たりうる操作に、無い日の扱いが書かれていない |
| E202 | `else reject` の操作が、範囲の中の入力で無い日に当たる |
| E203 | データの範囲の外の日が営業日かを問う計算がある |
| E204 | 計算した日付が 0001-01-01〜9999-12-31 の外に出る |
| W201 | 無い日に当たりえない操作に `else` が書かれている（日が 28 以下、または `else` を取らない操作） |
| W202 | 同じ意味の短い書き方がある（`end of month`、`start of month`、`close end of month`） |
| E301 | 条件が成り立たない入力がある |
| E302 | 単調でない（隣り合う日で、後の日のほうが早い結果になる） |
| E303 | 例の値が違う（例の入力が範囲の外のときも） |
| E304 | 例に入力か日付の列が足りない |
| E305 | 検査の予算を超えた（確かめていない） |

番台は、構文と名前（E0xx）、カレンダーと出典（E1xx）、日付の計算（E2xx）、条件と例（E3xx）で分けた。増やすときは番台の末尾に足し、番台をまたがない。

エラー[E201]: tests/mutants/E201_無い日の扱いが無い.cal:7:3: `+ 1 month` はその月に無い日に当たることがありますが、そのときどうするかが書かれていません
     7 |   + 1 month
  = 受領日 2026-01-29 なら 2026-02-29 になります
  = 直し方: 次のどれかを書いてください。`+ 1 month else end_of_month`（2026-02-28 にする）、`+ 1 month else start_of_next_month`（2026-03-01 にする）、`+ 1 month else reject`（範囲の中で起きないことを検査が確かめる）
  そうなる例:
      受領日    2026-01-29（木）
      一か月後                    1 か月後の同じ日: 2026-02-29 は無い
```

例の入力を探すため、E201 のときも、その操作の前までを範囲の入力で順に計算する。範囲の中で一度も無い日に当たらない操作でも、E201 は出す（書かなければエラーにする、という決まりは、書いたものだけから決める）。そのときの注は「範囲の中では起きませんが、`else reject` と書けば、起きないことを検査が確かめます」になる。

## 5. コマンド

|---|---|

## 6. 生成するコード

### 6.1 共通の形

**決定**：`koyomi gen` は、検査を通ったファイルから、出力先ごとに依存の無いファイルを一つ（Go は一つのパッケージ）と、そのランナーを書く。検査を通らないファイルからは書かない（診断を出し、ほかのファイルは書いて、exit 1）。

| 出力先 | 生成物 | ランナー |
|---|---|---|
| TypeScript | `typescript/<別名>.ts` | `typescript/<別名>_runner.ts` |
| Python | `python/<別名>.py` | `python/<別名>_runner.py` |
| Go | `go/<パッケージ名>/<パッケージ名>.go` | `go/<パッケージ名>/<パッケージ名>_runner_test.go` |
| Rust | `rust/<別名>.rs` | `rust/<別名>_runner.rs` |
| SQL（PostgreSQL） | `sql/<別名>.sql` | `sql/<別名>_runner.sql` |

書き出す先は `--out`（既定は `generated`）。calendar のファイルからは `is_open` だけの生成物を、dates のファイルからは日付ごとの関数と、カレンダーを読んでいれば `is_open` を書く。中身が変わらないファイルは書き直さない。`--check` は書かずに比べ、違うファイルと無いファイルを挙げて exit 1 にする（CI 用）。二つの `.cal` が同じ別名で同じ場所に書こうとしたら、何も書かずに exit 2 で止める。

頭には、どの `.cal` のどの版から作ったかを書く。`koyomi gen examples/payment_20th_close_next_10th.cal` の TypeScript の頭（実際の出力）：

```ts
// Code generated by koyomi 0.23.0. DO NOT EDIT.
// Source: payment_20th_close_next_10th.cal (dates payment_20th_close_next_10th v1, sha256:9973542043dbee17)
// Calendar: calendars/tokyo_business_days.cal (calendar tokyo_business_days v1, sha256:37af228cf6ba7b95)
// Cites: national_holidays = file calendars/data/syukujitsu.csv sha256:cec37a743c96995c (https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv), covers 1955-01-01..2027-12-31
```

日本語の版 `koyomi gen examples/payment_20th_close_next_10th.ja.cal` では次のとおり。

```ts
// Code generated by koyomi 0.23.0. DO NOT EDIT.
// Source: payment_20th_close_next_10th.ja.cal (dates 支払条件 v1, sha256:75482b2e796019d0)
// Calendar: calendars/東京の営業日.cal (calendar 東京の営業日 v1, sha256:d7b6134e23a8cb9f)
// Cites: 祝日 = file calendars/data/syukujitsu.csv sha256:cec37a743c96995c (https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv), covers 1955-01-01..2027-12-31
```

一行目は Go の決まり（`^// Code generated .* DO NOT EDIT\.$`）の形にし、どの言語でも英語のまま書く。二行目から下は `--lang ja` で日本語（`もと:`、`カレンダー:`、`出典:`）になる。ハッシュはどれも SHA-256 の先頭 16 桁で、`source` の固定と同じ長さである。パスは生成のもとにした `.cal` のディレクトリから数え、生成した機械のパスは書かない。読んだカレンダーがさらに別のカレンダーを読んでいれば、その分も `Calendar:` の行に並ぶ。法令を引いていれば、`Cites: 民法 = law 129AC0000000089 asof 2026-10-01 (第140条 sha256:e880059021fbb67d, …), revision 129AC0000000089_20260624_508AC0000000045` の形の行が足される。

頭の一行目と二行目は、ritsu の土台（ritsu-emit の `header`）が書く形で、rulec・chobo・dandori の生成物も同じ形にそろえた（ritsu の DESIGN 9.2）。一行目のバージョンは ritsu のバージョンで、ワークスペースの一つのバージョンである（いまは 0.1.0 で、koyomi のクレートのバージョンと同じ数なので、`koyomi gen` の出力は変わらない）。ritsu の `ritsu gen`（ritsu の DESIGN 9.3）がパッケージに入れるときは、`.cal` のパスと、`Calendar:` と `Cites:` の行のパスを、プロジェクトのルートから数えて書く（`codegen::unit_shown`）。`ritsu gen` が `crates/ritsu/tests/projects/stockroom` から書いた TypeScript の頭（koyomi の例から作ったものではないので、`tests/design.rs` が生成物と照らし合わせる `ts` の塊にはしていない）：

```
// Code generated by koyomi 0.23.0. DO NOT EDIT.
// Source: dates/payment_terms.cal (dates payment_terms v1, sha256:20eacc1719046107)
// Calendar: calendars/weekdays.cal (calendar weekdays v1, sha256:dbf95c1f04262520)
```

日付の計算は、通算日（1970-01-01 からの日数）の整数の上で、生成物の中に書いた小さな関数で行う。どの関数も `src/date.rs` と `src/calendar.rs` の同じ名前の手順を移植したもので、五つの出力先に同じ手順を書く。言語の日付のライブラリは使わない（1.7 の表のとおり、言語ごとに結果が違うから）。言語の日付の型に触れるのは、入力を受け取るときと結果を返すときだけである。Python の `date` は年・月・日の値を読み書きするだけで、SQL の `date` は `d - DATE '1970-01-01'` と `DATE '1970-01-01' + z` で日数に直すだけである。

小さな関数の名前は `_` で始め、言語の書き方に合わせる（TypeScript と Go は `_closeDay`、ほかは `_close_day`）。書くのは、そのファイルの操作が使う関数と、それが呼ぶ関数だけである（`net30.cal` の生成物に `_closeDay` は無い）。無い日の扱いと営業日の慣行は、`.cal` の語を文字列のまま渡す（`"end_of_month"`、`"preceding"`）。無い日に当たりえない操作（日が 28 以下の `day N of month` と `close day N`、月初と月末）には `"none"` を渡す。`"none"` で無い日に当たるのは koyomi の不具合なので、`KoyomiError` ではない例外（Go と Rust は panic、SQL は SQLSTATE XX000）にする。

公開する関数は、日付ごとに一つ（名前は別名。Go はパスカルケース）と、`at` のある日付の時刻の関数（`<別名>_at`）と、カレンダーを読んでいれば `is_open` である。名前と署名は `src/naming.rs` が決めていて、`koyomi api` が出すものと一字一句同じになる（生成物の中に api の署名がそのままあることを `tests/api.rs` が確かめる）。日付の関数は、始まりの日付から自分までの操作を順に並べ、ほかの日付の関数を呼ばない。`<別名>_at` だけは、自分の日付の関数を呼んでから時刻にする。関数の中の変数は `day` 一つで、これは koyomi のキーワードなので、どの別名ともぶつからない。

同じファイルの TypeScript から、payment の二つの関数（実際の出力）：

```ts
/**
 * Gives payment.
 * It takes received 2026-01-01..2027-11-20, the range koyomi check checked every input of; outside it, the error is a KoyomiError of kind range.
 */
export function payment(received: string): string {
  let day = _inputDate(received, "received", 20454, 21142); // range >=2026-01-01 <=2027-11-20
  day = _closeDay(day, 20, "none"); // close day 20  (closing)
  day = _dayOfMonth(day, 10, 1, "none"); // day 10 of month +1
  day = _roll(day, "preceding"); // roll preceding
  return _formatDate(day);
}

/** Gives the time of payment's day (at 09:00, offset +09:00) in RFC 3339, in UTC, ending in Z. */
export function payment_at(received: string): string {
  return _at(payment(received), 540, 540);
}
```

日本語の版の、支払日の二つの関数：

```ts
/**
 * Gives 支払日 (payment).
 * It takes 受領日 2026-01-01..2027-11-20, the range koyomi check checked every input of; outside it, the error is a KoyomiError of kind range.
 */
export function payment(received: string): string {
  let day = _inputDate(received, "受領日", 20454, 21142); // range >=2026-01-01 <=2027-11-20
  day = _closeDay(day, 20, "none"); // close day 20  (締め日)
  day = _dayOfMonth(day, 10, 1, "none"); // day 10 of month +1
  day = _roll(day, "preceding"); // roll preceding
  return _formatDate(day);
}

/** Gives the time of payment's day (at 09:00, offset +09:00) in RFC 3339, in UTC, ending in Z. */
export function payment_at(received: string): string {
  return _at(payment(received), 540, 540);
}
```

行末のコメントは、その操作の `.cal` の行である。始まりの日付の操作には、一行目にその日付の名前を添える（`(締め日)`）。

**エラー**：どの言語でも、エラーから種類が取れる（TypeScript・Python・Rust は `kind`、Go は `Kind`、SQL はメッセージの頭の `koyomi <種類>:`）。種類は四つある。

| 種類 | いつ起きるか | 参照インタプリタでは |
|---|---|---|
| `range` | 入力が `range` の外（入口のガード） | 範囲の外の入力 |
| `data` | カレンダーが知らない日が営業日かを問うた | `OpFail::Outside`（E203） |
| `reject` | `else reject` の操作が無い日に当たった | `OpFail::Missing`（E202） |
| `date` | 日付が 0001-01-01〜9999-12-31 の外に出た。または、入力が日付として読めない（TypeScript の文字列、Go と Rust の `Date` の値） | `OpFail::OutOfRange`（E204） |

検査を通ったファイルでは、範囲の中のどの入力でも `data`・`reject`・`date` は起きない。検査がすべての入力で確かめたからである。したがって公開する関数から実際に出るのは、範囲の外の入力の `range`、`is_open` にデータの範囲の外の日を渡したときの `data`、読めない日付の `date` の三つで、ほかは起きないはずのことへの備えである。

**生成物が使う名前**：生成物とぶつかる別名は、生成する前に E009 でエラーにする（`src/naming.rs` の `GENERATED` と `src/reserved.rs`。予約語の表そのものは C.10 から ritsu-emit のもの。11.1）。生成物が置く `is_open`・`Date`・`KoyomiError`・`ParseDate`、Python が読み込む `date`・`datetime`・`timedelta`、Go の関数が使う `err`、Python の生成物が呼ぶ組み込みの関数（`range`・`str`・`int`・`bool`・`tuple`・`isinstance`・`frozenset`・`super`）、PostgreSQL の予約語と PL/pgSQL の予約語（`begin`・`declare`・`execute`・`foreach` など）である。ファイルの別名は Python と Rust のモジュール、PostgreSQL のスキーマの名前になるので、生成物が読み込むモジュール（Python の `datetime`・`json`・`sys`・`typing`、Rust の `std`・`core`・`alloc`）と PostgreSQL のスキーマ（`pg_catalog` など）の名前もエラーにする（`src/naming.rs` の `MODULES`）。`err`、Python の組み込みの関数、PL/pgSQL の予約語、モジュールとスキーマの名前は、C の段階で足した。生成物を書いてみて、引数や関数がその名前だとコードが動かなくなることが分かったからである（Python で日付の別名を `range` にすると、`_close_day` の中の `range(...)` がその関数を呼ぶ）。

`--lang ja` を付けると、頭の二行目から下、関数の説明、エラーのメッセージが日本語になる。

**捨てたもの**：

- 小さな関数を、使わないものも含めて全部の生成物に書くこと。どの生成物も同じ形になるが、読む人は使われない関数まで読むことになる。どの関数もどこかの生成物で使われ、突き合わせで確かめられていることは、6.4 の helpers のファイルが受け持つ。
- Go のエラーを panic で運び、公開する関数の `defer` で `error` に直すこと。本体は短くなるが、名前付きの戻り値が要るので `koyomi api` の署名（`(Date, error)`）と合わなくなり、Go を読む人にも見慣れない形になる。
- 無い日の扱いと慣行を列挙の定数にすること。TypeScript の `enum` は型を剥がすだけでは走らない（6.2）。文字列なら、どの言語でも `.cal` の語がそのまま読める。

### 6.2 出力先ごとの形

| 出力先 | 日付の型 | エラー | 確かめるツール（テスト） |
|---|---|---|---|
| TypeScript | `"YYYY-MM-DD"` の `string` | `KoyomiError`（`Error` の子、`kind`） | `node`（型を剥がして走らせる）、`tsc --strict --erasableSyntaxOnly` |
| Python | `datetime.date` | `KoyomiError`（`ValueError` の子、`kind`） | `python3`、`mypy --strict` |
| Go | パッケージの `Date{Year, Month, Day int}`、`ParseDate`、`String()` | `error` を返す（中身は `*KoyomiError`、`Kind`） | `gofmt -l` が何も出さない、`go vet`、`go test -c` |
| Rust | モジュールの `Date { year, month, day }`（`FromStr`、`Display`、`Copy`、`Ord`） | `Result<_, KoyomiError>`（`kind`） | `rustc -D warnings` をエディション 2021 と 2024 で |
| SQL（PostgreSQL 14 以降） | `date` | `RAISE EXCEPTION 'koyomi <種類>: …' USING ERRCODE = '22023'` | 使い捨てのクラスタの PostgreSQL |

- TypeScript は Node が型を剥がすだけで走る形にする（`enum`、実行時のコードを含む `namespace`、コンストラクタの引数でのプロパティ宣言を書かない。dandori の生成物と同じ制約）。テストは `tsc --erasableSyntaxOnly` で、その形から外れていないことも確かめる。日付を `string` にしたのは、日付だけの型が標準に無く（`Date` はタイムゾーンを持ち、Temporal は Node 23 に無い）、JSON でそのまま運べるからである。ランナーは生成物を名前空間として読み込む（`import * as m`）ので、日付の別名がランナーの名前とぶつからない。
- Python は標準の `datetime.date` で受け取り、返す。範囲は Python の `date` と同じなので、変換で溢れない。どの関数にも型注釈を付け、`mypy --strict` を通す。
- Go と Rust は日付だけの型が標準に無いので、生成物の中に小さな `Date` の型を置く。`time.Time` を使う案は、タイムゾーンの取り違え（JST の時刻を UTC に直してから日付を取ると前の日になる）を呼び込むので採らなかった。
- Go の関数は、失敗しうるものは小さな関数も含めて `(int, error)` を返し、呼ぶたびに `err` を見る。gofmt が揃える行末のコメント（祝日の表）は、gofmt と同じ揃え方（いちばん長い行の一つ後ろ。幅は文字数）で書く。ランナーは同じパッケージのテストのファイル（`TestMain`）にした。環境変数 `KOYOMI_RUNNER` があれば、テストを走らせる代わりに vectors を読む。`go test -c` で作ったプログラムを走らせる。同じパッケージなので import のパスが要らず、生成したディレクトリをどのモジュールに置いても動く。
- Rust の生成物はモジュール（`main` を持たない）で、エディション 2021 でも 2024 でも通る書き方にする（let チェーンを使わない、など）。利用者のクレートのエディションに依らないようにするためである。小さな関数は `_` で始まるので、使わないものがあっても警告にならない。ランナーは `#[path]` でモジュールを読み、`#[allow(dead_code)]` をその読み込みにだけ付ける。標準のライブラリに JSON が無いので、ランナーは vectors の `in` を自分で読む（名前にエスケープは無く、値は引用符の中の日付か数）。
- SQL は、ファイルの別名のスキーマ（`CREATE SCHEMA IF NOT EXISTS <別名>`）に関数を作る。公開する関数と、ループや分岐のある小さな関数は PL/pgSQL で、式一つで書ける小さな関数（曜日、うるう年、月の日数、表の日か、切り捨ての割り算、年月日の文字列）は SQL 標準の関数本体（`RETURN 式`、PostgreSQL 14 以降）にした。後者には `STRICT` を付けない。`STRICT` の関数の本体に `CASE` や `AND` があると、PostgreSQL はその関数を呼ぶ側の式に展開しないからである。展開されるようにしたことで、SQL の突き合わせ（この出力先だけを走らせたとき）は 33.7 秒から 22.5 秒になった。祝日の表は `_is_holiday` の中の `= ANY (ARRAY[…])` に一行一日で埋める。年・月・日のように値を二つ以上返す関数は、整数の配列を返す。公開する関数は `STRICT` で、`NULL` を渡すと `NULL` が返る。スキーマで分けたのは、一つのファイルが関数をいくつも持つので、名前を `<別名>_<日付>` とつなぐと別のファイルの名前とぶつかりうるからである（`a_b` の `c` と `a` の `b_c`）。ランナーは psql のスクリプトで、vectors を `\copy … FROM pstdin` で一時テーブルに入れ、一行ずつ `pg_temp` の関数で計算して `COPY … TO STDOUT` で出す。その関数は SQLSTATE 22023 を受け止めて `error <種類>` にする。

**捨てたもの**：

- 言語の日付のライブラリ（dateutil、`time.AddDate`、`interval`、Temporal）を呼ぶこと。1.7 の表。
- 実行時のライブラリを別に配ること。rulec の P5 と同じく、生成物は一つで読めて依存が無いほうがよい。小さな関数を生成物ごとに書く重複は、テストで同じ結果になることを確かめる（6.4）。
- 日付を通算日の整数で受け渡すこと（rulec の生成物の `date` はそうしている）。期日を使う側のコードは日付で考えるので、言語ごとの日付の形にした。通算日は生成物の内側だけで使う。
- Go のランナーを別のパッケージ（`package main`）にすること。生成物のパッケージを import するパスが、置かれるモジュールで変わる。go.mod を二つ書いて `replace` でつなぐ形（rulec の Go のランナー）もあるが、生成物に go.mod を書かない（dandori の Go の生成物と同じ）ほうを選んだ。

### 6.3 vectors

`koyomi vectors <file.cal>` は、範囲のすべての入力について、一行に一つの JSON を出す。キーは名前（rulec の vectors と同じ）。`koyomi vectors examples/payment_20th_close_next_10th.cal` の 91 行目（実際の出力）：

```jsonl
{"in":{"received":"2026-04-01"},"out":{"closing":"2026-04-20","payment":"2026-05-08","payment.at":"2026-05-08T00:00:00Z"}}
```

日本語の版 `koyomi vectors examples/payment_20th_close_next_10th.ja.cal` の 91 行目：

```jsonl
{"in":{"受領日":"2026-04-01"},"out":{"締め日":"2026-04-20","支払日":"2026-05-08","支払日.at":"2026-05-08T00:00:00Z"}}
```

`out` には、ファイルの日付を宣言の順に、`at` のある日付ならその直後に時刻（`<名前>.at`、`Z` で終わる UTC）を置く。行は検査が回す順（`check::Inputs`。整数の入力が外側で、最後に宣言したものがいちばん速く回り、日付が内側）に出すので、n 行目は検査が n 番目に計算した入力である。

範囲の行のあとに、範囲のすぐ外の入力を足し、そこでは `"error":"range"` を期待する。日付の範囲の最初の日の前日と最後の日の翌日（整数の入力は最小の値）、続いて整数の入力ごとに、最小の値の一つ下と最大の値の一つ上（日付は範囲の最初の日）である。どの日付の関数も受け取らない入力（条件だけが使う整数）は、生成したコードにガードが無いので、外の行を出さない。0001-01-01 の前日のように日付にならない値も出さない。

```jsonl
{"in":{"received":"2025-12-31"},"error":"range"}
{"in":{"received":"2027-11-21"},"error":"range"}
```

```jsonl
{"in":{"受領日":"2025-12-31"},"error":"range"}
{"in":{"受領日":"2027-11-21"},"error":"range"}
```

calendar のファイルの vectors は、データの範囲のすべての日について `{"in":{"date":"…"},"out":{"open":true}}` を出し、データの範囲の前日と翌日で `"error":"data"` を期待する。表の無いカレンダーはどの日のことも分かるので、1900〜2100 年（73,414 日）に限って出し、外の行は無い。

行の数（PLAN C.8 の数と同じ）は、`england_and_wales` 3,655、`net30` 1,066、`close_20th_pay_10th` 1,057、`close_and_pay_on_given_days` 872,968、`period_of_months` 4,384、日本の暦の例は英語の版と日本語の版で同じで、`payment_20th_close_next_10th` 691、`civil_code_period_end` 4,384、`closing_and_payment_days_as_inputs` 871,604、`tokyo_business_days`（`東京の営業日`）と `civil_code_142_days`（`民法142条の休日`）26,665 である（`tests/vectors.rs`）。検査を通らないファイルには出さない（診断を出して exit 1。`gen` と同じ）。

### 6.4 突き合わせ

**決定**：生成したコードを、範囲のすべての入力で参照インタプリタと突き合わせる（P1）。

- ランナーは vectors の行を標準入力から読み、一行ごとに生成した関数を呼んで、結果を一行に書く。日付の値と時刻を `out` と同じ順に空白で区切って並べ（calendar なら `true` か `false`）、例外が出たら、最初に出た例外の種類で `error <種類>` と書く。
- `tests/targets.rs` は、出力先ごとに、`examples/` の検査を通るファイル全部（英語を先にした段階から、calendar の五つと dates の十。England and Wales の例、日本の暦の例の英語の版と日本語の版）と `tests/fixtures/` の十四のファイル（英語の七つと、同じものを日本語で書いた七つ）を生成し、その出力先のツールで生成物を確かめてから（6.2 の表の右の列）、ランナーに vectors の全部の行を流して一行ずつ比べる。vectors はテストの中で作りながらパイプで流し、ディスクには書かない。合わない行があれば、最初の五行の入力と、参照インタプリタの結果と、生成したコードの結果を出して落ちる。合えば `compared <出力先> <ファイル>: <行数> lines` を一行出す。ツールが無ければ `SKIP: <理由>` の行を出して通す。
- `--lang ja` の生成物も、同じツールで確かめる（型の検査、gofmt と go vet、二つのエディションの rustc、PostgreSQL への読み込み）。日本語の生成物が英語と違うのはコメントとエラーのメッセージだけだが、メッセージの文字列がその言語の構文を壊していないことと、エラーのときに実際に組み立てられることを確かめるため、`payment_20th_close_next_10th.ja.cal` と英語の版 `payment_20th_close_next_10th.cal`（範囲の外の行で `range`）、`東京の営業日.cal` と `england_and_wales.cal`（データの範囲の外の行で `data`）は、日本語の生成物でも全部の行を突き合わせる。

## 7. 人が読むページ（doc）

**決定**：`koyomi doc` は、コードが実現すべきものを理解し、確かめる人（経理、法務、会社のカレンダーを決める人、コードをレビューする開発者）が読むページを、Markdown か、一枚の HTML で出す。書くのは `.cal` と検査の結果から言えることだけで、どの文も `.cal` の行か検査の結果に遡れる（rulec の §1.6）。操作を言い直す文は、7.1 の表（`src/paraphrase.rs`）からだけ作る。

ページは一度だけ、見出し・段落・表・引用・月の表のブロックの並び（`src/doc/mod.rs` の `Page`）として組み、Markdown（`src/doc/markdown.rs`）と HTML（`src/doc/html.rs`）は、それをそれぞれの書き方で出すだけにした。二つの形のあいだで中身が食い違わないようにするためである。

dates のファイルのページは、次の順に並ぶ。

1. 見出し：名前、バージョン（`v1`）、description。もとにしたファイル（`.cal`、カレンダー、表、法令の条）とハッシュ、koyomi のバージョン。ハッシュが今のファイルと違えばページは古い、と一文で添える。
2. 判定：通ったファイルなら `koyomi check` が出す一行（「3 つの条件が、受領日 2026-01-01〜2027-11-20 の 689 日のすべてで成り立ちます」）。成り立たない条件や違う例があれば、その診断の見出しを並べる。
3. 計算のしかた：日付ごとに、操作を一行ずつ普通の言葉で言い直し、後ろに `.cal` の行をコメントごと置く。行末のコメントは書いた人が `.cal` に残したもので、契約や条文のどの言葉にあたるかを書いておけば、そのままページに出る（10 章）。`roll` と `if closed` の行には、範囲の中で休みに当たって効いた入力の数と、`roll` ならいちばん大きく動いた日数を添える。法令を引いた行には、コピーから引いた条文と、何年何月何日時点のどの版かを添える。
4. 確かめたこと：入力の範囲と組み合わせの数、条件ごとの結果。比較の条件は、成り立てば余裕がいちばん少ない入力を、成り立たなければいちばん外れる入力を書く。成り立たない条件ごとに、成り立たない入力の全部（整数の入力があれば、その値ごと）と、診断と同じ最初の入力の計算を載せる。
5. 無い日の扱い：`else` ごとに、範囲の中で使われた入力の数と最初の例、ほかの二つの扱いに替えたら日付が変わる入力の数（`reject` なら計算が止まる入力の数）。無い日に当たりうる操作が無ければ、そう書く。
6. エッジケース（7.3 の選び方）。
7. 例：`examples` に書いた値と、計算した値と合っているか。
8. カレンダー：読んでいるカレンダーと description、休みの決まり（ファイルごとに `.cal` の行つき）、出典とデータの範囲、入力と計算した日付が入る範囲でいちばん長い連休、月の表。

calendar のファイルのページは、見出し、休みの決まり、出典とデータの範囲、営業日の数（表の月を含む年のうち、カレンダーが一年まるごと知っている年）、表の月でいちばん長い連休、月の表である。東京の営業日の 2026 年は 240 日が営業日で、2026-01〜2027-12 でいちばん長い連休は 2026-12-29〜2027-01-03 の 6 日になる（`tests/doc.rs`）。

### 7.2 月の表

**決定**：月の表は月曜から始まる七列にする。Markdown では、休みの日を（ ）で囲み、条件が成り立たない入力の日を太字にし、エッジケースの入力の日に ◆ を、カレンダーが知らない日に ? を付ける。表の下に、名前のある休み（祝日、毎年の休み、特定の日）と、`open` で営業する日を並べる。HTML では、休みの日に色を付けて祝日の名前をその日のところに書き、成り立たない入力の日を枠と色で目立たせる。日付にマウスを載せると、休みの理由、成り立たない条件（整数の入力の値つき）、エッジケースに選んだ理由が出る（`title`）。

出す月は、dates のファイルなら、入力の範囲と計算した日付が入る月の全部である。24 か月を超えれば、成り立たない入力のある月と、エッジケースの入力と計算した日付のある月だけにし、省いた月の数を書く。`net30.cal` は 2026-01〜2028-12 の 36 か月のうち 8 か月を載せる。エッジケースの計算した日付の月も入れたのは、支払日が Good Friday から動いた例で、その Good Friday の月が表に無いと、なぜ動いたかが表から読めないからである。calendar のファイルなら、データの範囲の最後の 24 か月にする。表を読まないカレンダーはどの日のことも知っているので月を選びようがなく、`--months` を書いたときだけ月の表を出す。どちらも `--months 2026-04..2027-03` で替えられる。今日の日付は使わない。走らせた日によってページが変わらないようにするためである。

**捨てたもの**：

- 日曜から始まる月の表。日本の壁掛けのカレンダーには日曜始まりが多いが、土日を並べて置くと休みの続き方が見やすく、ISO 8601 と koyomi の曜日の番号（月曜を 0）にもそろう。
- Markdown の月の表で、日付の隣に祝日の名前を書くこと。列が広がって表が読めなくなるので、表の下に並べた。
- 月の表に、計算した日付（支払日）にも印を付けること。締めや翌月の N 日のように多くの入力が同じ日に集まる決まりなら読めるが、Net 30 のように入力ごとに違う日になる決まりでは、ほとんどの営業日に印が付いて何も読めない。

### 7.3 エッジケースの選び方

**決定**：ページを作るときに範囲のすべての入力をもう一度計算し（`src/doc/edges.rs`）、次に当たる入力を、検査が計算する順で最初のものを選ぶ。

- 条件ごとに、成り立たない最初の入力か、成り立つ中でいちばん余裕の無い入力（比較の条件で、`=` でないもの）。
- `else` ごとに、無い日に当たって使われた最初の入力。`if closed` ごとに、休みに当たって効いた最初の入力。
- ほかの日付の始まりにならない日付（結果）ごとに、入力から結果までの日数がいちばん多い入力と少ない入力。同じ入力で同じ日数になる日付はまとめて言う。日数がいつも同じ日付（`+ 30 days` だけの日付など）は選ばない。
- `roll` ごとに、日付を動かした休みの理由（曜日、祝日の名前、毎年の休み、特定の日）ごとの最初の入力（六つまで）と、いちばん大きく動いた入力（2 日以上動くときだけ）。
- 入力の日が、休みの日、毎年の休みの日、祝日の前日と翌日（入力の日が営業日のとき）、月末（31 日、30 日、うるう年でない年の 2 月 28 日、2 月 29 日）である最初の入力。

同じ入力は一行にまとめる。16 行を超えるときは、上に挙げた順に残し（条件、`else` と `if closed`、日数、`roll`、入力の日の順）、残った行を検査が計算する順に並べる。どの行にも、何に当たったかを書く。

**理由**：読む人が見たいのは、決まりが効く日である。月末や祝日の前後は、人が手で確かめるときにまず試す日で、koyomi は範囲を全部計算しているので、その中から最初のものを選べば足りる。日数のいちばん多い入力と少ない入力を結果の日付に限ったのは、締め日のような途中の日付まで並べると、同じ入力が同じ理由で何度も出て表が読めなくなったからである（A の段階の計画では日付ごとにしていた）。

**ほかの扱いに替えたときの数**：`else` のある操作ごとに、範囲のすべての入力で、その操作だけをほかの扱いに替えて日付を計算し直し、元の日付と比べる。無い日に当たった入力だけを計算し直せば足りるように見えるが、`close day` は違う。`close day 31 else start_of_next_month` で 2026-05-01 を締めると、4 月の締め日が 5 月 1 日に送られるのでその日に締まり（無い日に当たる）、`else end_of_month` なら 4 月の締め日は 4 月 30 日で、5 月 1 日は 5 月 31 日に締まる（無い日に当たらない）。扱いを替えると、無い日に当たるかどうか自体が変わる。だから全部の入力を計算し直す。`closing_and_payment_days_as_inputs.ja.cal` の 871,596 通りでも、ページ全体が 0.3 秒ほどで出る（release のビルド）。

### 7.4 検査を通らないファイル

構文、名前、出典、無い日の扱い、日付の計算、予算（E0xx、E1xx、E201〜E204、E305）でエラーがあれば、ページを作らない。壊れた決まりを整ったページにすれば、読む人を誤らせる。条件と例が成り立たないこと（E301〜E303）は決まりについての事実なので、ページを作り、成り立たない日に印を付ける。ここが rulec と違う。rulec は検査を通らない規則のページを作らないが、koyomi の条件は「決まりが満たすべきこと」で、満たさない日を読む人に見せることが、このページのいちばんの役目だからである。

**決定**：ページを出せば、条件が成り立たなくても exit code は 0 にする。ページを作れないときは 1 で、診断は標準エラーに出す。標準出力はページだけにしたので、`koyomi doc x.cal > x.md` で診断がページのファイルに混ざることはない。成り立たないことを CI で止めたいなら、`koyomi check` がその役をする。

### 7.5 HTML

**決定**：HTML は一枚で、script も、外のファイル（フォント、画像、スタイルシート）も読まない。メールで送っても、印刷しても、そのまま読める。明るい配色と暗い配色を CSS の変数で持ち、`prefers-color-scheme` に従う。`<html data-theme="light|dark">` と書けば、どちらかに決められる（rulec のページと同じ）。計算の段は、Markdown では `koyomi check` と同じ字下げのテキストにし、HTML では表にした。等幅のフォントでも、日本語の幅は二文字分にそろわないことが多いからである。

`tests/doc.rs` は、Chrome（`KOYOMI_CHROME`、無ければ macOS の Google Chrome、それも無ければ PATH の `google-chrome` か `chromium`）で、わざと破る二つの例のページのスクリーンショットを撮る。ページの先頭は明るい配色で、月の表は暗い配色で撮る。ヘッドレスの Chrome は OS の外観に従い、`--force-dark-mode` でも `--blink-settings` でも `prefers-color-scheme` が替わらなかったので、ページをコピーし、その `<html>` に `data-theme` を書いてから撮る。スクリーンショットは `KOYOMI_BLESS=1` のときに `docs/images/` に置き、README が載せる。

**捨てたもの**：

- HTML に script を入れて、入力を変えて計算を試せるようにすること（rulec のページの「試してみる」）。生成した TypeScript を埋め込めばできるが、一つの入力を試すなら `koyomi eval` がある。何も読まない一枚のほうが、読む人の手元で確実に開ける。
- 法令の条文を、ページの最後にまとめて一度だけ載せること。読む人は日付ごとに読むので、引いた場所ごとに載せる（142 条のように二度載ることがある）。条文は、項ごとに一行にし、項の番号と文とただし書を同じ行に置いて、法令の書き方に近づけた（`sources::article_lines`）。`source outdated` が比べる `xml_text` は文ごとに一行のままである。

## 9. 出典のコマンド

**決定**：rulec と同じく三つ。通信するのは `fetch` と `outdated` の二つだけで、`curl` を子プロセスで呼ぶ（HTTPS を自前で書かず、依存も足さない）。HTTP と HTTPS の URL は三度まで試し（二度めの前に 2 秒、三度めの前に 4 秒待つ）、`file://` の URL は一度だけ読む。どのコマンドも `.cal` を構文の段まで読み、検査は通さない。コピーが無い（E101）、固定が無い（E102）、固定と違う（E103）は、どれもこのコマンドで直すものだからである。

- `koyomi source fetch <file.cal>`：`url` のある表を取り、`file` に書く。配られているバイト列をそのまま書き、文字コードを変えない（1.5）。書いたあと、固定と合うかを言う。法令の出典は、固定している条と引いている条ごとに、e-Gov 法令 API v2 の `law_data/<法令ID>?asof=<日付>&elm=<要素>&law_full_text_format=xml` を引き、返ってきた XML（`law_full_text` の base64 を戻したもの）をコピーのファイルに、`revision_info.law_revision_id` を `revision.txt` に書く。本文（タグを落としたもの）が前のコピーと同じなら、コピーを書き換えない（rulec の §15.71 と同じ。e-Gov は改正の無い条の属性や改行を書き換えることがある）。
- `koyomi source pin <file.cal>`：コピーの SHA-256 の先頭 16 桁を、`source` の行の `sha256:`（法令なら条の固定の行）に書く。変えるのはその 16 桁だけで、ほかの文字は、行の終わりの CR LF も含めて一字も変えない。固定の無い `source` の行には、コメントの前に ` sha256:…` を足す。引いているのに固定の行が無い条には、その出典の最後の固定の行のあとに一行を足す。表なら、行の数と `covers` も言う。

```
$ koyomi source pin examples/calendars/england_and_wales.cal
bank_holidays: already pinned at sha256:538b3482c28b85ec; the table has 83 rows, covers listed years = 2019-01-01..2028-12-31
$ koyomi source pin examples/civil_code_period_end.cal
civil_code: all 4 articles already pinned
$ koyomi source pin examples/calendars/東京の営業日.cal
祝日: already pinned at sha256:cec37a743c96995c; the table has 1,067 rows, covers 1955-01-01..2027-12-31
$ koyomi source pin examples/civil_code_period_end.ja.cal --lang ja
民法: 4 条とも固定済みです
```

- `koyomi source outdated <file.cal>`：表は、`url` から取ったもののハッシュを固定と比べる。同じなら「変わっていません」で exit 0。違えば、コピーと取ったものの両方を読み、増えた日、消えた日、名前の変わった日をそれぞれ六件まで並べて全部の数を言い、`covers` の書き換え案（`covers listed years` なら範囲の変わり方）を言って、exit 1。法令は、`law_revisions/<法令ID>` で `asof` より後に施行される版を引き、その施行日を `asof` にして条を取り、本文を比べる。比べる相手は一つ前の施行日の本文（最初はコピー）なので、改正は施行の日に一度だけ言う。同じ日に施行される版が二つ以上あっても、その日の本文は一つなので一度だけ問う。変わる条があれば、施行日と版と、変わる文を `-` と `+` で並べて exit 1。

`tests/fetch.rs` は、内閣府の表のコピーから 2027 年の 17 行を除いた表を固定し、元のコピーを指す `file://` の URL を `url` に書いた `.cal` で `outdated` を走らせる。URL が変わったと言う一行め（テストの場所のパスを含むので省く）のあとは、次のとおり（実際の出力。exit 1）：

```
  2027 年の 17 日が増えます: 2027-01-01 元日、2027-01-11 成人の日、2027-02-11 建国記念の日、2027-02-23 天皇誕生日、2027-03-21 春分の日、2027-03-22 休日、ほか 11 日
  表が延びるので、covers も延ばします: `covers 1955-01-01..2027-12-31`（いまは 1955-01-01..2026-12-31）
  読んでから koyomi source fetch で取り直し、koyomi source pin で固定します
```

本物の内閣府、GOV.UK、e-Gov には、C の段階で一度だけ問い合わせた（`KOYOMI_NET=1 cargo test --test fetch the_real_sources_when_asked`）。2026-10-01 より後に施行される五つの版のどれでも、140〜143 条の本文は変わらなかった（`outdated` は本文を比べる。1.5 に書いた、XML が一バイトも変わらないという事実は A の段階で確かめたもの）。

```

$ koyomi source outdated examples/calendars/東京の営業日.cal

$ koyomi source outdated examples/calendars/england_and_wales.cal
bank_holidays: unchanged (https://www.gov.uk/bank-holidays.json is sha256:538b3482c28b85ec, as pinned)
$ koyomi source outdated examples/civil_code_period_end.ja.cal
民法: the revision in force from 2027-06-23 (129AC0000000089_20270623_508AC0000000045) leaves the cited articles as they are
民法: the revision in force from 2027-12-05 (129AC0000000089_20271205_507AC0000000057) leaves the cited articles as they are
民法: the revision in force from 2028-06-13 (129AC0000000089_20280613_505AC0000000053) leaves the cited articles as they are
民法: the revision in force from 2028-12-23 (129AC0000000089_20281223_508AC0000000045) leaves the cited articles as they are
民法: the revision in force from 2029-06-23 (129AC0000000089_20290623_508AC0000000045) leaves the cited articles as they are
```

exit code は rulec と同じにした。`fetch` と `pin` は済めば 0、`outdated` は元が変わっていれば 1、`.cal` が構文の段で読めなければ 1、引数の誤り・読めないファイル・`curl` の失敗は 2 である。

`check` は通信しないので、改正を知る手段は `outdated` だけである。CI の定期実行に置く（rulec の §15.68 と同じ）。`check`・`eval`・`api` が通信しないことは、テストが PATH を空にして走らせて確かめる。

テストは通信しない。表の `url` は `file://` にする（curl は `file://` を読める）。e-Gov の API の場所は環境変数 `KOYOMI_EGOV` で替えられるようにし、テストは、用意したレスポンスを返す小さな HTTP サーバーをテストの中に立てて（`127.0.0.1` の空いたポート。テストの終わりに止める）、その場所を渡す。用意するのは民法 140〜143 条（例のコピーを base64 にしたもの）と後の版が五つある `law_revisions` で、ある施行日から 143 条の本文を一文字変えたレスポンスや、属性だけを変えたレスポンスも返せる。本物の内閣府、GOV.UK、e-Gov に取りに行くテストは、環境変数 `KOYOMI_NET=1` のときだけ走らせる。走らせないときは `SKIP:` ではなく `not asked:` の行を出す。ツールが欠けているのではなく、通信しないことを既定にしているからである。

### 10.1 英語の版と日本語の版の名前

**決定**（英語を先にした段階）：例、テストの材料、文書は英語を先にする。日本語のものは消さず、中身も変えず、日本語の版として残す。英語のものは足して先に見せる。英語の版と日本語の版の対は、名前で分かるようにする。決まりは次の三つで、chobo と同じにした。

- **例（`examples/`）**：dandori と同じ形にする。英語の版を `<英語の名前>.cal`、日本語の版を `<英語の名前>.ja.cal` とする。もとからあった日本語の例は、中身を一字も変えずに `<英語の名前>.ja.cal` へ名前だけを替え（`git mv`）、英語に訳した版を足した。英語の名前は、日本語の版の別名と違うものにする（`payment_20th_close_next_10th` と `payment_terms`）。テストは全部の例を一つのディレクトリに生成するので、別名が同じだと生成物がぶつかる。
- **カレンダー（`examples/calendars/`）**：`use calendar` で読まれるので、日本語の版は名前を替えない（`東京の営業日.cal`）。替えれば、それを読む日本語の版の `use calendar` の行を書き換えることになる。dandori の日本語の規則（`宿泊の与信額.rule`）も名前を替えていない。英語の版は英語の名前で足し（`tokyo_business_days.cal`）、description の最後に「The English version of 東京の営業日.cal」と書いて対を示す。
- **テストの材料、変異、golden（`tests/`）**：日本語の名前のものは、名前も中身もそのまま残す。日本語の名前で日本語の版だと分かるからである。同じ振る舞いを確かめる英語のものを、英語の名前で足す。変異の対は、診断のコードを頭に付けた名前でそろえる（`E001_閉じていない文字列.cal` と `E001_unclosed_string.cal`）。どちらも同じ診断のコードと終了コードを出すことを、`tests/mutants.rs` の `every_japanese_mutant_has_an_english_one` が確かめる。テストの材料は、英語の名前の版を足す（`helpers_月を足す.cal` と `helpers_add_months.cal`、`calendars/土日.cal` と `calendars/weekends.cal`）。名前が英語で中身が日本語のデータ（`data/holidays.csv`）には、`.en` を挟んだ英語の版を足す（`data/holidays.en.csv`）。例の golden は、例の名前に合わせて名前を替えた（中身は変えていない）。

- **`explain` の再現（台帳）**：台帳の項は、再現を英語と日本語の二つ持てる（ritsu-base の `Entry::english`）。`koyomi explain` は、英語の出力では英語の名前の再現を、日本語の出力では日本語の名前の再現を見せる。決めて変えたことで、日本語の出力は変えていない。英語の出力そのものである `docs/codes.md` の再現が英語の例になり、`docs/codes.ja.md` は変わらない。英語の再現を足したのは 14 項（E001、E009、E010、E101〜E106、E110、W101、E203、E301、E302）で、持たないのは、e-Gov の条を引く再現の E111 と W102 だけである（koyomi が固定できる法令は e-Gov のものだけで、英語の対が書けない）。この二つは、どちらの出力でも同じ（日本語の名前の）例を見せる。`tests/codes.rs` が、持っている再現の全部を走らせ、そのコードが出ることを確かめる。

日本語でしか確かめられない振る舞い（内閣府の Shift_JIS の CSV、e-Gov の条文、漢数字の条、全角の幅、数字から始まり日本語が続く名前）のテストは、日本語の材料のまま持つ。そのうえで、同じ振る舞いを英語の材料でも確かめるテストを足した。英語の名前の版でも e-Gov の条は `第143条` と書く（引けるのは e-Gov の法令だけで、条の名前は e-Gov のものだから）。Shift_JIS の読み方に当たる英語の材料は無いので、UTF-8 として読めない表（Windows-1252 で保存された表）で、読めないバイトの場所を言う振る舞いを確かめる。テストは英語と日本語の両方を回す。

**捨てたもの**：

- 英語の README に、日本語の名前の例を載せること。英語を読む人には名前が読めない。
- 日本語の例やテストの材料を、英語に訳して置き換えること。日本語の版が無くなる。日本語で読む人にも、同じものが要る。
- `tests/` の下の日本語の名前のファイルにも `.ja` を付けること。日本語の名前で日本語の版だと分かり、名前を替えると、そのファイルを名指すテストや文書を全部直すことになる。
- 英語の例を日本の暦だけで書くこと。英語を読む人の多くにとって身近な暦（GOV.UK の bank holidays）を先に見せる。米国の連邦の祝日は、そのまま読める公開の表（CSV か GOV.UK の形）が見つからず、手で書いた表は出典を固定できないので、まだ置かない。

## 11. 実装

- Rust（edition 2024、手元の stable 1.94.1 で通ること）。依存は serde_json だけ（GOV.UK の JSON、`api`、vectors、`--format json`）。`preserve_order` の機能を使い、`api` と `--format json` のキーをこの文書の順に出す。
- テストのビルドは `[profile.test] opt-level = 2` にした。1900〜2100 年のすべての日を月数や締め日ごとに何度も回すテスト（`tests/date.rs`）が、最適化なしでは遅すぎるため。ritsu に取り込んでからは、cargo がワークスペースの根のプロファイルしか読まないので、根の `Cargo.toml` の `[profile.test.package.koyomi]` に置いている。
- SHA-256 は ritsu-base のものを使う（依存を足さずに書いたもので、FIPS 180-4 の既知の値でテストしている）。
- Shift_JIS は自前で読む。変換表は WHATWG の `index-jis0208.txt` から作った `src/sjis_table.rs`（作る手順は `tools/sjis/`。表の頭に、元の索引の Identifier、日付、SHA-256 を書く）。テストは、python3 があれば、全符号を Python の `cp932` と比べる（無ければ SKIP）。
- 通信は `curl` を子プロセスで呼ぶ（`source fetch` と `source outdated` だけ。`src/fetch.rs` が、ritsu-base の `sources` の e-Gov への問い合わせを呼ぶ）。
- 生成器は `src/codegen/`（共通の部分と、出力先ごとに一つのファイル）。PLAN は `src/gen/` としていたが、`gen` は Rust 2024 の予約語なので、rulec と同じ `codegen` にした。
- 突き合わせのテストが使う型の検査器は、版を固定して `tools/` に置く。TypeScript は `tools/package.json` と `tools/package-lock.json`（`npm ci --prefix tools`。`tools/node_modules` は git に入れない）、mypy は `tools/requirements.txt`（`uv venv --python 3.13 tools/.venv` に入れる。venv は git に入れない。2026-10-06 から、`tools/requirements.in` の mypy 2.4.0 から `uv pip compile --generate-hashes` で作った、依存までバージョンとハッシュを固定したロックファイルにした。ritsu の脆弱性の検査が、入れるバージョンのとおりに読めるように。ritsu の DESIGN 3.6）。テストは環境変数 `KOYOMI_TSC` と `KOYOMI_MYPY` でほかの場所のものも使える。PostgreSQL は `KOYOMI_PG_BIN`（`initdb`・`pg_ctl`・`psql` のあるディレクトリ）と `KOYOMI_PG_SOCKET_DIR`（ソケットのディレクトリ。パスは 103 バイトまで）で受け取る。
- 診断の文面は `tr!` で英語と日本語を隣に書く。二つの文の引数が違うときは `;` で分ける（`tr!("{}曜", "{}", ja; en)`）。`tr!` と、診断の共通の部分、台帳の書き出し、コマンドの表の読み方は ritsu-base のもので、台帳の中身（`src/codes.rs`）とコマンドの表（`src/cli.rs`）と計算の段（`src/diag.rs` の `Example`）が koyomi のものである（11.1）。
- 人が読むページは `src/doc/`。`mod.rs` がページを組み、`edges.rs` が範囲をもう一度計算してエッジケースと無い日の扱いの数を集め、`months.rs` が月の表を作り、`markdown.rs` と `html.rs` がそれぞれの形で出す（7 章）。
- 文書は `docs/`（英語の `reference.md` と `generated-code.md`、`koyomi explain --all --format markdown` の出力そのものの `codes.md` と `codes.ja.md`）、README.md、README.ja.md、`skills/koyomi`（`SKILL.md` は手で書き、ほかは `skills/sync.sh` が `docs/` からコピーする）。`tests/docs.rs` が、README と `docs/` とスキルに載せた `.cal` の行、コマンドの出力、診断、生成したコード、vectors の行、比べた行の数が、実際のものと同じかを確かめ、`tests/skill.rs` が、スキルにコピーしたページとリンクと frontmatter を確かめる。
- テストの共通の部分（自分を消す一時ディレクトリ、ツールの探し方、時間を区切って走らせること、golden、SKIP、使い捨ての PostgreSQL、Chrome、テストの中の HTTP サーバー）は ritsu-testkit のものを使う。Chrome は `RITSU_CHROME` か `KOYOMI_CHROME` で受け取り、無ければ macOS が Google Chrome を入れる場所、それも無ければ PATH の `google-chrome` か `chromium` を探す（dandori と chobo と同じ順）。ヘッドレスの Chrome はスクリーンショットを書き出したあとも終わらないことがあるので、ritsu-testkit がそのファイルの大きさが変わらなくなったところで止める。

モジュールの分け方と、各段階の作業は PLAN.md にある。

### 11.1 ritsu の土台へ移したもの

koyomi は ritsu（七つの言語を一つにまとめる処理系）に取り込まれ、ほかの言語と重なっていたコードを、ritsu の土台のクレート（ritsu-base と ritsu-testkit）のものに替えた（ritsu の PLAN の C.4）。替えたのは、SHA-256、二つの言語の文（`tr!`、`Text`、`Lang`）、診断の共通の部分、台帳の書き出しと再現の走らせ方、コマンドの表の読み方と `--help` の組み立て、法令のコピーの扱い（引用から要素の名前を作ること、コピーの場所と本文、固定の行の書き換え、e-Gov への問い合わせ）、人が読むページの HTML の頭と配色の変数、テストの共通の部分である。koyomi に残したのは、台帳の中身、コマンドの表の中身、計算の段（`Example`）、祝日の表、法令のコピーのうち koyomi が引くもの（本則の条・項・号だけ）、ページの中身と koyomi だけの色である。

出力は、次のものを除いて一字も変えていない（ritsu の土台で決めたこと）。

- 言語の選び方に `RITSU_LANG` が入った。`--lang`、`KOYOMI_LANG`、`RITSU_LANG`、英語の順に読む。ritsu のどの言語も同じ変数を読むので、一つの設定で全部の言語の文面を日本語にできる。`--lang` の説明と `koyomi --help` の最後の行が、この順を書くようになった。
- HTML のページの配色の変数のうち、ほかの言語と共通の役割（背景、文字、線、パネル、コードの背景、成り立つ・注意の色）は、ritsu-base の値（GitHub の配色。chobo と dandori の値）になった。koyomi だけの色（休み、成り立たない日、エッジケース、カレンダーが知らない日、法令の引用）は値を変えていない。変数の並びは一行にまとめて書く。README の画像（`docs/images/`）は取り直した。
- 行の無い診断（UTF-8 でないファイルの E001）の `--format json` は、`line` と `col` を `0` でなく `null` で書く。行が無いことを、行番号の 0 で表さないためである（ritsu の診断の共通の形）。
- `source fetch` と `source outdated` の curl に `--compressed` が付いた（eCFR は付けないと 406 を返す。ritsu-base で rulec が見つけたこと）。e-Gov が JSON でないページを返したときは、二度まで取り直してから止める。curl が無いときは、三度試さずにすぐそう言う。
- コピーの本文の取り出し（`source outdated` が比べて差分に出すもの）は、rulec と yuen の形になった。表の行と列も一行ずつ・空白で区切って読む。koyomi が引く本則の条には表が無いので、いまの例では変わらない。固定の行を書き換えるとき、文字列の中の `\"` を文字列の終わりと読まなくなった。
- テストの SKIP の行は、ritsu のどのクレートとも同じ `SKIP: koyomi: <理由>` の形になった。

続く C.10 で、生成先の言語の表面にかかわるところを、ritsu の生成器が共に使うクレート（ritsu-emit）のものに替えた。五つの出力先の予約語の表（E009 でエラーにする語。ECMAScript 2025、Python 3.14.6、Go 1.25、Rust 1.94、PostgreSQL 18.0 のもの）、Go の名前の作り方（`PaymentAt`、`paymentterms`）、文字列のリテラル（四つの出力先は JSON の文字列、SQL は `'…'`）、生成物の頭の一行（`Code generated by koyomi 0.1.0. DO NOT EDIT.`）とそれを書くコメントである。koyomi に残したのは、生成物が使う名前（`GENERATED`、`MODULES`）と、各出力先の生成器の中身である。例の全部の `.cal` を五つの出力先に生成したファイル（80 個）が一バイトも変わらないこと、五つの出力先の突き合わせのテストと golden が通ることを確かめた。

段階 D の最初の部分で、ritsu の口（ritsu の DESIGN 3.2）に答える `src/ports.rs` を足した。`ritsu_ports::Dates` の事実（関数、入力とその範囲、カレンダーとデータの範囲、`at` の時刻と UTC オフセット、条件の名前と文）は、`koyomi api` と同じものを型で渡す。日付がとりうる値の集合と、日付の入力からの日数の最小と最大は、`koyomi check` と同じく範囲のすべての入力で計算して渡す。入力の組み合わせが `check` の確かめる数を超えるとき、途中で計算が止まる入力があるときは、決められないと言う。評価は参照インタプリタのものである。`.cal` が持つもの（入力、日付、条件、出典）の定義の文は、日付なら `date … =` の塊の行（操作の行と `at` を含む）、条件ならその行で、どの行もコメントと前後の空白を除く。外を名指すものは、`use calendar` の先と、出典のコピーのファイルである。ritsu の DESIGN 7.5 の例（`payment_20th_close_next_10th.ja.cal` の `支払日` は 23 通り、受領日から 18〜51 日）は、口から数えても同じだった（`tests/ports.rs`）。コマンドの振る舞いは変えていない（例と fixture の全部のコマンドの 352 回の出力が一字も違わない）。

段階 D の最後の部分で、`ritsu_ports::Sources` にも答えるようにした（ritsu の DESIGN 3.2）。yuen が、日付のファイルとカレンダーのファイルが保存して固定している出典を借り、要件のコピーと比べるためである（yuen の DESIGN 1.4、3.3）。出典ごとに、名前、行、法令ならデータベースと ID と時点と条ごとの固定、ファイルならパス（そのファイルからの相対）と url と固定を渡す。答えるのは `koyomi check` を通るファイルだけで、通らないファイルには検査の診断を返す。コマンドの振る舞いは変えていない。

段階 E の言語をまたぐ検査（ritsu の DESIGN 7.5〜7.8）のために、日付の口の問いを二つ足した。`span` は、日付の入力から日付までの日数の最小と最大を、それぞれに初めてなる日付の入力の日とともに返す（ritsu の X5 が、仮押さえが必ず期限切れになる例に、その日を書く）。`input_for` は、日付がある日になる最初の入力を返す（X3 の (a) と X6 が、範囲を外れる日の例に、koyomi のどの入力でその日になるかを書く）。どちらも `check` と同じく範囲のすべての入力を計算し、入力の組み合わせが確かめる数を超えるときは答えない。コマンドの振る舞いは変えていない。

段階 E の最初の部分で、コマンドの本体を `src/main.rs` からライブラリの `koyomi::run::run` に移した。クレートのバイナリと ritsu の `ritsu koyomi`（ritsu の DESIGN 8.2）が、同じ関数を呼ぶ。`ritsu check` のために、`koyomi::ports::Engine::checked` が、`koyomi check` が印字するもの（診断一つずつのテキストと `--format json` のオブジェクト、通ったファイルの `ok —` の行）を、コマンドと同じ関数で作って渡す（ritsu の DESIGN 8.3）。コマンドの振る舞いは変えていない。

## 12. まだやらないこと

どれも、作る理由が見えたら作る。ここに書くのは、黙って消えたように見せないためである。

コマンド：

- `koyomi diff <古い.cal> <新しい.cal>`：決まりを変えたとき、どの入力の結果がどれだけ動くか（rulec の `diff`）。読む人が知りたいことなので、いずれ要りそうだが、今回のコマンドの一覧には入れていない。
- `koyomi test <dir>`：利用者の CI で、生成したコードを vectors と突き合わせる（rulec の `test`）。ランナーは `gen` が書くので、要れば足せる。
- `koyomi fmt`：書き方をそろえる。それまでは W202 で代える。

言語：

- 週の締め（`close weekly fri`）、月の何番目の曜日、年度の締め（`close every 03-31`）。
- 日付の入力を二つ持つこと（1.3）。整数を返す関数（1.3）。
- 比較で分ける一般の `if`、`if open`、条件の `!=` と `is closed`（1.8、1.10）。成り立たなくてもエラーにしない比較（1.10）。
- tz データベースと夏時間（1.9）。
- 法令の附則と別表を引くこと（1.5）。

ページと文書：

- 人が読むページの中で、入力を変えて計算を試すこと（7.5）。
- 日本語の `docs/reference.md` と `docs/generated-code.md`。今は英語だけで、日本語は README.ja.md と `docs/codes.ja.md` にある。
- ドキュメントのサイト、MCP サーバー、ブラウザで試すページ（rulec と dandori にはある）。

公開：

- リリースとバイナリ、crates.io。今の入れ方は、リポジトリを clone して `cargo install --path .` である。
- dandori が `koyomi api` を読んで、ワークフローの中で koyomi が生成した関数を呼ぶこと（8 章）。dandori の側で決めることなので、koyomi は `api` を出すところまでにした。
