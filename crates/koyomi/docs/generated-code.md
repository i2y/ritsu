# The generated code

`koyomi gen` turns a file that passes `koyomi check` into code in five languages: TypeScript,
Python, Go, Rust and SQL for PostgreSQL. Each target gets one file, or one Go package, and a
runner beside it. There is nothing else to install: the file holds the small functions it calls
and the calendar's table of holidays, and it uses no date library of its language, because those
disagree about months (the one-month-after of 2023-01-31 is 2023-02-28 in most and 2023-03-03 in
Go). Every function computes on day numbers, days since 1970-01-01, with the same steps as
koyomi's reference interpreter, and the tests hold every target to it on every input of the range
(the end of this page).

The examples on this page are what `koyomi gen examples/payment_20th_close_next_10th.cal`
writes: closing on the 20th and paying on the 10th of the next month, on Tokyo's business days,
whose offset gives the payment a time too.

## What it writes

| Target | The code | The runner | A date is |
|---|---|---|---|
| TypeScript | `typescript/<alias>.ts` | `typescript/<alias>_runner.ts` | a `"YYYY-MM-DD"` string |
| Python | `python/<alias>.py` | `python/<alias>_runner.py` | a `datetime.date` |
| Go | `go/<package>/<package>.go` | `go/<package>/<package>_runner_test.go` | the package's `Date{Year, Month, Day int}` |
| Rust | `rust/<alias>.rs` | `rust/<alias>_runner.rs` | the module's `Date { year, month, day }` |
| SQL | `sql/<alias>.sql` | `sql/<alias>_runner.sql` | a `date` |

The alias is the file's (`dates net30 v1` writes `net30.ts`, and the Japanese version
`dates 支払条件(payment_terms) v1` writes `payment_terms.ts`), and the Go package is the alias
without `_`. A calendar file writes `is_open` alone; a dates file writes a
function for each date, and `is_open` too when it reads a calendar.

`--out <dir>` says where (`generated` unless given), `--target` picks one target, and `--lang ja`
writes the comments and the error messages in Japanese. A file that does not pass check writes
nothing and makes the run exit 1, while the files that pass are still written; two files with one
alias stop the run before anything is written. `koyomi gen --check` writes nothing and exits 1
when a file on disk is not what gen would write, for CI.

## The head

Every file starts by saying what it was made from:

```ts
// Code generated by koyomi 0.25.0. DO NOT EDIT.
// Source: payment_20th_close_next_10th.cal (dates payment_20th_close_next_10th v1, sha256:9973542043dbee17)
// Calendar: calendars/tokyo_business_days.cal (calendar tokyo_business_days v1, sha256:37af228cf6ba7b95)
// Cites: national_holidays = file calendars/data/syukujitsu.csv sha256:cec37a743c96995c (https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv), covers 1955-01-01..2027-12-31
```

The first line has the form Go's tools look for. The paths start from the `.cal`'s directory, and
no path of the machine that ran gen is written. Each digest is the first 16 hex digits of a
SHA-256, as the pins of `source` lines are, so a generated file that is older than its `.cal`, its
calendar or its table of holidays can be told apart. A file that cites a law has a `Cites:` line
for it too, with the pins of the articles and the revision.

## The functions

A date becomes a function named by its alias (in Go, the alias in PascalCase), taking the inputs
the date uses and nothing else. Its operations are the lines of the function, in the `.cal`'s
order, each with the `.cal` line it comes from as a comment; the first line of a date that starts
from another date names that date in parentheses. A date with `at` has a second function,
`<alias>_at` (`PaymentAt` in Go), that gives its time in RFC 3339, in UTC, ending in `Z`. The
names and the signatures are the ones `koyomi api` gives.

In TypeScript, dates are `"YYYY-MM-DD"` strings, which JSON carries as they are. The code is
TypeScript that Node runs by stripping the types (no `enum`, no `namespace` with code):

```ts
/**
 * Gives payment.
 * It takes received 2026-01-01..2027-11-20, the range koyomi check checked every input of; outside it, the error is a KoyomiError of kind range.
 */
export function payment(received: string): string {
  let day = _inputDate(received, "received", 20454, 21142); // range >=2026-01-01 <=2027-11-20
  day = _closeDay(day, 20, "none"); // close day 20  (closing)
  day = _dayOfMonth(day, 10, 1, "none"); // day 10 of month +1
  day = _roll(day, "preceding"); // roll preceding
  return _formatDate(day);
}

/** Gives the time of payment's day (at 09:00, offset +09:00) in RFC 3339, in UTC, ending in Z. */
export function payment_at(received: string): string {
  return _at(payment(received), 540, 540);
}
```

In Python, `datetime.date`, with annotations that `mypy --strict` accepts:

```python
def payment(received: date) -> date:
    """Gives payment.

    It takes received 2026-01-01..2027-11-20, the range koyomi check checked every input of; outside it, the error is a KoyomiError of kind range.
    """
    day = _input_date(received, "received", 20454, 21142)  # range >=2026-01-01 <=2027-11-20
    day = _close_day(day, 20, "none")  # close day 20  (closing)
    day = _day_of_month(day, 10, 1, "none")  # day 10 of month +1
    day = _roll(day, "preceding")  # roll preceding
    return _to_date(day)
```

In Go, the package's own `Date`, since the standard library has no type for a day without a time
zone; every function that can fail returns an `error`:

```go
// Payment gives payment.
// It takes received 2026-01-01..2027-11-20, the range koyomi check checked every input of; outside it, the error is a KoyomiError of kind range.
func Payment(received Date) (Date, error) {
	day, err := _inputDate(received, "received", 20454, 21142) // range >=2026-01-01 <=2027-11-20
	if err != nil {
		return Date{}, err
	}
	day, err = _closeDay(day, 20, "none") // close day 20  (closing)
	if err != nil {
		return Date{}, err
	}
	day, err = _dayOfMonth(day, 10, 1, "none") // day 10 of month +1
	if err != nil {
		return Date{}, err
	}
	day, err = _roll(day, "preceding") // roll preceding
	if err != nil {
		return Date{}, err
	}
	return _date(day), nil
}
```

In Rust, the module's own `Date` (`FromStr`, `Display`, `Copy`, `Ord`), in code that compiles
under the 2021 and the 2024 editions alike, so that it does not care which edition the crate it
lands in uses:

```rust
/// Gives payment.
/// It takes received 2026-01-01..2027-11-20, the range koyomi check checked every input of; outside it, the error is a KoyomiError of kind range.
pub fn payment(received: Date) -> Result<Date, KoyomiError> {
    let mut day = _input_date(received, "received", 20454, 21142)?; // range >=2026-01-01 <=2027-11-20
    day = _close_day(day, 20, "none")?; // close day 20  (closing)
    day = _day_of_month(day, 10, 1, "none")?; // day 10 of month +1
    day = _roll(day, "preceding")?; // roll preceding
    Ok(_date(day))
}
```

In SQL, a schema named by the alias, with a function for each date. The functions with loops are
PL/pgSQL; the ones that are a single expression are SQL-standard bodies, which PostgreSQL can
inline:

```sql
CREATE OR REPLACE FUNCTION payment_20th_close_next_10th.payment(received date) RETURNS date
LANGUAGE plpgsql IMMUTABLE STRICT PARALLEL SAFE AS $$
DECLARE
  day integer;
BEGIN
  day := payment_20th_close_next_10th._input_date(received, 'received', 20454, 21142); -- range >=2026-01-01 <=2027-11-20
  day := payment_20th_close_next_10th._close_day(day, 20, 'none'); -- close day 20  (closing)
  day := payment_20th_close_next_10th._day_of_month(day, 10, 1, 'none'); -- day 10 of month +1
  day := payment_20th_close_next_10th._roll(day, 'preceding'); -- roll preceding
  RETURN DATE '1970-01-01' + day;
END
$$;
```

## Errors

Every target raises one kind of error, and the error says which of four things went wrong:

| Kind | When | In the check |
|---|---|---|
| `range` | an input is outside its `range` | outside what the check went through |
| `data` | a day the calendar does not know was asked about | E203 |
| `reject` | a day the month does not have, under `else reject` | E202 |
| `date` | a date outside 0001-01-01..9999-12-31, or a value that is not a date | E204 |

The check computed every input of the range, so a file that passes raises nothing on an input
inside it. What a caller can meet is `range` for an input outside the range, `data` from
`is_open` on a day outside the data range, and `date` for a string or a `Date` that is not a
day.

```ts
export class KoyomiError extends Error {
  readonly kind: KoyomiErrorKind;
  constructor(kind: KoyomiErrorKind, message: string) {
    super(message);
    this.name = "KoyomiError";
    this.kind = kind;
  }
}
```

```python
class KoyomiError(ValueError):
    """What the functions of this file raise. kind is range (an input outside its range), data (a day the calendar does not know), reject (a day the month does not have under else reject) or date (outside 0001-01-01..9999-12-31)"""

    def __init__(self, kind: str, message: str) -> None:
        super().__init__(message)
        self.kind = kind
```

```go

type Date struct {

func ParseDate(s string) (Date, error) {
	z, err := _parseDate(s)
	if err != nil {
		return Date{}, err
	}
	return _date(z), nil
}

func (d Date) String() string {
	return _ymd(d.Year, d.Month, d.Day)
}

	Kind    string
	Message string
}

}
```


## The runners

A runner reads the lines of `koyomi vectors` on its standard input and writes, for each, what the
functions give: the dates and the times, separated by spaces, in the order `out` has them, or
`error <kind>`. It is how the tests hold the code to the reference interpreter, and how the code
can be held to it again after it is copied somewhere else:

```sh
koyomi vectors examples/payment_20th_close_next_10th.cal | node generated/typescript/payment_20th_close_next_10th_runner.ts
koyomi vectors examples/payment_20th_close_next_10th.cal | python3 generated/python/payment_20th_close_next_10th_runner.py
go test -c -trimpath -o runner ./generated/go/payment20thclosenext10th && koyomi vectors examples/payment_20th_close_next_10th.cal | KOYOMI_RUNNER=1 ./runner
rustc --edition 2024 -O generated/rust/payment_20th_close_next_10th_runner.rs -o runner && koyomi vectors examples/payment_20th_close_next_10th.cal | ./runner
psql -f generated/sql/payment_20th_close_next_10th.sql && koyomi vectors examples/payment_20th_close_next_10th.cal | psql -X -q -f generated/sql/payment_20th_close_next_10th_runner.sql
```

The Go runner is a test file of the package, so it needs no import path and works wherever the
package is put inside a Go module; built with `go test -c`, it runs the package's tests unless
`KOYOMI_RUNNER` is set. The TypeScript one:

```ts
// Code generated by koyomi 0.25.0. DO NOT EDIT.
// Reads the lines of koyomi vectors on standard input and writes what the functions give, a line each (separated by a space; error <kind> for an error)
import { createInterface } from "node:readline";
import * as m from "./payment_20th_close_next_10th.ts";

function run(input: Record<string, unknown>): string {
  const out: string[] = [];
  out.push(m.closing(input["received"] as string));
  out.push(m.payment(input["received"] as string));
  out.push(m.payment_at(input["received"] as string));
  return out.join(" ");
}

let buf: string[] = [];
for await (const line of createInterface({ input: process.stdin, crlfDelay: Infinity })) {
  if (line === "") continue;
  const input = (JSON.parse(line) as { in: Record<string, unknown> }).in;
  try {
    buf.push(run(input));
  } catch (e) {
    if (!(e instanceof m.KoyomiError)) throw e;
    buf.push("error " + e.kind);
  }
  if (buf.length >= 4096) {
    process.stdout.write(buf.join("\n") + "\n");
    buf = [];
  }
}
if (buf.length > 0) process.stdout.write(buf.join("\n") + "\n");
```

## How the code is checked

`tests/targets.rs` generates every example that passes check, and seven files under
`tests/fixtures/` that use every operation, every way of handling a missing day, the four
conventions, `if closed` and `at` over 1900–2100, for each target. The target's own tools look at
the code first: `tsc --strict --erasableSyntaxOnly` for TypeScript, `mypy --strict` for Python,
`gofmt`, `go vet` and `go test -c` for Go, `rustc -D warnings` under both editions for Rust, and a
PostgreSQL made for the test for SQL. Then every line of the vectors, every input of every range
and the inputs just outside, goes through the runner and is compared with what the reference
interpreter gives; none is skipped. The code written with `--lang ja` is checked the same way, and
two of the files are run through it too. A tool that is missing prints a `SKIP:` line and the test
passes; the numbers of the last run are in the README.
