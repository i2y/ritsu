# 立場ごとの使い方

同じ道具ですが、**手元に何があり、何を出したいか**で通る道が違います。三つの立場に分けました。自分に近いところから読んでください。

| あなたは | 手元にあるもの | 出したいもの | 読む節 |
|---|---|---|---|
| 公的なルール（法令、公開されている規約、料金表）を**実装する** | 条文や規約の PDF | 条文どおりに動き、改正に気づけるコード | [1. 既存の公的なルールを実装する](#1-既存の公的なルールを実装する) |
| 新しいルールを**検討する**（新しい公的ルール、社内ルール、EC サイトや自社サービスの決まり） | 決めたい条件が、文章か頭の中に | 抜けも矛盾も無い表と、承認や公開のための資料 | [2. 新しいルールを検討する](#2-新しいルールを検討する) |
| できあがったルールを元に**実装する** | 検査を通った `.rule` | 自分の言語で動く、表と同じ答えを返すコード | [3. 新しいルールを元に実装する](#3-新しいルールを元に実装する) |

どの道も、真ん中の一歩は同じです。**`rulec check` を通らない表からは何も出ません**（[何を証明するか](checks.md)）。コマンドは全部、この一覧から出てくるものだけを使います。

```console
$ rulec --help
```

---

## 1. 既存の公的なルールを実装する

法令や公開された規約を、そのとおりに動くコードにしたい場合です。ここでの主役は**出典**です。表のどの行がどの条文から来たかを書き、条文の写しに縛り、改正が出たら気づけるようにします。

![法令や公開された規約を、エージェントが表（.rule）に写し、条文を @ で引用する。rulec が写しと照合し、抜けと重なりを証明して、九言語に生成する。承認する人は rulec doc の資料で条文と表を見比べる。改正が出れば rulec source outdated が言い、表を読み直す](images/scenario-existing-ja.svg#only-dark)
![法令や公開された規約を、エージェントが表（.rule）に写し、条文を @ で引用する。rulec が写しと照合し、抜けと重なりを証明して、九言語に生成する。承認する人は rulec doc の資料で条文と表を見比べる。改正が出れば rulec source outdated が言い、表を読み直す](images/scenario-existing-ja-light.svg#only-light)

### 1-1. 条文を引用しながら表に写す

写すのはエージェントでも人でも構いません。ポイントは、表や行の行末に **`@出典 第○条`** と書いて、どこから写したかを残すことです。法令なら `source` に e-Gov 法令検索の法令 ID と、いつの時点の条文かを書きます。

```rule
source 法 = law "342AC0000000023" asof 2026-04-01
source 措置法 = law "332AC0000000026" asof 2026-04-01

define 軽減期間(reduced) : bool = 作成日 <= 2027-03-31  @措置法 第91条

table 本則(base)  @法 別表第一
policy unique
         | 金額の記載あり | 契約金額         | -> 印紙税額(tax) : money[円] |
記載なし | false          | -                | 200円                        |
r3       | true           | >=1万円 <=10万円 | 200円                        |
```

書き方の全部は[表(.rule)を書く](tour.md#どこから写したかを書くsource-と-)にあります。附則を引くなら `@法 附則第3条`、改正法の附則なら `@法 附則（令和七年三月三一日法律第一三号）第3条` です。

### 1-2. 条文の写しを取って、固定する

`check` は通信しません。条文の写しを規則の隣に置き、そのハッシュを規則に書き込みます。二つのコマンドで済みます。

```console
$ rulec source fetch rules/印紙税.rule --lang ja
措置法: 第91条 を取りました（sha256:85faf53f6f6e8196）
$ rulec source pin rules/印紙税.rule --lang ja
措置法: 1 箇所のハッシュを固定しました
```

`pin` は `source` の下に `  第91条 sha256:85faf53f6f6e8196` の一行を書きます。写しは `sources/law/<法令ID>@<日付>/` に入るので、git に入れてください。

### 1-3. 検査する

```console
$ rulec check rules/印紙税.rule --lang ja
ok rules/印紙税.rule
```

条文の側で何かが変わると、`check` はそこで止まります。写しが差し替わっていれば **E038** で、読み直す定義を名指しします。

```console
$ rulec check rules/印紙税.rule --lang ja
error[E038]: 出典 `措置法` の `第91条` が変わっています
  --> rules/印紙税.rule:7 出典 措置法
  |
7 |   第91条 sha256:85faf53f6f6e8196
  |   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 固定: sha256:85faf53f6f6e8196
  |
 いまの写し: sha256:cac55089de86c8eb
 読み直す定義: 定義 軽減期間、表 軽減
```

ハッシュを書き忘れれば E037、写しが無ければ E039 です。どれも `rulec explain E038` のように引けます。

### 1-4. 承認する人に見せる

条文と表を見比べるのは人の仕事です。`rulec doc` が、引用した条文を写しから引用した資料を出します。

```console
$ rulec doc rules/印紙税.rule --lang ja > 印紙税.md
```

資料の表の見出しの下には、こう出ます。

```markdown
出典: 措置法 第91条（法令 332AC0000000026、2026-04-01 時点。2026-04-01 施行、令和8年法律第12号による改正後）

> 第九十一条
> 平成二十六年四月一日から令和九年三月三十一日までの間に作成される…
```

承認する人は、表の行とこの引用を見比べるだけです。資料の読み方は[承認する人に見せる](checks.md#承認する人に見せる)にあります。

### 1-5. 生成して、突き合わせる

```console
$ rulec gen rules/印紙税.rule --out generated/
$ rulec test generated/
ok    stamp_duty_split (Python) ベクタ 296 件
ok    stamp_duty_split (SQL) ベクタ 296 件
…
```

生成したファイルのヘッダには、写した条文とその時点とハッシュが刻まれます。生成物を読む人が、どの条文から作られたかを確かめられます。

```python
# Cites: 措置法 = law 332AC0000000026 asof 2026-04-01 (第91条 sha256:85faf53f6f6e8196)
```

### 1-6. 改正に気づく

条文は改正されます。`check` は写しに縛られているので、改正を知る手段はこの一つです。CI の週次に置いてください。

```console
$ rulec source outdated rules/厚生年金保険料.rule --lang ja
厚生年金保険法: 2027-09-01 施行の改正で 第20条 が変わります。その日から効く版には、読み直した規則が要ります
  `source 厚生年金保険法_20270901 = law "329AC0000000115" asof 2027-09-01` を足し、その日以後に効く行をそこから写してください
  第20条: - 六〇五、〇〇〇円以上
  第20条: + 六〇五、〇〇〇円以上六三五、〇〇〇円未満
  第20条: + 第三二級
  第20条: + 六五〇、〇〇〇円
  …
```

何が、いつから変わるかと、足す `source` の行まで出ます。改正が効く日は表の行の条件（`月分 >=2027-09-01` のような日付の列）として書き、古い行と新しい行を同じ表に置きます。隙間や重なりがあれば `check` が止めます。

!!! note "改正への備えは、日付を入力に取ること"

    法令の改正はたいてい「施行日以後に作成する文書について適用し、それより前のものは従前の例による」と言います。つまり切り替わるのは処理した日ではなく、作成日や支払日や月分です。その日付を入力に取り、行の条件に書けば、版を別のファイルに分けなくて済みます。

CI の置き方は[インストール](install.md#ci-に置く)にあります。`outdated` は改正があると exit 1 で止まるので、その出力をそのまま issue にできます。

## 2. 新しいルールを検討する

送料やクーポンの条件、返品の可否、社内の判定基準、新しい公的なルール。まだ決めている途中のものを、表にして固めたい場合です。ここでの主役は**検査**です。書いた表の抜けと矛盾を、それを起こす具体的な入力つきで返してくるので、決め漏れが決める前に見えます。

![決めたいこと（送料、クーポン、返品の可否、社内の判定基準）を、検討する人が表（.rule）に書く。rulec check が抜けと重なりを、それを起こす入力つきで返し、通るまで直す。通った表からは承認者向けの資料、お客向けの案内、改定の影響が出る](images/scenario-designing-ja.svg#only-dark)
![決めたいこと（送料、クーポン、返品の可否、社内の判定基準）を、検討する人が表（.rule）に書く。rulec check が抜けと重なりを、それを起こす入力つきで返し、通るまで直す。通った表からは承認者向けの資料、お客向けの案内、改定の影響が出る](images/scenario-designing-ja-light.svg#only-light)

### 2-1. まず表に書く

条件を列に、答えを右端の列にして書きます。文章で「北海道と沖縄は 2kg まで 1,200 円」と言っていたことが、一行になります。

```rule
rule 送料(shipping_fee) v1
description "通常便の送料"

import std/都道府県
group 遠隔地 = 北海道, 沖縄県

inputs
  届け先(dest) : 都道府県
  重量(weight) : mass[g]  range >=1g <=40kg

outputs
  送料(fee) : money[円, incl_tax]  round up(10円)

table 基本送料(base)
policy unique
| 届け先      | 重量    | -> 送料(fee) : money[円, incl_tax] |
| 遠隔地      | <=2000g | 1200円                             |
| 遠隔地      | >2000g  | 1800円                             |
| not: 遠隔地 | <=2000g | 800円                              |
| not: 遠隔地 | >2000g  | 1100円                             |
```

すでに Excel や CSV があるなら、下書きを起こしてもらえます。推定した箇所には全部「推定」と印が付くので、そこだけ確かめます。

```console
$ rulec import csv 運賃.csv --name 運賃 --lang ja > rules/運賃.rule
```

自分のルールが表で書けるかは、[自分のルールが入るか](fit.md)で先に確かめられます。

### 2-2. 検査にかける

```console
$ rulec check rules/送料.rule --lang ja
```

抜けがあれば、**それを起こす入力**と、足す行の形が返ります。金額だけは人が決めます。

```console
error[E101]: 完全性の欠落: どの行にも当てはまらない入力があります
  --> rules/運賃.rule:34 表 運賃表
   |
34 | table 運賃表(fee_table)
   |       ^^^^^^ 起こりうる入力を覆いきっていません
   |
 当てはまらない例: あて先 = 山梨県, サイズ = S60
 ヒント: この入力に当てはまる行を足してください。
 足す行の形: `| 山梨県 | S60 | 820円 |`。出力の値は表の一行目から写した「形」で、正しい額ではありません。
```

矛盾があれば、**両方に当てはまる入力**つきで止まります。

```console
error[E105]: 行の重なり: 同じ入力が 行8 と 行22 の両方に当てはまります
  --> rules/運賃.rule:58 表 運賃表
 両方に当てはまる例: あて先 = 青森県, サイズ = S60
 `policy unique` では重なりは許されません。どちらが正しいか決めるか、順序に意味を持たせるなら `policy first` を宣言してください。
```

通るまで直します。直すのは表であって、コードではありません。七つの検査の中身は[何を証明するか](checks.md#七つの検査)にあります。

### 2-3. 例を書く

決めた答えを `examples` に書いておくと、`check` のたびに実行されます。仕様書の「例えば」が、消えない試験になります。

```rule
examples
| 届け先 | 重量  | -> 送料 |
| 沖縄県 | 2500g | 1800円  |
| 東京都 | 1999g | 800円   |
```

### 2-4. 承認と公開の資料を出す

同じ表から、読む相手ごとの資料が出ます。承認する人には、表には出ない事実（何を確かめたか、どの行がどの行に隠れているか、どの丸めが仮置きか）を添えた資料。お客には、別名や診断コードを省き、条件の境目の両側で答えがどう変わるかの例を添えた案内。

```console
$ rulec doc rules/送料.rule --lang ja > 送料.md
$ rulec doc rules/送料.rule --lang ja --audience customer > 送料の案内.md
```

```markdown
## 境目の例

- 重量が 2000g のとき 送料 1200円、2001g のとき 送料 1800円（届け先: 北海道）
```

### 2-5. 改定の影響を、入れる前に知る

ルールを改定するとき、何件がいくら動くかを先に出せます。過去の記録（一件一行の JSON）があれば、旧と新の二つの版を同じ記録に当てます。

```console
$ rulec fixtures lint 記録.jsonl rules/送料.rule --lang ja
記録.jsonl: 記録 70 件（そのまま 70、補った分 0）
形式の問題はありません。
$ rulec diff 送料.rule 送料_新.rule --fixtures 記録.jsonl --lang ja --terse
照合 70 件 / 一致 60 (85.714%)
相手: 送料.rule → 送料_新.rule

影響 10 件 (14.286%)  金額 +1,700
  表 基本送料 行2 / 表 負担判定 行2                                3 件  差 +100 一様  合計 +300
  表 基本送料 行2 / 表 負担判定 行3                                7 件  差 +200 一様  合計 +1,400
```

すでに動いている実装があるなら、それを置き換える前に `rulec verify` で表と突き合わせられます。どちらも[突き合わせと再生](compare.md)にあります。

## 3. 新しいルールを元に実装する

検査を通った `.rule` を受け取って、自分の言語のアプリやバッチに組み込みたい場合です。ここでの主役は**生成物**で、書くのは呼び出し側だけです。

![検査を通った表（.rule）から rulec gen が九言語のコードを出し、rulec test が参照評価器と突き合わせる。実装する人は rulec api で呼び方を読み、関数・SQL・Wasm・MCP サーバのどれかを自分のアプリやバッチやエージェントに組み込む。生成物は編集せず、表が変われば CI の gen --check が止める](images/scenario-implementing-ja.svg#only-dark)
![検査を通った表（.rule）から rulec gen が九言語のコードを出し、rulec test が参照評価器と突き合わせる。実装する人は rulec api で呼び方を読み、関数・SQL・Wasm・MCP サーバのどれかを自分のアプリやバッチやエージェントに組み込む。生成物は編集せず、表が変われば CI の gen --check が止める](images/scenario-implementing-ja-light.svg#only-light)

### 3-1. 生成する

```console
$ rulec gen rules/送料.rule --out generated/
```

`generated/` の下に、言語ごとのディレクトリができます。Python・TypeScript・JavaScript・Rust・Ruby・Go・Swift は関数、SQL は入力の関係に対する一つの問い合わせ、Wasm は一つのモジュールです。ランタイムも依存もありません。

### 3-2. 呼び方を読む

生成物を読まなくても、呼び方は目録から分かります。

```console
$ rulec api rules/送料.rule | jq -r .python.signature
def shipping_fee(dest: Prefecture, weight: Gram, total: YenInclTax, member: MemberKind) -> YenInclTax:
$ rulec api rules/送料.rule | jq -r .go.signature
func ShippingFee(in Input) (YenInclTax, error)
```

値は宣言した単位の整数で渡します（1,999g なら `1999`、率は刻みの数）。列挙は目録に載っている綴りで渡します。入口で範囲と列挙を検査するので、宣言の外の値は黙って計算されず、例外かエラーで返ります。詳しくは[生成して呼ぶ](generate.md#呼び方は読まなくても分かる)にあります。

### 3-3. 突き合わせる

生成した全言語が、参照評価器と同じ答えを返すことを確かめます。境界から作った試験ケースを全言語に流し、バイト単位で比べます。

```console
$ rulec test generated/
ok    shipping_fee (Python) ベクタ 68 件
ok    shipping_fee (TypeScript) ベクタ 68 件
ok    shipping_fee (Go) ベクタ 68 件
ok    shipping_fee (SQL) ベクタ 68 件
ok    shipping_fee (Wasm) ベクタ 68 件
…
```

手元に無い言語のツールチェーンは飛ばして、そう言います。

### 3-4. 組み込む

組み込み先で形を選びます。

| 組み込み先 | 使うもの | 読むところ |
|---|---|---|
| アプリのコード | 生成した関数 | [生成して呼ぶ](generate.md#出るものの形) |
| DB の再計算、締めのバッチ | SQL の問い合わせ（入力の関係に対して一文） | [SQL は関数ではなく、問い合わせ](generate.md#sql-は関数ではなく問い合わせ) |
| ブラウザや、どの実行環境でも | Wasm のモジュール | [Wasm](generate.md#wasm-どの実行環境にも入る一つのモジュール) |
| エージェントに判断させたい場面 | 生成した MCP サーバ（規則が一つのツールになる） | [規則をエージェントのツールにする](generate.md#規則をエージェントのツールにする) |
| フォームや API の入口 | `rulec schema` が出す JSON Schema | [入口の検査も同じ表から](generate.md#入口の検査も同じ表から) |

生成物は編集しません。直したいことは表の側にあり、表を直せば全言語が一緒に変わります。

### 3-5. 表が変わったときに、ずれないようにする

生成物は git に入れ、CI で `--check` を付けて生成し直します。表が変わったのに生成物が古いままなら、そこで止まります。

```console
$ rulec gen rules/ --out generated/ --check
```

CI のジョブ全体は[インストール](install.md#ci-に置く)にあります。改定の影響を PR に貼る二行もそこにあります。
