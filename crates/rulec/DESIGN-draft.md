# 設計草案 決定表と条文を一つの意味論に置く（第二稿）

2026-09-19 の第二稿である。
第一稿の骨（§0、§2 の書式の方向、§4、§6）は残し、採否を決めた。
第一稿から変えたところには「第一稿から変えた」と書き、変えた理由をその場に置く。
DESIGN.md への転記は、実装した増分ごとに §15 の形で行う。
実装の順序は §9、増分ごとに触る場所の一覧も §9 にある。

この草案が検討するのは、rulec の検査（完全性、重なり、当てはまらない行）を厳密なまま保ちながら、条文の書き方を二つ受け入れられるか、という一点である。
受け入れたい二つは、「原則と例外」（ただし書）と、準用である。
比較の相手は Catala で、あちらは条件に任意の式を許すかわりに、当てはまる定義がゼロのとき（empty error）と、優先順位の付いていない定義が同時に当てはまるとき（conflict error）を実行時の誤りとして持ち、静的に潰すには SMT を呼ぶ。
rulec は同じ二つを完全性と重なりとしてコンパイル時に決めている。
この差を手放さずに、向こうの書き味だけを取る。

## 0. 中核の考え

**節は行であり、表は行の束である。そして順序は、出力ごとの半順序である。**

rulec の行は、自列への単項テストの連言であり、入力空間の箱だった。
Catala の定義は、条件つきの定義と、その上の優先順位だった。
条件を箱に制限した Catala の定義は、rulec の行そのものである。
違いは、rulec が行を表に並べて位置で順序を付けるのに対し、Catala は定義に名前を付けて例外関係を明示することだけである。

そこで意味論を一本にする。

> プログラムは、**ラベル付きの定義**（箱と、一つの出力と、その値）の集合と、**出力ごと**の**厳密な半順序**（「i は j に優先する」）である。

`policy unique` は「同じ表の行どうしに辺が無く、交われば誤り」の場合、`policy first` は「同じ表の行どうしに位置の全順序がある」場合として、どちらも特別な場合に戻る。
**第一稿から変えた**のは「出力ごと」の一語である。
表の一行は出力列の数だけ定義を束ねていて、順序は出力ごとに閉じる。
これを書かないと、出力を二つ持つ行の一方だけを節が上書きしたとき、もう一方の値がどこから来るのかが決まらない。

## 1. 幾何が壊れない理由

三つの検査が、いまと同じ算術のまま残る。

**完全性**：出力ごとに、その出力を定める箱の和が、制約で狭めた宇宙を覆うか。
半順序はここに関与しない。

**決定性**：同じ出力を定め、交わる二つの定義は、半順序で比較可能であること。
これが成り立てば、点に当てはまる定義の集合は鎖になり、最小が一つ決まる。
判定は箱の交差の総当たりで、いまの重なり検査と同じ計算量である。
つまり Catala の conflict error を、静的に、反例つきで出せる。

**第一稿から変えた**：第一稿はこれを「一意の極小元がある」ことと同値だと書いていたが、片方向しか成り立たない。
A と B が交わって比較不能でも、両方に優先する C が A と B の交わりを丸ごと覆えば、どの点でも最小元は C 一つである。
検査はこの配置も弾く。
弾いてよい理由は、この配置が「第三の規定が既に取る領域でだけ、二つの規定が競っている」形であり、原文でそう読める条文は無いからである。
十分条件を、そのまま決定性の定義にする。

**到達性**：定義が、自分に優先する定義の和に覆われていないか。
`policy first` の残余領域の計算は、引く相手を「先行する行」から「優先する定義の集合」に替えるだけで済む。
実装上もその集合を作っている場所は `region.rs` の `check_table` の一か所（`earlier`）で、消費する側（`hole_within`）は集合の中身を問わない。

**閉路が無い理由**：辺は、後で宣言した定義から前で宣言した定義へ向く（§2.3）か、同じ `first` の表の中で上から下へ向く。
前者は宣言の順を必ず下げ、後者は表の中に閉じるので、閉路は作れない。
循環検査は要らない。

半順序を入れても厳密さは落ちない。
ここがこの草案の要である。

## 2. 書式

意味が一本なら、書式は原文の形に合わせてよい。
列が揃っているものは表で書き、条件がばらばらで例外関係が主役のものは節で書く。
どちらも同じ出力を定めてよく、順序は辺で書く。

```
rule 送料 v3
import std/都道府県
source 郵便 = file "ゆうパック基本運賃.pdf" sha256:9e4edb5b6a1c0f42

enum サイズ区分 = S60 | S80

inputs
  あて先   : 都道府県
  サイズ   : サイズ区分
  会員     : bool
  注文金額 : money[円] range >=0円 <=1000万円

outputs
  送料 : money[円] round up(10円)

table 運賃表   @郵便 別表第一
policy unique
     | あて先 | サイズ | -> 基本運賃 : money[円] |
r1   | 北海道 | S60    | 1150円                  |
r2   | 東京都 | S60    | 820円                   |

clause 通常 -> 送料   @郵便 第3条第1項
  when always
  then 基本運賃

clause 無料 -> 送料   @郵便 第3条第2項
  when 注文金額 >=3900円 and 会員 true
  then 0円
  overrides 通常
```

### 2.1 ラベル

**決定**：表の行には任意でラベルを付けられる。
ラベルは行頭、最初の `|` の前に書く識別子で、同じ表の中で一意（重複は E034）、予約語は不可（E009）。
節の名前と表の名前も同じ名前空間のラベルであり、ファイルの中で一意である。
呼び出した規則の定義は、呼び出しの名前を前に付けて `退職手当:第2項`、行なら `退職手当:支給表:r5` と指す（§5）。

ラベルの無い行は今までどおり位置で数える。
既存の `.rule` は一行も変えずに通る。

**理由**。`overrides` と `except` が指す先に名前が要る。
それとは別に、`policy first` では位置が意味を持つので、行を一本挿すと意味が黙って変わり、記録に入る行番号も動く。
§4 が隠れ対の同一性を行番号でなくセルの正規形から取っているのは同じ問題への答えで、ラベルは人が選ぶ同一性をそこに足す。

### 2.2 節

**決定**：`clause <名前>(<別名>) -> <出力>` で始まるブロックを足す。
本体は `when`、`then`、任意の `overrides` の三行である。

- `when` は、列名とセルの対を `and` でつないだもの。
  セルは §3 の七種そのままで、列は表の列に使えるもの全部（入力、導出、真偽と列挙の中間値）。
  つまり節は、書かなかった列が `-` の一行にすぎない。
  条件が無い節は `when always` と書く。省くことはできない（空セルを don't-care と読まないのと同じ理由。§3）。
- `then` は、出力セルに書けるもの（リテラルか名前。§3.2）。
  式は書けない。
- `overrides` は、この節が優先する定義のラベルの並び（§2.3）。

出力は `outputs` の名前か、前の表か節が導入した中間値の名前。
新しい中間値を導入するなら、表と同じく `-> 名前 : 型` と型を書く。
節が定める出力は一つである。
ただし書が二つの値を同時に変えるなら、節を二つ書く（一つの節に二つの `then` を許す案は、測ってから）。

**捨てたもの**：`when -`（`always` の代わり。読めるが、書き間違いに見える）。
`when` の省略（書き忘れと区別が付かない）。
`then` に式を書くこと（§3.2 の理由がそのまま効く）。

### 2.3 順序の辺

**決定**：優先を書く場所は二つ。
節の `overrides` 行と、表の `policy` の次（`policy` を省くなら `table` の行の次）に置く `overrides` 行である。
どちらも、その節（表なら全行）が優先する相手を並べる。
相手は、節、表（全行）、`表:行ラベル` のどれでもよく、いずれも**その位置より前で宣言されている**こと（後ろを指すと E035）。
相手は**同じ出力を定めている**こと（違えば E036）。

半順序は、書いた辺と、`first` の表の位置の順の、推移閉包である。
`policy unique` はそのままで、意味は「辺の無い交わりは誤り」になる。
辺の無い今日の `unique` は、字も意味も変わらない。
第三の方式の語は足さない。

行が辺を書く場所は作らない。
行が何かに優先したいなら、それは節として書く。
表の全行が節や別の表に優先する形（本則の表に対する特例の表）は表の `overrides` で書ける。

辺の両側が交わらないときは W117（効かない例外）を出す。
ただし書が本文の一部を切り出す形になっていない、という転記の誤りの徴候であり、意味論は壊れないので警告に留める。

### 2.4 定義集合、検査の単位

**決定**：検査の単位を「表」から「一つの出力を定める定義の集合」に移す。
以下、定義集合と呼ぶ。
表だけがその出力を定めるなら、定義集合は表そのもので、今日の検査と一字も変わらない。

定義集合に表が二つ以上、または節が入るときは、列の和集合を軸に取り、無い列を `-` で埋めた一つの合成表を作って `check_table` に渡す。
合成表の各行は、元の表と行の位置とラベルを覚えていて、診断はそれで元の場所を名指しする。

- **E101** は定義集合ごとに探す。本則の表に穴があっても、節がそこを覆っていれば穴ではない。
- **E105 / W114** は、交わる対のうち比較可能でないものに出す。文面の末尾は「どちらが優先するか決めるなら `overrides` を、順序を位置で決めるなら `policy first` を」に変わる。同じ表の中の対は今日のまま。
- **E102** は、優先する定義の和に覆われた定義に出す。節にも出る。
- `first` の表の隠れの三分類（階段・同じ答え・要確認、W105）は表の中の対だけに残る。書いた辺は意図そのものなので、辺の対は W105 にしない。
- `constraint` の篩、上流の値の制限、E109 の予算は、合成表の上でそのまま効く。

**制限**：他の表や節と出力を共有する表は、出力列を一つだけ持つ（E045）。
二つの出力を持つ表の一方だけに節が掛かると、その表の行が二つの定義集合に半分ずつ属し、生成コードでは同じ行の条件が二つの分岐の列に現れる。
書けなくはないが、1 行 1 分岐（§8.1）の対応が崩れるので、実例を数えるまで断る。
二つ目の出力は別の表に分ければよく、それは定義集合を分けることでもある。

### 2.5 評価と生成の順序

**決定**：評価器も生成器も、定義集合を**半順序の線形拡大**の順に並べた一本の「最初に当たったものが勝つ」鎖として扱う。
並べ方は、節と表を宣言の**逆順**に、表の中の行は上から下の順に置く。
これが線形拡大である理由は §1 の閉路の議論と同じで、辺の勝者は必ず後で宣言されているか、同じ表の上の行だからである。

こうすると、いまの評価器（`eval.rs` の `Env::table` は方式に関係なく `position` で最初の一致を取る）も、生成器の `if` / `elif` の鎖も、行の**並べ方**を変えるだけで新しい意味論に乗る。
W114 の対にガードを生成する仕組みも、対の定義が「比較可能でない交わり」に広がるだけで、そのまま残る。
生成物の見た目は「例外を先に、本則を後に」であり、人が `policy first` で書いてきた形と同じになる。

分岐のコメントには、元の表名と行番号（ファイルに書かれた順の番号）とラベルを転記する。
1 行 1 分岐は保たれる。

### 2.6 記録、trace、replay

**決定**：発火の記録は、定義集合ごとに勝った定義を一つ持つ。
形は今日の `{"table":…,"row":N}` のままで、`N` はファイルに書かれた順の番号（`Row.index`。いまは持っているが読まれていない）である。
ラベルのある行は `"label"` を足す。
節は、自分の名前を表名とする一行の表として記録する（`{"table":"無料","row":1}`）。
新しい形は増えない。
出力を二つ持つ表は、共有していなければ一行が両方の出力に勝つので、記録も一つである。

`replay` と `diff` の `transition` は、両側にラベルがあればラベルで、無ければ番号で対応を取る。
これで、行を一本挿しても `moved` が立たなくなる。
`vectors` の散文の trace（`row_tag`）は、ラベルがあればそれを添える。散文は変えてよい（§11 原則 5）。
`docs/formats.md` には欄を足すだけで、既存の欄の意味は変えない。

### 2.7 doc

**決定**：承認者向けの描画は、表ごとの節に加えて、節（clause）ごとの節と、出力ごとの「決まり方」の段を持つ。

- 節は、名前と出典の下に、`when` に現れた列だけを見出しにした一行の表として描く。
- 出力ごとの段は、定義集合の辺を文で書く。「印紙税額 は、軽減（措置法第91条）が本則（印紙税法別表第一）に優先する」。
  辺の勝者の箱が敗者の箱に収まっているときは「例外」、収まっていないときは「優先」と書き分ける。
  推移律で外側でも勝つのは Catala と同じ意味だが、「例外」と印字してよいのは収まっているときだけである。
- 「`rulec check` が確かめたこと」に、「辺の無い交わりは無い」の一文が増える。
- 行番号の列 `#` は、ラベルのある行ではラベルを出す。HTML の `data-r` は番号のままにして、trace からの照合を壊さない。

### 2.8 網羅

**決定**：三つの基準（§9.2）はそのまま定義集合に載る。
行被覆は定義ごと（節も一つの定義）。
境界両側被覆は表ごとで変わらない。
隠れ対被覆は「比較可能で交わる対」に一般化する。
交わりの内側で勝者が勝つ点と、敗者だけの領域で敗者が発火する点の二点で、`first` の隠れ対はその特別な場合である。
JSON の基準名 `shadow_pair` は安定 API なので変えない。

### 2.9 fmt

ラベルは最初の `|` の前の列として、ブロックの中で幅を揃える。
見出し行はラベルが無いので、その幅ぶん空ける。
`is_row` の定義は「`|` で始まる、または識別子一つの後に `|` が来る」に広げる。
`clause`、`apply`、`source` のブロックは二字下げで、語の後は一つの空白。
引用（`@`）は行の本体と `#` の間に置き、`#` の中は今までどおり触らない。

## 3. 出典を契約にする

**決定**：文書と版を `source` で宣言し、表・節・行・導出・定義は `@` でその**断片**を指す。
指した断片のハッシュを `.rule` に固定し、写しが変われば `check` が誤りとして止め、引いている行を名指しする。
原文そのものは `.rule` に埋めない。

**第一稿から変えた**：ハッシュの単位を文書全体から断片に、写しの形を「持たない」から「規則の隣に置く」に変えた。
理由は §3.7 に、§15.32 を覆す理由と一緒に書く。

### 3.1 二種の出典

出典は二種ある。
断片に分けて取れるものと、ひとかたまりの不透明なものである。

```
source 法     = law "342AC0000000023" asof 2026-04-01
  別表第一 sha256:0ba69792e960021e
source 措置法 = law "332AC0000000026" asof 2026-04-01
  第91条   sha256:85faf53f6f6e8196
source 郵便   = file "ゆうパック基本運賃.pdf" sha256:9e4edb5b6a1c0f42
```

- `law` は e-Gov 法令検索の法令 ID（`342AC0000000023` は印紙税法、`332AC0000000026` は租税特別措置法。数字で始まるので `"…"` で囲む）と、`asof` の日付である。
  法令 API v2 は法令 ID と日付と要素の指定で本文を返すので（`/law_data/{法令ID}?asof=…&elm=MainProvision-Article_91`）、断片は条・項・号・別表の単位で取れる。
  断片ごとの固定行を `source` の下に置く。
- `file` は規則ファイルからの相対パスで、ハッシュはファイル全体に一つ、`source` の行に置く。
  断片の名前は `@` に書けるが、検査はされない（PDF の中の「別表第一」を機械は指せない）。

`asof` は、その版の規則が写した時点である。
§4 の施行日と同じ日を書くのが普通で、規則の版と法令の時点が一対一に結びつく。
`source` は `import` の次、`enum` の前に置く。

**捨てたもの**：`doc` という語（`rulec doc` と衝突する。§15.60 が `import schema` を同じ理由で捨てた）。
URL を直接書く形（`check` が網を見ることになる。§3.5）。
文書全体のハッシュ一つで済ませる形（§3.7）。

### 3.2 引用

**決定**：`@<出典名> <断片>[, <断片>…]` を、`table`・`clause`・`apply`・`derive`・`define` の行末と、表の行の最後の `|` の後に書ける。
`#` のコメントより前に置く。
`@` はいま字句誤り（E002）なので、既存のファイルには現れず、後方互換で入る。

断片の書き方は原文の呼び方そのままで、`第20条`、`第20条第2項`、`第20条の2`、`第20条第2項第3号`、`別表第一` を受ける。
法令 XML への対応は `Article_20`、`Article_20-Paragraph_2`、`Article_20_2`、`…-Item_3`、`AppdxTable[n]`（`別表第一` は `AppdxTableTitle` の一致で n を決める）である。
附則と号の細分は v1 では受けない。実例を数えてから足す。

`# 出典: …` のコメントは今までどおり書け、`doc` にも今までどおり出る。
違いは、`@` は検査されコメントは検査されない、という一点だけである。

### 3.3 写しと固定

**決定**：`law` の写しは、規則ファイルの隣の `sources/law/<法令ID>@<asof>/<要素>.xml` に、断片ごとに一つ置く。
`file` の写しは、そのファイル自身である。
固定行のハッシュは、写しのバイト列の SHA-256 の先頭 16 桁である。

写しは git に入れる。
法令の本文は著作権の対象でなく（著作権法第13条）、`file` の写しをどう扱うかは書く人の判断である。
写しが規則の隣にあることで、`check` は網を見ず、`doc` は原文を引用でき、改正の差分は写しの diff として PR に現れる。

固定行は機械が書く（§3.5）。
手で書いてもよいが、`check` の `fix.text` がその行をそのまま出すので、写す必要はない。

### 3.4 検査

新しい段 `sources::check` を `enums::check` の隣に置く。
ファイルを読む唯一の段（`lib.rs` の一行）が二つになるだけで、検査器本体はテキストから診断への関数のままである。
wasm の playground では E013 と同じ形で「読めない」と言う。

- 引用した断片が `source` の下に固定されていない → **E037**。`fix.text` はいまの写しから作った固定行。
- 固定したハッシュと写しが違う → **E038**。「第91条 は変わっています。引いている行: 軽減 r1, r4, r7」。`fix.text` は新しい固定行。写しの diff を見てから貼る、というのが手順である。
- 写しが無い、または断片が写しに無い → **E039**。「`rulec source fetch` を走らせてください」。
- 固定したが、もう引用していない断片 → **W119**。`rulec source pin` が消す。

警告ではなく誤りにする理由は第一稿のままである。
誰も読んでいない改訂が黙って通るほうが危ない。
E032/E033 が `.proto` を変えた側で落ちるのと同じ構図で、落ちるのは写しを更新した PR である。

### 3.5 コマンド

`rulec source` に三つの動詞を置く。

- `fetch <rule>`：`source law` の宣言と `@` の引用を読み、法令 API から断片を取って写しに書く。
  既にある写しと違えば、どの断片が変わったかを出す。
  網を見る唯一のコマンドで、実装は `curl` を子プロセスで呼ぶ（`git` を呼ぶのと同じ扱い。HTTPS を自前で書かず、依存も足さない）。
  API の包みは JSON で本文は base64 なので、`json.rs` の読み手と、自前の base64 の復号で足りる。
- `pin <rule>`：写しから固定行を作り直して `.rule` に書き戻す。
  触るのは固定行だけで、`fmt` が整列だけを触るのと同じ節度を守る。
  `check` の `fix.text` を手で貼るのと同じバイト列になる。
- `outdated <rule>`：`/law_revisions/{法令ID}` で改正の履歴を引き、`asof` より後に施行された版で引用している断片が変わっていれば、施行日と一緒に出す。
  `asof` で固定している限り `check` は改正を知りようがないので、改正を知る手段はこの一つである。
  CI の定期実行に置く。

`check` は網を見ない。これは動かさない。

SHA-256 は自前で書く（依存を足さないのは §12 のとおり）。
生成物ヘッダの `sha256:` は、いまは FNV-1a を名乗り違えて出している（§10）。
この機会に本物の SHA-256 に替え、名乗りと中身を一致させる。

### 3.6 doc

`law` の出典を持つ表と節は、見出しの下に**引用した断片の本文**を写しから引用して出す。
承認者は原文と表を一枚の上で見比べる。
検査器が知っていて字面に現れない事実を人の言葉で添える、という §1.6 の仕事そのものである。
`file` の出典は、ファイル名とハッシュと断片の名前だけを出す。

### 3.7 §15.32 を覆す

§15.32 は `source` 構文とダイジェストを名指しで捨てた。
理由は「ダイジェストの変化から言えるのは、この出典を引く行は読み直し、までで、どのセルかは分からない。それは表の性質ではなくレビューの引き金なので、check の診断にはしない」だった。
その理由に、二つ答える。

一つ。
単位を断片にすると、変化が言えるのは「第91条を引く三行は読み直し」までになる。
断片は一条か一項で、引いている行は名指しされる。
「どのセルか」は人が見比べれば分かる大きさに縮んでいる。
文書全体のハッシュではこうはならない。
三百条ある法律のどこかが改正されるたびに、その法律を引く全部の規則が落ち、無関係の改正でハッシュを書き換える作業が続けば、人は更新を読まずに通すようになる。
第一稿の形は、契約が守りたかったことを契約自身が壊す。

二つ。
「表の性質ではない」は正しい。
これはファイルの性質であり、E032 と同じ場所にある。
`.proto` が変わったときに落ちるのが正しいなら、写した条文が変わったときに落ちるのも正しい。
§15.32 の時点で相手は運賃表とクーポン規約で、改定は年に一度も無く、承認する人は業務の担当者だった。
相手を法令に向けると、改正は毎年あり、承認する人は法的に責任を負う。
費用（`fmt`・parser・reference・fixtures が一語ぶん増える）は変わらないが、払う理由が変わった。

## 4. 版は言語に入れず、生成物に出す

**決定**：施行期間はファイルの属性とし、適用日から版を選ぶのは生成されたディスパッチャの仕事とする。
第一稿のままである。

Catala は時点を言語に持っている。
これを列にすると、すべての表の幾何に時間軸が増え、完全性が日付を量化することになる。
各版の表は時間軸を持たないまま検査し、`diff` は版と版を比べ、`replay` は過去の記録を当時の版に当てる。

一つ足す。
「適用日から版を選ぶ」の前に、**どの日を適用日にするか**を条文が決めている。
施行前の行為はなお従前の例による、が典型である。
版の選び方は生成側でよいが、各版が何の日を基準に選ばれるかは承認の紙に一行出る必要がある。
出さなければ、法的に効いている部分がまた資料から消える。
施行期間と基準日の宣言（`effective`）は、ディスパッチャの生成と一緒に決める。
この草案の四つの増分（§9）には入れない。

## 5. 準用を写すための呼び出し

**決定**：非巡回で深さ一の呼び出し `apply` を入れる。
引数はすべて明示で束縛し、束縛がそのまま読替えになる。
呼び先は同じリポジトリの相対パスに限る。

呼び出しを入れる理由は準用である。
「第20条の規定は、Xについて準用する。この場合において、『勤続年数』とあるのは『在職期間』と読み替えるものとする」は、第20条の規則を引数を差し替えてもう一度使う、と言っているだけである。
アプリ側で二回呼ぶ形に逃がすと、準用という条文そのものが承認する人の資料から消える。
条文のうち法的に効いている部分が資料に出てこないので、この逃がし方は法令では取れない。

```
rule 退職手当 v1                            # 第20条
source 法 = law "…" asof 2026-04-01
  第20条 sha256:…

enum 事由 = 定年 | 自己都合 | 死亡

inputs
  勤続年数 : number range >=1 <=40
  退職事由 : 事由
outputs
  手当 : money[円] round down(1円)

table 支給表   @法 第20条第1項
policy unique
     | 勤続年数 | 退職事由 | -> 手当 |
r1   | <10      | -        | …       |

clause 減額 -> 手当   @法 第20条第2項
  when 退職事由 自己都合
  then …
  overrides 支給表
```

```
rule 非常勤退職手当 v1                      # 第31条
source 法 = law "…" asof 2026-04-01
  第31条 sha256:…

enum 終了事由 = 任期満了 | 辞職

inputs
  在職期間     : number range >=1 <=3
  任期終了事由 : 終了事由
outputs
  非常勤手当 : money[円] round down(1円)

apply 退職手当 = "退職手当.rule" sha256:9e4edb5b6a1c0f42   @法 第31条
  勤続年数 = 在職期間
  退職事由 = 任期終了事由 with 任期満了 -> 定年, 辞職 -> 自己都合
  except 減額
  手当 -> 非常勤手当
```

**第一稿から変えた**：第一稿の例は在職期間の範囲が `0..3` で、勤続年数の `1..40` に含まれていなかった。
0 が外である。
それに、任期終了事由と退職事由は別の列挙で、束縛の型が合わなかった。
弾かれるべき例だったのに、本文は「包含は成り立つ」と言っていた。
上の例は範囲を `>=1 <=3` に直し、列挙の対応を `with` で書いている。

呼び出しの語を `apply` としたのは、`doc` で「これは準用である」と出すためである。
呼び先の名前は `apply <名前> = "<パス>"` の左辺で、同じ規則を二度使うとき（往復の送料）は左辺を変える。
`as` のような語は足さない。宣言の形は `source 名 = …` と同じである。

### 5.1 束縛

**決定**：呼び先の**すべての入力**を `<呼び先の入力> = <値>` で束縛する（足りない、または呼び先に無い名前は E041）。
右辺は、呼び元の入力、導出、定義、前の表や節の出力、リテラルのどれか。
型は一致すること（E042。単位・税区分・型の不一致）。

列挙どうしは `with <値> -> <値>, …` で対応を書く。
対応は呼び元の列挙の全値を覆うこと（欠けは E042）。
綴りが同じ値は書かなくてよい（同じ綴りは同じ意味に読む。違えば E042 で名指しされる）。
これが「『退職』とあるのは『任期の終了』と読み替える」の形であり、呼び先の列挙型を呼び元に持ち込まない。

呼び先の出力は、同じ名前で呼び元の中間値になる。
`<呼び先の出力> -> <名前>` で改名でき、列挙型の出力は逆向きの `with` で呼び元の列挙に写す。
呼び元の `outputs` と同名なら、表の出力と同じく、その出力がそれになる。
呼び先の出力は、呼び先が宣言した丸めを掛けた値で来る。呼び元の出力の丸めはその上に、いつもどおり一度だけ掛かる。

`apply` は `derive`・`define`・`table` と同じ列に並ぶ項目である。
束縛できるのは前で宣言した名前だけで、後の項目がその出力を使える。

### 5.2 呼び先の範囲と制約は、呼び元の証明義務になる

**決定**：呼び元が束縛した値の到達区間が、呼び先の入力の `range` に収まり、呼び先の `constraint` が呼び元の宣言から導けることを、`check` が区間演算で確かめる（E043）。
導けなければ誤りである。
呼び先の完全性はその範囲と制約の上で証明されていて、外の点には定義が無い。

第一稿はこれを箱の包含として書いたが、**新しい算法ではない**。
`apply` を領域 IR の前の置換と定めれば、広すぎる側は呼び元の E101 がそのまま反例つきで捕まえる。
新しいのは文面で、`fix.text` が「行を足せ」になってはいけない、という点だけである。
足す行は呼び先のもので、呼び先は別の承認の単位だからである。
文面は、在職期間の範囲を `>=0` にした場合なら「在職期間 = 0 は、退職手当 の 勤続年数 の範囲 >=1 <=40 の外です。呼び元の範囲を狭めるか、その領域を呼び元の節で定めてください」とし、`fix.text` は付けない。
どちらにするかは業務の判断である。

生成コードには、呼び先の入口ガード（範囲と制約）を束縛した値に対して展開して入れる。
静的に証明したことを実行時にも守らせる、という §15.43 と §15.55 の線と同じである。

到達区間の計算は、いまの `feasible` と E112 の区間演算で足りる。
束縛の右辺が表の出力なら、列の値域はセルから決まる（§15.34）。

### 5.3 狭い側、使われない行

呼び元の到達領域が呼び先の範囲より狭いのが普通である（在職期間 1..3 に対して勤続年数 1..40）。
そのまま展開すると、呼び先の表の勤続年数 4 年以上の行は呼び元の中で全部死に、E102 が並ぶ。
その行は呼び先の自分のファイルで生きている。

**決定**：展開した定義には E102 を出さない。
`doc` が「この準用で使われない行」として、表ごとに行のラベル（無ければ番号）を列挙する。
呼び先の表の**全行**が使われないときだけ W118 を出す。
束縛か対応の書き間違いの徴候で、承認の紙に出るだけでは遅い。

`vectors` の行被覆も、使われない行を義務から外す。
外さないと網羅が永遠に満たせない。

### 5.4 一部準用と、呼び先への例外

「第20条（第2項を除く。）の規定は…準用する」は法令でごく普通の形である。
「ただし、…については、この限りでない」が準用の側に付くことも普通である。

**決定**：二つの形を入れる。

- `except <ラベル>, …`：呼び先の定義（節、表、`表:行`）を展開から外す。
  本則を外せば穴が開き、呼び元の E101 が「その領域を呼び元で定めよ」と言う。それが正しい。
  例外の節を外せば、本則がそのまま効く。
- 呼び元の節が `overrides 退職手当:減額` のように呼び先の定義に優先する。
  §2.3 の辺がファイルをまたぐだけで、新しい仕組みは無い。

どちらも、指す先はラベルが要る。
`except` は呼び出しのブロックの中にあるので、名前は呼び先のままで書く。ブロックの外から指すときは `退職手当:減額` と前置きする。
呼び先の行にラベルが無ければ E035 で「呼び先にラベルを付ける」と言う。
番号で指す形は作らない。番号は行を挿すと動く。

### 5.5 禁止するもの

**条番号の読替え**（「第3条とあるのは第5条と読み替える」）は入れない。
呼び先そのものが値になると呼び出しグラフが静的に決まらず、包含の検査も完全性も成り立たなくなる。
準用先ごとに別の規則を書く。

**包括読替え**（「必要な技術的読替えは政令で定める」）も外に置く。
政令を読むまで確定しないので、道具の中で閉じない。

**深さ二**。`apply` を持つ規則は `apply` できない（E044）。
準用の準用は実在するが稀で、法律家にも読みにくい。
展開の対象が一段なら、固定するハッシュも一段、再承認の連鎖も一段で済む。
第一稿の「深さに上限」を、根拠のある最小の上限に決めた。
実例が要求したら二にする。

**列を歩く規則**（`elements`、`fold`、`count`）と、`check` を通らない規則も `apply` できない（E044）。
前者は歩きの意味を呼び元に埋め直す設計が要り、後者は壊れた規則の展開が壊れた規則だからである。

**定数の読替え**（「十万円とあるのは二十万円と」）は、この四つの増分には入れない。
入力の付け替えでは書けず、呼び先が名前つきの定数を宣言してセルに使い、`apply` で付け替える形（`param 上限 : money[円] = 10万円`）が候補である。
セルに名前が入るのは七種のセル（§3）に八種目を足すことなので、実例を数えてから決める。
数える対象は §11 に書く。

### 5.6 生成はインライン展開にする

**決定**：呼び出しは検査と文書の上だけの概念とし、生成コードでは呼び先を展開する。

九つの生成器に関数呼び出しの形を足さずに済み、関数境界を持たない SQL も通る（並べ方とラベルで触る箇所は §9 のとおり）。
展開した表と節は、呼び出しの名前を前に付けた内部名（`退職手当_支給表`）で呼び元の鎖に並び、trace は `{"table":"退職手当:支給表","row":12}` と返す。
なぜこの金額かの答えは一枚に収まったままである。
`doc` も展開して一枚にし、呼び出しの段に「第31条 準用: 退職手当.rule（第20条）を次の読替えで適用」と束縛と `except` を書き、その下に呼び先の表を呼び先の出典つきで描く。
承認の紙は割れない。
`rulec api` は呼び元の署名だけを出し、ヘッダに呼び先のパスとハッシュを刻む。

代償は生成コードが大きくなることだが、表はもともと展開して出している。
本物の関数呼び出しへの切り替えは、生成側の最適化として後から選べる。

### 5.7 固定と承認

**決定**：`apply` の行に呼び先ファイルの SHA-256 を固定し、違えば E040 にする。
`fix.text` は新しいハッシュ、文面は「`rulec diff` で呼び元の答えが何件いくら動くかを見てから貼る」である。
固定行の更新は `rulec source pin` が引き受ける。
§3 の契約を、散文からほかの規則へ、同じ形で伸ばしたものである。

費用を書いておく。
第20条の改正のたびに、それを準用する全規則に新しい版が要る。
別表を十の条文が準用していれば、一回の改正で十回の再承認である。
法的にはそれが正しい（合成された規則は変わった）。
緩和は `diff` で、呼び元ごとに影響の件数と金額を出す。
影響ゼロの呼び元は、その数字を見て固定行だけを貼り直せばよい。

`--diff-base` と `replay` / `diff` が git から古い規則を読むときは、呼び先も同じ版から読む（`base_source` と `load_rule` を呼び先にも当てる）。
`gen --check` は、呼び先が変われば生成物が変わるので、そのまま古さを捕まえる。

したがって、出典の契約（§3）が先で、呼び出し（§5）が後になる。
固定と `pin` の仕組みを共有するからで、逆順では入らない。

### 5.8 重ね合わせだけでどこまで書けるか

**測った（第一稿のまま）。** 準用を呼び出しなしで書けるかを、二つの形で試した。

**読替えを上流の表にする形**は、出力セルに入力の名前を書く。
当初は下流の表の全行が E102 で落ちたが、原因は検査側の隙で、直した（DESIGN.md §15.65）。
直したあとは通り、九つの生成対象が参照評価器と一致することも確かめた。

```
table 読替え
| 区分   | -> 期間 : number |
| 常勤   | 勤続年数         |
| 非常勤 | 在職期間         |
```

**列を広げて複製する形**は、準用先の行を `-` 込みで並べる。
最初から通る。
ただし条文の表が準用先の数だけ複製され、複製どうしが一致しているかは検査されない。

**第一稿に無かった代償**を一つ足す。
読替え表の形は、常勤と非常勤の両方の入力を一つの規則が持つ。
非常勤の呼び出しでも勤続年数を渡すことになり、生成された API と承認の紙に意味の無い入力が残る。
`constraint` は列挙で条件付けできないので（§15.55）、消せない。

したがって、同一ファイルに収まるなら読替え表のほうがよい、と言えるのは**二つの条文の入力が一致するとき**に限る。
呼び出しが要るのは、次のどれかが成り立つときである。
準用元が別ファイルの独立した承認対象であること。
準用元の表を書き換えたくないこと。
準用元が自分の周期で改定され、その変更が呼び元の再承認を要求すること。
そして、準用先の入力が準用元と違うこと。

### 5.9 引き受ける危険

規則どうしの依存グラフができる。
DESIGN.md §5.4 がこれを断った理由は二つで、GUI モデラの引力と、どの版を共有しているのかという問題だった。

前者は、グラフが一次表現になると絵で書きたくなり、絵は diff できない、という話である。
呼び出しはテキストが一次表現で、グラフはその帰結にすぎず、深さ一なら帰結は星形にしかならない。
引数をすべて明示すること、深さ一であること、一つの規則を読んで意味が閉じることの三つが、その条件である。

後者は避けられず、§5.7 の固定がその答えになる。

残る費用は、変更の影響範囲がファイルで閉じなくなることで、`gen --check` と `--diff-base` と `replay` が呼び先を同じ版で読む仕事を負う（§5.7）。

## 6. 捨てるもの

**条件の任意式**。
ここを曲げれば検査が六つとも死ぬ。

**日付の演算**。
日付は順序付きのリテラルと区間だけにする。
`+1ヶ月` を持たないので、Catala が論文一本かけて形式化した曖昧さがそもそも発生しない。
法令では年齢と期間の計算が曖昧さの本体で、その全部がアプリ側に行く。
外に出したものは承認の紙に書く。`doc` の入力の説明に「呼び出し側が計算して渡す」と出る欄を、§4 の `effective` と一緒に決める。

**実行時の empty と conflict**。
すべてコンパイル時に決める。

**言語別の字句解析器**。
Catala は自然言語ごとに lexer を持つ。
識別子は uppercase か lowercase で始まり、続く字もその二類と数字と `_` に限られるので（`compiler/surface/lexer.cppo.ml`）、漢字かなは識別子に書けない。
これは向こうがいつでも変えられる決定なので、事実として書くに留める。
rulec の識別子は、いまの字句解析器のとおり「アルファベット類か `_` で始まり、区切り字まで」であり、大文字小文字の同一視も NFC 正規化もしていない（§10）。
**第一稿から変えた**：第一稿は「大文字小文字を区別しない Unicode」と書いたが、実装はそうなっておらず、依存ゼロで Unicode の表を持たない以上、いまはそう約束しない。
キーワードは ASCII の正準形を一つ置き、表記ゆれは `fmt` が正規化する。これは今までどおりである。

## 7. 書き写せる範囲はどう変わるか

**形式的な表現力は、ほとんど変わらない。**
半順序は線形拡大で全順序に写せ、`policy first` で同じ関数が書ける（§2.5 はそれを構成的に使っている）。

変わるのは二つである。

一つは**検査が弾くもの**である。
`first` では、意図しない重なりが階段の件数に紛れて黙る。
辺の意味論では、すべての重なりが書いた辺で正当化されていなければ止まる。
第一稿は「表現力は変わらない」と控えめに言ったが、買っているのはこれで、承認者が読める辺として `doc` に出るところまでが一つの買い物である。

もう一つは**承認を通せる範囲**である。
関係のない列が `-` で埋まった行は、原文の「ただし書」と見比べられない。
承認する人が原文と対応を取れない規則は、書けても承認されないので、実務では写せないのと同じことになる。
出典の契約（§3）は表現力に無関係だが、改定の多い文書を写せる範囲を変える。
いま写すと対応が腐りはじめ、腐ったことが検出されない。

本当に範囲が広がるのは**呼び出し**（§5）だけであり、その範囲は §5.8 の測定で狭まり、代償の発見で少し戻った。

そして境界そのもの、つまりセルが箱であるという性質は動かさないので、外に出るものも動かない。
期間の按分、明細をまたぐ累積、条番号の読替えと包括読替え、そもそも一回の判定でない手続きは、外のままである。

## 9. 実装の順序と、増分ごとの登録簿

四つの増分に切る。
順序は 1、2、3、4 で、4 は 1（ラベル）と 3（固定と `pin`）に依る。
`except` も呼び先への `overrides` もラベルが前提である。

1. **ラベルと辺**：行ラベル、表の `overrides`、定義集合、線形拡大、記録の `label`、E034〜E036、E045、W117。
2. **節**：`clause` / `when` / `then` / `always`、doc の節と「決まり方」の段。
3. **出典**：`source` / `law` / `file` / `asof`、`@`、写し、SHA-256、`rulec source fetch|pin|outdated`、E037〜E039、W119、doc の引用。
4. **呼び出し**：`apply` / `with` / `except`、展開、E040〜E044、W118。

1 と 2 を分けるのは、1 だけで表どうしの例外（本則の表と特例の表）が書け、それだけで §11 の最初の測定ができるからである。

増分ごとに触る場所は次のとおりで、どれも「おまけ」にしない。

- 字句と構文：`lex.rs`（`@` を字句に足す）、`parse.rs`（`grid` と `split_cells` の行頭、`table` の `overrides` 行、新しいブロック）、`ast.rs`（`Row.label`、`Row.cite` などの引用、`Table.overrides`、`Item::Clause`、`Item::Apply`、`RuleFile.sources`）、`kw.rs`（行頭の語 `clause` `source` `apply`、ブロックの中の語 `when` `then` `overrides` `always` `except` を予約語に。`law` `file` `asof` `with` は位置で見分ける）、`fmt.rs`（§2.9）。

## 10. 実装を読んで分かったこと

草案を実装に結ぶために読んで、直すべきものが四つ見つかった。
どれもこの草案が原因ではないが、この草案の増分と同じ場所にある。

- **生成物ヘッダの `sha256:` は FNV-1a 128 である**（`codegen::hash`）。名乗りが違う。§3.5 で本物の SHA-256 に替える。生成物のヘッダが全部変わるので、`gen --check` の golden はその増分でまとめて更新する。
- **`Row.index` は持っているが読まれていない**。行番号は全部ループ変数の `i + 1` から来ている。§2.6 で trace の番号の正として使う。
- **`check` の `codes` が台帳より少ない**（§8）。台帳と `--help` の照合は「help が名指すコードは台帳にある」の向きしか無く、逆向きが無い。逆向きの検査を `tests/codes.rs` に足す。
- **識別子の NFC 正規化は無い**。DESIGN.md §1.1 は「識別子は NFC に正規化する」と書くが、字句解析器はそのまま格納し、依存ゼロで Unicode の表も無い。§6 で約束を実装に合わせた。正規化を入れるかは、表を持ち込む費用と一緒に別に決める。

## 11. 測る

決めたことは、実装の前か直後に、次の順で測る。

1. **表どうしの例外**（増分 1）：`tests/corpus/印紙税.rule` を、本則の表（印紙税法 別表第一）と軽減の表（租税特別措置法 第91条）に分け、軽減が本則に `overrides` する形に書き直す。
   いまの一表（`軽減期間` の列と `-` の行）と、`check` の診断、`coverage` の義務、九言語のベクタ一致を比べる。
   `doc` の「決まり方」の段が、二つの原文とそれぞれ見比べられる形になっているかを見る。
2. **節**（増分 2）：同じ規則の「契約金額の記載のないもの」と「非課税」を節に書き、`doc` で原文の文と並ぶかを見る。
   あわせて、条文を見た目でなく**判定の形**で数える。
   印紙税、所得税、健康保険料の三本と次に写す法令の条文を、「表になる」「表の連鎖と定義・導出になる」「節になる」「入力に外す（期間・年齢の計算、不確定概念）」「外に残る（集約、手続き、比率按分）」の五つに分ける。
   表として組んであるかどうかは境界ではない。区分は列挙の列に、段になった条件は表の連鎖に、文の中の閾値と差は定義と導出に、ただし書は節に落ちる。
   この五つの数が、賭けの大きさそのものである。
3. **出典**（増分 3）：印紙税の二つの出典を e-Gov から取り、固定し、`asof` を 2026-06-03 の版に進めて `fetch` が「別表第一 は変わっていない」または「変わった」と正しく言うかを見る。`outdated` が 2026-06-03 施行の改正を報告するかを見る。
4. **呼び出し**（増分 4）：e-Gov で、表の形をした条文を準用している条文を一組見つける。無ければ §5 の例を二ファイルにして、E043 が範囲の外を、`except` が本則の穴を、`diff` が呼び先の改正の影響を、それぞれ言うかを見る。
5. **定数の読替えの実例**（§5.5 の後回しを決めるため）：見つけた準用の条文で、読替えが「語の付け替え」「定数の付け替え」「条番号の付け替え」のどれかを数える。
