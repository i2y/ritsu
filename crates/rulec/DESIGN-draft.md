# 設計草案 決定表と条文を一つの意味論に置く

2026-09-19 の草案である。
DESIGN.md の決定ではなく、採否も決めていない。

この草案が検討するのは、rulec の検査（完全性、重なり、当てはまらない行）を厳密なまま保ちながら、条文の書き方を二つ受け入れられるか、という一点である。
受け入れたい二つは、「原則と例外」（ただし書）と、準用である。
比較の相手は Catala で、あちらは条件に任意の式を許すかわりに、当てはまる定義がゼロのとき（empty error）と、優先順位の付いていない定義が同時に当てはまるとき（conflict error）を実行時の誤りとして持ち、静的に潰すには SMT を呼ぶ。
rulec は同じ二つを完全性と重なりとしてコンパイル時に決めている。
この差を手放さずに、向こうの書き味だけを取れるかを見る。

## 0. 中核の考え

**節は行であり、表は行の束である。そして順序は半順序である。**

rulec の行は、自列への単項テストの連言であり、入力空間の箱だった。
Catala の定義は、条件つきの定義と、その上の優先順位だった。
条件を箱に制限した Catala の定義は、rulec の行そのものである。
違いは、rulec が行を表に並べて位置で順序を付けるのに対し、Catala は定義に名前を付けて例外関係を明示することだけである。

そこで意味論を一本にする。

> プログラムは、**ラベル付きの箱と出力**の集合と、その上の**厳密な半順序**（「i は j の例外である」）である。

`policy unique` は「半順序が空であり、交われば誤り」の場合、`policy first` は「位置による全順序」の場合として、どちらも特別な場合に戻る。

## 1. 幾何が壊れない理由

三つの検査が、いまと同じ算術のまま残る。

**完全性**：箱の和が、制約で狭めた宇宙を覆うか。
半順序はここに関与しない。

**決定性**：点に当てはまる箱の集合が、一意の極小元を持つか。
これは「**交わる二つの箱は半順序で比較可能である**」と同値である。
交わる対がすべて比較可能なら、当てはまる箱の集合は鎖になり、最小が一つ決まる。
逆に比較可能でない対が交われば、その交わりの点で勝者が決まらない。
判定は箱の交差の総当たりで、いまの重なり検査と同じ計算量である。
つまり Catala の conflict error を、静的に、反例つきで出せる。

**到達性**：箱が、自分に勝つ箱の和に覆われていないか。
`policy first` の残余領域の計算で、引く相手を「先行する行」から「勝つ行の集合」に替えるだけで済む。

半順序を入れても厳密さは落ちない。
ここがこの草案の要である。

## 2. 書式を二つ持つ

意味が一本なら、書式は原文の形に合わせてよい。
列が揃っているものは表で書き、条件がばらばらで例外関係が主役のものは節で書く。

```
rule 送料 v3
  source 郵便 = doc "ゆうパック基本運賃" ed 2026-04-01 sha256:9e4edb5b...

inputs
  あて先   : enum 都道府県
  サイズ   : enum サイズ区分
  会員     : bool
  注文金額 : money[円] range 0円..1000万円

outputs
  送料 : money[円] round up(10円)

table 運賃表 -> 基本運賃 : money[円]        @郵便 別表第一
  | あて先   | サイズ | -> 基本運賃 |
  r1 | 北海道 | S60   |     1,150円 |
  r2 | 東京都 | S60   |       820円 |

clause 通常 -> 送料                          @郵便 第3条第1項
  when  always
  then  基本運賃

clause 無料 -> 送料                          @郵便 第3条第2項ただし書
  when  注文金額 >= 3900円 and 会員
  then  0円
  overrides 通常
```

`when` に書けるのは、宣言済みの入力への単項テストの連言だけである。
つまり節は、列を省略した一行にすぎない。
節が表全体の例外でもよく、表の一行が節の例外でもよい。

副次的に、行にラベルが要るようになる。
`policy first` では位置が意味を持つので、行を一本挿すと意味が黙って変わり、trace と記録に入る行番号も動く。
ラベルと `overrides` にすれば、順序が位置から独立し、trace が改定をまたいで安定する。
diff の「動いた行」は、本当に動いた行だけになる。

## 3. 出典を契約にする

**決定**：文書と版とハッシュを `source` で宣言し、表と行はその断片を指す。
原文そのものはファイルに埋めない。

Catala は条文をソースに埋め、形式化と対置する。
rulec は出典をコメントで指している。
埋める案は §1.1 で却下済みで、理由は地の文と表の境界の規則が増えるだけ、というものだった。
そこで、指したまま、**指す先を検査の対象にする**。

検査は二つになる。
引用先の断片が存在しなければ誤りである。
文書のハッシュが承認時と違えば誤りであり、そのとき「この文書は改訂されている。引用している六行を読み直せ」と行を名指しで言う。

これは `import proto` で作った形の転用である。
外部の権威が真実の一部を所有し、集合がずれれば E032、値に行も `default` も無ければ E033、という構図を、列挙ではなく散文に当てる。
警告ではなく誤りにする理由も同じで、誰も読んでいない改訂が黙って通るほうが危ない。

**捨てたもの**：原文を `.rule` に埋める案（§1.1 の却下理由がそのまま効く）。
出典を自由なコメントのままにする案（何も検査されないので、写した瞬間から対応が腐りはじめ、腐ったことが誰にも分からない）。

## 4. 版は言語に入れず、生成物に出す

**決定**：施行期間はファイルの属性とし、適用日から版を選ぶのは生成されたディスパッチャの仕事とする。

Catala は時点を言語に持っている。
これを列にすると、すべての表の幾何に時間軸が増え、完全性が日付を量化することになる。
各版の表は時間軸を持たないまま検査し、`diff` は版と版を比べ、`replay` は過去の記録を当時の版に当てる。
時点で引けるという性質は、表の幾何を汚さずに手に入る。

## 5. 準用を写すための呼び出し

**決定**：非巡回の呼び出し `apply` を入れる。
引数はすべて明示で束縛し、束縛がそのまま読替えになる。
呼び先は同じリポジトリの相対パスに限り、深さに上限を置く。

呼び出しを入れる理由は準用である。
「第20条の規定は、Xについて準用する。この場合において、『勤続年数』とあるのは『在職期間』と読み替えるものとする」は、第20条の規則を引数を差し替えてもう一度使う、と言っているだけである。
アプリ側で二回呼ぶ形に逃がすと、準用という条文そのものが承認する人の資料から消える。
条文のうち法的に効いている部分が資料に出てこないので、この逃がし方は法令では取れない。

```
rule 退職手当                          # 第20条
inputs  勤続年数 : number range 1..40
        退職事由 : enum 事由
outputs 手当 : money[円] round down(1円)
table 支給表 -> 手当                   @法 第20条

rule 非常勤退職手当                    # 第31条
inputs  在職期間     : number range 0..3
        任期終了事由 : enum 終了事由
apply 退職手当 @法 第31条
  勤続年数 = 在職期間
  退職事由 = 任期終了事由
```

呼び出しの語を `apply` としたのは、`doc` で「これは準用である」と出すためである。

### 5.1 呼び元の領域が、呼び先の範囲に収まるか

**決定**：呼び元が実際に渡しうる領域が、呼び先の `range` と `constraint` の中に収まることを静的に確かめる。

準用は、元の条文が想定していない状況へ規定を持ち込む操作である。
上の例では第20条の `勤続年数` が 1..40 年、非常勤の `在職期間` が 0..3 年で、包含は成り立つ。
逆向きなら破れる。
条文を読んだだけでは気づきにくく、箱の包含なので厳密に決まり、破れたときは反例が出せる。
成り立たない準用を検出できることが、呼び出しを入れる見返りの中心である。

費用も書いておく。
呼び元の到達領域を出すには呼び元の表を全部解く必要があるので、深くなると E109 の側に流れやすくなる。
深さの上限はこのためでもある。

### 5.2 禁止するもの

**条番号の読替え**（「第3条とあるのは第5条と読み替える」）は入れない。
呼び先そのものが値になると呼び出しグラフが静的に決まらず、包含の検査も完全性も成り立たなくなる。
準用先ごとに別の規則を書く。

**包括読替え**（「必要な技術的読替えは政令で定める」）も外に置く。
政令を読むまで確定しないので、道具の中で閉じない。

### 5.3 生成はインライン展開にする

**決定**：呼び出しは検査と文書の上だけの概念とし、生成コードでは呼び先を展開する。

八言語の生成器を触らずに済み、関数境界を持たない SQL も通る。
`traced` が返す行は展開後に一意に決まるので、規則名を付けて `退職手当:支給表:r12` と返せば、なぜこの金額かの答えは一枚に収まったままになる。
`doc` も展開して一枚にできるので、承認の紙が割れない。
代償は生成コードが大きくなることだが、表はもともと展開して出している。
本物の関数呼び出しへの切り替えは、生成側の最適化として後から選べる。

### 5.4 版と承認

**決定**：呼び元は呼び先のハッシュを固定し、呼び先が変わればエラーにする。

呼び先が変わったとき呼び元の承認が生きているのか、という問題は避けられない。
§3 の出典の契約を、散文からほかの規則へ、同じ形で伸ばす。

直す手順は既存の道具のままである。
`check` が `fix.text` に新しいハッシュを出し、`diff` が「呼び先が変わったことで呼び元の答えが何件いくら動くか」を出す。
その数字を見てから、人がハッシュを書き換える。
E101 が行の形は出すが金額は出さないのと同じ立場である。

したがって、出典の契約（§3）が先で、呼び出しが後になる。
逆順では入らない。

### 5.5 重ね合わせだけでどこまで書けるか

**測った。** 準用を呼び出しなしで書けるかを、二つの形で試した。

**読替えを上流の表にする形**は、出力セルに入力の名前を書く。
当初は下流の表の全行が E102 で落ちたが、原因は検査側の隙で、直した（DESIGN.md §15.65）。
直したあとは通り、九つの生成対象が参照評価器と一致することも確かめた。

```
table 読替え
| 区分   | -> 期間 : number |
| 常勤   | 勤続年数         |
| 非常勤 | 在職期間         |
```

**列を広げて複製する形**は、準用先の行を `-` 込みで並べる。
最初から通る。
ただし条文の表が準用先の数だけ複製され、複製どうしが一致しているかは検査されない。

したがって呼び出しが要るのは、三つが揃うときだけである。
準用元が別ファイルの独立した承認対象であること。
準用元の表を書き換えたくないこと（条文の表に、準用先のための行や列を足したくない）。
準用元が自分の周期で改定され、その変更が呼び元の再承認を要求すること。

同一ファイルに収まるなら、読替え表のほうがよい。
一枚の doc、一回の承認、一つの diff で閉じる。

### 5.6 引き受ける危険

規則どうしの依存グラフができる。
DESIGN.md §5.4 がこれを断った理由は二つで、GUI モデラの引力と、どの版を共有しているのかという問題だった。

前者は、グラフが一次表現になると絵で書きたくなり、絵は diff できない、という話である。
DMN XML を §1.1 で捨てたのと同じ場所に着く。
呼び出しはテキストが一次表現で、グラフはその帰結にすぎないので、ここは形で避けられる。
引数をすべて明示すること、非巡回で浅いこと、一つの規則を読んで意味が閉じることの三つが、その条件である。

後者は避けられず、§5.4 の契約がその答えになる。

残る費用は二つある。
変更の影響範囲がファイルで閉じなくなるので、`gen --check` と `--diff-base` が推移閉包を扱うことになる。
そして規則の数が増えたときにグラフを見たくなる圧力は、上限と明示引数で抑えるほかない。

## 6. 捨てるもの

**条件の任意式**。
ここを曲げれば検査が六つとも死ぬ。

**日付の演算**。
日付は順序付きのリテラルと区間だけにする。
`+1ヶ月` を持たないので、Catala が論文一本かけて形式化した曖昧さがそもそも発生しない。

**実行時の empty と conflict**。
すべてコンパイル時に決める。

**言語別の字句解析器**。
Catala は自然言語ごとに lexer を持つが、識別子が Lu と Ll の前提を連れてくる。
漢字とかなは Lo なので、この前提のもとでは識別子に書けない。
識別子は大文字小文字を区別しない Unicode とし、キーワードは ASCII の正準形を一つ置いて、表記ゆれは `fmt` が正規化する。

## 7. 書き写せる範囲はどう変わるか

**形式的な表現力は、ほとんど変わらない。**

半順序は、そのトポロジカル順序による全順序へ写せる。
線形拡大は半順序を保つので、当てはまる箱の鎖の最小は、その全順序で最も早い箱と一致する。
つまり §0 と §2 で書けるようになる規則は無い。
条件の形が違う例外も、いまは関係のない列を `-` で埋めた行として表に入る。

変わるのは、**承認を通せる範囲**のほうである。
関係のない列が `-` で埋まった行は、原文の「ただし書」と見比べられない。
承認する人が原文と対応を取れない規則は、書けても承認されないので、実務では写せないのと同じことになる。
原文との対応が読めるかどうかが、そのまま写せる範囲を決めている。

出典の契約（§3）は表現力に無関係だが、**写す価値のある文書の範囲**を変える。
改定の多い文書は、いま写すと対応が腐りはじめ、腐ったことが検出されない。

本当に範囲が広がるのは**呼び出し**（§5）だけであり、その範囲も §5.5 の測定で狭まった。
同一ファイルに収まる準用は、読替え表で書ける。
呼び出しが広げるのは、準用元が別ファイルの独立した承認対象であるときだけである。

呼び出しの無い今日でも、往復送料のように同じ表を二度使う計算は、生成コードをアプリ側で二回呼べば済む。
できないのは、それを一本の規則として検査と承認と diff の対象にすることのほうである。
業務の規約なら、合成の部分が規則の外に出ることは払える。
準用は払えない。
準用という条文そのものが法的に効いているので、アプリ側に逃がすと、承認する人が見る資料からその部分が消える。

そして境界そのもの、つまりセルが箱であるという性質は動かさないので、外に出るものも動かない。
期間の按分、明細をまたぐ累積、条番号の読替えと包括読替え（§5.2）、そもそも一回の判定でない手続きは、外のままである。

## 8. この草案から出た結論

新しいのは四つだけである。

1. ラベルと半順序（`policy unique` と `policy first` の一般化）
2. 節の書式（表の一行の別記法）
3. 出典のハッシュ契約（`import proto` の形の転用）
4. 呼び出しと、constraint の証明義務

残りは rulec が既に持っているか、生成側だけの話である。
そして 1 から 3 は後方互換で入る。
既存の `.rule` は一行も変えずに通る。

ゼロから設計しても、着く先は rulec に四つ足したものだった。
別の言語を立てる理由は、この設計からは出てこない。

入れる順序は決まっている。
3 の出典の契約が先で、4 の呼び出しが後になる（§5.4）。
1 と 2 はそれらと独立で、単体でも価値がある。
