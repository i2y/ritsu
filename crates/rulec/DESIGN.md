# rulec 設計文書

業務ルールを決定表として記述し、静的に検査し、Python と Go の両方へ読めるコードを生成する道具の設計を決める。
実装はまだ書かない。
本文の構文例と生成コード例は、決定を説明するためのスケッチである。

合意済みの前提は再論せず、以下の記号で参照する。

- **P1**：最初の対象領域は送料。次がクーポンとポイント、引当は最後
- **P2**：記述の中心は決定表。業務担当者が読めること
- **P3**：ルールは純関数。時刻も在庫も会員区分も入力として渡される
- **P4**：型で守るのは、単位、丸め、網羅性、優先順位と重複の四つ
- **P5**：出力は Python と Go への依存ゼロの読めるコード生成。実行時ランタイムは持たない
- **P6**：道具本体はデータ不要、旧実装があれば等価検証、過去データがあれば影響算出、と段階的に価値が出ること
- **P7**：汎用言語にしない。ループも再帰も状態も GUI も持たない

本書は v0 草案を、公開規約からの転記実測を受けて改訂した v1 である。
実測とは、公開情報（日本郵便ゆうパック基本運賃 東京発、ヤマト宅急便のサイズ区分、楽天市場の送料無料ライン、39 キャンペーン、複数クーポンの計算方法とクーポン利用条件、Yahoo!ショッピングのクーポン利用条件）を 2 本の `.rule` に転記した計測を指す。
規模はゆうパック運賃が 84 行（表 55 行、列 2、群 6）、クーポン割引が表 15 行、列 6 である。
本文で「実測」と言うときはこの転記を指し、転記そのものは回帰コーパスとして §13 に収録する。
実測が支持した決定（二方式の共存、単項セルの制限、線形パイプライン、群、表引き出力への丸め宣言、完全性の常時必須）は各所に一文で記す。
覆った決定は本文を書き換え、v0 が持っていた検査の抜け道は塞いだ経緯ごと残す（§5.3）。

## 0. 全体像

rulec は一本のパイプラインである。

```
.rule ── 構文解析 ──> AST ── 型付け ──> TIR（型付き表 IR）
                                        ├──> 領域 IR（圧縮座標上の箱集合）──> 検査 E101/E102/E105
                                        ├──> 参照評価器 ──> 例の検証・ベクタ期待値・verify/replay/diff
                                        └──> コード生成 ──> generated/python/…  generated/go/…
```

単位の誤り（E103）と丸めの漏れ（E104）は型付けの段で出る。
網羅性（E101）、冗長（E102）、重複（E105）は領域 IR の段で出る。

意味論の原本は TIR 上の**参照評価器**一つに置く。
例の検証も、テストベクタの期待値も、過去再生も、すべて同じ評価器を通す。
生成された Python と Go は、共通ベクタでこの評価器との一致を機械的に確かめる（§9）。
参照評価器は rulec の内部にだけ存在し、本番で実行されるのは生成コードのみである。
P5 の「実行時ルールエンジンにしない」は、この線引き（評価器は検証系専用、出荷物は生成コード）で守る。

この全体像に、境界の宣言を一つ足しておく。
**この道具の本当の境界はヒットポリシーではなく、セルの言語である。**
rulec は DMN の読み手でも部分集合でもない。
借りるのは決定表の骨（単一ヒットの二方式と、完全性・重複という解析の問題設定）だけで、セルに書けるのは自列への単項テストに限る（§3）。
公開されている実在の DMN 資産には、セルに任意の FEEL 述語（`some … satisfies …` や `count(…)`）を書くものがあり、我々はそれをヒットポリシー以前にセルの言語で受け付けない（§4 の調査で開いた伊 ANAC の調達規則がその実例）。
この狭さは妥協ではなく購入である。
セルが単項だから行が箱になり、完全性も重複も厳密に決定できる（§6）。
入れ子のデータへの述語も同じ線の上にある。
入れ子は境界で平たい入力に潰してから渡し、セルには入れない（§3、§15-6）。
「FEEL なら書けるのに」という圧力は実務で必ず来る。
曲げてよいのは境界の外（入力の作り方。§15-6）だけで、セルの言語を曲げた瞬間に、この道具の検査は成り立たなくなる。

## 1. 表面構文

### 1.1 ファイル形式

**決定**：行指向の独自テキスト形式。拡張子は `.rule`。エンコーディングは UTF-8（BOM なし）で、識別子は NFC に正規化する。表はパイプ区切りで、1 行が決定表の 1 ルール行に対応する。セル内改行は存在しない。

git diff の意味単位を業務ルールの行に一致させることが、この形式の唯一の設計目標である。
パイプ表は開発者も業務担当者も PR 上で読み慣れており、新しい読み方を教える必要がない。

キーワード（規則、取込、型、群、入力、出力、定義、表、方式、結果、例、範囲、丸め、以外、無し など）は日本語一種類だけを正とし、英語の同義キーワードは用意しない。
同じ意味の綴りが二つあると、grep と diff の両方で敵になる。

**捨てたもの**：

- **YAML / TOML への埋め込み**：二次元の表をネストで書くと列の対応が視覚から消え、P2 が死ぬ。
- **CSV**：型宣言とメタデータの置き場がなく、引用符の規則が業務担当者に説明できない。
- **DMN XML**：diff 不能。借りるのは意味論だけで、交換形式は借りない（前提のとおり）。
- **Markdown 文書内埋め込み（literate 形式）**：地の文と表の境界の規則が増えるだけで、表自体の可読性は上がらない。

### 1.2 ファイルの構造

一つの `.rule` ファイルが一つの規則（一つの生成関数）である。
構造は上から、ヘッダ、取込、型と群、入力、出力、定義と表の列、結果、例、の順で固定する。
全体のスケッチを示す。以降の節はすべてこの例を参照する。

```
規則 送料(shipping_fee) v4
説明 "通常便の送料。2026-04 の運賃改定を反映"

取込 標準/都道府県

型 会員区分(member_kind) = 一般(basic) 既定扱い | ゴールド(gold) 既定扱い | プラチナ(platinum)
群 遠隔地 = 北海道 ・ 沖縄

入力
  届け先(dest)    : 都道府県
  重量(weight)    : 質量[g]         範囲 >=1g <=40kg
  注文金額(total) : 金額[円, 税込]   範囲 >=0円 <=1000万円
  会員(member)    : 会員区分

出力
  送料(fee) : 金額[円, 税込]  丸め 切り上げ(10円)

定義 大口 : 真偽 = 注文金額 >= 3万円

表 基本送料
方式 一意
| 届け先       | 重量    | → 基本送料 : 金額[円, 税込] |
| 遠隔地       | <=2000g | 1200円 |
| 遠隔地       | >2000g  | 1800円 |
| 以外: 遠隔地 | <=2000g |  800円 |
| 以外: 遠隔地 | >2000g  | 1100円 |

表 負担判定
方式 上から
| 大口 | 会員     | → 負担率 : 率 |
| 真   | -        | 0%   |
| -    | プラチナ | 50%  |
| -    | -        | 100% |

結果 送料 = 基本送料 × 負担率

例
| 届け先 | 重量  | 注文金額 | 会員     | → 送料 |
| 沖縄   | 2500g | 40000円  | 一般     | 0円    |
| 東京都 | 1999g | 12000円  | プラチナ | 400円  |
```

`例` は実行される仕様である。
`rulec check` が参照評価器で全行を検証し、外れたら発火行つきでエラーを出す（E107）。
例の期待値は全出力について必須で、列の欠けはエラーにする（空セルと同じ理屈で、書き忘れを沈黙にしない）。
例は三者一致の盲点を破る唯一の楔でもある。
評価器と両生成器が同じ誤りを共有すると三者一致は緑のまま通すが（複数出力の丸めが三方で揃って落ちていた実測）、人が書いた期待値だけがそれと食い違える。
出力と同名の中間値が存在するなら、その出力の `結果` は省略できる（表が一つだけの規則が典型で、複数出力でも出力ごとに効く）。

### 1.3 日本語識別子と ASCII 別名

**決定**：識別子は日本語を許す。ASCII 別名（丸括弧で併記）が必須なのは、公開 API に出る名前だけとする。すなわち規則名、入力、出力、そして入出力の型に現れる列挙型とその値である。内部に閉じる名前（群、表、定義、導出、内部でしか使わない型）の別名は任意で、省略すると生成コードも日本語識別子をそのまま使う。表の中身（セル）と例は常に日本語だけで書く。

Go の公開識別子は先頭が Unicode の大文字である必要があり、漢字とかなは大文字を持たないため公開名になれない[^go-export]。
つまり公開面には ASCII 名が必須で、その名前は宣言時に人間が一度だけ決めるのが、レビュー可能性ともっとも安い。
一方、非公開の位置には大文字要件がなく、漢字かなの識別子は Go でも Python でも合法である。
内部名にまで別名を要求する理由は、生成の都合には存在しない。

実測がこの線引きを与えた。
ゆうパック運賃 84 行に別名は 23 個要り、うち公開面に出るのは 5 個（規則名 1、入力 3、出力 1。都道府県は標準取込が別名込み）だけだった。
残り 18 個はヘッダを埋めるだけで、v0 の「全宣言で必須」はこの実測で捨てた。
公開面に別名が欠けているときは、エラー（E011）が不足している名前の一覧と書き足す位置を示す。

**捨てたもの**：

- **自動ローマ字化**：漢字の読みは辞書依存で、「届け先」が `todokesaki` になるか `delivery` になるかを機械が決めた結果は誰もレビューしない。
- **識別子を英語に限定**：セルまで英語になり、P2 の「業務担当者が読める」が崩れる。
- **全宣言での別名必須（v0 案）**：実測で 8 割が公開されない内部名だった。書かせる理由が測って消えた。

[^go-export]: Go 言語仕様の exported identifiers の定義による。先頭文字が Unicode uppercase letter（Lu）であることが公開の条件で、CJK 文字は Lo に属する。非公開識別子に大文字要件はないため、内部の関数名や型名は漢字かなのままで合法である。

### 1.4 Excel と CSV からの取り込み

**決定**：構文レベルでは考慮しない。`rulec import xlsx` と `rulec import csv` が一方向に `.rule` の草稿を生成し、人間がレビューして確定する。`.rule` から Excel への逆方向は作らない。

双方向同期を始めた瞬間に Excel が正本になり、GUI モデラへの一本道が始まる（P7）。
既存の Excel ルールは移行の入口としてだけ扱う。

### 1.5 git diff の読みやすさ

**決定**：`rulec fmt` を唯一の整形器とし、CI で `rulec fmt --check` を強制する（gofmt と同じ運用）。列は表ごとに内容最大幅へ揃え、文字幅は East Asian Width の W と F を 2、それ以外を 1 として数える。全角数字は半角へ、比較記号 ≦ ≧ ＜ ＞ は `<= >= < >` へ、セルの集合区切りは `・` へ正規化する。

既知のコストとして、列の最大幅が変わる編集は表全体を再整列させ、diff が表全体に及ぶ。
再整列は表の中に閉じるので許容し、PR レビュー向けには `rulec changes --base <rev>` が空白を無視した行単位の構造差分（追加行、削除行、変更行、新たに生じた遮蔽）を出す。

列幅はヘッダを含む全行の内容最大幅で取る。
出力列のヘッダは型注記を含めて長く（`→ サイズ(size) : サイズ区分` で 27 桁）、値が数桁しかない列がヘッダ幅まで膨らむ。
M0 の実装で見えたこの不格好さは、承知の上で受け入れる。
ヘッダを幅から外す案と、型注記だけ溢れさせる案は、パイプの位置が行ごとに変わって本節の唯一の目標を壊すので捨てた。
そしてヘッダが幅の天井になることには実利がある。
日常の編集（値の修正、行の追加）はヘッダ幅を超えない限り再整列を起こさず、diff が 1 行に閉じる。
余白は、値の編集を局所 diff に保つための買い物である。
転記の現場で実害が出たら、型注記をヘッダの外の行に出す構文変更が指定の逃げ道で、実害が測れるまでは動かさない。

`#` コメントの正準位置もここで凍結する（実装で決めた規則の追認）。
表の行では、最後の `|` より後ろにあるものを行末コメントとして切り離し、整形後の行に空白二つを挟んで付け直す。
表以外の行は、コメントを含めてそのまま残す（行末の空白だけ落とす）。
表の行の途中に `#` を書くと行の残りが消えて列数の不一致になり、構文エラーとして捕まる（静かに欠けることはない）。

数値リテラルは `3万円` `1000万円` の万・億接尾辞と `10_000` の下線区切りを許す。
桁区切りのカンマは、セルの集合区切りと衝突するので許さない。

版と履歴は git に任せる。
ヘッダの `v4` は人間向けの目印で、rulec は生成物ヘッダへの転記だけに使う。
CLI の `送料@v3` という参照は、git タグ `rules/送料/v3` を引く糖衣とする。

## 2. 型システム

### 2.1 型の一覧

- **列挙**：閉じた有限集合。`型 会員区分(member_kind) = 一般(basic) | …`。開いた列挙は存在しない。値が増えたら網羅性検査が既存の表を割る。これが P4 の網羅性の動力源になる。値には `既定扱い` を付けられ、「専用の行を持たず、既定の行に落ちるのが意図」を宣言する（付ければ W111 が名指しの無さを問わなくなる。§11）。§1.2 のスケッチでは、プラチナだけが特別で残り二値は既定、という業務の形がこの印で読める。
- **群**：列挙の名前つき部分集合。`群 遠隔地 = 北海道 ・ 沖縄`。セルで値と同格に使える。検査時には常に展開される。実測では 47 都道府県 × 7 サイズ = 329 通りが群で 42 行に縮み、さらに群の分割が 47 県の完全な分割になっているかを網羅性検査が保証した。転記の作業そのものが検査される。
- **導出**：入力だけの線形結合（整数定数倍と加減のみ）で定める名前つきの数量・金額。`導出 残余 : 金額[円, 税込] = 商品合計 - 適用済割引 - 額面  範囲 …`。`範囲` 宣言必須。数量のまま表の列に置ける唯一の中間値で、本体は §5.2 と §6.2。
- **数量**：次元と単位を持つ整数。`質量[g]`。同一次元内の単位換算はリテラルの厳密な整数換算だけ（`2kg` は `2000g` の糖衣）で、実行時値は宣言単位の整数一本である。
- **金額**：`金額[円, 税込]`。通貨と税区分の二重 brand。税込と税抜の演算は型エラーで、変換演算子は用意しない。税率とその丸めは業務ルールそのものなので、必要なら表として書かせる。円と銭は別単位で、混ぜるには明示の丸めが要る。
- **率**：無次元。リテラル `3%` `0.5%` は正確な有理数として扱う。入力にする場合は `率[刻み 0.1%]` と分解能を宣言させ、実行時表現を整数に保つ。
- **真偽**：`真` と `偽`。
- **文字列**：等値と集合一致だけ。パターン一致は持たない（§15-1）。
- **日付**：タイムゾーンを持たない暦日。比較と範囲だけで、加減算は持たない。JST 前提などの解釈は呼び出し側の契約に置く。内部表現は元期からの通算日とする。後者関数が +1 と一致するので、境界の ±1、区間の空判定、隣接の合流が整数の機構のまま正しい。`y×10⁴ + m×10² + d` の形は順序こそ保つが、月末と年末に実在しない整数の隙間を作り、`<=2026-03-31` と `>=2026-04-01` で敷き詰めた自然な表に偽の完全性エラーを出す。証人とベクタの ±1 は 1 日を意味する。
- **optional**：`T?`。セルの `無し` でだけ消費でき、式には現れない。式に来る前に表で場合分けさせることで、null を算術から締め出す。
- **未丸め**：数量と金額の演算が作る、静的スケールつきの中間型。ユーザが書く構文は無く、推論でだけ現れる（§2.3、§7）。

完全な次元解析はやらない。
次元の掛け合わせ（円×g のような合成次元）が業務ルールに現れたら、それはモデリングの誤りとしてエラーにする。
必要なのは brand の混同防止までで、そこで止める（前提のとおり）。

### 2.2 宣言場所と範囲宣言

**決定**：型はファイル内宣言と `取込` の二段だけ。`取込` はパスを引数に、型、群、単位の宣言だけを取り込む。表と定義は取り込めない。組み込みの `標準/` 名前空間に、都道府県（47 値、ASCII 別名込み）、質量（g、kg）、長さ（cm、m）、金額（円、銭）、率、日付を同梱する。都道府県の別名はヘボン式で長音を落とす表記（Hokkaido、Oita）で凍結した。訓令式にしないのは、自治体の英語表記の慣行に合わせるためである。

数量、金額、率、日付の入力と、すべての導出には `範囲` 宣言を必須とする。
入力の範囲は三役を兼ねる。
オーバーフロー証明の前提（§7）、網羅性検査の全体集合（40kg 超の行を書かなくてよい根拠）、生成コードの入口ガード（§8）である。
上限のない金額入力は業務にも存在しないので、書かせることが仕様の発掘になる。
導出の範囲は検査の軸の全体集合になり、健全性のための包含条件を負う（§6.2）。

**捨てたもの**：**中央型レジストリ**（リポジトリ横断の型サーバのようなもの）。ファイルと取込で足りる規模の道具に、名前解決のインフラを持ち込まない。

### 2.3 演算規則

| 式 | 結果の型 | 備考 |
|---|---|---|
| 金額 ± 金額（単位・税区分が同一） | 金額。丸め済＋丸め済は丸め済、未丸めが混ざれば未丸め | 税込と税抜の混合は E103 |
| 金額 × 整数定数 | 左と同じ丸め状態 | 厳密 |
| 金額 × 率 | 未丸め金額 | スケールが積になる |
| 金額 ÷ 正整数定数 | 未丸め金額 | |
| 金額 ÷ 金額定数（同単位・同税区分） | 未丸め無次元数 | 「100円につき1点」用 |
| 数量 ± 数量（同次元） | 数量 | 単位換算はリテラル位置のみ |
| 数量 × 率、数量 ÷ 定数 | 未丸め数量 | |
| 数量 ÷ 数量定数（同次元） | 未丸め無次元数 | 「100gごとに」用 |
| 率 ± 率、率 × 率 | 率 | 厳密な有理数 |
| 比較 `< <= > >= =`（同型） | 真偽 | 未丸め同士も厳密比較（共通スケールへ静的に揃える） |
| 最小(a, b)、最大(a, b)（同型） | 同型 | |
| 丸めモード(式, 格子) | 丸め済 | 未丸めから戻る唯一の道 |

禁止するもの：金額×金額、税込±税抜、異次元の混合、**変数による除算**、日付の加減算。
変数除算を禁じるのは、スケール（§7）を静的に決めるためである。
割る数が業務データなら、それは率か定数表のどちらかとして表に現れるはずで、実際 P1 から P2 の領域（送料、クーポン、ポイント）で変数除算が要る計算を私は挙げられなかった。
挙がったら §15 で扱う。

### 2.4 丸め済と未丸めを別型にする案の是非

**決定**：採用する。ただしユーザに未丸め型を書かせない。演算が値を自動で未丸めへ持ち上げ、丸め関数だけが丸め済へ戻す。

「丸め前の値が出力に漏れない」（P4）は規約では守れず、型でしか守れない。
一方で型を二重にする複雑さは実在するので、その支払いを書き手ではなく検査器に寄せる。
書き手が未丸め型に出会うのは、丸めを書き忘れたときのエラーメッセージの中だけである（E104、§11）。

**捨てたもの**：**丸めを暗黙適用して型を一本化する案**。表の出力セルに `805円` と書いたとき、出力宣言が `切り上げ(10円)` だからと黙って 810 円にする道具は、差分を見る道具として自殺である。リテラルが格子に載っていなければエラーにする（E106）。

## 3. セルに書けるもの

**決定**：セルの単項テストは次の七種で全部である。空セルは構文エラー。テストの対象になる列は、入力、導出、真偽と列挙の中間値である（§5.3）。

1. `-`：don't-care。任意の値に一致する。don't-care の表記はこれ一つだけで、空欄を don't-care と解釈しない（書き忘れと区別がつかなくなる）。
2. リテラル一致：列挙値、`真` `偽`、`2000g`、`1200円`、`2026-04-01`、`"WELCOME10"`、`無し`。数量と金額のリテラルには単位が必須で、裸の `2000` はエラー（「2000g ですか」と聞き返す）。
3. 集合：`北海道 ・ 沖縄`。いずれかに一致。要素はリテラルか群名。
4. 補集合：`以外: 北海道 ・ 沖縄`。集合にも群にも付けられ、意味は宣言された全体集合に対する補集合で、行単体で閉じている。
5. 比較：`<=2000g` `>2000g` `>=2025-04-01` など四種の演算子。全角の ≦ ≧ ＜ ＞ も受け、fmt が正規化する。
6. 区間＝比較の並記：`>=1000円 <20000円`。空白区切りは連言。空区間は型エラー。
7. optional 列に対する `無し`。比較とリテラルは値が在るときだけ一致し、`無し` には `-` と `無し` だけが一致する。

### 3.1 境界の開閉の表記

**決定**：範囲は必ず比較演算子で書く。`..` を使った範囲記法は、片側でも両側でも構文エラーにする。

当初スケッチの `..2000g` と `2000g..` は、この道具がいちばん守りたい場所に曖昧さを残す。
「2000g まで」は日本語では両端含みに読めるが、`..2000g` を含みに解釈すると隣の `2000g..` と 2000g ちょうどで重なり、排他に解釈すると業務の読みと 1g ずれる。
数学の `[0, 2000)` は開閉が正確だが、括弧の向きの規則を業務担当者に教えることになる。
比較演算子は全員が既に読めて、開閉の解釈が一意で、教えることが何もない。

隣接する行を `<=2000g` と `>2000g` で書けば敷き詰めは目で追える。
`<=2000g` と `>=2000g` と書き間違えれば、重複検査が「重量=2000g が両方に当たる」という証人つきで捕まえる（E105）。
境界の曖昧さを構文で禁じ、貼り合わせの誤りを検査で拾う、という分担である。

**捨てたもの**：

- **半開区間を既定にする案**（`a..b` を a 以上 b 未満と定める）：敷き詰めは美しいが、「まで」の直感と静かに 1 単位ずれる。静かにずれる仕様は、この道具では最悪の性質である。
- **セル内の区間の合併**（`<500g ・ >30kg` のような書き方）：行を二つに分ければ書ける。実測（運賃表とクーポンの転記）で必要になった箇所は 0 件で、v1 から外すことが決着した（旧 §15-1）。
- **列をまたぐ条件をセルに書くこと**：セルは自列への単項テストに限る。複合条件は `定義` で名前を付けて真偽列にするか、入力の線形結合なら `導出` にする（§5.2）。この制限が検査の決定可能性の土台になる（§6）。実測でいちばんきつい試金石は、ヤマトの「3 辺計と実重量を比較し、大きい方のサイズの扱いになる」規約だったが、列ごとの単項テストと `上から` でそのまま書けた。50cm/8kg の荷は 60 サイズ行を重量で外れ、80 も外れ、100 で当たる。
- **正規表現・前方一致**：クーポンコードの実形式を見るまで入れない（§15-1）。実測の公開規約では、文字列そのものが列に一度も現れなかった。
- **セル内のパス式・量化子**（`注文.配送先.都道府県`、`some … satisfies …`）：実在の DMN 業務資産（伊 ANAC の調達規則）はセルが任意の FEEL 述語で、我々はヒットポリシー以前にセルの言語で受け付けない。それでよい（§0）。入れ子は境界で平たい入力に潰してから渡し、セルには入れない。射影の宣言と生成という拡張候補は §15-6。

### 3.2 出力セルに書けるもの

**決定**：出力セルにはリテラルのほかに、名前（入力、導出、定義）を書ける。式は書けない。

リテラル限定では書けない規則が実在する。
楽天の複数クーポンは「％引きクーポンを先に適用し、その後円引きクーポンを適用する。パーセンテージ割引は商品の元価に対して計算される」という規約で、クーポン種別によって割引の基準額が変わる。
率引き行の出力は「元価 × 割引率」という計算値であり、リテラルでは書けない。
リテラル限定のまま逃げるなら率クーポン規則と額クーポン規則にファイルを割ることになるが、どちらを呼ぶかの判断がホスト言語へ漏れる。

式そのものをセルに許さないのは、表を眺めて桁が読める性質を保つためである。
計算には `定義` で名前を付けさせ、セルからは一往復で辿れるところに置く（§5.4 のスケッチにこの形がある）。
名前の丸め状態は列に合流し（どれかが未丸めなら列は未丸め）、E106 の静的な格子検査はリテラルにだけ適用する（§7.2）。
領域解析は入力側の列だけで行われるので、この拡張は完全性にも重複にも影響しない。

名前の先の `定義` がさらに前の定義を参照する連鎖は、構文上は無制限である。
それでも機械的な深さ制限は置かない。
コーパスの実測は深さ 1 で、根拠なく選んだ上限は恣意にしかならないからである。
深い連鎖が実表に現れたら、そのとき件数を数えて W 系の lint として決める。

**捨てたもの**：

- **出力セル内の式**：表が計算式の置き場になり、P2 の可読性が崩れる。名前を一つ挟む往復が、複雑さの上限として働く。
- **表出力の名前参照**：`結果` で書けることと重複する。拡張は実測が要求した最小に留めた。

## 4. ヒットポリシー

**決定**：採用は二つ。`方式 一意`（DMN の Unique）と `方式 上から`（DMN の First）。既定は `一意`。単一ヒットの二方式だけを採るので、完全性は全表で常に必須とし、宣言項目にしない（この不変が単一ヒットの性質であることは本節末尾に記す）。

`一意` は解析がもっとも強く効く方式で、行の重なりはすべてエラーになる（E105）。
順序に意味がないので、行の並べ替えが意味を変えない。
既定を `一意` にするのは、順序依存を書き手に意識して選ばせるためである。
実測でも二方式は同一ファイルの中で共存した。
ヤマトのサイズ判定は階段なので `上から` が合い（`一意` で書くと `>60cm <=80cm` の区間並記になり、同じ境界を二度書くことになる）、運賃表は重なりようがないので `一意` である。

`上から` は「例外を先に、一般則を後に」という業務の書き方をそのまま受けるために要る。
最後に全部 `-` の行を置く書き方が既定行になる。
`上から` でも完全性と死行（先行行に完全に覆われて決して当たらない行、E102）はエラーである。

部分的な遮蔽の扱いは、M0 の実装が教えた事実で設計を直した。
v1 は「遮蔽はすべて証人つきの注記（W105）」としていたが、階段表ではそれが信号にならない。
ゆうパックのサイズ判定は 7 行の階段で 21 対すべてが重なり、しかも階段は出力が全部違うのが正常なので、「出力が同じ重なりは冗長」という文言の区別も効かない。
`--diff-base` も、階段への 1 行追加で良性の新規対が 6〜7 個まとめて出る。
そこで `上から` の遮蔽対を三つに分類する。

- **構造的**：後の行の領域が前の行の領域を包含する（交わりが前の行の領域そのもの）。階段と既定行がこれで、`上から` を選んだ時点で書き手が意図している構造である。既定では件数だけ報告する。
- **同値**：包含でない部分交差だが、両行の出力が同じ。「〜なら不可」を並べる守り行が互いに交わる形で、どちらが勝っても値は変わらない。既定では件数だけ報告する。
- **要確認**：包含でない部分交差で、出力が異なる。順序が円を変える唯一の形で、これだけを証人つきで一覧する（W105）。合意した五つ目の文面「意図通りですか」の仕事は、この分類が引き継ぐ。

この分類で、ゆうパックの 21 対は全部が構造的、クーポンの適用可否の 10 対は構造的 4 と同値 6 になり、どちらも一覧はゼロになる。
例（§1.2）の負担判定の 行1×行2（0% と 50%）は要確認として残る。
黙る二分類には安全網が残っている。
階段の並びの事故は包含の向きが逆転して死行になるから、注記ではなく E102（エラー）が捕まえる。
同値の対は、片方の出力を後で変えた瞬間に要確認へ遷移して一覧に現れる。
全対は `--show-shadow` で一覧でき、既定の出力は「遮蔽 21 対（構造的 21、同値 0、要確認 0）」という件数の注記になる。
CI の `rulec check --diff-base <rev>` は要確認の対の集合で差分を取り、新たに生じた分（同値からの遷移を含む）だけを浮かせる。
対の同一性は行番号ではなく、セルの正規形から作った鍵で照合する。
行を挿入しても fmt が再整列しても鍵は変わらず、既知として伏せた対があるときは伏せた件数を言う。
遮蔽の既知集合をファイルに書かせる案（行番号での承認リスト）は、行の挿入で番号が静かにずれる罠なので捨てたままである。
状態は git の履歴に置き、rulec 自身は無状態を保つ。
逆向きの検査（重なりが一つもない `上から` に `一意` を提案する W110）は、実装の初回から有用だった。

当初スケッチにあった `完全性 = 必須` という宣言は落とした。
宣言できるなら宣言し忘れが生まれ、既定 OFF の網羅性検査は P4 に反する。
穴を許したい表は書けない。それがこの道具である。

公開の実使用も測った（2026-08、GitHub のコード検索。`.dmn` 17,536 ファイル、数字は一致ファイル数）。
FIRST 4,568、UNIQUE 2,384（宣言なしの約 8,000 は既定の UNIQUE なので、実質シェアは 6 割前後）、COLLECT 1,720、PRIORITY 518、ANY 326、RULE_ORDER 2、OUTPUT_ORDER 0。
採用した二方式が実使用の一位と二位で、捨てた側では COLLECT だけが突出する（PRIORITY と ANY の合計の 2 倍）。
ただしこの数字には限界が三つある。
一ファイルに複数の表が入りうること、コード検索の順位が非ランダムなこと、そして企業の DMN は SaaS の中にあって公開リポジトリに出てこないこと。
一番知りたい母集団が、最も薄い。

**捨てたもの**：

- **A（Any、326 件）**：出力が同じなら重なりを許す方式。今日同じでも明日の編集で片方だけ変わる。重なりは冗長でも検出したい対象（Calvanese らの言う redundancy）で、表現力も増えない。重なりの出力が一致している表は、行をそのまま `上から` に写せば同じ関数になる。
- **P（Priority、518 件）**：優先順位が出力値の順序という別の場所に書かれる。優先は紙面の上下で見えるべきで（P4）、行を優先順に並べ替えれば `上から` がそのまま P である。表現力は増えない。
- **C（Collect）と集約**[^dmn-multi]：実在する（上の調査で 1,720 件）。ただし出所を深いページで 200 件掘ると 51% がエンジンやツール由来で、業務モデルの候補は 26%、うち 6 割は伊 ANAC（反汚職庁）の一つの調達規則集だった。その実物と英 HMCTS のタスク設定が C で行っているのは「当てはまる項目を全部集める」＝検証であって、金額の集約ではない。つまり C の採否はヒットポリシーの選択ではなく、検証という別の仕事を範囲に入れるかどうかの決断である。単一の値を計算する道具でいる限り、要らない。前回ここに書いた「実測のクーポン転記でも集約は要らなかった」は撤回する。書けるように書いた自選の二表から、必要性の不在は導けない（測り直しは §15-8）。クーポンの重ね掛けが粒度の構成で書けること自体（§5.4）は、構成を示した事実として残る。

C を入れる日に何を失うかも、ここに記録しておく。
労働基準法の割増賃金は「重なると足す」の教科書例に見える。
時間外 25%、法定休日 35%、深夜 25% で、厚労省の計算例には休日深夜 1.60（1.35 ＋ 0.25）が明記されている。
ところが法定休日労働には時間外という概念がなく、8 時間を超えても 35% のままなので、素朴な合計は休日＋時間外に 60% という違法な答えを出す。
正しく書くには時間外の行に「法定休日 = 偽」という排他を書き込むしかなく、それを書いた瞬間、表は単一ヒットと同じ仕事をしている。
違いは一点だけで、単一ヒットならその排他の正しさを完全性と重複の検査が確かめるのに対し、合計方式では重なりが仕様そのものになるため、どちらの検査も意味を失う。
この道具の検査能力は、単一ヒットの上に立っている。

検証の形の需要も、表現力だけなら今日の道具で書ける。
検査項目ごとに真偽の出力を持たせれば表になり、当たった項目を集めるのはホストの一行で、各項目は網羅と重複の検査を受ける。
C が買うのは簡潔さであって表現力ではなく、支払うのは排他と網羅の保証である。
この取引を受けるかどうかが、上の「範囲の決断」の中身になる。
本節の「完全性は常に必須」と「表は値を一つ返す」は、単一ヒット方式の性質として述べている。
C を入れる日は、この二つの不変を検証の意味論のために作り直す日で、ヒットポリシーを一つ足す変更では済まない。

[^dmn-multi]: DMN の multiple hit にはほかに R（Rule order）と O（Output order）があるが、公開の `.dmn` 17,536 件で R は 2 件、O は 0 件だった。標準に載っていても誰も使わないものは実在する。DMN を全部実装しないという方針の、実測の裏づけでもある。

## 5. 表の合成と中間値

### 5.1 線形パイプライン

**決定**：合成はファイル内で完結する線形パイプラインとする。`導出`、`定義`、`表` は上から順に名前を導入し、後のものは前の名前だけを参照できる（define-before-use）。最後の `結果` が出力を束ねる。DRD に相当する図は作らない。

前方参照を許さないので循環は構文的に存在せず、ファイルを上から読めば依存が読める。
ファイルの並び順そのものが DRD である。
規則が図を要するほど育ったら、それは規則の分割が要る徴候として扱う。

実測では運賃が実際に 3 段の連鎖（県から地帯へ、地帯とサイズから運賃へ）を要求した。
発地と着地の対応は静的な部分集合である群では表せず、表の連鎖でだけ書ける。
最大の表は 144 行、列 3 で、§6.3 の設計目標の内側の規模だった。

表は複数の出力列を持てる。
意味はタプルで、各出力が独立の名前と型を持つ。
`→` は入力と出力の境目を一度だけ示す印で、最初の出力列に付ける。
境目より後ろの列は、印の有無にかかわらずすべて出力である（パーサは余分な `→` も受け、fmt が正準形に畳む）。
列ごとに印を要求する v0 の形は、二列目の印の書き忘れが列を黙って入力へ化けさせた実測（M1 の例の検査）で捨てた。
例も同じ綴りで、出力が複数なら期待値の列を出力の数だけ並べる。

規則から規則を呼ぶことはできない。
上流の規則の答えが要るなら、それは入力として宣言し、呼び出し側が渡す。
これは P3 の「外から来るものはすべて入力」の合成への一般化で、二つの利益がある。
規則単位で過去再生が閉じる（送料の replay にクーポンの実装が要らない）ことと、規則間の版の組合せ爆発を呼び出し側の責任に置けることである。

### 5.2 導出

**決定**：「導出」を入力、定義、表出力に並ぶ第四の名前つき値として一級にする。右辺は入力だけの線形結合（整数定数倍と加減のみ）で、上流の表の出力も定義も使えない。`範囲` 宣言必須。数量・金額のまま表の列に置ける。

```
導出 残余(margin) : 金額[円, 税込] = 商品合計 - 適用済割引 - 額面
  範囲 >=-110万円 <=100万円
```

なぜ要るか。
実測で、値引き後の金額で判定する規約が二件見つかった。
楽天は送料無料ラインをクーポン利用前の購入合計で判定する一方、39 キャンペーンのポイント条件はクーポン適用後の金額で判定する。
同一プラットフォームの中で、特典ごとに判定の前後が違う。
Yahoo には「値引き額が商品合計を上回るか同額ならクーポンは適用されない」という判定がある。
どちらも「入力 − 入力」の線形結合で、これを列に書けないと、値引き後という一番間違えやすい引き算が呼び出し側の裸の一行になり、単位も税区分も丸めも検査されない。
OSS の EC 実装にも同じ形がある。
Saleor はカタログ割引を先に計算し、その後の価格にオーダー割引を適用する。
値引き後の金額を次の判定と計算が使う形の、これで三例目である。

なぜ線形結合までか。
実測で列に要求されたのは線形結合だけで、率 × 金額のような非線形は `結果` と `定義` にしか現れなかった。
そして線形結合なら、検査の決定可能性を箱代数のまま保てる（§6.2）。
整数定数倍と加減は丸め済のまま閉じて厳密な int64 で計算できるので、丸めの新しい場所も生まれない（§7.1）。

範囲宣言は検査の軸としての全体集合になる。
宣言は、入力範囲から区間演算で計算した到達区間を含まなければならない（E112）。
含まないと網羅性検査が実際に到達する値を見ず、不健全な緑が出るからである。
到達区間より広い分は実現不能領域として篩われるので害はない（§6.2）。

### 5.3 列に使える値と真偽定義の原子

**決定**：表の列に使えるのは、入力、導出、そして真偽と列挙の中間値（定義と表出力）である。数量と金額の中間値（表出力と一般式の `定義`）は列に使えず、`結果` と式の中でだけ使える。真偽の `定義` の原子は二形。セルの単項テスト（§3）を入力か導出に適用したものと、導出で差の取れない型（日付、列挙）に限った同型の入力・導出どうしの比較（`A期限 <= B期限`。日付は四種の比較、列挙は等値。型の一致は §2.3 に従う）である。数量・金額・率どうしの直接比較は E113 のままとし、差を導出として宣言してから定数と比べさせる。そのほうが厳密に解析できるからで、精度の規律（下記）が数値には導出という正しい家を既に持っている。連言、選言、否定を許す。名前どうしの比較はセルには書けない（セルは単項のまま）。

v0 草案にはここに抜け道があった。
数量の定義（`適用後金額 = 注文金額 − 割引額`）を真偽の定義（`適用後金額 >= 3980円`）が参照でき、その真偽が列に置けたので、`x − y >= c` という半空間が列に入り込み、§6.2 の「定義は DNF 展開で箱和になる」が原子の形の前提ごと崩れていた。
原子を入力と導出に制限することでこの穴を塞ぐ。
線形結合が要るなら導出として宣言させ（E113 が書き換えを提示する）、表出力との比較が要るなら、その表に真偽の出力列を足すのが正しい書き方である。

名前どうしの比較の原子は、適用順序の規則が要求した。
§5.4 の「期限が近い順」は二つの日付入力の比較そのもので、日付に減算が無い以上、導出（差を取って定数と比べる形）では書けない。
これを許しても検査は壊れない。
真偽の定義は解析では自由な真偽軸として扱われ（§6.2）、原子の形が何であれ扱いは変わらないからである。
一方、数量の定義への参照を禁じる E113 は残る。
自由軸として健全に扱えるかどうかの問題ではなく、導出にすれば厳密に解析できるものを、怠けて不透明にさせないという精度の規律である。

### 5.4 規則の粒度

**決定**：規則の粒度は「一回の判定」に固定する。可変個数のものを規則の中で畳み込まない。リスト型も集約も導入しない。

クーポンは可変個数で、併用の順序があり、枚数の制約がある。
これを解くのはリスト型ではなく粒度である。
規則は「このクーポン 1 枚は適用できるか、いくら引くか」を答える純関数で、重ね掛けの順序と反復は呼び出し側が持つ。
順序が呼び出し側にあるのは欠点ではない。
順序こそが業務判断であり、規則の中に隠すべきではないからである。

適用順序そのものも規則として書ける。
楽天の「％引きが先、円引きは有効期限が近い順」は、`(A種別, B種別, A期限, B期限) → 先/後` という二引数の純関数になり、呼び出し側はこれを比較関数としてソートに渡す。
反復はホスト、判定（比較を含む）は規則、という分担が一貫する（期限の比較は、真偽定義の名前どうしの比較の原子で書く。§5.3）。
有効期限の比較が要るので、日付型は v1 に入る（旧 §15-7 は逆向きに決着した）。
併用の制約も入力で書ける。
「対象商品指定クーポンは同一商品に 2 枚以上使えない」は、`同商品適用済 : 真偽` を入力にすれば表になる。
状態はホストが持ち、P3 のままである。

クーポン 1 枚の規則のスケッチを示す。
導出（§5.2）と出力セルの名前（§3.2）もここに現れる。

```
規則 クーポン一枚(coupon_step) v1
説明 "クーポン1枚の適用可否と素割引。重ね掛けの順序と反復は呼び出し側が持つ"

型 クーポン種別(coupon_kind) = 率引き(percent) | 額引き(fixed) | 送料無料(free_ship)

入力
  商品合計(subtotal)  : 金額[円, 税込]  範囲 >=0円 <=100万円
  適用済割引(applied) : 金額[円, 税込]  範囲 >=0円 <=100万円
  種別(kind)          : クーポン種別
  割引率(rate)        : 率[刻み 1%]     範囲 >=0% <=100%
  額面(face)          : 金額[円, 税込]  範囲 >=0円 <=10万円
  同商品適用済(dup)   : 真偽

出力
  可否(ok)     : 真偽
  素割引(raw)  : 金額[円, 税込]  丸め 切り捨て(1円)  # 端数処理は公開規約に記載なし。切り捨てに仮置き

導出 残余(margin) : 金額[円, 税込] = 商品合計 - 適用済割引 - 額面
  範囲 >=-110万円 <=100万円

定義 率割引 : 金額[円, 税込] = 商品合計 × 割引率

表 適用可否
方式 上から
| 種別   | 残余  | 同商品適用済 | → 可否 : 真偽 |
| -      | -     | 真           | 偽 |
| 額引き | <=0円 | -            | 偽 |
| -      | -     | -            | 真 |

表 素の割引
方式 一意
| 可否 | 種別     | → 素割引 : 金額[円, 税込] |
| 偽   | -        | 0円    |
| 真   | 率引き   | 率割引 |
| 真   | 額引き   | 額面   |
| 真   | 送料無料 | 0円    |
```

二つの出力はどちらも同名の中間値を持つので `結果` は省略されている（§1.2 の糖衣）。
`素割引` 列は、リテラル（丸め済）と `率割引`（未丸め）が合流するので列として未丸めになり、出力宣言の `切り捨て(1円)` が一度だけ掛かる（§7.2）。

畳み込みそのものを宣言にする案（順序規則、一段の規則、アキュムレータを指定し、参照評価器が畳み込みまで実行する形）は、ここで検討して v1 では見送った。
宣言にすれば検査の網（三者一致、過去再生）が畳み込みまで届き、手書きの fold のバグはこの網のどれにも掛からないから、魅力は本物である。
見送りの決め手は、単一アキュムレータの畳み込みが、動機になった当のクーポンをまだ表せないことにある。
併用制約の入力 `同商品適用済` は「これまでに適用したクーポンの対象商品の集合」から来る状態で、残額一本のアキュムレータからは導けない。
塞ぐ道は二つしかない。
段ごとにホストが状態を注入する形は、畳み込みが閉じなくなり、評価器が実行できるという肝心の利点そのものが消える。
アキュムレータに集合を許す形は、コレクションが型システムに入り、P7 への圧力になる。
どちらも、実畳み込みの根拠が楽天の一件だけの今に払う理由がない（採否の測定は §15-5）。

それまでの緩和として、**連鎖の例**の慣行を置く。
連続する `例` 行で一続きの場面を書き、行 k の `適用済割引` に行 k−1 までの結果を手で入れる。
評価器が各段を検査し、ホスト両実装の端から端までのテストが同じ表を fixtures として共有できる。
新しい構文はゼロで、畳み込みの「データとしての仕様」だけが規則側に残る。

**捨てたもの**：

- **DMN DRD 相当の規則間依存グラフ**：GUI モデラの引力の中心。ファイル内線形で書けない規則は分割の合図とみなす。
- **規則間 `取込`（表の再利用）**：共有したくなるのは型と群で、実際に共有できるのもそこまで。表の共有は「どの版を共有しているのか」問題を持ち込む。
- **リスト型と規則内の畳み込み**：可変個数は粒度で規則の外に出す（§5.4）。ただし値引きの明細行への按分（端数の再配分）は実測に現れておらず、この粒度で書けるかは未検証として残る（§15-7）。

## 6. 検査の実装方針

### 6.1 何を検査するか

先に、全検査に共通する保証の向きを固定する。
**見逃さない**。
緩めるときは常に過剰報告の方向へ緩め、不健全な緑（実際には成り立たない「検査済み」）はどの検査も出さない。
この改訂で入った変更（導出の軸化、実現可能性の篩、実現可能性未検証の札）はすべてこの向きに倒してあり、以降の各所で個別に確認する。

- **E101 完全性**：どの行にも当たらない入力領域の検出。導出が入っても健全なまま（§6.2）。
- **E102 冗長**：決して当たらない行の検出（`上から` では先行行への完全被覆、`一意` では到達不能な上流値も含む）。
- **E105 / W114 / W105 重複**：同じ入力に複数行が当たる状況の検出。`一意` では実在を確認できた重なりだけが E105（エラー）で、確認も反証もできなかった重なりは W114（警告）に落ち、生成コードの番人が引き受ける（§6.2、§8.1）。`上から` は遮蔽注記（W105）。出力が異なる重なり（矛盾の恐れ）と同じ重なり（冗長）は文言を分ける。Calvanese らの contradiction と redundancy の区別[^calvanese]に対応する。偽陽性が出うるのは導出が絡む場合に限る（§6.2）。

[^calvanese]: Calvanese, Dumas, Laurson, Maggi, Montali, Teinemaa. "Semantics and Analysis of DMN Decision Tables" (BPM 2016, arXiv:1603.07466)。欠落ルールと重複ルールの検出を決定表の幾何として定式化している。検出対象の分類はこの論文に合わせ、実装は下記のとおり独自に決める。

### 6.2 区間の格子で足りるか

**決定**：足りる。SMT ソルバは v1 では使わない。検査の空間を「各入力と各導出を独立の軸とする圧縮座標」に取り、すべてを**箱（直積領域）の有限和**の代数として実装する。導出の従属関係（残余 = 商品合計 − 適用済割引 − 額面 という等式）は空間には入れず、**実現可能性の篩**として発見の報告段で回収する。

まず箱和に閉じる根拠は、§3 と §5.3 の構文制限がちょうど決定可能性の境界に置いてあることによる。

- セルは自列への単項テストしか書けないので、行は「軸ごとの部分集合の直積」、すなわち箱の有限和になる（`以外` と集合は座標の合併）。真偽の `定義` は自由な真偽軸として扱い、原子の中身は領域解析に入れない。当初の設計は DNF 展開で代入する予定だったが、M0 の実装は自由軸で出荷され、これを設計に昇格する。真も偽も到達可能とみなすのは過剰報告の向きで、完全性の見逃しは生じず、E102 は相関起因の死を黙って見送るだけで偽の「決して当たりません」を出さない。行が直積のままなので、遮蔽の包含判定の速い形（§6.3）の前提も保たれる。
- 列に使える中間値は真偽と列挙に限られるので、中間値の各値の逆像（軸空間でその値になる領域）も帰納的に箱の有限和である。上から方式の「行 i が勝つ」も先行行の補集合との交差で、圧縮座標上では補集合も箱和に閉じる。

閉性自体は自明（圧縮格子の任意の部分集合は箱和）で、問題は大きさと、導出を独立軸にしたことで空間に混ざる「実在しない点」（等式を満たさない座標）である。
後者を篩が引き受ける。

- **篩**：箱 B と導出 d = f(入力) について、f を B の入力部分の区間に区間演算で適用した結果が B の d 区間と交わらなければ、B は実現不能。線形な f の区間評価は厳密で、判定は導出 1 本あたり定数時間。ソルバは要らない。
- **完全性（E101）は健全なまま**：軸の全体集合は導出の宣言範囲で、E112 が到達区間の包含を強制するので、実空間の穴は必ず軸空間の穴として現れる。篩は「実現不能と証明できた穴」だけを報告から外す。したがって偽の緑は出ない。証明しきれない実現不能の穴が報告に残ることはある（過剰報告の向き）。
- **重複（E105/W114/W105）**：交差箱にも同じ篩を掛け、実現不能と証明できた発見は出さない。残った発見は、証人の入力を実際に構成して評価器で確認できたかどうかで重大度を分ける。構成できた重なりは実在が確認された矛盾で、`一意` では E105（エラー）。構成できず、実現不能の証明もない重なりは、`一意` でも W114（警告）に落とす。未証明の存在で CI を止めないためである。ただし警告に落とすだけでは足りない。行の排他は生成器が分岐の並びを正当化する前提でもあり、未検証のまま何もしなければ、その重なりが万一実在したとき `一意` が宣言なしの `上から` に静かに化ける。そこで生成コードに**番人**（当該行対の実行時の排他検査）を入れる（§8.1）。両方の行の条件を評価し、同時に当たる入力が来たら黙って先の行を選ばずエラーを返す。静的に閉じなかった証明義務を実行時検査が引き受ける分担は、入力範囲の入口ガードと同じである。出力が構文的に同一の行対は、どちらが選ばれても値が変わらないので番人を省く。`上から` の遮蔽は宣言された順序が解決するので、従来どおり W105 の注記のままで番人も要らない。導出が複数あって入力を共有すると、導出ごとに独立な区間篩は従属を見ないため W114 が出やすくなるが、外れる向きは常に過剰報告で、見逃しは生じない。
- **死行（E102）**：残余箱にも篩を掛け、証明できたときだけ報告する（未証明の「決して当たりません」を断定しない）。残余が空でなくても全箱の実現不能が証明できたなら、「この行に当たる実入力は存在しない」の文面変種で報告する。
- **定義軸の証人**：真偽定義（名前比較の原子を含む）が絡む発見の証人は、入力を構成して定義を評価器で計算し、軸の値と一致することを確かめてから出す。構成できない `一意` の重なりは導出と同じく W114 に落ち、番人が引き受ける（番人の条件は原子を実行時に評価するだけなので、そのまま生成できる）。精度が足りないときの増強も決めてある。単項原子の DNF 代入（当初設計）で、発動条件は自由軸起因の過剰報告が実表で邪魔になること（§15-9）。M0 の篩は導出軸までで、定義軸の証人検証と W114 降格は番人の生成と対で M1 が実装する。それまでの正直化として、定義列が交差に絡む E105 の文面には「この例は定義の中身との整合を確認していません」の一行を足し、証明済みの顔を避ける。

保証の非対称を一行で言えば、**完全性は健全なまま、重複と冗長には偽陽性が出うる。ただし偽陽性はエラーではなく W114 と番人の形で現れ、エラーで止めるのは実在を確認できたものだけ**、である。
導出が 1 本だけの表では篩はほぼ厳密に効く（残るのは整数の粒度による過大評価だけ）。
一方、導出が入力を共有する形は仮定の話ではない。
コーパスのクーポン規則が最初から含んでいる（`最低差` と `支払差` が `現在残額` を共有する。tests/corpus/クーポン割引.rule）。
当の表は `上から` なので W114 の実害はまだ出ていないが、`一意` で同じ形が書かれる前提は既に現実である。
W114 が実表に積もるか、番人に本番で当たりが出たら、そのときの増強も決めてある。
箱の線形制約系への Fourier–Motzkin 消去で、有理数演算のまま厳密、決定的、外部依存なしに実現可能性が正確になる。
v1 には入れない（§15-4）。

数量の中間値（表出力や一般式の `定義`）を列に許すと、行の領域に任意の従属が現れて篩の形にも収まらない。
§5.3 の制限はこのためにあり、v0 ではこの制限に抜け道が実際に開いていた（同節）。
導出は、その表現力のうち実測が要求した部分（入力の線形結合）だけを、篩で回収できる形に限って取り込み直したものである。
非線形の列条件は実測で一度も現れず、旧 §15-3 の SMT 導入案は当面不要と決着した。

### 6.3 アルゴリズムと計算量

- **正規化**：群を展開し、`以外` を補集合化する。真偽の `定義` は自由な真偽軸として加える（§6.2）。導出は独立の軸として加える。上流表の出力（真偽・列挙の中間値）も独立の軸とし、逆像の展開はせず、座標を上流が出力セルで実際に出す値に制限する（M0 の実装判断。値の到達までを見て、組合せの相関は追わない。外れは過剰報告の向きで、E102 の上流値変種は空になった行マスクとして死行検出にそのまま乗る）。各軸の座標を、その軸に現れる全境界値で圧縮する（列挙は値ごと、数値は境界で区切った区間ごとに 1 座標、真偽は 2 座標）。隣接する境界の差が刻み（日付は 1 日、数量・金額は 1、率は宣言の刻み）ちょうどのときは、あいだの開区間の座標を作らない。値を一つも含まない座標は幻の穴になる。通算日への変更だけでは足りないことは、M0 の両端含みの敷き詰めが実測で示した。
- **実現可能性の篩**：発見（穴、交差、残余）の箱数に比例し、1 箱あたり導出本数 × 定数時間。探索予算には効かない。
- **遮蔽の三分類**（§4）：包含の意味は「前の行の領域 − 後の行の領域 = ∅」である。現行の断片では行は軸ごとの部分集合の直積（単一の箱）なので、この判定は軸ごとの部分集合検査と厳密に一致し、実装はその速い形でよい。M0 で領域減算の実装が合成ベンチを落とし（減算は軸数に指数的）、直積の性質に置き換えて三分類の件数の不変を確認した。行が箱の和になる拡張（真偽定義の代入や表出力の逆像を分類に持ち込むとき）では軸ごとの検査は近似になるので、減算へ戻す。篩は掛けず、実現不能な断片のせいで包含が崩れる対は要確認側へ倒れる。外れる向きはここでも過剰報告で、見逃しは生じない。
- **重複と遮蔽**：行対ごとの箱の交差判定。行数 r、列数 c、行あたり箱数 b として O(r²·c·b²)。r が数百、c が十数なら瞬時である。証人は交差領域から、列挙は宣言順の最小値、数値は境界値を優先して選ぶ。
- **完全性と死行**：列を圧縮座標数の昇順に並べた再帰分割で、全体集合から行の箱を引いていく。残り列がすべて don't-care の行が生き残っている部分木は被覆確定として枝を刈る。訪問数の当初の見込み（行数 × 列数に線形）は実測で外れ、行数に対して二乗で伸びる。速度は約 6 万ノード/ms（下の予算の段）。見つかった穴は隣接領域を貪欲に合流させ、点ではなく「届け先 ∈ {離島}、重量は任意」という箱の形で報告する。証人と穴の報告は表の列順で書き、探索の列順（圧縮座標数の昇順）を読み手に見せない。
- **DNF と逆像の膨張**：`定義` の DNF 展開と表合成の逆像展開には上限（例：1 行あたり箱 64 個）を置き、超えたらエラーで表の分割か群化を促す。

爆発時の逃げ道は一つだけ用意する。
訪問ノード予算（既定 5×10⁷、`--budget` で変更）を超えたら、検査は**未証明**としてエラーで止まる。
サンプリングによる近似検査へ静かに縮退することはしない。
不健全な緑は、この道具が存在する理由の否定だからである。
エラーには「どの列の境界数が支配的か」を添え、群化と表分割という現実的な回避先を示す。

実用限界は M0 の合成ベンチで実測した（§15-2 は決着）。
設計目標（列 12、行 500、数値列 4）は 1,004 万ノード、164 ms で収まり、行数を 1000 に倍加すると二乗則どおり約 4 倍（4,075 万ノード、622 ms）だった。
既定予算 5×10⁷ は、設計目標に 5 倍の余裕を取り、使い切っても 1 秒弱で止まる値として実測から決めた。
回帰コーパスの実測は 522、267、7 ノードで、予算の五桁下にいる。

**捨てたもの**：

- **SMT ソルバ（Z3 等）**：v1 の断片には過剰で、証人の決定性（同じ入力に同じ証人）と単一バイナリ配布（§12）を損なう。列の線形条件は導出と篩で取り込み、精度が足りなくなったときの増強も Fourier–Motzkin 消去まで（§6.2）。SMT が要る形（非線形の列条件）は実測で 0 件だった。
- **BDD / MDD**：座標圧縮後の問題規模なら箱代数の素朴な実装で足り、変数順序のチューニングという新しい闇を持ち込むほどではない。ベンチで裏切られたら再訪する。

## 7. 丸めと単位の意味論

### 7.1 実行時表現

**決定**：すべての数値の実行時表現は int64 一本とする。値は r × s（r が実行時整数、s が型に付く静的な正の有理スケール）で、丸め済の型は s = 1 単位、未丸めの型は演算が合成したスケールを持つ。

浮動小数点も任意精度も decimal も生成コードに入れない。
言語間の一致（P5 の等価性）は、両言語が同じ int64 演算を実行することで機械的に成立させる。
`基本送料 × 負担率` は、円の整数 × パーセント整数で「0.01 円」単位の整数になり、スケール 1/100 円が型に記録される。
導出は整数定数倍と加減だけなので丸め済のまま閉じ、スケールを持たない（常に単位の整数一本で、丸めの新しい場所を作らない）。

### 7.2 いつ丸めるか

**決定**：丸めは明示した場所でだけ起きる。場所は三つ。(1) 出力宣言の `丸め`（数値出力には必須）、(2) 表の出力列ヘッダの `丸め`、(3) 式中の丸め関数 `切り上げ(式, 10円)` など。出力宣言の丸めは、結果式が未丸めのときに一度だけ適用される。結果式が既に丸め済なら再丸めせず、格子との整合だけを検査する。

「各表で丸めるか、最終出力で丸めるか」への答えは、**既定では最終出力の一回だけ、中間で丸めたければ書け**、である。
中間丸めの有無は円が動く業務仕様であって、道具が決めてよいことではない。
だから既定をもっとも情報を失わない側（丸めない）に置き、丸めるなら紙面に見える形で書かせる。
旧実装が中間で丸めているなら、等価検証がその差を「丸め差異」クラスタとして出し（§10）、書き手が中間丸めを明示して一致させる。
この往復こそが「差分の主要因になる」ことへの設計上の答えで、丸め位置の違いはすべて `.rule` の diff に現れる。

丸めの計算は、スケール s = p/q と格子 g に対して r·p を q·g' で割る整数除算一回と余りの検査で厳密に実行できる（g' は基準単位に直した格子）。
したがって格子とスケールの整除性のような制約は存在しない。
唯一の制約はオーバーフローで、`範囲` 宣言からの区間演算で int64 に収まることを規則ごとに静的に証明する。
証明できなければエラー（E108）で、中間丸めの挿入か刻みの粗直しを促す。
このエラーは円が動く業務判断を要求するので、文面は §11 の設計対象に含める。

出力セルに名前が書ける（§3.2）ことに伴う規則も、ここで固定する。
出力列の丸め状態は全セルの結合で決まる（どれかが未丸めなら列は未丸め。リテラルは常に丸め済）。
E106 の静的な格子検査はリテラルにだけ適用する。
名前の値が格子に載っているかは静的に分からないためで、列や出力の丸め宣言は名前の値にも宣言どおり一度掛かる。
宣言は紙面にあるので、これは「黙って変える」ことにはならない。
実測でこの検査がまず効いたのは計算のない表引きの運賃表で、丸め宣言が `1451円` のような転記タイポを桁の検査として落とした。
設計時は計算のための規約と考えていたが、実際には転記の検査として先に働く。

公開規約の転記は、丸めについてもう一つのことを教えた。
複数クーポンの端数処理は、楽天にも Yahoo にも書かれていない。
割引上限が素割引に掛かるのか最終額に掛かるのかも書かれていない。
つまり E104 と丸め宣言の必須化が要求する決定は、規約の側に存在しないことがある。
このとき書き手の仮置きが仕様の顔をして生成コードに入るので、規約に根拠のない丸めには出典と仮置きの旨をコメントで残す慣行を置き（§5.4 のスケッチの `# 端数処理は公開規約に記載なし。切り捨てに仮置き`）、過去データが来たら replay が仮置きを裁定する（§10）。
丸めを書けと迫ること自体の価値は、公開規約の欠落という形で、データを見る前に実証された。

### 7.3 丸めモードの定義

**決定**：モードは四つ。負の値に対する向きまで仕様で固定する。

- **切り上げ**：0 から遠ざける（-4.2 円 → -5 円）
- **切り捨て**：0 へ寄せる（-4.8 円 → -4 円）
- **四捨五入**：半分ちょうどは 0 から遠ざける
- **銀行家丸め**：半分ちょうどは偶数へ

負の値まで固定するのは、Python の `//` が −∞ 方向、Go の整数除算が 0 方向と、言語既定の除算が食い違っているからである。
生成コードが言語の素の除算を使うと、同じ表から違う円が出る。
そこで両言語に同一アルゴリズムの丸めヘルパ（十数行、生成ファイル内に自己完結）を吐き、負値と半分ちょうどを含む共通ベクタで一致を検証する（§9）。
値引きや返金で負の金額は現実に通るので、この固定は飾りではない。

### 7.4 除算と比率

除算は正の整数定数と、同型の定数（`注文金額 / 100円`、`重量 / 100g`）に限る（§2.3）。
結果は未丸めの無次元数で、丸めモードを明示しないと整数にならない。
「100 円につき 1 点」は `切り捨て(注文金額 / 100円)` と書き、切り捨てという業務仕様が紙面に残る。

## 8. 生成コードの形

### 8.1 可読性の基準

生成物の可読性は次の五つで定義し、golden テストで固定する。

1. 表の 1 行が分岐 1 本に対応する。分岐条件は行の全セルを省略せずに書き（先行分岐で真とわかる条件も消さない）、コメントに元の行を転記する。
2. 使う抽象は標準ライブラリの列挙と整数まで。テーブル駆動、クラス階層、ジェネリクスを使わない。
3. `.rule` の 1 行の編集が、生成物でも局所的な diff になる（条件の共通化や並べ替えという「賢い」最適化をしない）。
4. 長さは行数に線形で、1 ルール行あたり 2〜4 行を目安とする。
5. gofmt と PEP 8 に素で適合し、出力はバイト決定的である。

依存ゼロは「第三者パッケージゼロ」の意味で、標準ライブラリ（Python の enum、Go の fmt）は使う。

識別子は公開と内部で流儀を分ける（§1.3）。
公開 API（関数名、入力、出力、その型と列挙値）は ASCII 別名を使い、内部（表の関数、群の集合、内部の型、導出、定義）は別名が無ければ日本語識別子をそのまま使う。
漢字かなの識別子は非公開の位置なら両言語で合法で、gofmt も black も通り、行とコードの目視対応（基準 1）には原文のままの内部名がむしろ効く。

出力セルの名前（§3.2）は、その行の分岐での変数参照になる（`raw = 率割引`）。
1 行 1 分岐の対応は変わらない。

未検証の重なり（W114。§6.2）を持つ `一意` の表には、番人を生成する。

```python
    # 番人: W114（表 適用判定 行2 × 行4）。排他を静的に証明できなかった行対
    if 残高A <= 1000 and 残高B >= 3980:
        raise RuleContradictionError("表 適用判定: 行2 と 行4 が同時に当たりました")
```

Go では同じ条件でゼロ値と error を返す。
Python の例外は入力契約違反の `RuleInputError` と区別して `RuleContradictionError` とする（規則そのものの矛盾であって、呼び出し側の誤りではないため）。
番人は未検証の行対にだけ生成され、対象の行対をコメントに刻む。
この分岐を踏む入力はベクタには存在しない（構成できたなら W114 ではなく E105 になっている）ので、生成されるが通常は実行されないコードであることをファイルヘッダの注記にも書く。
細目も約束しておく。
番人を入れる対は、生成時点の解析が出す W114 の対そのもの（`一意` の表で、出力が構文的に異なるもの）で、「構文的に同一」の判定は `--diff-base` と同じセル正規形の鍵で行う（同一性の定義を二つ作らない）。
複数の対は表の行順に並べ、メッセージは「表名: 行i と 行j が同時に当たりました」の形に固定する（運用が grep する面なので安定させる）。
導出の範囲には番人を置かない。
E112 が宣言範囲 ⊇ 到達区間を静的に保証し、入口ガードが入力を範囲内に保つので、導出が宣言範囲を出る実行は存在しない。

### 8.2 Python

```python

    """宣言された入力域の外。呼び出し側の契約違反。"""

                 total: YenInclTax, member: MemberKind) -> YenInclTax:

    if not 1 <= weight_g <= 40_000:
        raise RuleInputError(f"重量 {weight_g}g は範囲 1g..40kg の外")

    if dest in _遠隔地 and weight_g <= 2000:        # 行1: 遠隔地 | <=2000g | 1200円
        base = 1200

        base = 1800
    elif dest not in _遠隔地 and weight_g <= 2000:  # 行3: 以外:遠隔地 | <=2000g | 800円
        base = 800
    elif dest not in _遠隔地 and weight_g > 2000:   # 行4: 以外:遠隔地 | >2000g | 1100円
        base = 1100
    else:
        raise AssertionError("到達不能: 完全性は rulec が静的に検査済み")
    ...
    raw = base * pay_rate          # 単位: 0.01円（円 × %）
    return YenInclTax(_ceil_10yen(raw))
```

金額の brand は `NewType` で表す。
mypy と pyright には効き、実行時コストはない。
列挙は stdlib の `Enum` で、値に和名文字列を持たせてログとワイヤ形式（§10）に使う。
網羅性は rulec が証明済みなので、pyright の網羅性検査に依存しない。
ただし Python は動的で列挙外の値が渡り得るため、入口で列挙と範囲を検証して `RuleInputError` を投げ、最終 else は「到達不能」の assert として残す。
証明の前提（入力が宣言域内）を実行時に守るのが入口ガード、証明そのものを信じるのが最終 assert、という分担である。

### 8.3 Go

```go

// 原本: rules/送料.rule (規則 送料 v4, sha256:9f2c1a…)

    Dest    Prefecture

```

金額の brand は defined type（alias ではない）で表す。
`YenInclTax + YenExclTax` は Go コンパイラが弾き、キャストは grep で見つかる。
Python の brand が型検査器頼みなのに対し Go は言語本体で守れるので、この点の非対称は Go 有利に倒れる。

sum type の不在への答えは「頼らない」である。
網羅性の証明は rulec が持ち、生成される switch は証明済みの全ケースと、列挙外の値を受ける default（error を返す）で構成する。
したがって `nishanths/exhaustive` 等の linter にも依存しない。
生成関数は `(値, error)` を返し、error は入力契約違反（列挙外、範囲外）だけを表す。
error か panic かは呼び出し側の流儀に合わせたく、実際に組み込む Go の慣行を見て最終決定する（§15-3）。
入力は 4 個を超えると同型の int が並んで危ないので、フィールド名に単位を含む Input 構造体で受ける。

### 8.4 生成物の置き場所

**決定**：生成物は git にコミットする。CI の `rulec gen --check` が、コミット済み生成物と再生成結果の一致を検証する。

理由は三つ。
表の変更 PR に生成コードの diff が並ぶことがレビューの実体であること（P5 の「人間がレビューできる」）。
利用側リポジトリが rulec なしで生成物を vendoring できること。
そして生成物の手編集が `--check` で即座に露見することである。
ヘッダには rulec の版と原本のハッシュを刻み、Go の生成コード規約（`^// Code generated .* DO NOT EDIT\.$`）に従う。

### 8.5 M1 の生成細目

設計文書に書かれていなかった前提を、M1 の着手前にここで固定する。

- **配置と命名**：`generated/python/<規則別名>.py`、`generated/go/<規則別名>/<規則別名>.go`。Go のパッケージ名は規則別名から `_` を落とした小文字。
- **決定性**：同じ `.rule` と同じ rulec からは、実行環境によらずバイト同一の生成物。内部の反復はすべて宣言順か整列済みで、ハッシュ順の混入は不合格。改行は LF。
- **複数出力**：Python は `typing.NamedTuple`、Go は名前付きの Output struct を返す。単出力は素の値のまま。
- **入口ガードの範囲**：列挙の妥当性、入力の `範囲`（率は刻み単位の整数で検査）、optional の `無し` の扱い。導出には置かない（§8.1）。
- **三者一致の判定**：宣言域内のベクタで、正準 JSON に直列化した出力のバイト一致。域外の挙動（Python の RuleInputError、Go の error）は言語ごとのユニットテストで域外 1 点ずつ確かめる。評価器は域外を受けないので、三者比較の対象は域内に限る。
- **丸めヘルパの単体ベクタ**：§7.3 の四モードについて、負値と半分ちょうどを含む共通ベクタを表のベクタとは別に出し、両言語のヘルパ単体で回す。表レベルの一致だけでは、端数の出ない表でヘルパの誤りが隠れる。
- **定義軸の篩**：定義軸の証人検証（点を構成して定義を評価器で確かめる）と、未確認の `一意` の重なりの W114 降格は、番人の生成と対で M1 が実装する（§6.2）。依存の共有だけで機械的に Unknown へ落とす形は採らない。検証を先に試み、実在する矛盾を W114 に逃がして CI を素通りさせない。
- **ベクタの原子境界**：真偽定義の原子の境界の抽出（§9.1）も M1 の実装範囲。
- **整形の内蔵**：gofmt 相当の整形は生成器が内蔵し、後段で環境の gofmt を走らせない（環境の版に依存した瞬間、決定性が壊れる）。`gofmt -l` が空であることは検証として残す。列の整列は `text/tabwriter` と同じルーン数で数える。表示幅の全角 2 ではない（和名の識別子が二行並んで初めて出た実測）。`.rule` の fmt は東アジア幅、生成 Go は Go の流儀と、それぞれの生態系の正準に合わせる。
- **PEP 8 の検証**：`ruff check --select E,W --ignore E501` が空であることを固定する。行長（E501）は意図した逸脱である。§8.1 の「表の 1 行を分岐 1 本に、原本のセルをコメントで添える」は 88 桁に収まらず、行長より 1 行 1 分岐の対応が優先する。
- **組み込みの遮蔽**：生成 Python は言語の組み込みを裸で呼ばない。入力の別名が `min` だっただけで生成物が壊れた実害から、`_min` `_max` などの内部名を生成側が持ち、衝突の族ごと消す。

## 9. 境界からのテストケース生成

### 9.1 値の候補

列ごとに候補値を決める。

- 列挙と真偽：その列のセル群が誘導する同値類（圧縮座標）ごとに代表 1 値。47 都道府県を全部舐めるのではなく、表が区別している区分だけを踏む。
- 数値（数量、金額、日付）：表に現れる各境界 b について {b − 最小刻み, b, b + 最小刻み}、および `範囲` の両端。
- 導出：境界は導出の値なので、入力ベクタへ写す（残りの入力は行の他セルを満たす値に固定する）。写し方は契約だけを決める。構成した点は必ず評価器で再評価し、目標に当たった点だけを採る。当たらなければ次の入力で試み、どうしても埋まらない義務は被覆判定器が赤で報告する。この二重の網（採用前の再評価と、義務の事後判定）の下では、解き方は実装の自由である。M1 の実装は記号解法ではなく数値の傾き（seed で評価し、一刻み動かして傾きを取り、目標へ跳んで、再評価で確かめる）で、上流の表や定義を挟んでも同じ一つの機構で通り、区分線形の継ぎ目や整除の外れは再評価が自然に落とす。解が入力範囲の外になる側の点は実現不能なので捨て、境界両側被覆の定義は実現可能な側に限る。
- 真偽定義の原子：解析は自由軸（§6.2）なので原子の境界を見ない。ベクタは定義から原子の境界を直接取り出して踏む（`注文金額 >= 3万円` なら 3万円 の両側、名前どうしの比較なら同着 A = B とその両側を、導出と同じ要領で入力へ写す）。解析に見えない境界こそ、ベクタが踏まないと誰も踏まない。
- optional：`無し` と、在る側の上記候補。

### 9.2 被覆基準

**決定**：三つの被覆を定義し、`rulec vectors` はこれを満たす最小に近い集合を決定的に生成する。

- **行被覆**：各行につき、その行が発火する（`上から` では勝つ）ベクタが 1 つ以上。
- **境界両側被覆**：数値列の各セル境界につき、他列をその行に当たる値へ固定したまま境界の両側を踏むベクタ対。行の削除、境界値の ±1、開閉の付け間違いは、この対の期待値を必ず変える。
- **遮蔽対被覆**：`上から` の遮蔽対 (i, j) ごとに、交差の内側（i が勝つ点）と j∖i（j が発火する点）の 2 点。隣接行の入れ替えという変異を殺す。

三基準は義務の集合として実装する。
義務は規則から静的に列挙し、生成器はそれを狙い、被覆判定器は各義務が実際に片づいたか（そのベクタで行が勝つか、境界の両側を対で踏んだか）を評価器で確かめ、片づけたベクタだけを残す。
発火したトレースから義務を作る形は禁じる。
踏めなかったものが「必要なかった」ことになるからである。
義務の列挙そのものは一箇所でよい。
同じ書き手による二重実装は盲点を共有しやすく、維持費だけが残る。
代わりに三つの網を張る。
遮蔽対の義務は解析器から取る（既に独立）。
境界の義務は、式の木から境界リテラルを数えるだけの素朴な収集器と件数で照合する。
規則ごとの義務の件数を回帰に固定し、言語に列の種類や原子の形を足すときは、該当カテゴリの義務が増えることを受け入れ条件にする。
増えなければ、列挙器がその機能を見ていない。

三基準を満たした上で、列間の相互作用の取りこぼしに保険を掛けるため、候補値のペアワイズ（全 2 因子網羅）を貪欲法で足す。
全直積は候補 10 値 × 6 列で 10⁶ に爆発するが、ペアワイズなら百数十件で収まり、行標的と合わせて規則あたり数百件が目安になる。
生成は決定的（同じ `.rule` から同じベクタ列）で、期待値は参照評価器が付け、発火行のトレースも記録する。

```
{"in":{"届け先":"沖縄","重量":2001,"注文金額":40000,"会員":"一般"},
 "out":{"送料":0},
 "trace":{"基本送料":2,"負担判定":1},
 "why":"境界両側: 基本送料 行2 重量>2000g の内側"}
```

### 9.3 ベクタの三つの使い道

1. **言語間一致テスト**：同じベクタを生成 Python と生成 Go に流し、参照評価器と三者一致を確かめる。データも旧実装も不要で、M1 の主力の保証になる（P6）。
2. **等価検証の入力**：旧実装アダプタ（§10）に同じベクタを流す。セル境界から作っているので、過去データが薄い境界近傍も踏む。
3. **golden**：生成された各言語のテストファイルにベクタを埋め込み、利用側 CI でも回るようにする。

## 10. 等価検証と過去再生のインタフェース

### 10.1 旧実装の呼び方

**決定**：アダプタプロセス方式。旧実装の言語で 20〜30 行のアダプタを書いてもらい、rulec が子プロセスとして起動して JSON Lines を stdin/stdout で流す。FFI もネットワークも使わない。

```
rulec → {"rulec":"adapter/1","rule":"送料","in":["届け先","重量","注文金額","会員"],"out":["送料"]}
旧側  ← {"ok":true,"impl":"legacy/shipping.py@a1b2c3d"}
rulec → {"id":1,"in":{"届け先":"北海道","重量":2500,"注文金額":12000,"会員":"ゴールド"}}
旧側  ← {"id":1,"out":{"送料":1800}}
旧側  ← {"id":2,"err":"unsupported: 離島"}
```

ワイヤ上の名前と値は `.rule` の正準名（和名）と正準単位の整数で、`rulec schema` が入出力の JSON Schema を吐く。
アダプタの雛形は `rulec adapter --template python|go` が印字する。
言語をまたぐ最小の共通面が「プロセスと行指向 JSON」で、Python でも Go でも Perl の遺物でも同じ書き方になる。

### 10.2 記録形式

過去データのスナップショットは 1 件 1 行の JSONL に固定する。

```
{"ts":"2025-08-14T09:12:33+09:00","tag":"order:1234567",
 "in":{"届け先":"鹿児島県","重量":800,"注文金額":4200,"会員":"一般"},
 "observed":{"送料":800}}
```

本番ログからこの形への抽出（ETL）は利用者の仕事と割り切り、rulec は `rulec fixtures lint` で型と範囲の検証だけを引き受ける。
注文金額を含むので fixtures はリポジトリに入れず、CI にはアーティファクトか保護ストレージで渡す。

### 10.3 入力が完全に復元できない場合

**決定**：モードは二つだけ。欄ごとに (1) その記録を除外する、(2) 既定値で補完し「補完系」の札を付ける。逆推定はしない。

補完の既定値は、規則の言語には入れない。
規則は純関数で、補完は特定の再生実験の判断だからである。
同じ規則を「会員は一般で埋める」「ゴールドで埋めて感度を見る」と別々に再生することが正当にありうるし、規則の宣言に書けば、意味に関与しない注記が規則のハッシュを変えて gen --check が無意味な再生成を要求する。
置き場所は版管理される再生マニフェスト（fixtures の隣に置く小さな JSON。既定値と対象欄だけで機微な数字を含まないので、リポジトリに入る）とし、CLI の `--fill` は感度分析のための一時上書きとして許す。
どちらから来た値でも、レポートが「使った既定値」と「補完した件数」を欄ごとに必ず刻む。
根拠は指定の場所ではなく、数字の出る場所（PR に貼られるレポート）に現れることで担保する。
なお、補完が見出しを膨らませる誘惑は構造的に存在しない。
見出しの一致率は実測系だけから計算するので、補完は二次集計にしか効かない。

fixtures の欄の欠けは、鍵の不在で表す。
optional の `無し` は値であり、`null` として明示的に書く。
「値が無いと分かっている」（無し）と「値が分からない」（欠け）は別物で、前者は補完の対象にならない。

レポートは実測系と補完系を必ず分けて集計し、見出しの一致率は実測系だけから計算する。
「982 件」の説得力は再現の正直さそのものなので、補完を混ぜた一致率を大きく見せる誘惑を、形式のレベルで断つ。

### 10.4 差分の帰属

replay と diff の不一致は、参照評価器の発火行トレースを鍵にクラスタする。
鍵は発火行の組だけ（diff は新旧両側、replay と verify は規則側のみ）で、金額は鍵に入れない。
表引きの行なら行の組が金額の組を一意に決めるので、金額で分ける意味がない。
計算の絡む出力（出力セルの名前、`結果` の式）で金額を鍵に入れると、金額の数だけクラスタが割れて要約が死ぬ。
代わりに、クラスタごとに件数、Δ の合計、最小と最大、証人例を必ず出し、Δ が全件同値ならそれを一行に畳む。
下の例の一行は、この一様な場合である。
既知の限界を一つ記す。
表そのものが増減した版の diff は、対応の取れない発火行を（旧のみ）（新のみ）と記すだけで、遷移としては読ませない。
構造の組み替えに意味のある対応は取れないからで、実表で頻発するようなら、そのとき設計する。

```
$ rulec diff 送料@v3 送料@v4 --fixtures replay/2025-08.jsonl
  影響 3,412 件 (0.27%)   金額 +182,400 円
  クラスタ 1: 基本送料 行2→行5（離島新設）      2,900 件  +196,800 円
    例: 届け先=沖縄, 重量=2400g, … v3: 1800円 → v4: 2000円
  クラスタ 2: |Δ| < 10円 の端数のみ              512 件   -14,400 円
    丸め差異の疑い（出力格子 10円 未満の一様なずれ）
```

出力格子未満のずれを「丸め差異の疑い」として自動で括るのは、§7 の規約が差分の主要因になるという予測を運用に折り返したものである。タグの条件は「クラスタの全件が、ゼロでなく格子未満のずれ」で、格子ちょうどのずれは丸めではなく値の食い違いなので付けない。複数出力では、食い違っている出力のすべてが格子未満であることを求める。

## 11. エラーメッセージ

設計原則を先に決める。

1. 一行目は業務の言葉だけで完結させる。型や IR の語彙を一行目に出さない。
2. 必ず具体の入力例（証人）を付ける。値は列挙の宣言順と境界値を優先して選ぶ。導出が絡む証人は入力として構成して評価器で確かめ、構成できなければ「実現可能性未検証」と明記する（証明していないことを証明済みの顔で出さない）。定義や導出の軸が絡んで実在を確認できた発見は、軸の座標（なぜ重なるか）を残したまま、それを作る入力を一行添える。証人を入力に差し替えると「なぜ」が消えるからである。
3. ヒントは「書き換え後の形」まで書く。
4. 位置はファイル:行に加え、表名、行番号、列名で示す。関与する行が複数なら全部にスパンを張る。
5. エラーコードと JSON 構造は安定 API とし、文言は改善してよい。
6. `--format json` が GitHub annotations にそのまま流せる形を吐く。exit code は 0（注記のみ）、1（エラー）、2（内部異常）。

以下、合意済みの五つの文面。表示は Rust 風の枠を借りる。

```
error[E101]: 完全性の欠落: どの行にも当たらない入力があります
  --> rules/送料.rule:23 表 基本送料
   |
23 | 表 基本送料
   |    ^^^^^^^^ 入力空間を覆いきっていません
   |
 当たらない例: 届け先 = 離島, 重量 = 500g
 覆われていない範囲: 届け先 ∈ {離島}, 重量は任意
 原因: 型 都道府県 に「離島」が追加されています（共通型.rule:3）が、
       この表の行はどれも「離島」を含みません。
 ヒント: 行を追加してください。例: | 離島 | - | 2400円 |
```

```
error[E102]: 冗長な行: 行3 は決して当たりません
  --> rules/送料.rule:31 表 基本送料
   |
29 | | 北海道 ・ 沖縄 | <=2000g | 1200円 |    行1
30 | | 北海道 ・ 沖縄 | >2000g  | 1800円 |    行2
31 | | 北海道         | -       | 1500円 |    行3: ここに到達する入力はありません
   |
 原因: 方式 上から のため、北海道の全域（重量も全域）を行1 と行2 が先に取ります。
 ヒント: 行3 が新しい仕様なら行1 より上へ移してください。
        不要なら削除してください。出力 1500円 は現在どの入力にも効いていません。
```

```
error[E103]: 単位の混同: 金額[円, 税込] に 質量[g] を足しています
  --> rules/送料.rule:40 結果
   |
40 | 結果 送料 = 基本送料 + 重量
   |             ^^^^^^^^   ^^^^ 質量[g]（入力 重量, 12行目）
   |             金額[円, 税込]（表 基本送料 の出力, 23行目）
   |
 ヒント: 重量に応じた加算料金なら、それは表で書きます。
        例: 表 重量加算 | 重量 | → 加算額 : 金額[円, 税込] |
```

税込と税抜の混同も E103 で、二行目が「金額[円, 税込] と 金額[円, 税抜] を足しています。税の変換は変換式ではなく表として書いてください」に変わる。

```
error[E104]: 丸めていない値が出力に到達します
  --> rules/送料.rule:8 出力 送料
   |
 8 | 出力 送料(fee) : 金額[円, 税込]
   |                  ^^^^^^^^^^^^^ 丸め の宣言がありません
41 | 結果 送料 = 基本送料 × (100% - 割引率)
   |             ^^^^^^^^^^^^^^^^^^^^^^^^^ ここで 1円未満の端数が生まれます
   |                                       （割引率 は 刻み 0.1% なので最小 0.001円）
   |
 例: 基本送料 = 800円, 割引率 = 12.3% のとき計算値は 701.60円 です。
     切り捨て(1円) なら 701円, 四捨五入(1円) なら 702円, 切り上げ(10円) なら 710円 と、
     丸め方で最大 9円 動きます。
 ヒント: 出力の宣言に丸めを書いてください。例: 丸め 切り上げ(10円)
```

E104 の文面は二形ある。
上は式が端数を生む場合（率の乗算や除算が経路にある場合）で、具体の円差を証人にする。
出力が表引きだけで端数が生じ得ない場合は、一行目を「出力に丸めの宣言がありません」に替え、円差の例は出さない。
代わりに「丸め宣言は、リテラルが格子に載っているかの検査（E106）に使われます。1451円 のような転記のタイポを桁で落とすのが、この宣言の第二の働きです」と言う（§7.2）。
どちらの形でも E104 の意味は「数値出力に丸め宣言が無い」で一つである。

```
warning[W105]: 行の重なり: 同じ入力が 行1 と 行2 の両方に当たります
  --> rules/送料.rule:35 表 負担判定（方式 上から）
   |
34 | | 真 | -        | 0%  |    行1
35 | | -  | プラチナ | 50% |    行2
   |
 両方に当たる例: 大口 = 真, 会員 = プラチナ
 方式 上から のため 行1（0%）が勝ちます。意図通りですか。
 意図通りならこのままで構いません。CI の check --diff-base は
 新たに生じた重なりだけを報告します。
 行2 を優先したいなら、行2 を行1 より上へ移してください。
```

W105 で一覧されるのは要確認の対（包含でない部分交差で出力が異なるもの）だけである（分類は §4）。
構造的と同値の対は「遮蔽 21 対（構造的 21、同値 0、要確認 0）」という件数の注記に畳まれ、`--show-shadow` で全対を一覧できる。

`方式 一意` での重なりは同型の文面で error[E105] になり、末尾が「出力が異なります（1200円 と 800円）。どちらが正しいか決めるか、順序に意味を持たせるなら 方式 上から を宣言してください」に変わる。
出力まで同じ重なりは「出力は同じですが、一意 では冗長です。片方を削ってください」とする。

E105 になるのは、証人を構成できた（実在を確認できた）重なりに限る。
構成できず、実現不能の証明もない重なりは warning[W114] に落ち、生成コードの番人が引き受ける（§6.2、§8.1）。
「証人を構成できなかった」を書き手にそのまま言っても伝わらないので、文面は「同時に起きる注文が存在するかどうかを判定できなかった」の形に固定する。

```
warning[W114]: 未確認の重なり: 行2 と 行4 の両方に当たる入力が有り得ます
  --> rules/クーポン併用.rule:31 表 適用判定（方式 一意）
   |
29 | | <=1000円 | -        | 偽 |    行2
31 | | -        | >=3980円 | 真 |    行4
   |
 重なる条件: 残高A <= 1000円 かつ 残高B >= 3980円
 二つの導出（残高A = 合計 - 割引A、残高B = 合計 - 割引A - 割引B）が入力を共有しているため、
 この条件を同時に満たす注文が存在するかどうかを、検査は判定できませんでした。
 存在するなら: 行を直してください。出力が異なる（偽 と 真）ので、当たれば矛盾です。
 存在しないなら: このままで構いません。生成コードには、万一この条件に当たる入力が来たとき
 黙って行2 を選ばずエラーを返す番人が入ります。
 この警告は check --diff-base では新規分だけ表示されます。
```

なお、この例の重なりは実際には実現不能である（割引B は 0円 以上なので、残高B は定義から必ず 残高A 以下。残高A が 1000円 以下のとき 残高B は 3980円 に届かない）。
導出ごとに独立な区間の篩はこの従属を見ないので、判定できずに W114 になる。
Fourier–Motzkin 消去なら証明できる形で、W114 が実表に積もることが、まさに §15-4 の増強の発動条件になる。

台帳をここで凍結する。
番号と意味は安定 API で、文言だけ改善してよい。
空き番も台帳の一部として明示する（残る空き番は E111 のみ。E009 と E110 は M1 で埋まった。増分は空き番から埋め、番台をまたがない）。


## 12. 実装言語と配布形態

**決定**：rulec は Rust で書く。配布は単一静的バイナリ（macOS arm64/x64、Linux x64/arm64 は musl 静的リンク）を GitHub Releases に置き、CI では sha256 を固定してダウンロードする。

理由。
この道具の本体はコンパイラ（AST、型付け、領域代数、正確な有理数演算、決定的な証人生成）であり、直和型とパターンマッチが実装の正しさに直接効く。
三候補のうちそれを言語本体で持つのは Rust だけである。
検査は 10⁶ ノード規模の探索なので Python は速度で外れ、Go は書けるが IR の直和が interface の運用規約になり、コンパイラを書くには一段落ちる。
Rust なら診断表示や有理数の枯れたクレートも使える（rulec 自身の依存はよい。ゼロにする対象は生成物である）。

生成物の行き先が Python と Go である事実は認めた上で、こう整理する。
毎日触られるのは `.rule` と生成された Python と Go であり、rulec 本体を触る人はコンパイラを書く人に限られる。
道具の保守者の裾野より、道具の正しさと配布の単純さ（ランタイム不要の 1 ファイル）を取る。

CI への組み込みは四行で完結する。

```yaml
- run: rulec fmt --check rules/
- run: rulec check rules/ --diff-base origin/main
- run: rulec gen rules/ -o generated/ --check
- run: rulec test generated/        # python3 と go の toolchain を使う唯一の段
```

replay は fixtures を持つ環境だけの別ジョブとし、`rulec replay` が Markdown を吐いて `gh pr comment` で貼る。
レポート整形まで rulec が持ち、投稿は CI の一行に任せて CI ベンダ非依存を保つ。

**捨てたもの**：

- **Go 実装**：書ける人の裾野は最大だが、上記のとおりコンパイラの内側で支払いが続く。
- **Python 実装**：検査の速度と、CI への配布（venv の管理）で二重に不利。
- **pip / npm ラッパ配布**：単一バイナリに対する追加価値がない。要望が出てから考える。

## 13. MVP の切り方

**決定**：四段。M0 と M1 は、データも旧実装も本番アクセスも一切使わずに完成する（P6 の第一段）。受け入れ条件の中心には、実測の転記を格上げした回帰コーパスを置く。

**回帰コーパス**は、公開情報だけから作った「通る `.rule`」の集合で、`tests/corpus/` として git に入れ、仕様の一部として扱う。
収録するパターンは実測で現れたものすべてである。

- ゆうパック基本運賃：47 都道府県 × 7 サイズ、群 6、3 段の連鎖（§5.1）
- ヤマトのサイズ判定：3 辺計と実重量の大きい方（単項セルと `上から`。§3）
- 楽天の送料無料ライン：クーポン利用前の金額で判定（素の入力列）
- 39 キャンペーン：クーポン適用後の金額で判定（導出。§5.2）
- 複数クーポンの素割引：種別で基準額が変わる（出力セルの名前。§3.2）と割引上限（`結果` の 最小）
- 併用制約：`同商品適用済` を入力に（§5.4）
- 適用順序：期限の日付比較の二引数規則（日付型。§5.4）
- 相関する導出：入力を共有する導出二本が作る、篩に見えない実現不能の重なり（W114 の実演。クーポン併用）
- 設計文書 §1.2 の送料スケッチ：真偽の `定義` を列に使う正常系、率の出力、`既定扱い`、要確認の遮蔽 1 対の実演

コーパスはパターン単位で最低一つの行使ファイルを持つ。
検査の意味論として新しくない転記は、独立のファイルを必須としない（ヤマトの大きい方は単項セルの多列 `上から`、送料無料ラインは入力列の閾値、39 キャンペーンの判定は導出列の閾値で、いずれも既存ファイルが行使している）。
逆に、どのファイルもまだ行使していないパターン（適用順序の日付比較、真偽定義の列）は、M0 の宣言前にファイルを足す。

日付型はこのコーパスが要求するので、v1 の型付け（M0）と生成（M1）に含める。

- **M0 検査器**：fmt、parse、型付け、§11 の台帳の全検査（E001〜E013、E101〜E109、E112、E113、W105・W110・W111・W114 と実現可能性の篩。篩は導出軸まで、定義軸の証人検証は M1。§6.2）、例の実行。完成の定義は五つ。(1) コーパス全部が check を通る。(2) 五種の誤りを仕込んだ変異ファイルが §11 の五つの文面をそのまま出す。コードの一致だけでなく、描画された文面をスナップショットで固定する。(3) fmt が冪等で、§1.5 の正規化を行い、`--check` で CI に組める。(4) `--format json` と exit code が §11 の原則 6 のとおりに出る。(5) `--diff-base` が要確認の遮蔽と W114 の新規分を差分で出せる。検査予算の既定値を §15-2 のベンチで決めることも、M0 の出口に含める。この時点で「手元の Excel や公開規約を転記して check に掛ける」という使い方が成立し、実測が示したとおり、転記の過程そのものが穴と重なりを見つけ始める。
- **M1 生成器**：Python と Go の生成、ベクタ生成、三者一致テスト（評価器、生成 Py、生成 Go）。完成の定義は、コーパス全部が両言語に生成でき、全ベクタで三者の出力がバイト一致し、生成物が gofmt と PEP 8 に素で通ること（PEP 8 は行長 E501 を除く。§8.5）。ここまでで「単一記述から両言語へ、ズレの証明つき」が成立する。
- **M2 等価検証**：アダプタプロトコル、雛形印字、verify レポート。旧実装へのアクセスが要る最初の段。レポートは §10 の設計どおり、発火行クラスタ、件数と金額差、証人、そして出力格子未満のずれへの「丸め差異の疑い」タグを含む。一致率の分母から外した件数は、外した理由ごとに明示する。
- **M3 過去再生**：fixtures lint、replay、diff、PR コメント用 Markdown。データが要る唯一の段。

完成の記録。M0 は宣言条件込みで完成。M1 と M2 も完成した（コーパス 7 本、テスト 68 本、被覆判定器と三つの網、定義軸の篩、番人まで。コミット fda2daa、d1dc5a7）。
追補が一つある。
生成テストファイル（§9.3 の三つ目の使い道）と `rulec test`（§12 の CI 四行目）は、どの段の完成定義にも割り付けられていなかったことが M3 の着手時に見つかり、M1 の取りこぼしとして M3 期間に実装された。
M3 も完成した（fixtures lint、replay、diff、markdown、`rulec test`。テスト 80 本、m3 の受け入れ 9 本。実データはゼロで、ベクタから合成した fixtures による行使。切り分けの有効性を実データで確かめる仕事は、§16 第二のとおり、記録を持つ側に残る）。

残件の台帳も置く。
`rulec import`（§1.4）と `rulec changes`（§1.5）は、どの段にも割り付けられていない。
どちらも導入期の便宜（Excel からの移行の入口、PR レビュー用の構造差分）で、正しさの機能ではない。
実際の導入が始まるとき、要否ごと決める。
ここに書くのは、黙って消えた顔をさせないためである。残るは M3 で、実装は合成 fixtures（ベクタと、欠陥を仕込んだアダプタ）で全部行使でき、実データでの検証だけが残る（§16 第二）。

「動くもの」の宣言は M1 で行う。
M0 だけでも道具として立つが、依頼の核（単一記述から両言語）を示すのは M1 だからである。

## 15. 未決事項と測定計画

実測で決着した v0 の未決を先に記録する。
セル内の区間の合併は 0 件で v1 から除外（§3）。
列の線形条件は導出として取り込み、SMT は当面不要（§5.2、§6.2）。
日付型は v1 入りが確定（§13）。
クーポンの重ね掛けは、粒度の構成で書けることを示した（§5.4）。
ただし前回そこから「集約は不要」と閉じたのは測り方の誤りだった。
書けるように書いた自選の二表から、必要性の不在は導けない。
撤回して §15-8 に開き直す（経緯は §4）。

残るものと、新たに開いたもの。
ここから先の大半は、動く検査器がないと測れない。
机上調査はここで打ち止めにし、以降の測定は M0 の実装と実地の転記で行う。

1. **文字列のパターン一致**：公開規約の転記では文字列が列に一度も現れなかったが、実運用のクーポンコード体系は公開情報では確認できない。実データ（コード形式の一覧）を見て、完全一致で足りるか前方一致が要るかを数えてから決める。
2. **検査予算の既定値（決着）**：M0 で実測した。設計目標（列 12、行 500）は 1,004 万ノード、164 ms で予算内。訪問数は行数に二乗、速度は約 6 万ノード/ms。既定は 5×10⁷（§6.3）。
3. **Go の入力契約違反の流儀**（error か panic か）：組み込み先の Go サービス 2〜3 本の慣行を見て合わせる。生成器のフラグにはしない（生成物の形は一つに保つ）。
4. **相関する導出と Fourier–Motzkin 消去**：導出が入力を共有する形は、コーパスのクーポン規則が最初から含んでいる（`最低差` と `支払差` が `現在残額` を共有）。ただし当の表は `上から` で、W114 を生む `一意` との組合せはまだ出ていない。コーパスを広げるたびに、導出の本数の分布と W114 の件数を数える。発動条件は二つのどちらか。W114 が実表に出続けること、または番人（§8.1）に本番で当たりが出ること。どちらも起きるまでは足さない。効果の物差しも用意できた。コーパスのクーポン併用にある W114 一件（区間の篩には見えない実現不能の重なり）が、FM を入れた日に消える。
5. **畳み込みの宣言化**：`畳み込み 順序=適用順序 一回=クーポン割引 累積=残額 ← 残額 − 割引額` の形で反復を宣言にし、参照評価器が畳み込みまで実行できるようにする案。見送りの理由と暫定の緩和（連鎖の例）は §5.4 に書いた。採否は次の三つで測る。(1) 二本目以降の実畳み込み（ポイント付与、按分、Yahoo の重ね掛け）を転記し、「比較規則によるソート → 段ごとの純関数適用」の形に収まるかを確かめる。(2) 各段の入力を「アキュムレータと当該要素から導ける」「畳み込み全体の定数」「外部状態」に分類して数える。外部状態が 0 で、アキュムレータがスカラーか固定形のレコードに収まる実例が 2 件以上そろい、かつコーパスのクーポン規則も同じ形に書き直せるなら入れる。(3) クーポン重ね掛けの呼び出し側を両言語で試作し、fold 単体ではなく、規則を呼ぶために書くホストコードの総量（射影、反復、前後処理）を行数と分岐数で数える。二重実装は畳み込み、射影、前後処理に分かれて出るので、別々に見ていると合計がいつ許容を超えたか分からない。fold が定型 30 行程度に収まるなら宣言化の利得は薄いままとし、膨らむか二実装が食い違うなら圧力が上がる。入れると決まった日のための設計メモも残す。順序規則には全順序性の検査が要る（全域・反対称・推移。二引数規則は積空間上の表なので、反対称は行対の突き合わせ、推移は圧縮同値類上の三重ループで有限に検査できる）。累積には初期値と各段の出力範囲からの帰納で範囲不変条件を検査する。丸めは各段の出力宣言が既に持つ。生成形は固定の短いループ骨格と一段関数の呼び出しで、1 行 1 分岐の基準は表側に残る（P7 が禁じるのは DSL 表面のループであって、生成物のループではない）。
6. **入力の射影と由来の宣言**：入れ子のドメインオブジェクトへの述語（`注文.配送先.都道府県`、`明細のいずれかが冷蔵品`、`count(明細) > 3`）は現実に普通にあり、平たい入力への射影は今はホストの手書きである。コーパスの入力は 13 個（クーポン 10、運賃 3）で、素朴に見積もれば射影だけで両言語 26 行の未検査グルーになり、規則を増やすたびに線形に増える（これは見積もりで、実数は §15-5 の試作で数える）。拡張候補は、入力宣言への由来の付記（`届け先(dest) : 都道府県 ← 注文.配送先.都道府県`、`冷蔵品あり : 真偽 ← 注文.明細 のいずれかが 区分 = 冷蔵`）と、既存スキーマの借用である。rulec は独自のドメインオブジェクト型システムを作らない（非交渉）。呼び出し側に既にある JSON Schema / protobuf / OpenAPI を読んでパスの存在と型を検査し、両言語の射影関数を生成する。受け入れの根拠は、検査に一切触れないこと。射影の出力はスカラーの入力で、領域解析も箱代数も無傷、言語機能ではなくコード生成機能である。先に置く設計上の注意が三つ。(1) 由来は check に不要な注記とし、スキーマが無くても検査は完結する（照合と生成は gen 側）。(2) 生成物ヘッダに原本ハッシュと並べてスキーマの版も刻む。スキーマと本番の乖離は、新しい偽の緑の通り道になるからである。(3) 射影の言語は「一つのコレクションへの いずれか / すべて / 件数 と、要素フィールドへの単項述語」で打ち止めにし、結合や入れ子の量化は実例を数えてから。セルにパス式や量化子を入れる形は採らない（§0）。優先度は畳み込み（§15-5）より上に置く。量が規則ごとではなく入力ごとに増えることに加え、畳み込みは動機の実例を表せずに見送られたのに対し、射影は実例を既に表せて検査にも触れず、採用の障壁が低い。着手は §15-5 の試作で総量を測ってから。
7. **按分**：値引きの明細行への按分（端数の再配分）は実測に現れなかった。ポイントか按分の規約を転記して、「一回の判定」の粒度で書けるかを測る。書けなければ、粒度原則の最初の例外候補として §5.4 に戻す。
8. **集約（C）の需要**：「実測のクーポン転記でも集約は要らなかった」という前回の記述を撤回して開き直す（経緯は §4）。公開調査で分かったのは、実需要の主形が検証（当てはまる項目の全収集）であることまでで、不在の証明ではない。以降は机上ではなく実地で数える。M0 の後、実表を転記するたびに「単一ヒットで書けなかった」「書けたが排他の書き込みが苦痛だった」事例を、検証の形と集約の形に分けて記録する。採ると決まったら、§4 の記録（排他と網羅の検査が意味を失う取引、範囲の決断）を前提に設計し直す。
9. **単項原子の DNF 代入**：真偽定義は自由軸で出荷した（§6.2）。代入すれば定義の中の閾値（`注文金額 >= 3万円` の 3万円）まで領域解析が見るようになり、実現不能な組合せ起因の過剰報告が減る。発動条件は、その過剰報告（穴や W114）が実表で邪魔になること。それまでは、ベクタが原子の境界を直接踏むこと（§9.1）で検査の穴を塞ぐ。§15-4 の増強（FM 消去）とは独立に発動できる。

## 16. この設計で最も危うい点

第一に、**rulec が消したかった二重実装が、一段上で小さく再発する**。
表現力の崖は実際にクーポンで来たが、導出と粒度の二手で、崖ではなく段差として越えられた（§5.2、§5.4）。
その代償が、重ね掛けの畳み込み（ソート、逐次適用、状態の運搬）を Python と Go の手書きに一つずつ残すという構図である。
「二重実装は必ずズレる」という、この道具が存在する理由そのものが、規則の外側で小さく再現される。
順序の判定まで規則に入れて畳み込みを自明な形に追い込む設計はその緩和だが、本当に自明になるかは試作で数えるまで分からない（§15-5）。
畳み込みを宣言にして検査の網を届かせる案は検討済みで、単一アキュムレータが当のクーポン（併用制約の状態）を表せないため見送った（§5.4）。
それまでは連鎖の例が、畳み込みの仕様をデータとして規則側に留める。
加えて按分は転記に一度も現れておらず、粒度原則の未検証領域として残っている（§15-7）。

第二に、**99.9% の先の 0.1% が道具の信用を決める**。
不一致 1,107 件の身元（旧実装のバグか、転記ミスか、fixtures の汚れか、丸め差異か）を報告書が自力で切り分けられなければ、「982 件」は証拠ではなくノイズになり、一致率を上げる過程が仕様の発掘ではなく徒労になる。
発火行クラスタ、丸め差異の自動タグ、実測系と補完系の分離はすべてこのための設計だが、その有効性は実データに当てるまで仮説にとどまる。
実測は道具の前半（記述、検査、生成）を現実の規約に当てたが、後半（M2 と M3）は依然として一件の実データにも触れていない。
検証済みと未検証の境界は、いまここにある。
M3 は機能を足す段ではなく、最初の実表 1 本でレポートの切り分け精度を磨き込む段として扱うべきである。

第三に、**丸めの決定が、規約に存在しないまま `.rule` に書かれて権威になる**。
実測は、公開規約が複数クーポンの端数処理も上限の掛かり先も書いていないことを示した（§7.2）。
E104 が丸めを書けと迫るのは設計どおりだが、迫られた転記者が書けるのは仮置きであり、生成コードに入った仮置きは仕様の顔をする。
出典コメントの慣行と replay での裁定は緩和であって解決ではなく、データが来るまで仮置きは仮置きのまま積み上がる。
オーバーフロー証明が要求する中間丸め（E108）も同じ圧力点で、円が動く業務判断が型エラーの顔をして業務担当者に届く。
E104 と E108 の文面がそれを業務の判断として提示し直せているかは、業務担当者に文面を読ませる実地の検証（誤読率を見る）まで含めて M0 の合否に入れないと、P2 の「読める」がここから崩れる。
