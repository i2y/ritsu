# rulec 設計文書

業務ルールを決定表として記述し、静的に検査し、Python と Go の両方へ読めるコードを生成する道具の設計を決める。
実装はまだ書かない。
本文の構文例と生成コード例は、決定を説明するためのスケッチである。

合意済みの前提は再論せず、以下の記号で参照する。

- **P1**：最初の対象領域は送料。次がクーポンとポイント、引当は最後
- **P2**：記述の中心は決定表。業務担当者が読めること
- **P3**：ルールは純関数。時刻も在庫も会員区分も入力として渡される
- **P4**：型で守るのは、単位、丸め、完全性、優先順位と重なりの四つ
- **P5**：出力は Python と Go への依存ゼロの読めるコード生成。実行時ランタイムは持たない
- **P6**：道具本体はデータ不要、旧実装があれば等価検証、過去データがあれば影響算出、と段階的に価値が出ること
- **P7**：汎用言語にしない。ループも再帰も状態も GUI も持たない

本書は v0 草案を、公開規約からの転記実測を受けて改訂した v1 である。
実測とは、公開情報（日本郵便ゆうパック基本運賃 東京発、ヤマト宅急便のサイズ区分、楽天市場の送料無料ライン、39 キャンペーン、複数クーポンの計算方法とクーポン利用条件、Yahoo!ショッピングのクーポン利用条件）を 2 本の `.rule` に転記した計測を指す。
規模はゆうパック運賃が 84 行（表 55 行、列 2、群 6）、クーポン割引が表 15 行、列 6 である。
本文で「実測」と言うときはこの転記を指し、転記そのものは回帰コーパスとして §13 に収録する。
実測が支持した決定（二方式の共存、単項セルの制限、線形パイプライン、群、表引き出力への丸め宣言、完全性の常時必須）は各所に一文で記す。
覆った決定は本文を書き換え、v0 が持っていた検査の抜け道は塞いだ経緯ごと残す（§5.3）。

## 0. 全体像

rulec は一本のパイプラインである。

```
.rule ── 構文解析 ──> AST ── 型付け ──> TIR（型付き表 IR）
                                        ├──> 領域 IR（圧縮座標上の箱集合）──> 検査 E101/E102/E105
                                        ├──> 参照評価器 ──> 例の検証・ベクタ期待値・verify/replay/diff
                                        └──> コード生成 ──> generated/python/…  generated/go/…
```

単位の誤り（E103）と丸めの漏れ（E104）は型付けの段で出る。
完全性（E101）、当てはまらない行（E102）、重なり（E105）は領域 IR の段で出る。

意味論の原本は TIR 上の**参照評価器**一つに置く。
例の検証も、テストベクタの期待値も、過去再生も、すべて同じ評価器を通す。
生成された Python と Go は、共通ベクタでこの評価器との一致を機械的に確かめる（§9）。
参照評価器は rulec の内部にだけ存在し、本番で実行されるのは生成コードのみである。
P5 の「実行時ルールエンジンにしない」は、この線引き（評価器は検証系専用、出荷物は生成コード）で守る。

この全体像に、境界の宣言を一つ足しておく。
**この道具の本当の境界はヒットポリシーではなく、セルの言語である。**
rulec は DMN の読み手でも部分集合でもない。
借りるのは決定表の骨（単一ヒットの二方式と、完全性・重なりという解析の問題設定）だけで、セルに書けるのは自列への単項テストに限る（§3）。
公開されている実在の DMN 資産には、セルに任意の FEEL 述語（`some … satisfies …` や `count(…)`）を書くものがあり、我々はそれをヒットポリシー以前にセルの言語で受け付けない（§4 の調査で開いた伊 ANAC の調達規則がその実例）。
この狭さは妥協ではなく購入である。
セルが単項だから行が箱になり、完全性も重なりも厳密に決定できる（§6）。
入れ子のデータへの述語も同じ線の上にある。
入れ子は境界で平たい入力に潰してから渡し、セルには入れない（§3、§15-6）。
「FEEL なら書けるのに」という圧力は実務で必ず来る。
曲げてよいのは境界の外（入力の作り方。§15-6）だけで、セルの言語を曲げた瞬間に、この道具の検査は成り立たなくなる。

### 0.1 対象の範囲

**決定**：対象は「**一件の取引を、決まった数の平たい値から一度で判定して、金額・可否・区分・順序のいずれかを返す規則**」で、かつ「**承認する人がいて、期日で改定されるもの**」である。運賃、割引とクーポン、料率と手数料、適用可否と期間区分がその形で、転記した 7 本はすべてここに入る。入力は 1〜10 個、出力は上の四種。

範囲を業種ではなく**判定の形**で書くのは、境界を決めているのがセルの言語だからである（§0）。セルが自列への単項テストだから行が箱になり、完全性と重なりが厳密に決まる。だから「送料の道具」でも「EC の道具」でもなく、上の形をした判定の道具である。

この領域を選んだのは、五つの性質が同時に成り立ち、道具の機能がその一つずつに対応して生えるからである。

1. **お金が動く** → 単位と税区分が型で（§2.1）、数値出力の `round` が必須で（§7.2）、書き忘れには円差を見せてから訊く（§11 E104）。
2. **原本が外にある** → 仕事は設計ではなく転記であり、最初の価値が「転記した瞬間に穴が出る」になる（§13）。`doc` が原本か検査結果に遡れない文を書かないのも同じ理由である（§1.6）。
3. **条件が絡み合う** → `if` 一本では書けず、網羅を目視で確かめられない。決定表と完全性検査に意味が出る（§4、§6）。
4. **期日で改定される** → 版、`--diff-base`、過去再生と差分（§10.4、§12）。
5. **書く人と決める人が違う** → `doc`（§1.6）と、決められないことを証人つきの問いに変える文面設計（§11 原則 2）。

五番目が満たされない規則も技術的には書けるが、この道具の半分（描画、差分、承認の通り道）は無用になる。

**捨てたもの**：

- **汎用のルールエンジンを名乗ること**：ループも状態も持たない以上、名乗れば期待を裏切る。P7 の言い換えでもある。
- **ワークフローと状態機械**：複数段階と状態は P3（ルールは純関数）と正面から衝突する。時刻も在庫も引数で渡すという決定が、過去再生を意味あるものにしている（§10.3）。
- **集合・集約の判定**：「明細のいずれかが冷蔵品」「カート全体で 3 点以上」。境界で平たくして渡す（§0、§15-6）。DMN の Collect を採らない判断（§4）と同じ線の上にある。
- **文字列のパターン一致**：`string` は等値と集合一致だけ。前方一致や正規表現はセルの言語を壊す（§2.1、§15-1 で実データを見てから再考する）。
- **スコアリング・最適化・機械学習**：証明できるのは「どの行に当たるか」であって、重みの妥当性ではない。検査の主張が成り立たない領域には行かない。

**按分（2026-09-13 に測った）**：粒度の原則（§5.4）は**配り方による**。「順に上限まで充てる」形は一明細ぶんの純関数として書け、反復は呼び出し側に残り、合計は構成上ぴったり合う（`tests/corpus/値引の充当.rule`。2,000 通りの明細で確かめた）。「定価の比で割り付ける」形は書けない — `明細 / 合計` が §7.4 の除算制限に当たる。比率を呼び出し側で作って率で渡す迂回も、率の刻みが実装上 1% 単位までしか書けないので実用にならない（下の「測って分かった欠陥」）。§15-7 はこの結果で閉じる。

## 1. 表面構文

### 1.1 ファイル形式

**決定**：行指向の独自テキスト形式。拡張子は `.rule`。エンコーディングは UTF-8（BOM なし）で、識別子は NFC に正規化する。表はパイプ区切りで、1 行が決定表の 1 ルール行に対応する。セル内改行は存在しない。

git diff の意味単位を業務ルールの行に一致させることが、この形式の唯一の設計目標である。
パイプ表は開発者も業務担当者も PR 上で読み慣れており、新しい読み方を教える必要がない。

キーワードは英語一種類だけを正とし、同義の綴り（日本語のキーワード、略語）は用意しない。
同じ意味の綴りが二つあると、grep と diff の両方で敵になる。
語彙は次の表で全部である（実装は `src/kw.rs` の一枚の表で、README のキーワード表と E009 の予約語判定はそこから引く）。

| 位置 | 語 |
|---|---|
| 行頭 | `rule` `description` `import` `enum` `group` `inputs` `outputs` `derive` `define` `table` `policy` `result` `examples` |
| 宣言の修飾 | `range` `round` `contract_only` `default` `step` |
| 方式 | `unique` `first` |
| セルと式 | `-` `not:` `none` `true` `false` |
| 型 | `money` `mass` `length` `rate` `bool` `date` `string`。金額の属性は `incl_tax` `excl_tax` |
| 丸め | `up` `down` `half_up` `half_even`（向きの語は Java の RoundingMode と同じ） |
| 結果の関数 | `min` `max` |
| 組み込み | `import std/都道府県` |
| 記号 | `->`（出力列の境目）、`,`（集合の区切り）、`-`（任意の値）。`→` `・` `、` `，` は読めるが、`rulec fmt` が `->` と `,` に正準化する |

英語にするのは道具の語だけである。
識別子（規則名、入力、群、表の名前）とセルの中身は業務の語であり、日本語のまま書く（§1.3）。
この線引きで、字面の上でも道具の語（ASCII）と業務の語（日本語）が見分けられ、キーワードと名前の衝突（E009）は実質的に起きなくなる。
単位（`円` `銭` `万` `億` `g` `kg` `cm` `m` `%`）は語彙ではなく数値の表記なので、そのまま残す。

**覆した決定**：2026-09-13 まではキーワードも日本語（規則、取込、型、群、入力、出力、導出、定義、表、方式、結果、例、範囲、丸め、以外、無し）だった。
「一種類だけ」の原則は変えず、その一種類を英語に切り替えた。
理由は上の線引きと、日本語を読まない開発者にも構造が読めること。
移行は機械的で、コーパス、変異、golden、README の例をすべて書き換えた。

**捨てたもの**：

- **YAML / TOML への埋め込み**：二次元の表をネストで書くと列の対応が視覚から消え、P2 が死ぬ。
- **CSV**：型宣言とメタデータの置き場がなく、引用符の規則が業務担当者に説明できない。
- **DMN XML**：diff 不能。借りるのは意味論だけで、交換形式は借りない（前提のとおり）。
- **Markdown 文書内埋め込み（literate 形式）**：地の文と表の境界の規則が増えるだけで、表自体の可読性は上がらない。

### 1.2 ファイルの構造

一つの `.rule` ファイルが一つの規則（一つの生成関数）である。
構造は上から、ヘッダ、取込、型と群、入力、出力、定義と表の列、結果、例、の順で固定する。
全体のスケッチを示す。以降の節はすべてこの例を参照する。

```
rule 送料(shipping_fee) v4
description "通常便の送料。2026-04 の運賃改定を反映"

import std/都道府県

enum 会員区分(member_kind) = 一般(basic) default | ゴールド(gold) default | プラチナ(platinum)
group 遠隔地 = 北海道, 沖縄

inputs
  届け先(dest)    : 都道府県
  重量(weight)    : mass[g]         range >=1g <=40kg
  注文金額(total) : money[円, incl_tax]   range >=0円 <=1000万円
  会員(member)    : 会員区分

outputs
  送料(fee) : money[円, incl_tax]  round up(10円)

define 大口 : bool = 注文金額 >= 3万円

table 基本送料
policy unique
| 届け先      | 重量    | -> 基本送料 : money[円, incl_tax] |
| 遠隔地      | <=2000g | 1200円                            |
| 遠隔地      | >2000g  | 1800円                            |
| not: 遠隔地 | <=2000g | 800円                             |
| not: 遠隔地 | >2000g  | 1100円                            |

table 負担判定
policy first
| 大口 | 会員     | -> 負担率 : rate |
| true | -        | 0%               |
| -    | プラチナ | 50%              |
| -    | -        | 100%             |

result 送料 = 基本送料 × 負担率

examples
| 届け先 | 重量  | 注文金額 | 会員     | -> 送料 |
| 沖縄   | 2500g | 40000円  | 一般     | 0円     |
| 東京都 | 1999g | 12000円  | プラチナ | 400円   |
```

`examples` は実行される仕様である。
`rulec check` が参照評価器で全行を検証し、外れたら発火行つきでエラーを出す（E107）。
例の期待値は全出力について必須で、列の欠けはエラーにする（空セルと同じ理屈で、書き忘れを沈黙にしない）。
例は実装間の一致の盲点を破る唯一の楔でもある。
評価器と生成器が同じ誤りを共有すると一致は緑のまま通すが（複数出力の丸めが揃って落ちていた実測）、人が書いた期待値だけがそれと食い違える。
出力と同名の中間値が存在するなら、その出力の `result` は省略できる（表が一つだけの規則が典型で、複数出力でも出力ごとに効く）。

### 1.3 日本語識別子と ASCII 別名

**決定**：識別子は日本語を許す。ASCII 別名（丸括弧で併記）が必須なのは、公開 API に出る名前だけとする。すなわち規則名、入力、出力、そして入出力の型に現れる列挙型とその値である。内部に閉じる名前（群、表、定義、導出、内部でしか使わない型）の別名は任意で、省略すると生成コードも日本語識別子をそのまま使う。表の中身（セル）と例は常に日本語だけで書く。

Go の公開識別子は先頭が Unicode の大文字である必要があり、漢字とかなは大文字を持たないため公開名になれない[^go-export]。
つまり公開面には ASCII 名が必須で、その名前は宣言時に人間が一度だけ決めるのが、レビュー可能性ともっとも安い。
一方、非公開の位置には大文字要件がなく、漢字かなの識別子は Go でも Python でも合法である。
内部名にまで別名を要求する理由は、生成の都合には存在しない。

実測がこの線引きを与えた。
ゆうパック運賃 84 行に別名は 23 個要り、うち公開面に出るのは 5 個（規則名 1、入力 3、出力 1。都道府県は標準取込が別名込み）だけだった。
残り 18 個はヘッダを埋めるだけで、v0 の「全宣言で必須」はこの実測で捨てた。
公開面に別名が欠けているときは、エラー（E011）が不足している名前の一覧と書き足す位置を示す。

**捨てたもの**：

- **自動ローマ字化**：漢字の読みは辞書依存で、「届け先」が `todokesaki` になるか `delivery` になるかを機械が決めた結果は誰もレビューしない。
- **識別子を英語に限定**：セルまで英語になり、P2 の「業務担当者が読める」が崩れる。
- **全宣言での別名必須（v0 案）**：実測で 8 割が公開されない内部名だった。書かせる理由が測って消えた。

[^go-export]: Go 言語仕様の exported identifiers の定義による。先頭文字が Unicode uppercase letter（Lu）であることが公開の条件で、CJK 文字は Lo に属する。非公開識別子に大文字要件はないため、内部の関数名や型名は漢字かなのままで合法である。

### 1.4 Excel と CSV からの取り込み

**決定**：構文レベルでは考慮しない。`rulec import xlsx` と `rulec import csv` が一方向に `.rule` の草稿を生成し、人間がレビューして確定する。`.rule` から Excel への逆方向は作らない。

双方向同期を始めた瞬間に Excel が正本になり、GUI モデラへの一本道が始まる（P7）。
既存の Excel ルールは移行の入口としてだけ扱う。

### 1.5 git diff の読みやすさ

**決定**：`rulec fmt` を唯一の整形器とし、CI で `rulec fmt --check` を強制する（gofmt と同じ運用）。列は表ごとに内容最大幅へ揃え、文字幅は East Asian Width の W と F を 2、それ以外を 1 として数える。全角数字は半角へ、比較記号 ≦ ≧ ＜ ＞ は `<= >= < >` へ、出力列の印 `→` は `->` へ、セルの集合区切り `・` `、` `，` は `,` へ正規化する。名前とセルの値以外に IME を要らなくするためで、`#` コメントと文字列の中は触らない。

既知のコストとして、列の最大幅が変わる編集は表全体を再整列させ、diff が表全体に及ぶ。
再整列は表の中に閉じるので許容し、PR レビュー向けには `rulec changes --base <rev>` が空白を無視した行単位の構造差分（追加行、削除行、変更行、新たに生じた隠れ）を出す。

列幅はヘッダを含む全行の内容最大幅で取る。
出力列のヘッダは型注記を含めて長く（`-> サイズ(size) : サイズ区分` で 28 桁）、値が数桁しかない列がヘッダ幅まで膨らむ。
M0 の実装で見えたこの不格好さは、承知の上で受け入れる。
ヘッダを幅から外す案と、型注記だけ溢れさせる案は、パイプの位置が行ごとに変わって本節の唯一の目標を壊すので捨てた。
そしてヘッダが幅の天井になることには実利がある。
日常の編集（値の修正、行の追加）はヘッダ幅を超えない限り再整列を起こさず、diff が 1 行に閉じる。
余白は、値の編集を局所 diff に保つための買い物である。
転記の現場で実害が出たら、型注記をヘッダの外の行に出す構文変更が指定の逃げ道で、実害が測れるまでは動かさない。

`#` コメントの正準位置もここで凍結する（実装で決めた規則の追認）。
表の行では、最後の `|` より後ろにあるものを行末コメントとして切り離し、整形後の行に空白二つを挟んで付け直す。
表以外の行は、コメントを含めてそのまま残す（行末の空白だけ落とす）。
表の行の途中に `#` を書くと行の残りが消えて列数の不一致になり、構文エラーとして捕まる（静かに欠けることはない）。

数値リテラルは `3万円` `1000万円` の万・億接尾辞と `10_000` の下線区切りを許す。
桁区切りのカンマは、セルの集合区切りと衝突するので許さない。

版と履歴は git に任せる。
ヘッダの `v4` は人間向けの目印で、rulec は生成物ヘッダへの転記だけに使う。
CLI の `送料@v3` という参照は、git タグ `rules/送料/v3` を引く糖衣とする。

### 1.6 検査済みの描画（rulec doc）

**決定**：`rulec doc` は、check を通った規則を markdown に描画する読み取り専用の副コマンドとする。恒等変換ではなく、検査器が知っていて字面に現れない事実を人間の言葉で添えることが仕事である。逆方向（markdown から `.rule`）は作らない。§1.4 と同じ強さの一方向原則で、ここに先に書いておく。

読み手は、承認する立場の人と、PR をレビューする業務担当者である（GitHub は `.md` を表として描画し、`.rule` はしない）。
規則を書く人は `.rule` を直接読むので対象でない。
§11 の五文面が書き手のための面だとすれば、これは承認者のための最初の面になる。

描画する事実は次のとおり。
群の展開と「この分割は全体を過不足なく覆う」という検査済みの言明（`近畿圏` の一語が 6 県を隠し、47 県の被覆は目視では確かめられない。検査器は知っている）。
表の依存（どの出力がどの列へ流れるか）。
隠れの三分類と既定行、W114 とガードの存在。
単位・税区分・丸め格子の列見出しへの畳み込み。
検証済みの例。
導出の式と到達範囲。
`contract_only` と `default` の宣言意図。
そして宣言行の行末コメント。丸めの仮置きの出典（§7.2）がここで承認者の目に浮上する。§16 第三（仮置きの権威化）への防波堤でもある。
検査器の出力に無い文章は書かない。
すべての行が、原本か検査結果に遡れること。

生成物としては扱わない。
コミットせず、CI が生成して PR に貼る（replay の markdown と同じ通り道）。
古い描画が正の顔をして残るのが最大の危険なので、長生きする成果物を作らない。
ヘッダに原本のパスとハッシュと rulec の版を刻み、貼られた先でも古さを検査できるようにする。
入力は check を通った規則に限り、通らない規則は描画しない（壊れた規則の綺麗な描画は嘘になる）。

描画の細目も固定する。
表のセルは AST から組み直さず原本の行から取り、描かれた全セルが原本に字面として現れることをテストが確かめる（創作を仕込むと落ちる腐敗検査つき）。
出力列の見出しだけは畳む（`→ 運賃（金額[円, incl_tax] / up(10円)）`）。
これは §1.6 の「畳み込み」の指定どおりだが、字面一致のゲートの対象外になるので、代わりのゲートを持つ。
畳んだ見出しに現れてよいトークンは宣言に由来するもの（名前、単位、税区分、丸めのモードと格子）だけで、これもテストで縛る。
範囲と証人は 万・億 で書き戻す（書き手が `100万円` と書いたものに `1000000円` と返すと、突き合わせに読み替えが要る）。
`not: 群` の補集合は展開せず、件数を添える（「以外: 遠隔地（残り 45 県）」）。
41 県の壁は目視の確認に耐えず、承認者の一次の問いは基数で答えられ、内訳は群の節の展開から引き算できる。
長い表は畳まない。
47 行の表は 47 行のまま出し、原本との行の対応を要約より優先する。

`rulec changes`（§1.5、残件台帳）とは別物である。
あちらは版と版の構造差分、こちらは今の状態の描画で、PR という行き先が同じでも成果物の種類が違う。
統合しない。

## 2. 型システム

### 2.1 型の一覧

- **列挙**：閉じた有限集合。`enum 会員区分(member_kind) = 一般(basic) | …`。開いた列挙は存在しない。値が増えたら完全性検査が既存の表を割る。これが P4 の完全性の動力源になる。値には `default` を付けられ、「専用の行を持たず、既定の行に落ちるのが意図」を宣言する（付ければ W111 が名指しの無さを問わなくなる。§11）。§1.2 のスケッチでは、プラチナだけが特別で残り二値は既定、という業務の形がこの印で読める。
- **群**：列挙の名前つき部分集合。`group 遠隔地 = 北海道, 沖縄`。セルで値と同格に使える。検査時には常に展開される。実測では 47 都道府県 × 7 サイズ = 329 通りが群で 42 行に縮み、さらに群の分割が 47 県の完全な分割になっているかを完全性検査が保証した。転記の作業そのものが検査される。
- **導出**：入力だけの線形結合（整数定数倍と加減のみ）で定める名前つきの数量・金額。`derive 残余 : money[円, incl_tax] = 商品合計 - 適用済割引 - 額面  range …`。`range` 宣言必須。数量のまま表の列に置ける唯一の中間値で、本体は §5.2 と §6.2。
- **数量**：次元と単位を持つ整数。`mass[g]`。同一次元内の単位換算はリテラルの厳密な整数換算だけ（`2kg` は `2000g` の糖衣）で、実行時値は宣言単位の整数一本である。
- **金額**：`money[円, incl_tax]`。通貨と税区分の二重 brand。税込と税抜の演算は型エラーで、変換演算子は用意しない。税率とその丸めは業務ルールそのものなので、必要なら表として書かせる。円と銭は別単位で、混ぜるには明示の丸めが要る。
- **率**：無次元。リテラル `3%` `0.5%` は正確な有理数として扱う。入力にする場合は `rate[step 0.1%]` と分解能を宣言させ、実行時表現を整数に保つ。
- **真偽**：`true` と `false`。
- **文字列**：等値と集合一致だけ。パターン一致は持たない（§15-1）。
- **日付**：タイムゾーンを持たない暦日。比較と範囲だけで、加減算は持たない。JST 前提などの解釈は呼び出し側の契約に置く。内部表現は元期からの通算日とする。後者関数が +1 と一致するので、境界の ±1、区間の空判定、隣接の合流が整数の機構のまま正しい。`y×10⁴ + m×10² + d` の形は順序こそ保つが、月末と年末に実在しない整数の隙間を作り、`<=2026-03-31` と `>=2026-04-01` で敷き詰めた自然な表に偽の完全性エラーを出す。証人とベクタの ±1 は 1 日を意味する。
- **optional**：`T?`。セルの `none` でだけ消費でき、式には現れない。式に来る前に表で場合分けさせることで、null を算術から締め出す。
- **未丸め**：数量と金額の演算が作る、静的スケールつきの中間型。ユーザが書く構文は無く、推論でだけ現れる（§2.3、§7）。

完全な次元解析はやらない。
次元の掛け合わせ（円×g のような合成次元）が業務ルールに現れたら、それはモデリングの誤りとしてエラーにする。
必要なのは brand の混同防止までで、そこで止める（前提のとおり）。

### 2.2 宣言場所と範囲宣言

**決定**：型はファイル内宣言と `import` の二段だけ。`import` はパスを引数に、型、群、単位の宣言だけを取り込む。表と定義は取り込めない。組み込みの `std/` 名前空間に、都道府県（47 値、ASCII 別名込み）、質量（g、kg）、長さ（cm、m）、金額（円、銭）、率、日付を同梱する。都道府県の別名はヘボン式で長音を落とす表記（Hokkaido、Oita）で凍結した。訓令式にしないのは、自治体の英語表記の慣行に合わせるためである。

数量、金額、率、日付の入力と、すべての導出には `range` 宣言を必須とする。
入力の範囲は三役を兼ねる。
オーバーフロー証明の前提（§7）、完全性検査の全体集合（40kg 超の行を書かなくてよい根拠）、生成コードの入口ガード（§8）である。
上限のない金額入力は業務にも存在しないので、書かせることが仕様の発掘になる。
導出の範囲は検査の軸の全体集合になり、健全性のための包含条件を負う（§6.2）。

**捨てたもの**：**中央型レジストリ**（リポジトリ横断の型サーバのようなもの）。ファイルと取込で足りる規模の道具に、名前解決のインフラを持ち込まない。

### 2.3 演算規則

| 式 | 結果の型 | 備考 |
|---|---|---|
| 金額 ± 金額（単位・税区分が同一） | 金額。丸め済＋丸め済は丸め済、未丸めが混ざれば未丸め | 税込と税抜の混合は E103 |
| 金額 × 整数定数 | 左と同じ丸め状態 | 厳密 |
| 金額 × 率 | 未丸め金額 | スケールが積になる |
| 金額 ÷ 正整数定数 | 未丸め金額 | |
| 金額 ÷ 金額定数（同単位・同税区分） | 未丸め無次元数 | 「100円につき1点」用 |
| 数量 ± 数量（同次元） | 数量 | 単位換算はリテラル位置のみ |
| 数量 × 率、数量 ÷ 定数 | 未丸め数量 | |
| 数量 ÷ 数量定数（同次元） | 未丸め無次元数 | 「100gごとに」用 |
| 率 ± 率、率 × 率 | 率 | 厳密な有理数 |
| 比較 `< <= > >= =`（同型） | 真偽 | 未丸め同士も厳密比較（共通スケールへ静的に揃える） |
| 最小(a, b)、最大(a, b)（同型） | 同型 | |
| 丸めモード(式, 格子) | 丸め済 | 未丸めから戻る唯一の道 |

禁止するもの：金額×金額、税込±税抜、異次元の混合、**変数による除算**、日付の加減算。
変数除算を禁じるのは、スケール（§7）を静的に決めるためである。
割る数が業務データなら、それは率か定数表のどちらかとして表に現れるはずで、実際 P1 から P2 の領域（送料、クーポン、ポイント）では、変数除算が要る計算は一つも挙がらなかった。
挙がったら §15 で扱う。

### 2.4 丸め済と未丸めを別型にする案の是非

**決定**：採用する。ただしユーザに未丸め型を書かせない。演算が値を自動で未丸めへ持ち上げ、丸め関数だけが丸め済へ戻す。

「丸め前の値が出力に漏れない」（P4）は規約では守れず、型でしか守れない。
一方で型を二重にする複雑さは実在するので、その支払いを書き手ではなく検査器に寄せる。
書き手が未丸め型に出会うのは、丸めを書き忘れたときのエラーメッセージの中だけである（E104、§11）。

**捨てたもの**：**丸めを暗黙適用して型を一本化する案**。表の出力セルに `805円` と書いたとき、出力宣言が `up(10円)` だからと黙って 810 円にする道具は、差分を見る道具として自殺である。リテラルが格子に載っていなければエラーにする（E106）。

## 3. セルに書けるもの

**決定**：セルの単項テストは次の七種で全部である。空セルは構文エラー。テストの対象になる列は、入力、導出、真偽と列挙の中間値である（§5.3）。

1. `-`：don't-care。任意の値に一致する。don't-care の表記はこれ一つだけで、空欄を don't-care と解釈しない（書き忘れと区別がつかなくなる）。
2. リテラル一致：列挙値、`true` `false`、`2000g`、`1200円`、`2026-04-01`、`"WELCOME10"`、`none`。数量と金額のリテラルには単位が必須で、裸の `2000` はエラー（「2000g ですか」と聞き返す）。
3. 集合：`北海道, 沖縄`。いずれかに一致。要素はリテラルか群名。
4. 補集合：`not: 北海道, 沖縄`。集合にも群にも付けられ、意味は宣言された全体集合に対する補集合で、行単体で閉じている。
5. 比較：`<=2000g` `>2000g` `>=2025-04-01` など四種の演算子。全角の ≦ ≧ ＜ ＞ も受け、fmt が正規化する。
6. 区間＝比較の並記：`>=1000円 <20000円`。空白区切りは連言。空区間は型エラー。
7. optional 列に対する `none`。比較とリテラルは値が在るときだけ一致し、`none` には `-` と `none` だけが一致する。

### 3.1 境界の開閉の表記

**決定**：範囲は必ず比較演算子で書く。`..` を使った範囲記法は、片側でも両側でも構文エラーにする。

当初スケッチの `..2000g` と `2000g..` は、この道具がいちばん守りたい場所に曖昧さを残す。
「2000g まで」は日本語では両端含みに読めるが、`..2000g` を含みに解釈すると隣の `2000g..` と 2000g ちょうどで重なり、排他に解釈すると業務の読みと 1g ずれる。
数学の `[0, 2000)` は開閉が正確だが、括弧の向きの規則を業務担当者に教えることになる。
比較演算子は全員が既に読めて、開閉の解釈が一意で、教えることが何もない。

隣接する行を `<=2000g` と `>2000g` で書けば敷き詰めは目で追える。
`<=2000g` と `>=2000g` と書き間違えれば、重なり検査が「重量=2000g が両方に当たる」という証人つきで捕まえる（E105）。
境界の曖昧さを構文で禁じ、貼り合わせの誤りを検査で拾う、という分担である。

**捨てたもの**：

- **半開区間を既定にする案**（`a..b` を a 以上 b 未満と定める）：敷き詰めは美しいが、「まで」の直感と静かに 1 単位ずれる。静かにずれる仕様は、この道具では最悪の性質である。
- **セル内の区間の合併**（`<500g, >30kg` のような書き方）：行を二つに分ければ書ける。実測（運賃表とクーポンの転記）で必要になった箇所は 0 件で、v1 から外すことが決着した（旧 §15-1）。
- **列をまたぐ条件をセルに書くこと**：セルは自列への単項テストに限る。複合条件は `define` で名前を付けて真偽列にするか、入力の線形結合なら `derive` にする（§5.2）。この制限が検査の決定可能性の土台になる（§6）。実測でいちばんきつい試金石は、ヤマトの「3 辺計と実重量を比較し、大きい方のサイズの扱いになる」規約だったが、列ごとの単項テストと `first` でそのまま書けた。50cm/8kg の荷は 60 サイズ行を重量で外れ、80 も外れ、100 で当たる。
- **正規表現・前方一致**：クーポンコードの実形式を見るまで入れない（§15-1）。実測の公開規約では、文字列そのものが列に一度も現れなかった。
- **セル内のパス式・量化子**（`注文.配送先.都道府県`、`some … satisfies …`）：実在の DMN 業務資産（伊 ANAC の調達規則）はセルが任意の FEEL 述語で、我々はヒットポリシー以前にセルの言語で受け付けない。それでよい（§0）。入れ子は境界で平たい入力に潰してから渡し、セルには入れない。射影の宣言と生成という拡張候補は §15-6。

### 3.2 出力セルに書けるもの

**決定**：出力セルにはリテラルのほかに、名前（入力、導出、定義）を書ける。式は書けない。

リテラル限定では書けない規則が実在する。
楽天の複数クーポンは「％引きクーポンを先に適用し、その後円引きクーポンを適用する。パーセンテージ割引は商品の元価に対して計算される」という規約で、クーポン種別によって割引の基準額が変わる。
率引き行の出力は「元価 × 割引率」という計算値であり、リテラルでは書けない。
リテラル限定のまま逃げるなら率クーポン規則と額クーポン規則にファイルを割ることになるが、どちらを呼ぶかの判断がホスト言語へ漏れる。

式そのものをセルに許さないのは、表を眺めて桁が読める性質を保つためである。
計算には `define` で名前を付けさせ、セルからは一往復で辿れるところに置く（§5.4 のスケッチにこの形がある）。
名前の丸め状態は列に合流し（どれかが未丸めなら列は未丸め）、E106 の静的な格子検査はリテラルにだけ適用する（§7.2）。
領域解析は入力側の列だけで行われるので、この拡張は完全性にも重なりにも影響しない。

名前の先の `define` がさらに前の定義を参照する連鎖は、構文上は無制限である。
それでも機械的な深さ制限は置かない。
コーパスの実測は深さ 1 で、根拠なく選んだ上限は恣意にしかならないからである。
深い連鎖が実表に現れたら、そのとき件数を数えて W 系の lint として決める。

**捨てたもの**：

- **出力セル内の式**：表が計算式の置き場になり、P2 の可読性が崩れる。名前を一つ挟む往復が、複雑さの上限として働く。
- **表出力の名前参照**：`result` で書けることと重複する。拡張は実測が要求した最小に留めた。

## 4. ヒットポリシー

**決定**：採用は二つ。`policy unique`（DMN の Unique）と `policy first`（DMN の First）。既定は `unique`。単一ヒットの二方式だけを採るので、完全性は全表で常に必須とし、宣言項目にしない（この不変が単一ヒットの性質であることは本節末尾に記す）。

`unique` は解析がもっとも強く効く方式で、行の重なりはすべてエラーになる（E105）。
順序に意味がないので、行の並べ替えが意味を変えない。
既定を `unique` にするのは、順序依存を書き手に意識して選ばせるためである。
実測でも二方式は同一ファイルの中で共存した。
ヤマトのサイズ判定は階段なので `first` が合い（`unique` で書くと `>60cm <=80cm` の区間並記になり、同じ境界を二度書くことになる）、運賃表は重なりようがないので `unique` である。

`first` は「例外を先に、一般則を後に」という業務の書き方をそのまま受けるために要る。
最後に全部 `-` の行を置く書き方が既定行になる。
`first` でも完全性と、先行行に完全に覆われて決して当てはまらない行（E102）はエラーである。

部分的な隠れの扱いは、M0 の実装が教えた事実で設計を直した。
v1 は「隠れはすべて証人つきの注記（W105）」としていたが、階段表ではそれが信号にならない。
ゆうパックのサイズ判定は 7 行の階段で 21 対すべてが重なり、しかも階段は出力が全部違うのが正常なので、「出力が同じ重なりは冗長」という文言の区別も効かない。
`--diff-base` も、階段への 1 行追加で良性の新規対が 6〜7 個まとめて出る。
そこで `first` の隠れ対を三つに分類する。

- **階段**：後の行の領域が前の行の領域を包含する（交わりが前の行の領域そのもの）。階段と既定行がこれで、`first` を選んだ時点で書き手が意図している構造である。既定では件数だけ報告する。
- **同じ答え**：包含でない部分交差だが、両行の出力が同じ。「〜なら不可」を並べる守り行が互いに交わる形で、どちらが勝っても値は変わらない。既定では件数だけ報告する。
- **要確認**：包含でない部分交差で、出力が異なる。順序が円を変える唯一の形で、これだけを証人つきで一覧する（W105）。合意した五つ目の文面「意図通りですか」の仕事は、この分類が引き継ぐ。

この分類で、ゆうパックの 21 対は全部が階段、クーポンの適用可否の 10 対は階段 4 と同じ答え 6 になり、どちらも一覧はゼロになる。
例（§1.2）の負担判定の 行1×行2（0% と 50%）は要確認として残る。
黙る二分類には安全網が残っている。
階段の並びの事故は包含の向きが逆転して当てはまらない行になるから、注記ではなく E102（エラー）が捕まえる。
同じ答えの対は、片方の出力を後で変えた瞬間に要確認へ遷移して一覧に現れる。
全対は `--show-shadow` で一覧でき、既定の出力は「隠れ 21 対（階段 21、同じ答え 0、要確認 0）」という件数の注記になる。
CI の `rulec check --diff-base <rev>` は要確認の対の集合で差分を取り、新たに生じた分（同じ答えからの遷移を含む）だけを浮かせる。
対の同一性は行番号ではなく、セルの正規形から作った鍵で照合する。
行を挿入しても fmt が再整列しても鍵は変わらず、既知として伏せた対があるときは伏せた件数を言う。
隠れの既知集合をファイルに書かせる案（行番号での承認リスト）は、行の挿入で番号が静かにずれる罠なので捨てたままである。
状態は git の履歴に置き、rulec 自身は無状態を保つ。
逆向きの検査（重なりが一つもない `first` に `unique` を提案する W110）は、実装の初回から有用だった。

当初スケッチにあった `完全性 = 必須` という宣言は落とした。
宣言できるなら宣言し忘れが生まれ、既定 OFF の完全性検査は P4 に反する。
穴を許したい表は書けない。それがこの道具である。

公開の実使用も測った（2026-08、GitHub のコード検索。`.dmn` 17,536 ファイル、数字は一致ファイル数）。
FIRST 4,568、UNIQUE 2,384（宣言なしの約 8,000 は既定の UNIQUE なので、実質シェアは 6 割前後）、COLLECT 1,720、PRIORITY 518、ANY 326、RULE_ORDER 2、OUTPUT_ORDER 0。
採用した二方式が実使用の一位と二位で、捨てた側では COLLECT だけが突出する（PRIORITY と ANY の合計の 2 倍）。
ただしこの数字には限界が三つある。
一ファイルに複数の表が入りうること、コード検索の順位が非ランダムなこと、そして企業の DMN は SaaS の中にあって公開リポジトリに出てこないこと。
一番知りたい母集団が、最も薄い。

**捨てたもの**：

- **A（Any、326 件）**：出力が同じなら重なりを許す方式。今日同じでも明日の編集で片方だけ変わる。重なりは冗長でも検出したい対象（Calvanese らの言う redundancy）で、表現力も増えない。重なりの出力が一致している表は、行をそのまま `first` に写せば同じ関数になる。
- **P（Priority、518 件）**：優先順位が出力値の順序という別の場所に書かれる。優先は紙面の上下で見えるべきで（P4）、行を優先順に並べ替えれば `first` がそのまま P である。表現力は増えない。
- **C（Collect）と集約**[^dmn-multi]：実在する（上の調査で 1,720 件）。ただし出所を深いページで 200 件掘ると 51% がエンジンやツール由来で、業務モデルの候補は 26%、うち 6 割は伊 ANAC（反汚職庁）の一つの調達規則集だった。その実物と英 HMCTS のタスク設定が C で行っているのは「当てはまる項目を全部集める」＝検証であって、金額の集約ではない。つまり C の採否はヒットポリシーの選択ではなく、検証という別の仕事を範囲に入れるかどうかの決断である。単一の値を計算する道具でいる限り、要らない。前回ここに書いた「実測のクーポン転記でも集約は要らなかった」は撤回する。書けるように書いた自選の二表から、必要性の不在は導けない（測り直しは §15-8）。クーポンの重ね掛けが粒度の構成で書けること自体（§5.4）は、構成を示した事実として残る。

C を入れる日に何を失うかも、ここに記録しておく。
労働基準法の割増賃金は「重なると足す」の教科書例に見える。
時間外 25%、法定休日 35%、深夜 25% で、厚労省の計算例には休日深夜 1.60（1.35 ＋ 0.25）が明記されている。
ところが法定休日労働には時間外という概念がなく、8 時間を超えても 35% のままなので、素朴な合計は休日＋時間外に 60% という違法な答えを出す。
正しく書くには時間外の行に「法定休日 = 偽」という排他を書き込むしかなく、それを書いた瞬間、表は単一ヒットと同じ仕事をしている。
違いは一点だけで、単一ヒットならその排他の正しさを完全性と重なりの検査が確かめるのに対し、合計方式では重なりが仕様そのものになるため、どちらの検査も意味を失う。
この道具の検査能力は、単一ヒットの上に立っている。

検証の形の需要も、表現力だけなら今日の道具で書ける。
検査項目ごとに真偽の出力を持たせれば表になり、当たった項目を集めるのはホストの一行で、各項目は網羅と重なりの検査を受ける。
C が買うのは簡潔さであって表現力ではなく、支払うのは排他と網羅の保証である。
この取引を受けるかどうかが、上の「範囲の決断」の中身になる。
本節の「完全性は常に必須」と「表は値を一つ返す」は、単一ヒット方式の性質として述べている。
C を入れる日は、この二つの不変を検証の意味論のために作り直す日で、ヒットポリシーを一つ足す変更では済まない。

[^dmn-multi]: DMN の multiple hit にはほかに R（Rule order）と O（Output order）があるが、公開の `.dmn` 17,536 件で R は 2 件、O は 0 件だった。標準に載っていても誰も使わないものは実在する。DMN を全部実装しないという方針の、実測の裏づけでもある。

## 5. 表の合成と中間値

### 5.1 線形パイプライン

**決定**：合成はファイル内で完結する線形パイプラインとする。`derive`、`define`、`table` は上から順に名前を導入し、後のものは前の名前だけを参照できる（define-before-use）。最後の `result` が出力を束ねる。DRD に相当する図は作らない。

前方参照を許さないので循環は構文的に存在せず、ファイルを上から読めば依存が読める。
ファイルの並び順そのものが DRD である。
規則が図を要するほど育ったら、それは規則の分割が要る徴候として扱う。

実測では運賃が実際に 3 段の連鎖（県から地帯へ、地帯とサイズから運賃へ）を要求した。
発地と着地の対応は静的な部分集合である群では表せず、表の連鎖でだけ書ける。
最大の表は 144 行、列 3 で、§6.3 の設計目標の内側の規模だった。

表は複数の出力列を持てる。
意味はタプルで、各出力が独立の名前と型を持つ。
`->` は入力と出力の境目を一度だけ示す印で、最初の出力列に付ける。
境目より後ろの列は、印の有無にかかわらずすべて出力である（パーサは余分な `->` も受け、fmt が正準形に畳む）。
列ごとに印を要求する v0 の形は、二列目の印の書き忘れが列を黙って入力へ化けさせた実測（M1 の例の検査）で捨てた。
例も同じ綴りで、出力が複数なら期待値の列を出力の数だけ並べる。

規則から規則を呼ぶことはできない。
上流の規則の答えが要るなら、それは入力として宣言し、呼び出し側が渡す。
これは P3 の「外から来るものはすべて入力」の合成への一般化で、二つの利益がある。
規則単位で過去再生が閉じる（送料の replay にクーポンの実装が要らない）ことと、規則間の版の組合せ爆発を呼び出し側の責任に置けることである。

### 5.2 導出

**決定**：「導出」を入力、定義、表出力に並ぶ第四の名前つき値として一級にする。右辺は入力だけの線形結合（整数定数倍と加減のみ）で、上流の表の出力も定義も使えない。`range` 宣言必須。数量・金額のまま表の列に置ける。

```
derive 残余(margin) : money[円, incl_tax] = 商品合計 - 適用済割引 - 額面
  range >=-110万円 <=100万円
```

なぜ要るか。
実測で、値引き後の金額で判定する規約が二件見つかった。
楽天は送料無料ラインをクーポン利用前の購入合計で判定する一方、39 キャンペーンのポイント条件はクーポン適用後の金額で判定する。
同一プラットフォームの中で、特典ごとに判定の前後が違う。
Yahoo には「値引き額が商品合計を上回るか同額ならクーポンは適用されない」という判定がある。
どちらも「入力 − 入力」の線形結合で、これを列に書けないと、値引き後という一番間違えやすい引き算が呼び出し側の裸の一行になり、単位も税区分も丸めも検査されない。
OSS の EC 実装にも同じ形がある。
Saleor はカタログ割引を先に計算し、その後の価格にオーダー割引を適用する。
値引き後の金額を次の判定と計算が使う形の、これで三例目である。

なぜ線形結合までか。
実測で列に要求されたのは線形結合だけで、率 × 金額のような非線形は `result` と `define` にしか現れなかった。
そして線形結合なら、検査の決定可能性を箱代数のまま保てる（§6.2）。
整数定数倍と加減は丸め済のまま閉じて厳密な int64 で計算できるので、丸めの新しい場所も生まれない（§7.1）。

範囲宣言は検査の軸としての全体集合になる。
宣言は、入力範囲から区間演算で計算した到達区間を含まなければならない（E112）。
含まないと完全性検査が実際に到達する値を見ず、不健全な緑が出るからである。
到達区間より広い分は実現不能領域として篩われるので害はない（§6.2）。

### 5.3 列に使える値と真偽定義の原子

**決定**：表の列に使えるのは、入力、導出、そして真偽と列挙の中間値（定義と表出力）である。数量と金額の中間値（表出力と一般式の `define`）は列に使えず、`result` と式の中でだけ使える。真偽の `define` の原子は二形。セルの単項テスト（§3）を入力か導出に適用したものと、導出で差の取れない型（日付、列挙）に限った同型の入力・導出どうしの比較（`A期限 <= B期限`。日付は四種の比較、列挙は等値。型の一致は §2.3 に従う）である。数量・金額・率どうしの直接比較は E113 のままとし、差を導出として宣言してから定数と比べさせる。そのほうが厳密に解析できるからで、精度の規律（下記）が数値には導出という正しい家を既に持っている。連言、選言、否定を許す。名前どうしの比較はセルには書けない（セルは単項のまま）。

v0 草案にはここに抜け道があった。
数量の定義（`適用後金額 = 注文金額 − 割引額`）を真偽の定義（`適用後金額 >= 3980円`）が参照でき、その真偽が列に置けたので、`x − y >= c` という半空間が列に入り込み、§6.2 の「定義は DNF 展開で箱和になる」が原子の形の前提ごと崩れていた。
原子を入力と導出に制限することでこの穴を塞ぐ。
線形結合が要るなら導出として宣言させ（E113 が書き換えを提示する）、表出力との比較が要るなら、その表に真偽の出力列を足すのが正しい書き方である。

名前どうしの比較の原子は、適用順序の規則が要求した。
§5.4 の「期限が近い順」は二つの日付入力の比較そのもので、日付に減算が無い以上、導出（差を取って定数と比べる形）では書けない。
これを許しても検査は壊れない。
真偽の定義は解析では自由な真偽軸として扱われ（§6.2）、原子の形が何であれ扱いは変わらないからである。
一方、数量の定義への参照を禁じる E113 は残る。
自由軸として健全に扱えるかどうかの問題ではなく、導出にすれば厳密に解析できるものを、怠けて不透明にさせないという精度の規律である。

### 5.4 規則の粒度

**決定**：規則の粒度は「一回の判定」に固定する。可変個数のものを規則の中で畳み込まない。リスト型も集約も導入しない。

クーポンは可変個数で、併用の順序があり、枚数の制約がある。
これを解くのはリスト型ではなく粒度である。
規則は「このクーポン 1 枚は適用できるか、いくら引くか」を答える純関数で、重ね掛けの順序と反復は呼び出し側が持つ。
順序が呼び出し側にあるのは欠点ではない。
順序こそが業務判断であり、規則の中に隠すべきではないからである。

適用順序そのものも規則として書ける。
楽天の「％引きが先、円引きは有効期限が近い順」は、`(A種別, B種別, A期限, B期限) → 先/後` という二引数の純関数になり、呼び出し側はこれを比較関数としてソートに渡す。
反復はホスト、判定（比較を含む）は規則、という分担が一貫する（期限の比較は、真偽定義の名前どうしの比較の原子で書く。§5.3）。
有効期限の比較が要るので、日付型は v1 に入る（旧 §15-7 は逆向きに決着した）。
併用の制約も入力で書ける。
「対象商品指定クーポンは同一商品に 2 枚以上使えない」は、`同商品適用済 : bool` を入力にすれば表になる。
状態はホストが持ち、P3 のままである。

クーポン 1 枚の規則のスケッチを示す。
導出（§5.2）と出力セルの名前（§3.2）もここに現れる。

```
rule クーポン一枚(coupon_step) v1
description "クーポン1枚の適用可否と素割引。重ね掛けの順序と反復は呼び出し側が持つ"

enum クーポン種別(coupon_kind) = 率引き(percent) | 額引き(fixed) | 送料無料(free_ship)

inputs
  商品合計(subtotal)  : money[円, incl_tax]  range >=0円 <=100万円
  適用済割引(applied) : money[円, incl_tax]  range >=0円 <=100万円
  種別(kind)          : クーポン種別
  割引率(rate)        : rate[step 1%]     range >=0% <=100%
  額面(face)          : money[円, incl_tax]  range >=0円 <=10万円
  同商品適用済(dup)   : bool

outputs
  可否(ok)     : bool
  素割引(raw)  : money[円, incl_tax]  round down(1円)  # 端数処理は公開規約に記載なし。切り捨てに仮置き

derive 残余(margin) : money[円, incl_tax] = 商品合計 - 適用済割引 - 額面
  range >=-110万円 <=100万円

define 率割引 : money[円, incl_tax] = 商品合計 × 割引率

table 適用可否
policy first
| 種別   | 残余  | 同商品適用済 | -> 可否 : bool |
| -      | -     | true         | false          |
| 額引き | <=0円 | -            | false          |
| -      | -     | -            | true           |

table 素の割引
policy unique
| 可否  | 種別     | -> 素割引 : money[円, incl_tax] |
| false | -        | 0円                             |
| true  | 率引き   | 率割引                          |
| true  | 額引き   | 額面                            |
| true  | 送料無料 | 0円                             |
```

二つの出力はどちらも同名の中間値を持つので `result` は省略されている（§1.2 の糖衣）。
`素割引` 列は、リテラル（丸め済）と `率割引`（未丸め）が合流するので列として未丸めになり、出力宣言の `down(1円)` が一度だけ掛かる（§7.2）。

畳み込みそのものを宣言にする案（順序規則、一段の規則、アキュムレータを指定し、参照評価器が畳み込みまで実行する形）は、ここで検討して v1 では見送った。
宣言にすれば検査の網（実装間の一致、過去再生）が畳み込みまで届き、手書きの fold のバグはこの網のどれにも掛からないから、魅力は本物である。
見送りの決め手は、単一アキュムレータの畳み込みが、動機になった当のクーポンをまだ表せないことにある。
併用制約の入力 `同商品適用済` は「これまでに適用したクーポンの対象商品の集合」から来る状態で、残額一本のアキュムレータからは導けない。
塞ぐ道は二つしかない。
段ごとにホストが状態を注入する形は、畳み込みが閉じなくなり、評価器が実行できるという肝心の利点そのものが消える。
アキュムレータに集合を許す形は、コレクションが型システムに入り、P7 への圧力になる。
どちらも、実畳み込みの根拠が楽天の一件だけの今に払う理由がない（採否の測定は §15-5）。

それまでの緩和として、**連鎖の例**の慣行を置く。
連続する `examples` 行で一続きの場面を書き、行 k の `適用済割引` に行 k−1 までの結果を手で入れる。
評価器が各段を検査し、ホスト両実装の端から端までのテストが同じ表を fixtures として共有できる。
新しい構文はゼロで、畳み込みの「データとしての仕様」だけが規則側に残る。

**捨てたもの**：

- **DMN DRD 相当の規則間依存グラフ**：GUI モデラの引力の中心。ファイル内線形で書けない規則は分割の合図とみなす。
- **規則間 `import`（表の再利用）**：共有したくなるのは型と群で、実際に共有できるのもそこまで。表の共有は「どの版を共有しているのか」問題を持ち込む。
- **リスト型と規則内の畳み込み**：可変個数は粒度で規則の外に出す（§5.4）。値引きの明細行への按分は、逐次充当型ならこの粒度で書ける（§15-7 で測定済み）。比率按分が書けないのは粒度ではなく除算の制限による（§7.4）。

## 6. 検査の実装方針

### 6.1 何を検査するか

先に、全検査に共通する保証の向きを固定する。
**見逃さない**。
緩めるときは常に過剰報告の方向へ緩め、不健全な緑（実際には成り立たない「検査済み」）はどの検査も出さない。
この改訂で入った変更（導出の軸化、実現可能性の篩、実現可能性未検証の札）はすべてこの向きに倒してあり、以降の各所で個別に確認する。

- **E101 完全性**：どの行にも当たらない入力領域の検出。導出が入っても健全なまま（§6.2）。
- **E102 当てはまらない行**：どの入力にも到達されない行の検出（`first` では先行行への完全被覆、`unique` では到達不能な上流値も含む）。
- **E105 / W114 / W105 重なり**：同じ入力に複数行が当たる状況の検出。`unique` では実在を確認できた重なりだけが E105（エラー）で、確認も反証もできなかった重なりは W114（警告）に落ち、生成コードのガードが引き受ける（§6.2、§8.1）。`first` は隠れ注記（W105）。出力が異なる重なり（矛盾の恐れ）と同じ重なり（冗長）は文言を分ける。Calvanese らの contradiction と redundancy の区別[^calvanese]に対応する。偽陽性が出うるのは導出が絡む場合に限る（§6.2）。

[^calvanese]: Calvanese, Dumas, Laurson, Maggi, Montali, Teinemaa. "Semantics and Analysis of DMN Decision Tables" (BPM 2016, arXiv:1603.07466)。欠落ルールと重複ルールの検出を決定表の幾何として定式化している。検出対象の分類はこの論文に合わせ、実装は下記のとおり独自に決める。

### 6.2 区間の格子で足りるか

**決定**：足りる。SMT ソルバは v1 では使わない。検査の空間を「各入力と各導出を独立の軸とする圧縮座標」に取り、すべてを**箱（直積領域）の有限和**の代数として実装する。導出の従属関係（残余 = 商品合計 − 適用済割引 − 額面 という等式）は空間には入れず、**実現可能性の篩**として発見の報告段で回収する。

まず箱和に閉じる根拠は、§3 と §5.3 の構文制限がちょうど決定可能性の境界に置いてあることによる。

- セルは自列への単項テストしか書けないので、行は「軸ごとの部分集合の直積」、すなわち箱の有限和になる（`not` と集合は座標の合併）。真偽の `define` は自由な真偽軸として扱い、原子の中身は領域解析に入れない。当初の設計は DNF 展開で代入する予定だったが、M0 の実装は自由軸で出荷され、これを設計に昇格する。真も偽も到達可能とみなすのは過剰報告の向きで、完全性の見逃しは生じず、E102 は相関起因の死を黙って見送るだけで偽の「決して当たりません」を出さない。行が直積のままなので、隠れの包含判定の速い形（§6.3）の前提も保たれる。
- 列に使える中間値は真偽と列挙に限られるので、中間値の各値の逆像（軸空間でその値になる領域）も帰納的に箱の有限和である。上から方式の「行 i が勝つ」も先行行の補集合との交差で、圧縮座標上では補集合も箱和に閉じる。

閉性自体は自明（圧縮格子の任意の部分集合は箱和）で、問題は大きさと、導出を独立軸にしたことで空間に混ざる「実在しない点」（等式を満たさない座標）である。
後者を篩が引き受ける。

- **篩**：箱 B と導出 d = f(入力) について、f を B の入力部分の区間に区間演算で適用した結果が B の d 区間と交わらなければ、B は実現不能。線形な f の区間評価は厳密で、判定は導出 1 本あたり定数時間。ソルバは要らない。
- **完全性（E101）は健全なまま**：軸の全体集合は導出の宣言範囲で、E112 が到達区間の包含を強制するので、実空間の穴は必ず軸空間の穴として現れる。篩は「実現不能と証明できた穴」だけを報告から外す。したがって偽の緑は出ない。証明しきれない実現不能の穴が報告に残ることはある（過剰報告の向き）。
- **重なり（E105/W114/W105）**：交差箱にも同じ篩を掛け、実現不能と証明できた発見は出さない。残った発見は、証人の入力を実際に構成して評価器で確認できたかどうかで重大度を分ける。構成できた重なりは実在が確認された矛盾で、`unique` では E105（エラー）。構成できず、実現不能の証明もない重なりは、`unique` でも W114（警告）に落とす。未証明の存在で CI を止めないためである。ただし警告に落とすだけでは足りない。行の排他は生成器が分岐の並びを正当化する前提でもあり、未検証のまま何もしなければ、その重なりが万一実在したとき `unique` が宣言なしの `first` に静かに化ける。そこで生成コードに**ガード**（当該行対の実行時の排他検査）を入れる（§8.1）。両方の行の条件を評価し、同時に当たる入力が来たら黙って先の行を選ばずエラーを返す。静的に閉じなかった証明義務を実行時検査が引き受ける分担は、入力範囲の入口ガードと同じである。出力が構文的に同一の行対は、どちらが選ばれても値が変わらないのでガードを省く。`first` の隠れは宣言された順序が解決するので、従来どおり W105 の注記のままでガードも要らない。導出が複数あって入力を共有すると、導出ごとに独立な区間篩は従属を見ないため W114 が出やすくなるが、外れる向きは常に過剰報告で、見逃しは生じない。
- **当てはまらない行（E102）**：残余箱にも篩を掛け、証明できたときだけ報告する（未証明の「決して当たりません」を断定しない）。残余が空でなくても全箱の実現不能が証明できたなら、「この行に当たる実入力は存在しない」の文面変種で報告する。
- **定義軸の証人**：真偽定義（名前比較の原子を含む）が絡む発見の証人は、入力を構成して定義を評価器で計算し、軸の値と一致することを確かめてから出す。構成できない `unique` の重なりは導出と同じく W114 に落ち、ガードが引き受ける（ガードの条件は原子を実行時に評価するだけなので、そのまま生成できる）。精度が足りないときの増強も決めてある。単項原子の DNF 代入（当初設計）で、発動条件は自由軸起因の過剰報告が実表で邪魔になること（§15-9）。M0 の篩は導出軸までで、定義軸の証人検証と W114 降格はガードの生成と対で M1 が実装する。それまでの正直化として、定義列が交差に絡む E105 の文面には「この例は定義の中身との整合を確認していません」の一行を足し、証明済みの顔を避ける。

保証の非対称を一行で言えば、**完全性は健全なまま、重なりと当てはまらない行には偽陽性が出うる。ただし偽陽性はエラーではなく W114 とガードの形で現れ、エラーで止めるのは実在を確認できたものだけ**、である。
導出が 1 本だけの表では篩はほぼ厳密に効く（残るのは整数の粒度による過大評価だけ）。
一方、導出が入力を共有する形は仮定の話ではない。
コーパスのクーポン規則が最初から含んでいる（`最低差` と `支払差` が `現在残額` を共有する。tests/corpus/クーポン割引.rule）。
当の表は `first` なので W114 の実害はまだ出ていないが、`unique` で同じ形が書かれる前提は既に現実である。
W114 が実表に積もるか、ガードに本番で当たりが出たら、そのときの増強も決めてある。
箱の線形制約系への Fourier–Motzkin 消去で、有理数演算のまま厳密、決定的、外部依存なしに実現可能性が正確になる。
v1 には入れない（§15-4）。

数量の中間値（表出力や一般式の `define`）を列に許すと、行の領域に任意の従属が現れて篩の形にも収まらない。
§5.3 の制限はこのためにあり、v0 ではこの制限に抜け道が実際に開いていた（同節）。
導出は、その表現力のうち実測が要求した部分（入力の線形結合）だけを、篩で回収できる形に限って取り込み直したものである。
非線形の列条件は実測で一度も現れず、旧 §15-3 の SMT 導入案は当面不要と決着した。

### 6.3 アルゴリズムと計算量

- **正規化**：群を展開し、`not` を補集合化する。真偽の `define` は自由な真偽軸として加える（§6.2）。導出は独立の軸として加える。上流表の出力（真偽・列挙の中間値）も独立の軸とし、逆像の展開はせず、座標を上流が出力セルで実際に出す値に制限する（M0 の実装判断。値の到達までを見て、組合せの相関は追わない。外れは過剰報告の向きで、E102 の上流値変種は空になった行マスクとして当てはまらない行の検出にそのまま乗る）。各軸の座標を、その軸に現れる全境界値で圧縮する（列挙は値ごと、数値は境界で区切った区間ごとに 1 座標、真偽は 2 座標）。隣接する境界の差が刻み（日付は 1 日、数量・金額は 1、率は宣言の刻み）ちょうどのときは、あいだの開区間の座標を作らない。値を一つも含まない座標は幻の穴になる。通算日への変更だけでは足りないことは、M0 の両端含みの敷き詰めが実測で示した。
- **実現可能性の篩**：発見（穴、交差、残余）の箱数に比例し、1 箱あたり導出本数 × 定数時間。探索予算には効かない。
- **隠れの三分類**（§4）：包含の意味は「前の行の領域 − 後の行の領域 = ∅」である。現行の断片では行は軸ごとの部分集合の直積（単一の箱）なので、この判定は軸ごとの部分集合検査と厳密に一致し、実装はその速い形でよい。M0 で領域減算の実装が合成ベンチを落とし（減算は軸数に指数的）、直積の性質に置き換えて三分類の件数の不変を確認した。行が箱の和になる拡張（真偽定義の代入や表出力の逆像を分類に持ち込むとき）では軸ごとの検査は近似になるので、減算へ戻す。篩は掛けず、実現不能な断片のせいで包含が崩れる対は要確認側へ倒れる。外れる向きはここでも過剰報告で、見逃しは生じない。
- **重なりと隠れ**：行対ごとの箱の交差判定。行数 r、列数 c、行あたり箱数 b として O(r²·c·b²)。r が数百、c が十数なら瞬時である。証人は交差領域から、列挙は宣言順の最小値、数値は境界値を優先して選ぶ。
- **完全性と当てはまらない行**：列を圧縮座標数の昇順に並べた再帰分割で、全体集合から行の箱を引いていく。残り列がすべて don't-care の行が生き残っている部分木は被覆確定として枝を刈る。訪問数の当初の見込み（行数 × 列数に線形）は実測で外れ、行数に対して二乗で伸びる。速度は約 6 万ノード/ms（下の予算の段）。見つかった穴は隣接領域を貪欲に合流させ、点ではなく「届け先 ∈ {離島}、重量は任意」という箱の形で報告する。証人と穴の報告は表の列順で書き、探索の列順（圧縮座標数の昇順）を読み手に見せない。
- **DNF と逆像の膨張**：`define` の DNF 展開と表合成の逆像展開には上限（例：1 行あたり箱 64 個）を置き、超えたらエラーで表の分割か群化を促す。

爆発時の逃げ道は一つだけ用意する。
訪問ノード予算（既定 5×10⁷、`--budget` で変更）を超えたら、検査は**未証明**としてエラーで止まる。
サンプリングによる近似検査へ静かに縮退することはしない。
不健全な緑は、この道具が存在する理由の否定だからである。
エラーには「どの列の境界数が支配的か」を添え、群化と表分割という現実的な回避先を示す。

実用限界は M0 の合成ベンチで実測した（§15-2 は決着）。
設計目標（列 12、行 500、数値列 4）は 1,004 万ノード、164 ms で収まり、行数を 1000 に倍加すると二乗則どおり約 4 倍（4,075 万ノード、622 ms）だった。
既定予算 5×10⁷ は、設計目標に 5 倍の余裕を取り、使い切っても 1 秒弱で止まる値として実測から決めた。
回帰コーパスの実測は 522、267、7 ノードで、予算の五桁下にいる。

**捨てたもの**：

- **SMT ソルバ（Z3 等）**：v1 の断片には過剰で、証人の決定性（同じ入力に同じ証人）と単一バイナリ配布（§12）を損なう。列の線形条件は導出と篩で取り込み、精度が足りなくなったときの増強も Fourier–Motzkin 消去まで（§6.2）。SMT が要る形（非線形の列条件）は実測で 0 件だった。
- **BDD / MDD**：座標圧縮後の問題規模なら箱代数の素朴な実装で足り、変数順序のチューニングという新しい闇を持ち込むほどではない。ベンチで裏切られたら再訪する。

## 7. 丸めと単位の意味論

### 7.1 実行時表現

**決定**：すべての数値の実行時表現は int64 一本とする。値は r × s（r が実行時整数、s が型に付く静的な正の有理スケール）で、丸め済の型は s = 1 単位、未丸めの型は演算が合成したスケールを持つ。

浮動小数点も任意精度も decimal も生成コードに入れない。
言語間の一致（P5 の等価性）は、両言語が同じ int64 演算を実行することで機械的に成立させる。
`基本送料 × 負担率` は、円の整数 × パーセント整数で「0.01 円」単位の整数になり、スケール 1/100 円が型に記録される。
導出は整数定数倍と加減だけなので丸め済のまま閉じ、スケールを持たない（常に単位の整数一本で、丸めの新しい場所を作らない）。

### 7.2 いつ丸めるか

**決定**：丸めは明示した場所でだけ起きる。場所は三つ。(1) 出力宣言の `round`（数値出力には必須）、(2) 表の出力列ヘッダの `round`、(3) 式中の丸め関数 `up(式, 10円)` など。出力宣言の丸めは、結果式が未丸めのときに一度だけ適用される。結果式が既に丸め済なら再丸めせず、格子との整合だけを検査する。

「各表で丸めるか、最終出力で丸めるか」への答えは、**既定では最終出力の一回だけ、中間で丸めたければ書け**、である。
中間丸めの有無は円が動く業務仕様であって、道具が決めてよいことではない。
だから既定をもっとも情報を失わない側（丸めない）に置き、丸めるなら紙面に見える形で書かせる。
旧実装が中間で丸めているなら、等価検証がその差を「丸め差異」クラスタとして出し（§10）、書き手が中間丸めを明示して一致させる。
この往復こそが「差分の主要因になる」ことへの設計上の答えで、丸め位置の違いはすべて `.rule` の diff に現れる。

丸めの計算は、スケール s = p/q と格子 g に対して r·p を q·g' で割る整数除算一回と余りの検査で厳密に実行できる（g' は基準単位に直した格子）。
したがって格子とスケールの整除性のような制約は存在しない。
唯一の制約はオーバーフローで、`range` 宣言からの区間演算で int64 に収まることを規則ごとに静的に証明する。
証明できなければエラー（E108）で、中間丸めの挿入か刻みの粗直しを促す。
このエラーは円が動く業務判断を要求するので、文面は §11 の設計対象に含める。

出力セルに名前が書ける（§3.2）ことに伴う規則も、ここで固定する。
出力列の丸め状態は全セルの結合で決まる（どれかが未丸めなら列は未丸め。リテラルは常に丸め済）。
E106 の静的な格子検査はリテラルにだけ適用する。
名前の値が格子に載っているかは静的に分からないためで、列や出力の丸め宣言は名前の値にも宣言どおり一度掛かる。
宣言は紙面にあるので、これは「黙って変える」ことにはならない。
実測でこの検査がまず効いたのは計算のない表引きの運賃表で、丸め宣言が `1451円` のような転記タイポを桁の検査として落とした。
設計時は計算のための規約と考えていたが、実際には転記の検査として先に働く。

公開規約の転記は、丸めについてもう一つのことを教えた。
複数クーポンの端数処理は、楽天にも Yahoo にも書かれていない。
割引上限が素割引に掛かるのか最終額に掛かるのかも書かれていない。
つまり E104 と丸め宣言の必須化が要求する決定は、規約の側に存在しないことがある。
このとき書き手の仮置きが仕様の顔をして生成コードに入るので、規約に根拠のない丸めには出典と仮置きの旨をコメントで残す慣行を置き（§5.4 のスケッチの `# 端数処理は公開規約に記載なし。切り捨てに仮置き`）、過去データが来たら replay が仮置きを裁定する（§10）。
丸めを書けと迫ること自体の価値は、公開規約の欠落という形で、データを見る前に実証された。

### 7.3 丸めモードの定義

**決定**：モードは四つ。負の値に対する向きまで仕様で固定する。

- **切り上げ**：0 から遠ざける（-4.2 円 → -5 円）
- **切り捨て**：0 へ寄せる（-4.8 円 → -4 円）
- **四捨五入**：半分ちょうどは 0 から遠ざける
- **銀行家丸め**：半分ちょうどは偶数へ

負の値まで固定するのは、Python の `//` が −∞ 方向、Go の整数除算が 0 方向と、言語既定の除算が食い違っているからである。
生成コードが言語の素の除算を使うと、同じ表から違う円が出る。
そこで両言語に同一アルゴリズムの丸めヘルパ（十数行、生成ファイル内に自己完結）を吐き、負値と半分ちょうどを含む共通ベクタで一致を検証する（§9）。
値引きや返金で負の金額は現実に通るので、この固定は飾りではない。

### 7.4 除算と比率

除算は正の整数定数と、同型の定数（`注文金額 / 100円`、`重量 / 100g`）に限る（§2.3）。
結果は未丸めの無次元数で、丸めモードを明示しないと整数にならない。
「100 円につき 1 点」は `down(注文金額 / 100円)` と書き、切り捨てという業務仕様が紙面に残る。

## 8. 生成コードの形

### 8.1 可読性の基準

生成物の可読性は次の五つで定義し、golden テストで固定する。

1. 表の 1 行が分岐 1 本に対応する。分岐条件は行の全セルを省略せずに書き（先行分岐で真とわかる条件も消さない）、コメントに元の行を転記する。
2. 使う抽象は標準ライブラリの列挙と整数まで。テーブル駆動、クラス階層、ジェネリクスを使わない。
3. `.rule` の 1 行の編集が、生成物でも局所的な diff になる（条件の共通化や並べ替えという「賢い」最適化をしない）。
4. 長さは行数に線形で、1 ルール行あたり 2〜4 行を目安とする。
5. gofmt と PEP 8 に素で適合し、出力はバイト決定的である。

依存ゼロは「第三者パッケージゼロ」の意味で、標準ライブラリ（Python の enum、Go の fmt）は使う。

識別子は公開と内部で流儀を分ける（§1.3）。
公開 API（関数名、入力、出力、その型と列挙値）は ASCII 別名を使い、内部（表の関数、群の集合、内部の型、導出、定義）は別名が無ければ日本語識別子をそのまま使う。
漢字かなの識別子は非公開の位置なら両言語で合法で、gofmt も black も通り、行とコードの目視対応（基準 1）には原文のままの内部名がむしろ効く。

出力セルの名前（§3.2）は、その行の分岐での変数参照になる（`raw = 率割引`）。
1 行 1 分岐の対応は変わらない。

未検証の重なり（W114。§6.2）を持つ `unique` の表には、ガードを生成する。

```python
    # ガード: W114（表 適用判定 行1 × 行2）。重ならないことを静的に証明できなかった行の対
    if rest_a <= 1000 and rest_b >= 3980:
        raise RuleContradictionError("表 適用判定: 行1 と 行2 が同時に当てはまりました")
```

Go では同じ条件でゼロ値と error を返す。
Python の例外は入力契約違反の `RuleInputError` と区別して `RuleContradictionError` とする（規則そのものの矛盾であって、呼び出し側の誤りではないため）。
ガードは未検証の行対にだけ生成され、対象の行対をコメントに刻む。
この分岐を踏む入力はベクタには存在しない（構成できたなら W114 ではなく E105 になっている）ので、生成されるが通常は実行されないコードであることをファイルヘッダの注記にも書く。
細目も約束しておく。
ガードを入れる対は、生成時点の解析が出す W114 の対そのもの（`unique` の表で、出力が構文的に異なるもの）で、「構文的に同一」の判定は `--diff-base` と同じセル正規形の鍵で行う（同一性の定義を二つ作らない）。
複数の対は表の行順に並べ、メッセージは「表名: 行i と 行j が同時に当たりました」の形に固定する（運用が grep する面なので安定させる）。
導出の範囲にはガードを置かない。
E112 が宣言範囲 ⊇ 到達区間を静的に保証し、入口ガードが入力を範囲内に保つので、導出が宣言範囲を出る実行は存在しない。

金額の brand は `NewType` で表す。
mypy と pyright には効き、実行時コストはない。
列挙は stdlib の `Enum` で、値に和名文字列を持たせてログとワイヤ形式（§10）に使う。
完全性は rulec が証明済みなので、pyright の完全性検査に依存しない。
ただし Python は動的で列挙外の値が渡り得るため、入口で列挙と範囲を検証して `RuleInputError` を投げ、最終 else は「到達不能」の assert として残す。
証明の前提（入力が宣言域内）を実行時に守るのが入口ガード、証明そのものを信じるのが最終 assert、という分担である。

金額の brand は defined type（alias ではない）で表す。

sum type の不在への答えは「頼らない」である。

したがって `nishanths/exhaustive` 等の linter にも依存しない。

### 8.4 生成物の置き場所

**決定**：生成物は git にコミットする。CI の `rulec gen --check` が、コミット済み生成物と再生成結果の一致を検証する。

理由は三つ。
表の変更 PR に生成コードの diff が並ぶことがレビューの実体であること（P5 の「人間がレビューできる」）。
利用側リポジトリが rulec なしで生成物を vendoring できること。
そして生成物の手編集が `--check` で即座に露見することである。
ヘッダには rulec の版と原本のハッシュを刻み、Go の生成コード規約（`^// Code generated .* DO NOT EDIT\.$`）に従う。

### 8.5 M1 の生成細目

設計文書に書かれていなかった前提を、M1 の着手前にここで固定する。

- **配置と命名**：`generated/python/<規則別名>.py`、`generated/go/<規則別名>/<規則別名>.go`。Go のパッケージ名は規則別名から `_` を落とした小文字。
- **決定性**：同じ `.rule` と同じ rulec からは、実行環境によらずバイト同一の生成物。内部の反復はすべて宣言順か整列済みで、ハッシュ順の混入は不合格。改行は LF。
- **複数出力**：Python は `typing.NamedTuple`、Go は名前付きの Output struct を返す。単出力は素の値のまま。
- **入口ガードの範囲**：列挙の妥当性、入力の `range`（率は刻み単位の整数で検査）、optional の `none` の扱い。導出には置かない（§8.1）。**日付もガードを持つ（2026-09-13 に追加）** — 日付は通算日の整数で、その `range` は完全性証明が使った全体集合そのものである。ガードが無いと、宣言範囲の外の日付がたまたま当たった行に落ちて、呼び出し側は静かに間違った答えを受け取る。§8.6 の照合（目録が言う範囲が生成物のガードの字面にあること）で見つかった抜けで、**この照合を入れた初回に実在の欠陥を一つ見つけた**という点で W111 のときと同じ形をしている。
- **実装間の一致の判定**：宣言域内のベクタで、正準 JSON に直列化した出力のバイト一致。域外の挙動（Python の RuleInputError、Go の error）は言語ごとのユニットテストで域外 1 点ずつ確かめる。評価器は域外を受けないので、比較の対象は域内に限る。
- **丸めヘルパの単体ベクタ**：§7.3 の四モードについて、負値と半分ちょうどを含む共通ベクタを表のベクタとは別に出し、両言語のヘルパ単体で回す。表レベルの一致だけでは、端数の出ない表でヘルパの誤りが隠れる。
- **定義軸の篩**：定義軸の証人検証（点を構成して定義を評価器で確かめる）と、未確認の `unique` の重なりの W114 降格は、ガードの生成と対で M1 が実装する（§6.2）。依存の共有だけで機械的に Unknown へ落とす形は採らない。検証を先に試み、実在する矛盾を W114 に逃がして CI を素通りさせない。
- **ベクタの原子境界**：真偽定義の原子の境界の抽出（§9.1）も M1 の実装範囲。
- **整形の内蔵**：gofmt 相当の整形は生成器が内蔵し、後段で環境の gofmt を走らせない（環境の版に依存した瞬間、決定性が壊れる）。`gofmt -l` が空であることは検証として残す。列の整列は `text/tabwriter` と同じルーン数で数える。表示幅の全角 2 ではない（和名の識別子が二行並んで初めて出た実測）。`.rule` の fmt は東アジア幅、生成 Go は Go の流儀と、それぞれの生態系の正準に合わせる。
- **PEP 8 の検証**：`ruff check --select E,W --ignore E501` が空であることを固定する。行長（E501）は意図した逸脱である。§8.1 の「表の 1 行を分岐 1 本に、原本のセルをコメントで添える」は 88 桁に収まらず、行長より 1 行 1 分岐の対応が優先する。
- **組み込みの隠れ**：生成 Python は言語の組み込みを裸で呼ばない。入力の別名が `min` だっただけで生成物が壊れた実害から、`_min` `_max` などの内部名を生成側が持ち、衝突の族ごと消す。

### 8.6 生成物の呼び方の目録（rulec api）

**決定（2026-09-13）**：`rulec api <file.rule>` が、生成物を**読まずに呼べるだけの情報**を JSON で出す。Python の module・function・署名・引数（和名、別名、型、単位、範囲、optional）・戻り値・出力（丸めつき）・列挙の値（その言語での綴り）・送出しうる例外。Go の package・func・署名・`Input` と `Output` の型と欄・列挙の値。言語に依らない（全部が生成物で実際に使われている名前か数値である）。

置き場所は `src/codegen.rs` の中、生成器の隣にした。目録は生成物の**二番目の説明**であり、離れた場所に置いた瞬間に、名前を一つ変えた日から食い違いはじめる。同じ `pub_name`・`pascal`・`py_ty`・`go_ty` から組むこと、そして**テストが生成物そのものと突き合わせること**の二つで縛る。突き合わせは三段ある。(1) 目録が言う署名・ガードの範囲・列挙の綴り・例外クラスが、生成されたファイルの字面にあること。(2) Python は生成物を import して `inspect.signature` と比べること。(3) Go は**目録だけから呼び出しプログラムを組み立てて** `go vet` に通すこと — 名前が一つでも違えばコンパイルが通らない。

範囲は「生成物のガードが実際に使っている数字」をそのまま出す。目録が別の計算をすると、目録どおりに送った値をコードが拒む、という最悪の食い違いが生まれる。

**捨てたもの**：

- **人の手で書いた呼び出し規約の文書だけで済ませる**：`docs/generated-code.md` は残すが、名前の正は目録に置いた。手書きの文書は、生成器が名前を変えた日から静かに嘘になる。
- **`--format` で python だけ / go だけを出す**：一つの JSON に両方入れる。呼ぶ側が両言語を同時に見たい場面（同じ表が二か所で使われている確認）が主で、片方だけ欲しければ `jq .python` で足りる。
- **目録に「使用例のコード」を入れる**：例は文書（§8.6 の `docs/generated-code.md`）の仕事で、目録は事実だけを持つ。例を目録に入れると、例が腐ったかどうかを目録のテストが見なければならなくなる。

## 9. 境界からのテストケース生成

### 9.1 値の候補

列ごとに候補値を決める。

- 列挙と真偽：その列のセル群が誘導する同じ答え類（圧縮座標）ごとに代表 1 値。47 都道府県を全部舐めるのではなく、表が区別している区分だけを踏む。
- 数値（数量、金額、日付）：表に現れる各境界 b について {b − 最小刻み, b, b + 最小刻み}、および `range` の両端。
- 導出：境界は導出の値なので、入力ベクタへ写す（残りの入力は行の他セルを満たす値に固定する）。写し方は契約だけを決める。構成した点は必ず評価器で再評価し、目標に当たった点だけを採る。当たらなければ次の入力で試み、どうしても埋まらない義務は被覆判定器が赤で報告する。この二重の網（採用前の再評価と、義務の事後判定）の下では、解き方は実装の自由である。M1 の実装は記号解法ではなく数値の傾き（seed で評価し、一刻み動かして傾きを取り、目標へ跳んで、再評価で確かめる）で、上流の表や定義を挟んでも同じ一つの機構で通り、区分線形の継ぎ目や整除の外れは再評価が自然に落とす。解が入力範囲の外になる側の点は実現不能なので捨て、境界両側被覆の定義は実現可能な側に限る。
- 真偽定義の原子：解析は自由軸（§6.2）なので原子の境界を見ない。ベクタは定義から原子の境界を直接取り出して踏む（`注文金額 >= 3万円` なら 3万円 の両側、名前どうしの比較なら同着 A = B とその両側を、導出と同じ要領で入力へ写す）。解析に見えない境界こそ、ベクタが踏まないと誰も踏まない。
- optional：`none` と、在る側の上記候補。

### 9.2 被覆基準

**決定**：三つの被覆を定義し、`rulec vectors` はこれを満たす最小に近い集合を決定的に生成する。

- **行被覆**：各行につき、その行が発火する（`first` では勝つ）ベクタが 1 つ以上。
- **境界両側被覆**：数値列の各セル境界につき、他列をその行に当たる値へ固定したまま境界の両側を踏むベクタ対。行の削除、境界値の ±1、開閉の付け間違いは、この対の期待値を必ず変える。
- **隠れ対被覆**：`first` の隠れ対 (i, j) ごとに、交差の内側（i が勝つ点）と j∖i（j が発火する点）の 2 点。隣接行の入れ替えという変異を殺す。

三基準は義務の集合として実装する。
義務は規則から静的に列挙し、生成器はそれを狙い、被覆判定器は各義務が実際に片づいたか（そのベクタで行が勝つか、境界の両側を対で踏んだか）を評価器で確かめ、片づけたベクタだけを残す。
発火したトレースから義務を作る形は禁じる。
踏めなかったものが「必要なかった」ことになるからである。
義務の列挙そのものは一箇所でよい。
同じ書き手による二重実装は盲点を共有しやすく、維持費だけが残る。
代わりに三つの網を張る。
隠れ対の義務は解析器から取る（既に独立）。
境界の義務は、式の木から境界リテラルを数えるだけの素朴な収集器と件数で照合する。
規則ごとの義務の件数を回帰に固定し、言語に列の種類や原子の形を足すときは、該当カテゴリの義務が増えることを受け入れ条件にする。
増えなければ、列挙器がその機能を見ていない。

三基準を満たした上で、列間の相互作用の取りこぼしに保険を掛けるため、候補値のペアワイズ（全 2 因子網羅）を貪欲法で足す。
全直積は候補 10 値 × 6 列で 10⁶ に爆発するが、ペアワイズなら百数十件で収まり、行標的と合わせて規則あたり数百件が目安になる。
生成は決定的（同じ `.rule` から同じベクタ列）で、期待値は参照評価器が付け、発火行のトレースも記録する。

```
{"in":{"届け先":"沖縄","重量":2001,"注文金額":40000,"会員":"一般"},
 "out":{"送料":0},
 "trace":{"基本送料":2,"負担判定":1},
 "why":"境界両側: 基本送料 行2 重量>2000g の内側"}
```

### 9.3 ベクタの三つの使い道

1. **言語間一致テスト**：同じベクタを生成した各言語に流し、参照評価器との一致を確かめる。データも旧実装も不要で、M1 の主力の保証になる（P6）。
2. **等価検証の入力**：旧実装アダプタ（§10）に同じベクタを流す。セル境界から作っているので、過去データが薄い境界近傍も踏む。
3. **golden**：生成された各言語のテストファイルにベクタを埋め込み、利用側 CI でも回るようにする。

## 10. 等価検証と過去再生のインタフェース

### 10.1 旧実装の呼び方

**決定**：アダプタプロセス方式。旧実装の言語で 20〜30 行のアダプタを書いてもらい、rulec が子プロセスとして起動して JSON Lines を stdin/stdout で流す。FFI もネットワークも使わない。

言語をまたぐ最小の共通面が「プロセスと行指向 JSON」で、Python でも Go でも Perl の遺物でも同じ書き方になる。
ワイヤ上の名前と値は `.rule` の正準名（和名）と正準単位の整数で、`rulec schema` が入出力の JSON Schema を吐き、雛形は `rulec adapter --template python|go` が印字する。
アダプタが「答えられない」と言った件は一致率の**分母から外す**。そうしないと、難しい件を断るだけで一致率が上がる。

**形式の定義そのものは [`docs/formats.md`](docs/formats.md) に移した（2026-09-13）。** ここに残すのは決定とその理由で、握手の順序や欄の名前は文書の側にある。二か所に書けば必ず片方が腐り、腐るのは決まって説明のほうだからである。

### 10.2 記録形式

過去データのスナップショットは 1 件 1 行の JSONL に固定する（欄の定義は [`docs/formats.md`](docs/formats.md)）。

本番ログからこの形への抽出（ETL）は利用者の仕事と割り切り、rulec は `rulec fixtures lint` で型と範囲の検証だけを引き受ける。
注文金額を含むので fixtures はリポジトリに入れず、CI にはアーティファクトか保護ストレージで渡す。

**数値は正準単位の整数で、小数は受け付けない。** この禁止をどこで守るかは 2026-09-13 に動かした。以前は JSON の読み手（`src/json.rs`）が小数を見た瞬間に行ごと断っていたが、rulec 自身が小数を書くようになったので（`verify`/`replay`/`diff` の一致率）、読み手は小数を `Frac` として読み、**`as_int` が否と言う**形に変えた。禁止は fixtures の側に残り、文面は「`observed.運賃`: 正準単位の整数 を期待しましたが 小数 でした」と、**どの欄が壊れているかを名指しする**ぶん良くなった。小数は浮動小数点にせず書かれた桁のまま持つ（§2.1 の「浮動小数点はどこにも現れない」を読み書きの経路でも守る）。指数表記は引き続き断る — 転記された記録が `1e3` と書く読み方は無い。

### 10.3 入力が完全に復元できない場合

**決定**：モードは二つだけ。欄ごとに (1) その記録を除外する、(2) 既定値で補完し「補完系」の札を付ける。逆推定はしない。

補完の既定値は、規則の言語には入れない。
規則は純関数で、補完は特定の再生実験の判断だからである。
同じ規則を「会員は一般で埋める」「ゴールドで埋めて感度を見る」と別々に再生することが正当にありうるし、規則の宣言に書けば、意味に関与しない注記が規則のハッシュを変えて gen --check が無意味な再生成を要求する。
置き場所は版管理される再生マニフェスト（fixtures の隣に置く小さな JSON。既定値と対象欄だけで機微な数字を含まないので、リポジトリに入る）とし、CLI の `--fill` は感度分析のための一時上書きとして許す。
どちらから来た値でも、レポートが「使った既定値」と「補完した件数」を欄ごとに必ず刻む。
根拠は指定の場所ではなく、数字の出る場所（PR に貼られるレポート）に現れることで担保する。
なお、補完が見出しを膨らませる誘惑は階段に存在しない。
見出しの一致率は実測系だけから計算するので、補完は二次集計にしか効かない。

fixtures の欄の欠けは、鍵の不在で表す。
optional の `none` は値であり、`null` として明示的に書く。
「値が無いと分かっている」（無し）と「値が分からない」（欠け）は別物で、前者は補完の対象にならない。

レポートは実測系と補完系を必ず分けて集計し、見出しの一致率は実測系だけから計算する。
「982 件」の説得力は再現の正直さそのものなので、補完を混ぜた一致率を大きく見せる誘惑を、形式のレベルで断つ。

### 10.4 差分の帰属

replay と diff の不一致は、参照評価器の発火行トレースを鍵にクラスタする。
鍵は発火行の組だけ（diff は新旧両側、replay と verify は規則側のみ）で、金額は鍵に入れない。
表引きの行なら行の組が金額の組を一意に決めるので、金額で分ける意味がない。
計算の絡む出力（出力セルの名前、`result` の式）で金額を鍵に入れると、金額の数だけクラスタが割れて要約が死ぬ。
代わりに、クラスタごとに件数、Δ の合計、最小と最大、証人例を必ず出し、Δ が全件同じ答えならそれを一行に畳む。
下の例の一行は、この一様な場合である。
既知の限界を一つ記す。
表そのものが増減した版の diff は、対応の取れない発火行を（旧のみ）（新のみ）と記すだけで、遷移としては読ませない。
構造の組み替えに意味のある対応は取れないからで、実表で頻発するようなら、そのとき設計する。

```
$ rulec diff 送料@v3 送料@v4 --fixtures replay/2025-08.jsonl
  影響 3,412 件 (0.27%)   金額 +182,400 円
  クラスタ 1: 基本送料 行2→行5（離島新設）      2,900 件  +196,800 円
    例: 届け先=沖縄, 重量=2400g, … v3: 1800円 → v4: 2000円
  クラスタ 2: |Δ| < 10円 の端数のみ              512 件   -14,400 円
    丸め差異の疑い（出力格子 10円 未満の一様なずれ）
```

出力格子未満のずれを「丸め差異の疑い」として自動で括るのは、§7 の規約が差分の主要因になるという予測を運用に折り返したものである。タグの条件は「クラスタの全件が、ゼロでなく格子未満のずれ」で、格子ちょうどのずれは丸めではなく値の食い違いなので付けない。複数出力では、食い違っている出力のすべてが格子未満であることを求める。

## 11. エラーメッセージ

設計原則を先に決める。

1. 一行目は業務の言葉だけで完結させる。型や IR の語彙を一行目に出さない。
2. 必ず具体の入力例（証人）を付ける。値は列挙の宣言順と境界値を優先して選ぶ。導出が絡む証人は入力として構成して評価器で確かめ、構成できなければ「実現可能性未検証」と明記する（証明していないことを証明済みの顔で出さない）。定義や導出の軸が絡んで実在を確認できた発見は、軸の座標（なぜ重なるか）を残したまま、それを作る入力を一行添える。証人を入力に差し替えると「なぜ」が消えるからである。
3. ヒントは「書き換え後の形」まで書く。
4. 位置はファイル:行に加え、表名、行番号、列名で示す。関与する行が複数なら全部にスパンを張る。
5. エラーコードと JSON 構造は安定 API とし、文言は改善してよい。
6. `--format json` が GitHub annotations にそのまま流せる形を吐く。exit code は 0（注記のみ）、1（エラー）、2（内部異常）。

**JSON v2（2026-09-13）。** 診断は同じ発見を二通りで言う — 人が読む文面と、プログラムが動く**データ**である。v1 の欄（severity, code, file, line, column, title, notes）は全部そのまま残り、`"v": 2` が書き手を名乗る。足したのは `where`（file, line, column, table, row）、`spans`（位置とラベル）、`witness`、`rows`（関与する表と行）、`fix`（kind と、貼れる書き換え後の形）、`key`（`--diff-base` の鍵）である。**構造は発行箇所で入れる。** 文面を後から解析して取り出さない — 原則 5 が文面の改善を明示的に許している以上、文面を解析する読み手は次の改善で壊れる。

**証人は「値の割り当て」だけを運ぶ。** `witness.inputs`（具体の入力）、`witness.outputs`（その入力から規則が実際に出す値）、`witness.expected`（例が言っていた値。E107 だけが持つ）。到達区間や「丸め方で動く幅」のような**区間や差は割り当てではないので入れない** — 文面に残し、行動できるものは `fix.text` に置く（E112 の広げた `range` がそれ）。こうすると証人はいつも一つの形になり、受け取った側はそのままベクタや fixtures として投げ返せる（§10.2 のワイヤと同じ形）。**捨てたもの**：証人に区間や統計を混ぜて型を増やす案（読み手が値と区間を場合分けすることになり、「そのまま投げ返せる」性質が消える）。

**`fix.text` は文面を含まない。** 言語に依らないバイト列で、`.rule` にそのまま貼れる形だけを持つ（`round down(1円)`、`range >=-110万円 <=100万円`、`| 山梨県 | S60 | 820円 |`）。丸めの向きも格子も、足す行の金額も**業務の判断**であって道具が決めてよいものではないから、その注意は言語に依る `notes` の側に置く。テストが E101 と E104 の `fix.text` を機械的に貼って、そのコードが本当に消えることを確かめている。嘘をつく fix は、fix が無いより悪い — 指示の顔をしていて、間違いだと分かるまでに一往復かかる。

**`--terse`。** text 出力を「見出し・位置・証人」の三行に絞り、走査の最後に一度だけ `details: rulec explain <code>` と出す。原則 3 は消えていない — 一件ごとに繰り返す代わりに、道案内として一度出る。`--format json` との併用は断る（JSON は既に機械向けの形で、どちらを削るかの判断が要らない）。
7. 文面は日本語と英語の二言語を持つ。`--lang ja|en`、無ければ環境変数 `RULEC_LANG`、無ければ**英語**。システムロケールは見ない。生成物は `gen --check` で照合され、CI のログは diff されるので、走らせた機械で出力が変わってはならない。コードは言語に依らない（原則 5）。実装は各文面を `tr!("日本語", "English")` で隣り合わせに書き（`src/i18n.rs`）、片方だけの文面を作れないようにしている。

**覆した決定（2026-09-13）**：既定は日本語だった。第一の利用者が AI エージェントであると決めたので、既定を英語にした。理由は二つ。英語のほうがトークンが少なく済み、モデルの読み書きが安定すること。そして `--help` と診断と JSON だけで手順を回させる以上、既定で出る言葉が道具の顔になること。日本語は失われていない — `--lang ja` か `RULEC_LANG=ja` の一つの設定で全面が戻り、承認者に貼る PR コメントを日本語にする CI はその一行を書く。**捨てたもの**：システムロケールを見て切り替える案（走らせた機械で出力が変わる。原則 7 の本文と衝突する）と、診断だけ英語・レポートだけ日本語のような面ごとの既定（どの面がどの言語かを覚える必要が生まれ、`tr!` の対一つという実装の単純さも壊れる）。

```

   |

31 | | -        | >=3980円 | true |    行4
   |

 二つの導出（残高A = 合計 - 割引A、残高B = 合計 - 割引A - 割引B）が入力を共有しているため、
 この条件を同時に満たす注文が存在するかどうかを、検査は判定できませんでした。
 存在するなら: 行を直してください。出力が異なる（偽 と 真）ので、当たれば矛盾です。
 存在しないなら: このままで構いません。生成コードには、万一この条件に当たる入力が来たとき
 黙って行2 を選ばずエラーを返すガードが入ります。

```

なお、この例の重なりは実際には実現不能である（割引B は 0円 以上なので、残高B は定義から必ず 残高A 以下。残高A が 1000円 以下のとき 残高B は 3980円 に届かない）。
導出ごとに独立な区間の篩はこの従属を見ないので、判定できずに W114 になる。
Fourier–Motzkin 消去なら証明できる形で、W114 が実表に積もることが、まさに §15-4 の増強の発動条件になる。

## 12. 実装言語と配布形態

**決定**：rulec は Rust で書く。配布は単一静的バイナリ（macOS arm64/x64、Linux x64/arm64 は musl 静的リンク）を GitHub Releases に置き、CI では sha256 を固定してダウンロードする。

理由。
この道具の本体はコンパイラ（AST、型付け、領域代数、正確な有理数演算、決定的な証人生成）であり、直和型とパターンマッチが実装の正しさに直接効く。
三候補のうちそれを言語本体で持つのは Rust だけである。
検査は 10⁶ ノード規模の探索なので Python は速度で外れ、Go は書けるが IR の直和が interface の運用規約になり、コンパイラを書くには一段落ちる。
Rust なら診断表示や有理数の枯れたクレートも使える（rulec 自身の依存はよい。ゼロにする対象は生成物である）。

生成物の行き先が Python と Go である事実は認めた上で、こう整理する。
毎日触られるのは `.rule` と生成された Python と Go であり、rulec 本体を触る人はコンパイラを書く人に限られる。
道具の保守者の裾野より、道具の正しさと配布の単純さ（ランタイム不要の 1 ファイル）を取る。

CI への組み込みは四行で完結する。

```yaml
- run: rulec fmt --check rules/
- run: rulec check rules/ --diff-base origin/main
- run: rulec gen rules/ -o generated/ --check
- run: rulec test generated/        # python3 と go の toolchain を使う唯一の段
```

replay は fixtures を持つ環境だけの別ジョブとし、`rulec replay` が Markdown を吐いて `gh pr comment` で貼る。
`--lang` はどのコマンドにも付けられる。CI では言語を明示する（環境に `RULEC_LANG` を置くか、各行に `--lang`）。生成物と PR コメントの文面が機械で変わらないためである（§11 原則 7）。
レポート整形まで rulec が持ち、投稿は CI の一行に任せて CI ベンダ非依存を保つ。

**捨てたもの**：

- **Go 実装**：書ける人の裾野は最大だが、上記のとおりコンパイラの内側で支払いが続く。
- **Python 実装**：検査の速度と、CI への配布（venv の管理）で二重に不利。
- **pip / npm ラッパ配布**：単一バイナリに対する追加価値がない。要望が出てから考える。

### 12.1 CLI は契約である

**決定（2026-09-13）**：コマンドとフラグの定義を `src/main.rs` の一枚の表に置き、`--help` の描画と引数の解析が同じ表を引く。`rulec <cmd> --help`（`rulec help <cmd>` も同じ画面）は、目的・引数・フラグ（値の型と既定）・exit code の意味・走らせられる例を二つ・出しうる診断コードを出す。`rulec --help` は一覧、`rulec --version` は版の一行だけ。

**知らないフラグは exit 2 で止める。** 同じ扱いを、値が閉じた集合の外にあるとき（`--format jsn`）、値を取るフラグに値が無いとき、繰り返せないフラグが二度書かれたときにも広げた。理由は第一の利用者が変わったことにある。人間なら出力を見て「あれ、効いていない」と気づくが、エージェントは `--shwo-shadow` と打って exit 0 を受け取ると、要求が通ったと信じて次に進む。**黙って無視することは、嘘の緑を返すことと同じ**である（§0 の「不健全な緑を出さない」と同じ原則を、CLI の面に広げたもの）。

**捨てたもの**：

- **clap などの引数パーサ**：依存を足さない方針（§12）の外にあるうえ、この表が持つべき情報（exit code の意味、例、関係する診断コード）はどのパーサも持たない。
- **未知のフラグを警告にして続行**：警告は読まれない。CI のログに一行増えるだけで、誤った引数のまま緑が出る。
- **短いフラグ（`-f` `-o`）**：綴りが二通りになる。§1.1 で語彙に同義語を置かないと決めたのと同じ理由で、CLI にも置かない（`-h` と `-V` だけは、慣習として `--help` `--version` の別名に残した）。
- **`rulec` を引数なしで叩いたときに exit 0**：何もしていないのだから 0 ではない。全体の `--help` を標準エラーに出して 2 で止める。

残るものと、新たに開いたもの。
ここから先の大半は、動く検査器がないと測れない。
机上調査はここで打ち止めにし、以降の測定は M0 の実装と実地の転記で行う。

1. **文字列のパターン一致**：公開規約の転記では文字列が列に一度も現れなかったが、実運用のクーポンコード体系は公開情報では確認できない。実データ（コード形式の一覧）を見て、完全一致で足りるか前方一致が要るかを数えてから決める。
2. **検査予算の既定値（決着）**：M0 で実測した。設計目標（列 12、行 500）は 1,004 万ノード、164 ms で予算内。訪問数は行数に二乗、速度は約 6 万ノード/ms。既定は 5×10⁷（§6.3）。
3. **Go の入力契約違反の流儀**（error か panic か）：組み込み先の Go サービス 2〜3 本の慣行を見て合わせる。生成器のフラグにはしない（生成物の形は一つに保つ）。
4. **相関する導出と Fourier–Motzkin 消去**：導出が入力を共有する形は、コーパスのクーポン規則が最初から含んでいる（`最低差` と `支払差` が `現在残額` を共有）。ただし当の表は `first` で、W114 を生む `unique` との組合せはまだ出ていない。コーパスを広げるたびに、導出の本数の分布と W114 の件数を数える。発動条件は二つのどちらか。W114 が実表に出続けること、またはガード（§8.1）に本番で当たりが出ること。どちらも起きるまでは足さない。効果の物差しも用意できた。コーパスのクーポン併用にある W114 一件（区間の篩には見えない実現不能の重なり）が、FM を入れた日に消える。
5. **畳み込みの宣言化**：`畳み込み 順序=適用順序 一回=クーポン割引 累積=残額 ← 残額 − 割引額` の形で反復を宣言にし、参照評価器が畳み込みまで実行できるようにする案。見送りの理由と暫定の緩和（連鎖の例）は §5.4 に書いた。採否は次の三つで測る。(1) 二本目以降の実畳み込み（ポイント付与、按分、Yahoo の重ね掛け）を転記し、「比較規則によるソート → 段ごとの純関数適用」の形に収まるかを確かめる。(2) 各段の入力を「アキュムレータと当該要素から導ける」「畳み込み全体の定数」「外部状態」に分類して数える。外部状態が 0 で、アキュムレータがスカラーか固定形のレコードに収まる実例が 2 件以上そろい、かつコーパスのクーポン規則も同じ形に書き直せるなら入れる。(3) クーポン重ね掛けの呼び出し側を両言語で試作し、fold 単体ではなく、規則を呼ぶために書くホストコードの総量（射影、反復、前後処理）を行数と分岐数で数える。二重実装は畳み込み、射影、前後処理に分かれて出るので、別々に見ていると合計がいつ許容を超えたか分からない。fold が定型 30 行程度に収まるなら宣言化の利得は薄いままとし、膨らむか二実装が食い違うなら圧力が上がる。入れると決まった日のための設計メモも残す。順序規則には全順序性の検査が要る（全域・反対称・推移。二引数規則は積空間上の表なので、反対称は行対の突き合わせ、推移は圧縮同じ答え類上の三重ループで有限に検査できる）。累積には初期値と各段の出力範囲からの帰納で範囲不変条件を検査する。丸めは各段の出力宣言が既に持つ。生成形は固定の短いループ骨格と一段関数の呼び出しで、1 行 1 分岐の基準は表側に残る（P7 が禁じるのは DSL 表面のループであって、生成物のループではない）。
6. **入力の射影と由来の宣言**：入れ子のドメインオブジェクトへの述語（`注文.配送先.都道府県`、`明細のいずれかが冷蔵品`、`count(明細) > 3`）は現実に普通にあり、平たい入力への射影は今はホストの手書きである。コーパスの入力は 13 個（クーポン 10、運賃 3）で、素朴に見積もれば射影だけで両言語 26 行の未検査グルーになり、規則を増やすたびに線形に増える（これは見積もりで、実数は §15-5 の試作で数える）。拡張候補は、入力宣言への由来の付記（`届け先(dest) : 都道府県 ← 注文.配送先.都道府県`、`冷蔵品あり : bool ← 注文.明細 のいずれかが 区分 = 冷蔵`）と、既存スキーマの借用である。rulec は独自のドメインオブジェクト型システムを作らない（非交渉）。呼び出し側に既にある JSON Schema / protobuf / OpenAPI を読んでパスの存在と型を検査し、両言語の射影関数を生成する。受け入れの根拠は、検査に一切触れないこと。射影の出力はスカラーの入力で、領域解析も箱代数も無傷、言語機能ではなくコード生成機能である。先に置く設計上の注意が三つ。(1) 由来は check に不要な注記とし、スキーマが無くても検査は完結する（照合と生成は gen 側）。(2) 生成物ヘッダに原本ハッシュと並べてスキーマの版も刻む。スキーマと本番の乖離は、新しい偽の緑の通り道になるからである。(3) 射影の言語は「一つのコレクションへの いずれか / すべて / 件数 と、要素フィールドへの単項述語」で打ち止めにし、結合や入れ子の量化は実例を数えてから。セルにパス式や量化子を入れる形は採らない（§0）。優先度は畳み込み（§15-5）より上に置く。量が規則ごとではなく入力ごとに増えることに加え、畳み込みは動機の実例を表せずに見送られたのに対し、射影は実例を既に表せて検査にも触れず、採用の障壁が低い。着手は §15-5 の試作で総量を測ってから。
7. **按分**（2026-09-13 に測定、決着）：配り方で割れる。**逐次充当型**（順に上限まで充てる）は「一回の判定」の粒度にそのまま収まり、`tests/corpus/値引の充当.rule` として収録した。呼び出し側は明細を回して残額を引くだけで、合計は構成上ぴったり合う（配りすぎも配り残しも起きない。2,000 通りの合成明細で確認）。**比率按分**（定価の比で割り付け、端数を再配分する）は書けない。`明細 / 合計` が §7.4 の「除算は正の整数定数と同型の定数に限る」に当たり、比率を呼び出し側で作って率の入力で渡す迂回も、率の刻みが実装上 1% 単位までしか書けないため実用にならない。粒度原則の例外に格上げはしない — 逐次充当が書ける以上、原則が破れたのではなく、比率按分が**除算の制限**に当たっただけである。比率按分を入れる日に動かすのは §5.4 ではなく §7.4 と率の実装になる。
8. **集約（C）の需要**：「実測のクーポン転記でも集約は要らなかった」という前回の記述を撤回して開き直す（経緯は §4）。公開調査で分かったのは、実需要の主形が検証（当てはまる項目の全収集）であることまでで、不在の証明ではない。以降は机上ではなく実地で数える。M0 の後、実表を転記するたびに「単一ヒットで書けなかった」「書けたが排他の書き込みが苦痛だった」事例を、検証の形と集約の形に分けて記録する。採ると決まったら、§4 の記録（排他と網羅の検査が意味を失う取引、範囲の決断）を前提に設計し直す。
9. **単項原子の DNF 代入**：真偽定義は自由軸で出荷した（§6.2）。代入すれば定義の中の閾値（`注文金額 >= 3万円` の 3万円）まで領域解析が見るようになり、実現不能な組合せ起因の過剰報告が減る。発動条件は、その過剰報告（穴や W114）が実表で邪魔になること。それまでは、ベクタが原子の境界を直接踏むこと（§9.1）で検査の穴を塞ぐ。§15-4 の増強（FM 消去）とは独立に発動できる。

### 15.9 按分を測ったときに出た実装の欠陥（2026-09-13）

§15-7 を測る過程で、設計どおりに動いていない箇所が三つ出た。いずれも**この道具の検査機構そのものが見つけた**ものではあるが、直すのは別作業として記録する。

1. **率の入力の入口ガードが誤っている。** `rate[step 1%]` の入力に `range >=0% <=100%` を宣言すると、生成コードのガードが `0 <= r <= 1` になる。ワイヤ表現は刻みの個数（0〜100）なので、1% を超える値がすべて弾かれる。さらに、その規則の生成物は参照評価器と食い違い、`rulec test` が赤になる（生成 0 / 期待 1）。範囲の Rat から分子だけを取っていることに由来する（§8.6 の `range_json` に同じ注記がある）。**率の入力を持つ規則は、いま正しく生成されない。**
2. **小数のリテラルが字句解析に通らない。** §2.1 は `0.5%` と `rate[step 0.1%]` を仕様として書いているが、実装は `.` を E002（読めない文字）で断る。率の分解能が実質 1% 単位に限られ、比率按分の迂回路が塞がっている原因でもある。
3. **使われない表の出力列があると、生成 Go がコンパイルできない。** Go は未使用のローカル変数をコンパイルエラーにするので、どこからも読まれない表の出力があると `declared and not used` で落ちる。Python は通るので、`rulec test` の Go 側だけが落ちる。W111（使われない宣言）は入力・導出・群・列挙値を見ており、表の出力列は見ていない。

三つとも、コーパスの 7 本では一度も踏まなかった。**コーパスが行使していない構造は検査されていない**という、当たり前だが忘れやすい事実の実例である。

### 15.10 三つを直したときに出たもの（2026-09-13）

§15.9 の三つを直した。直す過程で、同じ根から出ている欠陥がさらに四つ出たので、合わせて記録する。

1. **ワイヤ表現の変換点が散らばっていた。** 率は「格納する値」と「運ぶ値」が違う唯一の型で、その境界を越える場所が十箇所あり、変換していたのは一部だった。JSON Schema の上下限、診断の証人、記録の読み込み、verify/replay/diff の比較と差額、入口ガード、表の出力の代入。`Checked::wire_scale` と `wire_int` / `from_wire` の一点に集め、全部をそこに通した。**捨てたもの**：値の側に単位を持たせて自分で変換させる案。`Val` は評価器の内側の型で、そこに表現の都合を持ち込むと評価器が表現を知ることになる。
2. **ベクタの重複判定が値を整数に切り詰めていた。** `vectors::show` は表示であると同時に重複判定の鍵でもあり、100% 未満の率が全部 "0" になっていた。率の列は軸まるごと一点に潰れ、行被覆も境界被覆も満たせない。`coverage` はそれを正しく「欠け」と言い続けていたのに、こちらが読んでいなかった。表示と鍵を分け、鍵は正確な値にした。
3. **出力のセルが最初の語だけを採っていた。** §3.2 は出力のセルに式を許さないが、実装は残りを黙って捨てていた。`| - | 商品合計 × 割引率 |` から、掛け算の無い生成コードが出る。**E014** を足した。
4. **刻みの間の値が黙って刻みに寄せられていた。** `rate[step 0.1%]` の列に `<=0.05%` と書くと、生成コードの比較は `<= 1`（0.1%）になる。紙面で読める境界と動く境界が食い違う。**E114** を足した。証人についても同じで、開区間の証人は中点だったが、中点は型が持てる値とはかぎらない（`(10%, 15%)` の中点は 12.5%）。閉じている側から一刻み入った点に変えた。日付だけは最初からそうしていた。

**決定**：コーパスに `決済手数料.rule`（刻み 0.1% の率）を足した。§15.9 の教訓そのままで、行使されていない構造は検査されない。

### 15.11 単位のない数の型（2026-09-13）

**決定**：無次元の整数型 `number` を入れる。件数・日数・点数のように単位を持たない数を、偽の単位をでっち上げずに書けるようにする。範囲宣言は他の数値型と同じく必須、出力なら `round` も必須（§7.2 を弱めない）。演算では率と同じ無次元数として振る舞い、`金額 × number` は金額、`金額 ÷ 同通貨の金額定数` は `number` になる。最後のものは §2.3 が最初から「100円につき1点」用として書いていたのに、結果を入れる型が無かったために書けなかった規則である。

同時に、除算の実装を直した。`x ÷ k`（k は定数）は**整数を割らない。スケールを k 倍する**だけでよく、それが値を厳密に保つ唯一の形である。実装は `//`（Python の床除算）を出していたので、参照評価器の厳密有理数と食い違っていた。コーパスに除算を使う規則が一本も無かったので、実装間の一致が踏まずに残っていた。`ポイント付与.rule` を足した。

**捨てたもの**：
- **`count[件]` のようにラベル付きの単位を持たせる案。** 件数と日数を型で分けられるが、ラベルは brand にしかならず、業務の側に「この数の単位は何か」を考えさせる手間が増えるだけだった。単位が無いことこそがこの型の意味である。
- **生成物で `Number` という brand を作る案。** 件数も日数も同じ brand になるので取り違えは防げず、呼ぶ側に整数を包む手間だけが残る。Python は `int`、Go は `int64` のまま出す。

### 15.12 無次元の値と、変数による除算（2026-09-13）

「複数の評価項目を合算し、満点に対する達成率でランクを付けられるか」を測った。答えは**書ける**で、`tests/corpus/評価ランク.rule` に収録した。重み付きの合計は `derive`、達成率は `define … : rate = 合計点 ÷ 満点定数`、ランクは達成率の列を持つ表になる。**実行時に割り算は起きない** — 満点が定数なので `>=90%` は生成コードで `合計点 >= 45` に畳まれる。

測る過程で三つ出た。

**決定**：**無次元の値は、宣言のほうが名前を決める。** `rate` と `number` はどちらも無次元で、実行時の表現も同じ（刻みつきの整数）なので、`derive`/`define` の宣言が `rate` なら率、`number` なら数として受ける。`達成率 : rate = 合計点 ÷ 50` は割合として `>=90%` と書けて、`基本点 : number = 税込金額 ÷ 100円` は点数として `>=10` と書ける。**捨てたもの**：`unifies` そのものを緩めて率と数を混ぜられるようにする案。それだと `品質 + 10%` まで通ってしまう。緩めるのは宣言の突き合わせ（`check_same`）だけに留めた。

**欠陥（直した）**：**変数で割れてしまっていた。** §2.3 と §7.4 は除算を定数に限っているが、実装は検査を持っていなかった。`合計点 ÷ 満点`（満点は入力）が `check` を通り、生成 Python は `//`（床除算）を出し、参照評価器の厳密有理数と食い違い、生成 Go はコンパイルさえできなかった。**E115** を足した。コーパスに除算を使う規則が一本も無かったので、実装間の一致が踏まずに残っていたもので、§15.10-2 と同じ形の見落としである。

**欠陥（直した）**：**ベクタ生成器が入力を一つしか動かせなかった。** 導出の目標値に届かせるために動かす入力を一つだけ選び、その入力の範囲で足りなければ諦めていた。`品質 × 2 + 納期 + 価格 + 対応`（各 0〜10）で合計 45 を狙うには複数を動かす必要があり、行カバーが 2/4 に落ちていた。各入力を自分の範囲いっぱいまで動かし、残りを次の入力に回す形にした（各手は評価で確認するので、非線形な式は誤って置かれるのではなく置けずに失敗する）。4/4 と 6/6 に戻った。

**残した課題**：それでも、境界の外側の点が「二手先」にしかない配置には届かない。合計 64 から 63 へ、重み 3 の項を 1 下げて（61）重み 1 の項を 2 上げる、という手順が要る場合である。最初の一手が目標から遠ざかるので、いまの貪欲法では見えない。重みを 2:1:1:1 にすれば一手で届くため、コーパスの例はそちらにした。整数計画に踏み込むかどうかは、実表でこの形が出てから決める。

### 15.13 生成対象の言語（2026-09-13、TypeScript を実施）

**決定**：TypeScript を三つめの生成対象にした。残りは Swift・Kotlin・Java・SQL を候補として順に置く。

一本通してみた実コストは **codegen.rs に約 700 行、そのほか runtest・api・テスト・文書で約 280 行**。生成器はいま「Python 風のテキストを一度組み立て、言語ごとに後段で綴りを直す」形（`go_expr` / `ts_expr`）で、C 系の言語はこの道をそのまま使える。三つめを足した時点で、言語ごとの差分をトレイトに切り出す設計変更は**まだ割に合わない** — 差分は型名・ゼロ値・分岐の括弧・ランナーの四箇所に集中していて、`Lang` 列挙一つで足りた。五つめあたりで再評価する。

**決定（TypeScript）**：数値は `bigint` にする。E108 の証明は int64 に対してであり、JavaScript の `number` は 2^53 までしか正確でないので、`number` を使うと 9000 兆を超えたところで黙って間違う。**黙って間違わないことがこの道具の存在理由**なので、ここで妥協しない。単位は branded bigint（`bigint & { __rulec: "YenInclTax" }`）で、実行時の費用はゼロ。

**捨てたもの**：`enum` を使う案。TypeScript の `enum` は消去可能構文ではなく、`node file.ts` の型ストリップで動かない。凍結オブジェクトと合併型にしたことで、**ビルド手順も tsconfig も要らずに `node` だけで走る**生成物になった。`rulec test` が node だけで TypeScript 側を回せるのはこのため。

**残りの候補**（着手順は未定）。

| 言語 | 要るもの | 形の注意 |
|---|---|---|
| Java | JDK | 単一ファイル実行（`java Main.java`）でランナーがビルドツール無しに書ける。`long` は int64 そのもの |
| Kotlin | kotlinc | JVM。コンパイルが遅く、CI の時間が目立つ |
| Swift | swiftc | 動かせる環境が限られる。`Int64` はそのまま |
| SQL | 方言の決定が先 | 形が違う。行が分岐ではなく `CASE` の枝になり、標準入出力の JSON ランナーが作れないので、一致検査の取り方から設計が要る。方言（SQLite / PostgreSQL）、出す形（スカラー関数 / CASE 式 / ビュー）、整数除算の方言差が論点 |

**原則**：新しい言語は、**一致検査に乗らないなら入れない**。参照評価器とバイト単位で突き合わせられない生成物は、証明済みという看板の外側にあることになる。

### 15.14 ASCII 別名は、書いた場所で効いていなかった（2026-09-13）

「`table 運賃表(fee_table)` の括弧は意味があるのか」という問いから、§1.3 と実装が二つの方向でずれていたことが分かった。

**欠陥（直した）その一：全部 ASCII で書いた規則が通らなかった。** §1.3 が別名を要求する理由は「漢字は大文字を持てず、Go の公開識別子になれない」ことなのに、実装は**名前が ASCII かどうかを見ずに**括弧の有無だけを見ていた。`rule shipping_fee v1` が E011 で止まり、通すには `rule shipping_fee(shipping_fee) v1` と書くしかなかった。名前がもとから ASCII なら別名は要らない、に直した。**この道具は日本語で書くことを想定しているが、英語だけで書くことを妨げる理由は一つも無い。**

**欠陥（直した）その二：内部名の別名が捨てられていた。** §1.3 は「内部に閉じる名前の別名は任意で、省略すると生成コードも日本語識別子をそのまま使う」と書いている。書けば使う、の意味である。実装には `pub_name()` があるのに、内部名には一度も呼ばれていなかった。`derive 残余(margin)` と書いても生成コードは `残余` のままで、**別名は解析されてから黙って捨てられていた**。識別子を決める場所を `Gen::ident` 一つにまとめ、群・導出・定義・表の出力列すべてをそこに通した。

**決定**：`table` の別名だけは行き先が無い（表は一つの関数にインライン展開されるので、表そのものの識別子が生成されない）。構文としては残し、**SQL 生成でビューや CASE に名前が要るときのために取っておく**。いまは使われないことを文法リファレンスに明記した。

直す過程で出たもの三つ。

- **Python も Go も、宣言した群の集合／述語を使わずに毎回メンバーを展開していた。** `_遠隔地 = frozenset(...)` や `func is遠隔地(...)` は宣言されるだけで、セルは `dest in {…47 県のうち 6…}` を書いていた。死んだ宣言であり、読みにくくもある。一つの群を名指しするセルは、その宣言を呼ぶようにした（TypeScript は最初からそうしていた）。
- **丸め前の一時変数が `raw` 固定だった。** 出力の別名が `raw` の規則（`クーポン割引`）で衝突し、Python は黙って再束縛、TypeScript は構文エラーになった。規則が使っていない名前を選ぶ `Gen::temp` にした。
- **読まれない `derive` / `define` があると生成 Go がコンパイルできなかった。** §15.10-3 で表の出力列について直したのと同じ形で、導出と定義には効いていなかった。`Gen::go_unread` に一本化した。

### 15.15 公開する日本語から「箱」と「証人」を外す（2026-09-14）

**決定**：README・ドキュメントサイト・診断の文面から「箱」と「証人」を外す。一行が覆う領域は **区画**、それを起こす具体的な入力は **それを起こす入力**（短い札が要る場所では「その入力」、表の列見出しでは「入力例」）と呼ぶ。英語側は box / witness のまま触らない。形式手法で定着した語であり、英語では浮かないからである。

理由は単純で、どちらも英語をそのまま訳したせいで日本語として浮いている。「箱」はアルゴリズムの比喩が表に出てきたもので、「証人」は法廷の言葉であって数の呼び名ではない。この道具の日本語は業務担当者が読む前提に立っているので、そこで浮く語は落とす。「区画」を選んだのは、一行が受け持つのは各列の幅を掛け合わせた長方形であり、日常の日本語でその形をした持ち場を指す語だからで、列が三つ以上でも言い方が壊れない。

**捨てたもの**：「反例」。意味としては正しく、形式手法の日本語としても定着している。捨てたのは、これも漢字熟語であることと、E105 に当てはまらないことによる。両方の行に当てはまる入力は何かの反例ではなく、矛盾そのものの実例である。呼び名を一つに保てないなら、呼び名を置かずに毎回「それを起こす入力」と書くほうが短く読める。

**残すもの**：DESIGN.md の「箱代数」「箱和」「交差箱」「残余箱」。ここは実装の設計記録で、読者は決定可能性の議論を追っている。公開文書と設計文書で語彙が割れることは承知のうえで、そのままにする。

### 15.16 出力が二つ以上のときの返り値（2026-09-14）

三段の表をつないだ規則を書いて測ったところ、出力が二つ以上ある経路がまとめて壊れていた。見つかった順に四つ。

1. **`result` が生成コードから消える。** 評価器は `result` を一つ目の出力に当てる（§1.2）。生成側は出力を「同じ名前の束縛」から取るので、`result` の式をどこにも書かない。出力が一つのときは両者が一致するので露見しない。`rulec check` は `ok` を出し、`rulec gen` は束縛のない名前を返す Python・TypeScript・Rust・Go を書いた。
2. **刻みの割り戻しが無い。** 一つ出力の経路は、値の保持スケールが線上のスケールと違うとき `raw` に束ねて `/ (scale / out_scale)` で戻す。複数出力の経路はこの割り戻しを持っていなかった。**コーパスの `クーポン一枚` がこれに当たっていて、`素割引` が 100 倍で返っていた。**
3. **`result <名前>` の名前が効かない。** 型検査は名指しされた出力の型で見るのに、評価は一つ目に入れる。`number` が `money` の枠に入って E103 が出ない。
4. **`result` を二本書くと二本目が一本目を黙って上書きする。** `RuleFile::result` が `Option` 一つで、診断が無い。

**決定**：生成側は、出力ごとに同じ三手（出どころ → 線上のスケールへ戻す → 宣言された丸めを一度だけ）を踏む。一つ出力と複数出力で別々に計算していたのをやめ、四つの言語それぞれで一本のループにした。出どころは、一つ目の出力だけ `result` の式、あとは同じ名前の束縛である。`result` は**一つ目の出力のための糖衣**のままとし、それ以外を名指ししたら E015、二本目を書いたら E016 で止める。

**捨てたもの**：`result <名前>` を名指しどおりに結ぶ案。書き手の期待には近いが、出力ごとの値は「同じ名前の束縛」で既に一般に取れる（`define 乙 = …` が二つ目の出力になる）ので、`result` を一般化すると同じことをする道が二本になる。糖衣のままにして、糖衣の効く場所を診断で固定するほうを採った。

**なぜ通っていたか。** ここでも §15.9 と同じで、行使されていない構造は検査されない。`result` を持つコーパスの規則は六本あって全部 outputs が一本、複数出力の規則は `クーポン一枚` 一本きりだった。しかもその一本は、境界から作ったベクタ 94 件が**すべて `素割引 = 0`** で、100 倍のずれが一件も現れない。突き合わせは 0 と 0 を比べて緑だった。`examples` は参照評価器しか走らせないので、こちらも黙っていた。コーパスに `会員特典.rule`（`result` + 出力二つ + 表の列から来る率）を足して固定する。

**残っている穴**：ベクタが出力の値を的にしていないこと。行・境界・隠れ対は的にしているが、「数値出力が全ベクタで同じ値」という状態を誰も咎めない。`rulec coverage` の第四の基準にするのが素直だが、これは別に決める。

### 15.17 英語圏のコーパスと、単位の表（2026-09-14）

**測ったこと。** 英語のサイトも図も、例が日本の地域と円で書かれている。これは文書の問題ではなく、**言語の問題**だった。

- `5USD` は書けない。`src/lex.rs` の `is_unit_char` が通すのは `円 銭 g k c m % ％` の 7 文字だけなので、`5` と `USD` の二語に割れて E014 で止まる。`lb` `oz` `in` `mi` も同じく無い。
- `src/types.rs` の `unit_info` も同じ 7 単位きりである。
- 一方で `Ty::Money { cur: String }` は通貨を自由な文字列として持っているので、**型のほうは既に用意ができている**。足りないのは字句と単位表だけである。
- 英語の生成物にも円が残っている。丸めヘルパの doc コメントが "Toward zero: -4.8 yen → -4 yen" と書く（`src/codegen.rs` に 6 箇所）。

**決めていないこと。** 単位表を (a) 組み込みで増やす（USD/cent、lb/oz、in/mi …）か、(b) 規則の側で宣言できるようにするか。(b) は「単位は型の一部」という §2.1 の骨格に触るので安易には採らない。通貨は主単位と補助単位の比が要る点で 円/銭 と同じ形をしているから、増やすなら既存の対がそのまま雛形になる。

**順序。** 公開のあと。単位が先で、次に英語圏の規則を一本コーパスへ、最後に英語版の図の描き直し（`overview.rule` は名前だけ英語で、金額は円のままである）。コーパスの既存 12 本は**実在する公開規約の転記**なので、円のまま残す。転記を書き換えたら転記ではなくなる。

### 15.18 単位の表を開く（2026-09-14）

**決定**：§15.17 で測った穴を塞ぐ。三つある。

**1. 通貨はそれぞれが独立した次元である。** いままで `unit_info` は `円` と `銭` を `money` という一つの次元に入れていた。同じ次元に `USD` を足すと、`money[円]` の列に書いた `100USD` が黙って換算される。**為替レートはこの道具の中に無いし、あってはならない。** だから次元を通貨そのものにする。`円` と `銭` は同じ通貨の主単位と補助単位、`JPY` は `円` の別綴り。通貨の違う値を混ぜれば E103 で止まる。

**2. 主単位と、その 1/100 の補助単位。** ISO 4217 のコードに `c` を付けたものを補助単位とする（`USD` と `USDc`、`EUR` と `EURc`）。`money[USD]` は整数ドル、`money[USDc]` は整数セントで、リテラルは両者のあいだで換算される（`5USD` は `money[USDc]` の列で 500、`599USDc` は `money[USD]` の列では 5.99 なので拒まれる）。`mass[kg]` と `mass[g]` の関係そのままである。この整理で既存の欠陥も一つ消えた — 旧実装は宣言側の係数を割っていなかったので、`money[銭]` の列に書いた `5円` が 5 になっていた（正しくは 500）。

**3. 質量と長さにヤードポンド法を足す。** `lb`（453.59237 g）、`oz`、`in`（2.54 cm）、`ft`、`yd`、`mi`、それと `mg` `t` `mm` `km`。換算係数はすべて厳密な有理数なので `Rat`（i128/i128）のままで誤差は出ない。`1lb` は `mass[g]` の列では 453.59237 で整数でないから拒まれる。これは正しい — ポンドの列にグラムは書けない。

**捨てたもの**：通貨を自由な識別子にして、宣言と綴りが一致するかだけ見る案。表が要らなくなるかわりに、`100lbs` が「lbs という通貨」として通る。閉じた集合であることがこの道具の骨格なので、通貨も閉じた表にする。

**字句解析**：`is_unit_char` は 7 文字の白名簿だった（`円 銭 g k c m % ％`）。ASCII の英字と `円 銭 % ％` に広げる。`5USD` が `5` と `USD` の二語に割れていたのはこれが原因である。

### 15.19 予定していない言語へ生成する（2026-09-14）

**きっかけ**：「私たちが予定していない未知の言語や、ワークフローシステムの式言語に組み込みたい場合がありうる」という問い。調べてみたら、**やり方はもうあって、書いていなかっただけ**だった。`rulec api` が呼び出し方を出し、`rulec schema` がやりとりする JSON の形を出し、`rulec adapter` がテンプレートを出し、`rulec verify --adapter <cmd>` が**どんなプロセスでも**立ち上げて生成ベクタ全件で突き合わせる。`verify` の一行説明が「旧実装を立ち上げる」としか言っていないので、新しい対象を確かめる手段だとは誰も読み取れない。それだけのことだった。

**決定**：やり方が二つあることを `docs/backends.md` に書く。**rulec の外で生成するほう**（自分のジェネレータで書き出し、adapter で包み、`verify` で押さえる／rulec は無改造）を先に、**rulec に組み込むほう**（`src/codegen.rs` にバックエンドを足す／§15.13 の手順とコスト）を後に置く。順番には意味がある。外で生成するほうは今日から使えて、対象を選ばず、証拠の強さは組み込みと変わらないからである。

**決定**：**CI で走らせられない対象は、禁じるのではなく、生成物に「確かめていない」と書かせる。** ライセンスの無いエンジン、スクリプトから叩けない表計算、他人のサービスの上で動く DSL — adapter が書けない以上、突き合わせる相手がいない。

理由は、禁じても要る人は要るからである。禁じられたら手で書き写すことになる。**手で書き写すことこそ、この道具が防ぐために存在している失敗**で、しかもそちらには何の印も残らない。「確かめていない」と自分で名乗る生成物のほうが、黙って正しい顔をしている手書きよりそのぶん安全である。ただし看板の外に置く — 証明済みとは呼ばないし、`verify` を通った対象と並べて一覧しない。

**§15.13 の原則を広げたのであって、置き換えたのではない。**「一致検査に乗らないなら入れない」は**組み込みバックエンド**を縛る規則として、そのまま残る。外で生成したものはこのリポジトリの中には無く、利用者のものである。その二つを分けているのが、この断り書きである。

**捨てたもの**：rulec 側に「確かめていない」と書かせる案。外での生成は他人のジェネレータの中で起きるので、rulec には書きようがない。ジェネレータを書く人への決まりごととして文書に書くのが、実際に効く唯一の形である。

**捨てたもの**：文書だけ書いて、例は載せない案。このページの主張は「証拠を手放さずに、予定していない相手へ生成できる」であり、走らせたことのない手順書ではその証拠にならない。だから SQL（SQLite。§15.13 の第一候補で、ランナーを持てない「形の違う」対象）で実際に一周して、ec261 の 88 件全件一致と、閾値を一つ壊したときの不一致報告の両方をページに載せた。`tests/backends.rs` が文書から SQL と adapter を取り出して走らせ、両方の出力を固定する。

### 15.20 五つめの生成対象に Ruby（2026-09-15）

**決定**：Ruby を五つめの生成対象にする。§15.13 の候補表（Java・Kotlin・Swift・SQL）より先に置く。

理由は三つ。**当たりが近い** — この道具が狙うのは運賃表・手数料・割引・可否判定で、その種のコードが実際に住んでいるのは Rails のアプリである。Swift や Kotlin（モバイル）より業務判断からの距離が短い。**一致検査に何も足さずに乗る** — `json` が標準添付なので、ランナーに gem が一つも要らない。`node` だけで走る TypeScript、`rustc` だけで通る Rust と同じ性質で、§15.13 の関門をそのまま通る。**形が既知** — Ruby の `/` は Integer に対して負の無限大方向へ丸め、Python の `//` と同じである。§15.11 で一度刺さった差なので、生成器に処理もテストもすでにある。

**決定（単位）**：**素の `Integer` にして、単位は署名とコメントで言う。** Ruby には実行時費用ゼロの別名型が無い。この道具の保証は**証明**であって host 言語の型検査ではなく、Python がすでにその前例である（`NewType` は mypy が見るだけで、実行時には何も起きない）。`.rbs` を隣に出して `steep` に見せる案は**足せる形にしておくが、いまは出さない** — 生成物が二つになり、型検査器を持たない読み手には使われないまま腐る側に回る。

**決定（整数の幅）**：Ruby の `Integer` は多倍長なので、E108 が証明する int64 の範囲を**破ることはないし、強制もしない**。JavaScript とは事情が逆で、2^53 を超えて黙って間違うことが無い。だから `bigint` に相当する措置は要らない。証明が守っているのは値であって、器ではない。

**決定（3.x と 4.x）**：生成物に 4.x 固有の機能を使わない。モジュール、メソッド、凍結した定数、`Integer`、`Struct` だけで書けるので、3.x と 4.x の両方で動く。`Data.define`（3.2 以降）は使わず `Struct.new` にするのはこのため。

**実装上の制約が一つ**：Ruby の定数は**大文字の ASCII で始まらなければならない**。モジュール直下に `遠隔地 = [...]` と書くと定数ではなくローカル変数になり、メソッドから見えない（実測で `NameError`）。だからグループは `GROUP_遠隔地` の形にする。列挙の値名は別名から大文字 ASCII になるので問題ないが、別名が無い場合に備えて同じ前置を通す。

**捨てたもの**：キーワード引数。Ruby では三つ以上の同型引数にキーワードを使うのが作法だが、ほかの四言語は位置引数で、`rulec api` の目録も署名を言語ごとに並べて比較できることに意味がある。位置引数に揃える。

**再評価（§15.13 が「五つめあたりで」と書いたもの）**：**§15.13 の見立ては誤りだった。** 実測は、生成コード本体が 540 行、それとは別に**手で編集したファイルが 22 個**である。

「差分は四箇所に集中していて `Lang` 列挙一つで足りる」は、`guards()` の内側だけの話だった。その外に**手書きの一覧が七つ**ある — `main.rs` の生成物、`runtest.rs`（五箇所）、`api()`、`tests/threeway.rs`、`tests/shapes.rs`、`tests/api.rs`、`tests/formats.rs`。さらに図の生成器が二つ、文書が九ファイル約二十箇所。どれも「言語を一つ足したら手で直す」ものである。

言語ごとの綴りを `Backend` トレイトに集め、登録簿を一つにして生成・実行・目録・テストをそこから回す整理を、**次にやる**。これは §15.9 と同じ形の教訓でもある — 一覧が七つあることは、七つとも手で直すまで見えなかった。

**唯一、止めてくれたのは図の `--verify` だった。** 流れ図が「rulec gen が書く言語」を実際のツール出力と突き合わせていて、Ruby を足した瞬間に落ちた。同じ検査が文書の側には無いので、そちらは黙って古いままになる。整理ではそこも閉じる。

### 15.21 対象言語の登録簿（2026-09-15）

**決定**：どの言語を生成するかを `src/backend.rs` の一箇所に持たせ、生成・実行・目録・テストはそこを回す。§15.20 が数えた「手書きの一覧が七つ」を一つにする。

登録簿の一行が持つのは、安定した id、人が読む名前、PATH に要る道具、書き出すファイル、走らせ方（`Plan`＝作業場所・任意のビルド・コマンド）である。**データで言えるものは登録簿に、言えないもの（生成器そのもの）は `codegen.rs` に**、という線で切った。

`guards()` にあった三つの `match lang` は消えた。言語ごとの綴り（コメント記号、`and` か `&&` か、`if` の頭、ブロックの閉じ方）は `Lang::spelling()` の一行になり、セル描画は `Gen::cell()` 一箇所になった。

**決定（文書も検査に乗せる）**：対象言語を三つ以上並べている行は、登録簿の全部を並べていなければ落とす。理由は §15.20 の実測で、Ruby を足したとき**私を止めたのは図の `--verify` だけ**だったからである。図には検査があり、文章には無かった。

**その検査が書いた直後に三箇所を見つけた。** `docs/generated-code.md` の冒頭（Ruby が抜けていた）、同 179 行（部分列挙）、そして `src/codes.rs` の E107 の説明 — そこには「**Three-way agreement (evaluator, Python, Go)**」「all three」が残っていた。TypeScript より前の文面であり、退役したはずの「三者一致」でもある。**Ruby とは無関係に、ずっと前から腐っていた。** §15.9 の「行使されていない構造は検査されない」が、文章についても成り立つことの実例である。

### 15.22 生成 Python は mypy を通っていなかった（2026-09-15）

**きっかけ**：「Python の生成コードに型注釈は適切に付いているか」という問い。注釈は付いていた。**一度も型検査器に通していなかった**のが問題だった。`mypy --strict` を当てると、コーパス 13 本のうち **8 本が落ちた**。

**原因**：`NewType` に算術をすると素の型に戻る。`YenInclTax * int` は `int` であり、丸めヘルパから出てきた値も `int` である。それをブランド付きの出力として返していたので、**ブランドが捕まえるために存在している取り違えを、生成物自身がやっていた**。

**決定**：出力の値をブランドで包み直す（`return YenInclTax(_round_up(fee, 10))`）。`NewType.__call__` は引数をそのまま返すので、実行時にはほぼ何も起きない。中間の `raw` は包まない — あれは出力の単位ではない別の刻みの値であり、包めば嘘になる。

**決定**：ランナーも同じ規律に従わせる。`m.Kilometer(int(d["距離"]))` のように引数を構築する。これは**呼び出し側が実際にやらねばならないこと**なので、ランナーが呼び出し方の手本として正しくなる。`_ord` と `_wire` にも注釈を付けた。

**決定**：`mypy --strict` をテストに乗せる（`生成pythonはmypy_strictを通る`）。mypy が無ければ飛ばして報告する、既存の `ruff` と同じ流儀。

**これも §15.9 である。** README と `docs/generated-code.md` は「ブランドは mypy と pyright で効く」と書いていた。**書いてあるだけで、それを行使する検査が無かった。** 行使されない主張は、行使されない構造と同じように腐る。

**残っていること**：`pyright` では試していない。`NewType` の扱いは両者でほぼ同じだが、確かめてはいない。

### 15.23 Ruby に署名を添える（2026-09-15）

**決定**：`rulec gen` が `ruby/sig/<規則>.rbs` も書く。§15.20 で「足せる形にしておくが、いまは出さない」と書いたものを出す。

**まず測った。** RBS で単位を分けられるかを `steep` で実験した。`type yen = Integer` と `type gram = Integer` を宣言して、gram を渡す呼び出しを書いた — **通る。** RBS にも newtype は無く、型別名は同じ型である。捕まったのは `String` を渡したときだけだった。**だから .rbs は §15.20 で諦めた単位安全性を取り戻さない。** そこは正直に書く。

**それでも出す価値がある。** 実験で効くと確かめたものが三つある。引数の数、引数の種別（`Integer` と `String` と `bool`）、そして**列挙**である。列挙は値そのものの合併（`"率引き" | "額引き" | "送料無料"`）として書けるので、**型のレベルで閉じる**。生成した Ruby 側では列挙の値は実行時まで単なる文字列で、入口ガードが弾くまで分からない。ここは .rbs のほうが強い。

**決定（検査の当て方）**：`.rbs` を**モジュール自身に当てる**。呼び出し側だけを見るのでは、署名が取りこぼしたメソッドが見つからない。実際、私有の丸めヘルパを宣言するまで `steep` は警告を出し、`Output.new` を宣言するまでエラーを出した。どちらも「呼び出し側だけ」の検査では出ない。

**決定（噛むことも検査する）**：`rbsは誤った呼び出しを拒む` が、誤った三つの呼び出し（種別違い・列挙外・引数不足）が拒まれ、正しい一つが拒まれないことを確かめる。**一度も失敗したことのない検査は、効いていることが示されていない。**

**捨てたもの**：実行時のラッパクラスで単位を分ける案。それなら単位安全性は戻るが、§15.20 の「実行時費用ゼロ」を捨てることになり、生成物が普通の Ruby でなくなる。単位は証明が守っていて、host 言語の型検査はその写しに過ぎない。

### 15.24 六つめの生成対象に Swift（2026-09-15）

**決定**：Swift を六つめの生成対象にする。§15.13 の候補表に残っていた三つ（Java・Kotlin・SQL）より先に置く。

理由は三つ。**当たりが近い** — 狙いは「同じ業務ルールを、バックエンドとクライアントで共有する」ことで、iOS 側が Swift なら表が一枚で済む。§15.20 が Ruby を Swift より先に置いた根拠は「業務判断からの距離」だったが、距離が短いのは *サーバ側の* Swift ではなく、**サーバとクライアントが同じ答えを返す必要**のほうである。**単位が型に載る** — 値ひとつの struct は Swift ではその整数と同じ配置になるので、Rust の newtype と同じ取引（実行時費用ゼロで取り違えを弾く）がそのまま成り立つ。§15.20 で Ruby に諦めさせたものが、ここでは戻る。**一致検査に何も足さずに乗る** — `swiftc` だけで通り、SwiftPM も `Package.swift` も要らない。整数除算は 0 方向で Go・Rust と同じなので、丸めヘルパはそちらの書き写しで済む。

**§15.21 の登録簿は効いたか。** 効いた。実測は、生成器に約 760 行、`src/backend.rs` に 1 行、**`src/` で他に手で直したファイルは無い**。§15.20 の Ruby は本体 540 行に加えて手編集 22 ファイルだったので、後半がまるごと消えたことになる。唯一の例外は `--help` の二文で、そこは対象言語を書き出していたのを登録簿から引くように直した — つまり**手書きの一覧が一つ残っていた**のを、Swift が見つけた。

**綴りは Swift のものにした。** 識別子は lowerCamelCase（`shipping_fee` → `shippingFee`）で、Go に `pascal` を書かせたのと同じ理由である — 生成物は他人の Swift のコードベースの中に住み、そこでは snake_case をリンタが叩く。§1.3 の「作者の書いた別名をそのまま使う」から外れる二つめの言語になるが、外れた綴りは `rulec api` が申告し、目録から組んだ呼び出しを `swiftc` に通すテストがそれを押さえる。予約語に当たる別名はバッククォートで囲む。**呼び出し側の引数ラベルだけは規則が逆で**、キーワードはそのまま置く（囲むと「囲む必要は無い」と警告される）。例外は `inout` ひとつだけ。

**`_min` / `_max` は自前のままにした。** 最初、Swift の標準ライブラリの `min` / `max` に寄せた。`クーポン割引.rule` が `最低購入額(min)` という入力を宣言していて、パラメータがグローバルを隠すので、`min(素割引, 上限額)` が**呼び出し側の渡した金額**に解決してコンパイルが落ちた。README の「組み込みをそのまま呼ばない」がそのまま刺さった形で、他の五つが最初から自前を持っていたのはこのためである。

**読まれない列には `_ = x` が要った** — Go と同じ device である。Swift は読まれない束縛を警告し、生成物は DO NOT EDIT なので後から黙らせられない。`is_read()` はすでにあったので、呼ぶ場所を足しただけで済んだ。

**ランナーは `main.swift` ではなく `@main` にした。** トップレベルのコードは `main.swift` という名前のファイルにしか書けず、規則の本体をその隣に置きたいので、ランナー側が `@main` を持つ。一方 `_round_test.swift` は単独でコンパイルされる＝それ自体が main ファイルになるので、逆にトップレベルのまま書く。

**ついでに見つかったもの**：予約語に当たる別名（`重量(where)` など）で、**Rust の生成物がコンパイルできない**。`r#where` が要る。Swift とは無関係に前からある穴で、直すのは別の変更である。`tests/shapes.rs` の新しいテストに、Rust をそこだけ検査していない理由として書いた。

**捨てたもの**：`Int` を使う案。Swift の `Int` は語長で、いまの対象では 64 ビットだが、E108 の証明が述べられているのは int64 である。証明の言葉と生成物の型を一致させるほうを採った。

### 15.25 式の中のリテラルは自分の単位で読む（2026-09-15）

**きっかけ**：Swift を足す途中で「真偽値の `define` を表の列にするとベクタが 0 件になる」規則に当たった。最初はそう報告したが、**原因も範囲もそれとは違った**。`送料.rule` も `define 大口` を列にしていて、そちらは動いている。

**原因**：`eval.rs` の `Expr::Lit` が、式の中のリテラルを **円・率・無単位の三つでしか試していなかった**。`500g` はどれにも当たらず `None` を返し、比較全体が `None`、`define` に値が付かず、表が一行も発火しない。「列が `define` だから」ではなく「リテラルの単位が円でないから」だった。

**実測**：15 単位系のうち通っていたのは 3 つ（円・`%`・無単位）だけ。mass の 5 つ、length の 4 つ、EUR と USD は**値が出ない**。`銭` はもっと悪く、`500銭` が 円 の枝に当たって 5 と読まれ、**百分の一の値で通っていた** — `499銭 >= 500銭` が真になり、オラクルが誤答する。`derive 超過 = 重量 - 2000g` も同じ経路で壊れていた。

**コーパスが全部 円 で式を書いていたから、ずっと見えなかった。** ec261 は EUR だが、金額が表のセルにしか出てこない（セルは列の型で読まれるので別経路）。§15.9 の「行使されていない構造は検査されない」がまた当たっている。

**決定**：`Expr::Lit` は `lit_ty_pub`、つまり**リテラル自身の型**で読む。`codegen.rs` は最初からそうしていて、ずれていたのは評価器だけだった。これが唯一の正しい読みだと言えるのは **E103 が式の中の単位混在を禁じている**からで、`重量(mass[g]) - 2kg` も `額(money[銭]) >= 5円` も検査で止まる。したがってリテラルが出会う相手の単位は必ず自分と同じである。

**壊れていたのはオラクルのほうで、生成コードは六言語とも正しかった。** `rulec test` は言語間の一致を見るので落ちて気づけるが、`replay` と E107 は評価器だけを見る。E107 は「例が成り立ちません」と言うので、**正しい規則を書いた人が、存在しない欠陥を出典に探しに行く**ことになる。そこが一番の害だった。

**検査を足した**（`tests/units.rs`）。単位表を全部歩いて、式の中のリテラルが評価でき、両方の行に当たるベクタが出ることを見る。`銭` は別に一本、境界の下の値が 1 行目に当たらないことを確かめる。

**ついでに見つけたもの**：TypeScript と Swift のランナーが規則を裸の名前で呼び、同じ場所で `d` という局所変数を使っていた。`rule d` が JSON を `d` に束ね、呼び出しがそちらに解決していた。Python・Ruby・Rust・Go は呼び出しを修飾しているので無事。衝突する名前だけを改名する（`runner_local`）ので、他の規則の生成物は 1 バイトも動かない。

### 15.26 ベクタ生成器が「一度に一つの入力」で詰まる（2026-09-15）

**きっかけ**：`policy first` の表で、到達可能な行にベクタが一つも当たらず、`coverage` が exit 1 のまま CI が緑にならない事例に当たった。`examples` でその行を明示的に固定しても変わらない（`examples` はベクタ集合に入らない）ので、書き手に打つ手がない。

**原因は二つあった。** どちらも「一度に動かす入力は一つ」という縛りの副作用である。

1. **`win_row` が、対象行が `-` にしている列しか動かさなかった。** 「対象行が名指しする列を動かすと対象行自身が壊れる」という理由づけだが、それが真なのは**セルが一点のときだけ**。`a >= 1` の行が `a = 1` の先行行を外すには `a = 2` があり、両立する。**全列を名指しする行は、どれだけ到達可能でも永久に勝てなかった。**
2. **`reach_row` が、後の列を直すときに前の列を壊した。** 導出 `d = b - a` の `d >= 0` を直すのに `place` は宣言順で最初に効く入力＝`a` を動かし、二列左の `a >= 2` を取り消す。二パス回す作りなので次のパスが戻し、その次がまた下げる — **振動して収束しない。**

**決定**：`win_row` は「動かしてよい列か」ではなく「動かしたあと対象行が保てるか」で判断し、受理条件を `violate_cell` に渡す（先に見つかる外し方は対象行も外すことが多く、使えるものはその先にある）。動かしたあとは行を組み直し、組み直しが先行行を戻したら捨てる。`place`・`satisfy_cell`・`reach_row` には**凍結集合**を通し、その行が既に固定した入力には手を出させない。凍結で行き止まりなら凍結なしで再試行するので、探索が狭まることはない。

**実測**：コーパス 13 本の**ベクタは一件も変わらない**（件数も中身も）。直るのは、これまで落ちていた形だけである。

**残っている（別件）**：`region` は導出列を、宣言された `range` だけに縛られた**自由な軸**として扱う。そのため `a = 1` と `d < 0` を同時に満たす点が在ると判断し、`policy unique` なら **E105 を出して正しい規則を弾く**。示される入力例も再現できない（導出値が入力の顔で並び、それを決める入力が出てこない）。ここは近似の設計そのものなので、切り分けて扱う。

### 15.27 導出軸の重なりを、証拠のあるものだけ報告する（2026-09-15）

**きっかけ**：§15.26 の調査中に、`policy unique` の表で **E105 が正しい規則を弾く**のを見つけた。示された入力例は `a = 1` と `d < 0` を同時に主張するが、`d = b - a` で `b >= 1` なら `a = 1` のとき `d >= 0` である。**その入力は存在しない。**

**原因**：§6 は一列を独立した軸にし、一行を箱にする。これが「完全性と重なりが厳密に決定可能」の土台である。ところが導出列にも独立した軸が与えられ、宣言された `range` にしか縛られない。箱の積には、どの入力からも到達できない点が混じる。篩（`feasible`）はそれを落とすためにあるが、**見ているのは軸ごと**で、「同じ点で別の軸が固定されているとき、この導出は何を取りうるか」は問わない。今回の矛盾は軸と軸の関係にあるので、構造的に落ちない。

**機構はすでにあった。** 定義軸については「箱が自由に置いた座標を鵜呑みにせず、実際の入力を構成し、**構成できたものだけ**を本物の矛盾として扱う」（`pair_witness`）。導出軸がその扉を通っていなかっただけである。

**決定**：同じ扱いを導出軸にも広げる。構成できなければ `Unknown` に落とす — 証明できていないものを証明済みとして出さない（§6.2）。`policy first` では、構成できなかった対を**影として数えない**（入力例を付けず、§9.2 の隠れ対の義務も課さない）。`first` では先行行が勝つだけで守るものが無いので、降格の代償が無い。

**副産物**：定義軸しか通っていなかった実証が導出軸にも効くので、W105 の「この例を作る入力」が出る場面が増えた。**箱由来の作り話ではなく、評価器が実際に構成した入力**が並ぶ。golden はその分だけ増えた。

**残っている**：構成できなかった対は W114 になり、生成コードに実行時ガードが入る。それが**起こり得ない**場合、警告も守りも空振りである。消すには導出を入力に結び直す必要があり、それは §15-9 の将来項目（真偽定義の代入）と同じ話で、発動条件も同じ — **その過剰報告が実表で邪魔になったとき**である。今回それが実表で起きたので、材料は揃った。

### 15.28 出力が、自分のしたことを正しく言っていなかった（2026-09-15）

**きっかけ**：出力の文面を、実態を知らないつもりで読み直した。§15.25〜15.27 はそこで出た大きい二つで、ここは残りをまとめる。**どれも致命的ではない。**共通しているのは「**道具が、自分が何をしたかを正しく言っていない**」ことである。

- **`number` に `%` が付いていた。** 領域の軸が単位を持ち、空の単位が「日付」の目印だったので、単位を持たない唯一の数値型がその隣の率の枝に落ちていた。「JSON は正しいので表示だけ」で済む話に見えるが、**そのまま貼れるはずの `fix.text` も `| 1% | 0% | true |` になっていて**、貼ると E103 になる。手順どおり動くエージェントが無効な行を貼る。
- **走らなかった実行を「食い違い」と呼んでいた。** toolchain が取れない、コンパイルできない、落ちた — 全部が `参照評価器と食い違います` の見出しで出ていた。比較が行われて結果が悪かった、と読める。行われていない。見出しを分け、JSON に `ran` を足した。
- **飛ばした言語があっても緑だった。** 中心的な主張は「参照評価器と**生成した全言語**がバイト単位で一致する」なのに、toolchain が無い言語を飛ばして `All 2 matched.` / exit 0 と出る。主張の範囲が環境で黙って縮む。要約に範囲を書き、`--require-all` を足して CI の手順書をそちらに変えた。既定は寛容なままにした — 六つの toolchain を全部持っている機械ばかりではない。
- **生成 `go.mod` が `go 1.25` を要求していた。** 1.21 以降その行は toolchain の切替指示でもあるので、古い `go` は新しい版を取りに行き、通信の無い環境で失敗する。生成コードが使うのは `fmt` などだけで、要求する根拠が無かった。**上の「食い違い」の見出しは、たいていこれが引き金だった。**
- **`examples` がベクタ集合に入っていなかった。** 実行される仕様と謳いながら、E107 が参照評価器に当てて終わりで、**人が書いた唯一の事例がどの言語にも届いていなかった**。カバー義務にも数えないので、生成器の穴を例で塞ぐこともできない。入力を全部名指しする行をベクタにした。ec261 は 88 件から 94 件になった。

**教訓**：五つのうち四つは「出力の言葉が実態とずれている」類で、実装の誤りではない。**文面は、実態を知らない読み手にしか試されない** — 書いた本人は実態のほうを知っているので、足りない言葉を補って読んでしまう。§15.9 の「行使されていない構造は検査されない」の、文面版だと思う。

### 15.29 導出を入力に結び直す（2026-09-15）

**きっかけ**：§15.27 は「構成できた重なりだけ報告する」で誤りを止めたが、**起こり得ない対が W114 として残り**、生成コード六言語に絶対に発火しない実行時ガードが入り、`rulec doc` は承認者に存在しない場合を訊いていた。§15-9 の将来項目（9 番）は、この着手条件を「過剰報告が実表で邪魔になったとき」と書いていた。**実表で起きたので着手した。**

**決定**：軸ごとの篩に加えて、**交差の箱の上で導出の式を区間演算する**。`derive` は §5 で「入力の線形結合」に限られているので、`+` `-` 定数倍の区間演算で足りる。`a = 1` が箱に固定されていて `d = b - a`、`b ∈ [1,10]` なら `d ∈ [0,9]`。箱が `d < 0` を主張していれば、その交差は空である。

**一点ではなく箱で見る。** 既存の篩は交差の**一点**（両方のマスクが立つ最初の座標）を見ていた。一点が不可能でも交差が空とは限らないので、そこを厳しくするのは危うい。各軸について両方が選ぶ座標の**包**を取り、その上で式を評価する。両側とも包＝外側に広いので、「交わらない」と言えたときは本当に空である。

**開区間を刻みで閉じる必要があった。** `< 0` の上端を 0 と読むと `0 < 0` が偽になって判定が落ちる。座標は軸の刻みの上にあるので、`Open` は `[a+刻み, b-刻み]` に閉じる。ここが効かないと、直しが一切発火しない。

**完全性の穴の探索には手を入れていない。** あちら（§6.1 の `hole_within`）が `feasible` に渡すのはパディングされた一点で、その一点が不可能でも別の埋め方が本物の穴かもしれない。厳しくすると**本物の E101 を落とす**——この道具が唯一やってはいけない向きである。重なり側は交差の箱全体を見るので、この危険が無い。

**逆向きを落とさないことを検査に乗せた**（`tests/region.rs`）。一文字だけ違う二つの規則を並べる。`b >= 1` なら `a = 1` のとき `d >= 0` で対は不可能、`b >= 0` なら `a = 1, b = 0` で `d = -1` となり対は**実在する**。前者は一切報告せず、後者は必ず報告する。締めすぎれば後者が落ち、緩ければ前者が残る。

**実測**：コーパス 13 本と mutants の診断は**一文字も変わらない**。消えるのは、これまで過剰に出ていた分だけである。

**残っている**：上流の表との相関は、まだ軸ごとである。`b → x` の表の下流で `a ∧ b` を名指しする行は実際には死んでいるが、E102 はそれを拾わない（`coverage` は「その行を勝たせるベクタが作れない」と正しく言う）。同じ近似の、同じ場所の話である。

### 15.30 上流の表との相関を見る（2026-09-15）

**きっかけ**：§15.29 の残りとして挙げた最後の一つ。下流の表が「上流の出す値」と「それを決める入力」を同時に名指しする行は、**片方ずつなら起こるのに同時には起こらない**ことがある。`reachable` は列ごとに「上流が出しうる値の集合」しか持たないので、その相関が見えない。実表で二行出た。

**決定**：E102 の判定に、上流の表を一段だけ読む検査を足す。下流の行が列 `k` に値 `v` を求めるとき、上流で `v` を出す行のうち、**この行の他のセルと両立し、かつ自分より前の行一つに丸ごと覆われていない**ものがあるかを見る。一つも無ければ、その行はどの入力でも勝てない。

**緩い側に倒してある。** 先行行の**和**は引かない（一行ずつしか見ない）し、上流のさらに上流までは追わない。だから「出せる」と言い過ぎることはあっても、「出せない」と言い過ぎることはない。**E102 はエラーなので、締めすぎれば正しい規則を弾く** — これまでの直し（報告を減らすだけ）と逆向きで、そこが唯一の危うさだった。検査は一値違いの二規則で押さえた。`黒` は `種 = 甲` からしか出ないので `黒 × 乙` は死に、`白 × 乙` は生きる。

**入れた直後に、道具が自分と矛盾した。** E102 が「この行は死んでいる、消せ」と言い、消すと E101 が「その組み合わせが覆われていない、足せ」と言う。完全性の探索（`find_hole`）が上流相関を知らないからで、**作者に正反対のことを二つ言う**状態になった。点に対しても同じ判定ができるようにして、そちらにも通した。

**その瞬間、既存の変異が一つ軽くなった。** `m_e102b` は「上流が出さない値を下流が名指しした」変異で、E102 三件のほかに **E101 を一件出していた** — 「決して出ない `可否 = true` に行を足せ」という要求である。同じ実行の中で E102 がその行を死んでいると言っているのだから、前から矛盾していた。`tests/m0.rs` の固定値を一件減らし、理由をその場に書いた。

**実測**：コーパス 13 本の診断は変わらない。mutants で変わったのはいま書いた一件だけである。

**残っている**：二段以上の連鎖（上流の上流）と、先行行の和による被覆は見ていない。どちらも「見落とす」側なので、正しい規則を弾く危険は増えない。

### 15.31 リテラルの尺度は一か所で決める（2026-09-15）

**きっかけ**：処理の流れを図解する作業で `codegen.rs` の §7.1 を読み直していて見つけた。§15.25 の**裏返し**である — あちらは評価器が間違っていて生成コードが正しかった。こちらは評価器が正しくて生成コードが間違っていた。

**原因**：リテラルの尺度を**二か所が別々に計算していた**。`types.rs` は「小数桁の 10 の冪 × 単位の分母」で決め、それを名前の尺度として記録する（`3.6%` なら 1000）。`codegen.rs` は**約分後の分母**を使っていた（`3.6%` は 9/250 なので 250）。`define` は前者の尺度で読み直されるので、250 で書いて 1000 で読む。黙って 4 倍ずれる。

**実測**：`3.6%` は 1/4、`8%` も 1/4、`50%` は 1/50 になる。`7%` と `1%` は正しい — 100 と約分できないからである。**100 と公約数を持つ率はほぼ全部壊れていて、抜き取りで確かめると助かっている側を引きうる。**

**コーパスが一度も踏まなかった。** コーパスの率はすべて**列**なので、生成器には名前として届く。名前は `types` が記録した尺度をそのまま持つので、ずれようがない。リテラルが式の中に出るのは `define` / `derive` の本体だけで、コーパスにその形が一本も無い。セルの中の `%` は列の型で読まれる別経路である。§15.9 の「行使されていない構造は検査されない」がまた当たっている。

**普段の網が二つとも効かない形だった。** `check` は通る — 評価器は別経路で、しかも正しいから。六言語も互いに一致する — 生成器のテキストを共有しているから。食い違うのは**生成コードと評価器のあいだだけ**で、それを見るのは `rulec test` しかない。

**決定**：`types::lit_scale` を一つ置いて、両側がそれを呼ぶ。約分後の分母は使わない。`3.6%` は `36`@1000、`8%` は `8`@100 として保管される。二度と離れないように、定義を一つにしたのが要点である。

**実測**：コーパス 13 本の生成物は **1 バイトも動かない**。踏んでいなかったのだから当然だが、確かめた。

**検査を足した**（`tests/wire.rs`）。率のリテラルを `define` に置いた規則を生成して、保管される整数と戻しの除数が名前の尺度と揃っていることを見る。このファイルは「率だけが保管値と転送値で違う型だから、変換を忘れた場所を捕まえる」ためにあり、これもその一件である。

**ついでに直したもの**：`÷` の右が変数のときのコメントが E103 と書いていたが、実際に出るのは E115 だった。

### 15.32 表と行に出典を書く（2026-09-16）

**決定**：表の出典は `table` 行の行末コメントに書き、その表の出典と違うところから来た行は、行の行末コメントに書く。`rulec doc` は前者を表の見出しの直下に、後者を「注記」の列として出す（例の行も同じ）。`description` は一行の要約に戻す。文法は変えず、check は関与しない。

理由。§16 第三の心配（仮置きが権威になる）は丸めについて書いたが、金額も同じ形をしている。出典の無い 42 行を承認する人は「表全体をもう一度読む」ことになり、出典のある行なら「この行とそのセルを見比べる」ことになる。出典が改定されたとき読み直す行も、その出典を引いている行に絞れる。書くのは転記している当人で、そのとき出典のページは開いている。

実装で分かったこと。宣言行の行末コメントは doc の注記に出ていたが、表の行のコメントは原本から行を取るときに落としていて、**書けるのに承認者に届いていなかった**。表に一つ書けるようにしたのは、42 行の表に同じ出典を 42 回書かせないためである。コメントの無い表は一字も変わらない（注記の列は、どれかの行にコメントがあるときだけ出す）。

**捨てたもの**：`source` という構文を足す案。コメントで足りるものに構文を足すと、fmt・parser・reference・fixtures の全部が一語ぶん増える。出典ファイルのダイジェストを持たせて、変化を check が名指しする案。ダイジェストの変化から言えるのは「この出典を引く行は読み直し」までで、どのセルかは分からない。それは表の性質ではなくレビューの引き金なので、check の診断にはしない。出典がスプレッドシートでセル参照まで書けるなら読み取り専用で突き合わせられるが、それは `import`（§1.4）と一緒に決める。

### 15.33 生成コードが、当てはまった行を返す（2026-09-16）

**決定**：生成する関数を二つにする。呼び出し側が使う関数は署名を変えず、隣に `_traced`（Go と Swift は `Traced`）を置く。同じ入力を取り、出力と一緒に当てはまった行を返す。行は表ごとに一つ、順に、表の名前と 1 から数えた行番号で、`doc` の `#` 列、verify と replay のクラスタの鍵と同じ番号である。分岐は `_traced` に一度だけ書き、素の関数はそれを呼んで行を捨てる。`rulec api` は `traced` と `traced_signature` で名前と署名を出す。

理由は三つ。第一に問い合わせ対応。「なぜこの送料か」に、ログの (表, 行) から承認済みの資料の行へ直接たどって答えられる。第二に一致検査が強くなる。expected.jsonl は `out` だけを持っていたので、「値は合っているが違う行で合った」は通っていた。vectors はもう行を持っているから、runner が行も出せば突き合わせは行の単位になる。§15.16 の「全ベクタが 0 だったので百倍のずれが見えなかった」と同じ種類の盲点が一つ減る。第三に本番の記録に行が乗る。本番が当てた行と規則が当てる行を組にすれば、金額が同じで行が違う食い違いが見える（記録の側は次の増分）。

**捨てたもの**：`--with-trace` という生成のフラグ。§15 の 3 番で「生成物の形は一つに保つ」と決めていて、フラグは形を二つにする。出力の構造体に行を足す案は、出力が一つのとき値そのものを返しているので置き場所が無い。省略可能な引数で行を受け取る案は、Go と Swift に自然な形が無く、Rust では署名が変わる。

**代償と、出たもの**：行ごとに一行増える（§8.1 の基準 4、1 行あたり 2〜4 行に収まる）。生成物の抜粋を載せている文書は全部動いた。Swift の runner は、文字列を `+` でつなぐ一行が長くなりすぎて型検査が「妥当な時間で型検査できない」と諦めたので、補間に変えた。生成物にも起きる実在の失敗として記しておく。生成物の中の一時変数の名前（`trace`、`raw`）は、別名の無い宣言名とも衝突しないように `temp` を直した。それまでは、別名を持つ名前としか比べていなかった。

### 15.34 表の列の範囲は、セルから決める（2026-09-16）

**きっかけ**：生成コードの記録関数（§15.35）を入れるとき、gen が書く期待値のファイルを fixtures として `fixtures lint` に通す検査を足した。`会員特典` で、出力 `付与点` の値 11999 が「宣言範囲 0..10000 の外」と報告された。規則は正しく、範囲のほうが間違っていた。

**原因**：式の区間を求める `interval` が、範囲の無い率の名前を **0%〜100% と仮定**していた。`付与点 = 基本点 × 倍率` の `倍率` は表の出力列で、セルには 100%・120%・150% が書いてある。仮定は「保守的」のつもりで書かれていたが、100% を超える率の列には保守的でなく、`rulec api` はこの出力の範囲を 0..10000 と公表し、int64 に収まることの証明（E108）も同じ誤った上限で進んでいた。しかもこの仮定は式の中だけのもので、範囲の無い率の**入力**には入口のガードが出ていなかった。証明が仮定したことを、生成コードは守らせていなかった。

**決定**：二つ。(1) 表の数値の出力列に、セルから範囲を付ける。リテラルの最小と最大、セルが名前ならその名前の範囲で広げる。範囲の無い名前を指すセルが一つでもあれば、列に範囲を付けない。(2) 範囲の無い率の入力は 0%〜100% とし、それを**宣言の場所で記録する**。区間の計算、入口ガード、`rulec api`、ベクタの絞り込みが同じ一つの範囲を読む。100% を超えうる率の入力は、ほかの数と同じく範囲を書く。式の中の仮定は消し、範囲の無い名前は区間を持たない。**分からないものは分からないままにする**ほうが、誤った数を出すより良い。

**検査**：`rulec api` が `付与点` の範囲を 0..15000 と言うこと。刻み 100% の率の列に 200% を置いた規則で、9×10¹⁸ 円の入力を掛けると E108 が出ること（旧仮定では 9×10¹⁸ が int64 に収まり、黙っていた）。

**開いたままのこと**：範囲の無い数値の入力は、文書では「必須」だが、検査器は専用の診断を出さない。完全性は E101 で、溢れは E108 の沈黙で、それぞれ穴になる。診断を足すかは別に決める。

## 16. この設計で最も危うい点

第一に、**rulec が消したかった二重実装が、一段上で小さく再発する**。
表現力の崖は実際にクーポンで来たが、導出と粒度の二手で、崖ではなく段差として越えられた（§5.2、§5.4）。
その代償が、重ね掛けの畳み込み（ソート、逐次適用、状態の運搬）を Python と Go の手書きに一つずつ残すという構図である。
「二重実装は必ずズレる」という、この道具が存在する理由そのものが、規則の外側で小さく再現される。
順序の判定まで規則に入れて畳み込みを自明な形に追い込む設計はその緩和だが、本当に自明になるかは試作で数えるまで分からない（§15-5）。
畳み込みを宣言にして検査の網を届かせる案は検討済みで、単一アキュムレータが当のクーポン（併用制約の状態）を表せないため見送った（§5.4）。
それまでは連鎖の例が、畳み込みの仕様をデータとして規則側に留める。
按分は 2026-09-13 に測って決着した。逐次充当型は粒度原則にそのまま収まり、比率按分は粒度ではなく除算の制限に当たる（§15-7）。粒度原則の未検証領域は、この一件ぶん狭まった。

第二に、**99.9% の先の 0.1% が道具の信用を決める**。
不一致 1,107 件の身元（旧実装のバグか、転記ミスか、fixtures の汚れか、丸め差異か）を報告書が自力で切り分けられなければ、「982 件」は証拠ではなくノイズになり、一致率を上げる過程が仕様の発掘ではなく徒労になる。
発火行クラスタ、丸め差異の自動タグ、実測系と補完系の分離はすべてこのための設計だが、その有効性は実データに当てるまで仮説にとどまる。
実測は道具の前半（記述、検査、生成）を現実の規約に当てたが、後半（M2 と M3）は依然として一件の実データにも触れていない。
検証済みと未検証の境界は、いまここにある。
M3 は機能を足す段ではなく、最初の実表 1 本でレポートの切り分け精度を磨き込む段として扱うべきである。

第三に、**丸めの決定が、規約に存在しないまま `.rule` に書かれて権威になる**。
実測は、公開規約が複数クーポンの端数処理も上限の掛かり先も書いていないことを示した（§7.2）。
E104 が丸めを書けと迫るのは設計どおりだが、迫られた転記者が書けるのは仮置きであり、生成コードに入った仮置きは仕様の顔をする。
出典コメントの慣行と replay での裁定は緩和であって解決ではなく、データが来るまで仮置きは仮置きのまま積み上がる。
オーバーフロー証明が要求する中間丸め（E108）も同じ圧力点で、円が動く業務判断が型エラーの顔をして業務担当者に届く。
E104 と E108 の文面がそれを業務の判断として提示し直せているかは、業務担当者に文面を読ませる実地の検証（誤読率を見る）まで含めて M0 の合否に入れないと、P2 の「読める」がここから崩れる。
